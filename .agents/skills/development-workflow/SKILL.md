# Development Workflow

모든 실행형 작업에 공통 승인 경계와 실행자-검증자 분리를 적용한다. 플랫폼별
어댑터보다 `AGENTS.md`를 우선하며, 충돌하거나 범위가 달라지면 작업을 멈추고
사용자에게 알린다.

## 1. 현재 상태 확인

1. `AGENTS.md`와 적용되는 하위 지시를 읽는다.
2. 사용자가 승인한 계획, 설계 정본과 현재 작업 단위를 확인한다.
3. 새 요청인지, 승인된 작업의 후속 실행인지, 단순 상태·승인 응답인지 구분한다.
4. 기존 산출물이 있으면 덮어쓰지 말고 현재 diff와 이전 검증 증거를 확인할 항목을
   계획에 포함한다.

아직 승인되지 않은 실행형 요청이면 명령, 파일 변경, 외부 시스템 작업이나 Agent
위임을 시작하지 않는다.

## 2. 계획 보고

`references/plan-report-template.md`를 읽고 다음을 사용자에게 보고한다.

- 주제, 목적, 내용, 기대 결과, 검증 방법
- 작업 단위와 분할 판단
- 변경 대상, 제외 범위, 위험과 되돌림 방법
- 실행 Agent가 수행할 쉬운 무외부 의존 검증
- 독립 검증 Agent가 다시 수행할 계획된 전체 검증

사용자의 명시적 승인을 기다린다. 일부 승인, 조건부 승인, 계획 수정은 새 승인
범위로 기록한다. 승인되지 않은 항목은 실행하지 않는다.

## 3. 작업 분할

`AGENTS.md`의 우선순위를 순서대로 적용한다. 각 작업 단위가 하나의 의도와 검증
가능한 결과를 갖는지 먼저 확인하고, 위험 격리와 독립 검증 가능성을 검토한다.
변경량 목표를 넘더라도 앞선 기준을 훼손하는 기계적 분할은 하지 않는다.

UI는 레이아웃 구조의 컴포넌트 경계를 그린 뒤 최상위 영향 컴포넌트에서 하위로
진행한다. 각 컴포넌트 단위의 관찰 가능한 상태와 검증 방법을 계획에 적는다.

## 4. 실행 Agent

승인 후 새 `task-executor` 인스턴스에 정확히 한 작업 단위를 맡긴다.

1. 승인 계획과 관련 정본을 읽는다.
2. 현재 diff에 범위 밖 변경이 있으면 중단하고 보고한다.
3. 승인 계획에 테스트 설계가 있으면 그대로 사용한다.
   테스트 관련 내용이 없을 때만 스스로 테스트 코드를 설계할 수 있다.
4. 예상한 assertion failure를 실제 확인한다. 테스트 오류면 테스트부터 고친다.
5. 최소 구현으로 GREEN을 만들고 필요할 때만 정리한다.
6. 외부 서비스, 네트워크, GPU, 컨테이너가 필요 없는 쉬운 검증만 실행한다.
7. 변경 파일, RED/GREEN 증거, 쉬운 검증 결과와 남은 검증을 보고한다.

실행 Agent는 최종 합격 판정을 하지 않는다. 계획 밖 변경이나 새 의사결정이
필요하면 즉시 중단하고 재승인을 요청한다.

## 5. 독립 검증 Agent

실행 Agent와 다른 새 `task-verifier` 인스턴스를 호출한다. 검증 Agent에는 승인 계획,
현재 diff와 `references/verification-report-template.md`를 전달하되 실행 Agent의 합격
주장을 전제로 주지 않는다.

검증 Agent는 read-only 상태에서 계획된 모든 검증을 처음부터 다시 실행한다. 테스트,
정적 검사, 외부 의존 검증과 수동 계약 점검을 계획대로 수행하고 실제 출력과 exit
code를 증거로 남긴다. 실패, 미실행, 환경 차이와 범위 누출을 통과로 축약하지 않는다.

## 6. 결과와 다음 승인

오케스트레이터는 실행 보고와 독립 검증 보고를 함께 사용자에게 전달한다. 승인
범위 안의 검증 실패는 아래 실패 루프로 처리하고, 범위 밖 수정이 필요할 때만 수정
계획을 새로 보고하고 승인을 기다린다. 한 작업 단위가 확인된 뒤에만 다음 단위의
계획 보고로 넘어간다.

### 조정 Agent와 검증 실패 루프

조정 Agent는 승인, Agent 배정과 결과 전달만 조율하며 구현하지 않고
자기 결과에 합격 판정을 내리지 않는다. 검증 실패가 나면 검증 Agent의 발견 전체를
실행 Agent에 반환한다. 실행 Agent가 승인 범위 안에서 모두 수정한 뒤
동일한 검증 Agent 인스턴스가 계획된 모든 검증을 처음부터 재실행한다. 계획 밖
수정이 필요하면 재승인 전까지 루프를 멈춘다.

## 배포 조건부 reference

배포, 재배포, 복구, 보정 같은 외부 환경 실행형 요청이면 작업을 위임하거나 명령을
실행하기 전에 반드시 `references/deployment-harness.md`를 처음부터 끝까지 읽는다.
단순 상태 확인, 개념 설명과 선택지 요청은 실행형 요청이 아니므로 이 조건만으로
배포 절차를 시작하지 않는다. Reference는 승인이나 서버 변경 권한을 대신하지 않으며,
`AGENTS.md`와 사용자가 승인한 현재 작업 단위가 언제나 우선한다.

## 예외와 오류 처리

- 승인 뒤 전제가 달라지면 변경을 멈추고 원래 계획과 차이를 설명한다.
- 실행 Agent 검증이 실패하면 원인을 숨기지 않고 구현 단계로 되돌아간다.
- 검증 Agent가 환경 때문에 명령을 실행하지 못하면 `blocked` 또는 `not run`으로
  기록하고 필요한 권한·환경을 사용자에게 요청한다.
- 사용자 피드백으로 일부만 수정하면 기존 산출물과 승인 범위를 읽고 해당 부분만 새
  작업 단위로 계획한다.
