# CREFLE 정보 조회 플랫폼(omf-retrieval) 헌법

이 헌법은 공통 정책 정본(기준이 되는 원본 문서)인 `AGENTS.md`의 원칙을 압축한 것이다. 상세 규칙은 복제하지 않고
`AGENTS.md`의 해당 절을 참조한다. 이 헌법과 `AGENTS.md`가 충돌하면 `AGENTS.md`가 우선한다.

## 핵심 원칙

### I. 계획 보고와 사용자 승인 게이트

- 모든 작업은 시작 전에 주제, 목적, 내용, 기대 결과, 검증 방법을 담은 계획을 보고하고 사용자의
  명시적 승인을 기다려야 한다. 승인 전에는 파일 변경, 명령 실행, 외부 시스템 변경, Agent(작업을 맡아
  수행하는 AI) 위임을 시작해서는 안 된다. 일부만 승인되면 승인된 부분만 실행한다. 단순 대화, 승인된 작업의 상태 전달,
  사용자의 승인·반려 응답은 새 작업으로 보지 않는다.
- 계획을 작성하는 동안 사용자 요청과 이미 제공된 문맥을 넘는 조사나 실행을 해서는 안 된다. 필요한
  사전 조사는 그 조사 자체를 계획에 넣는다.
- 객관적 지표를 정의하기 어려운 결과물은 정성적 평가 기준과 합격 예시를 계획에 적어야 한다.
- 약어, 은어, 다른 문서에서 가져온 키워드는 첫 사용 위치에서 설명하거나 문서 최상단 용어표에 둔다.
- 새 가정, 범위 변경, 예상 밖의 제약, 계획된 검증의 변경이 생기면 즉시 멈추고 차이와 영향을
  보고한 뒤 재승인을 받아야 한다.
- 전체 계획이 승인되면 단위별 결과와 검증 증거를 계속 보고하고, 범위 변경·새 의사결정·검증
  실패가 없으면 다음 단위로 자동 진행한다.
- 다음 항목은 Agent가 단독으로 확정하거나 구현해서는 안 된다. 핵심 기능의 범위와 동작, 시스템
  아키텍처와 서비스 경계, 데이터 모델과 정본·버전·권한 정책, Agent 도구 및 외부 API(Application
  Programming Interface, 프로그램 간 호출 규약) 계약, 검색·색인(검색용으로 자료를 가공해 저장한
  구조)·랭킹(검색 결과 순위 결정)·생성 전략, 외부 의존성의 선택·추가·교체, 인증·보안·배포·운영 방식.
- 위 의사결정이 필요하면 권장안과 근거, 2~3개 대안, 비용·복잡도·향후 변경 가능성을 먼저 설명하고
  사용자 확인 후 반영한다. 승인된 결정도 전제가 바뀌면 다시 확인해야 한다.

근거: 되돌리기 어려운 결정의 주체를 사용자로 고정해 세션이 바뀌어도 설계 상태를 유지한다.

### II. 작업 분할 우선순위

작업은 아래 순서로 분할하며, 뒤의 기준을 맞추려고 앞의 기준을 훼손해서는 안 된다.

1. Single Intent: 한 작업 단위는 하나의 사용자 의도와 관찰 가능한 결과만 가진다.
2. 호환성·위험 격리: 호환성 위험과 되돌리기 어려운 변경을 다른 변경에서 격리한다.
3. 독립 테스트 가능성: 각 단위는 가능한 한 독립적으로 실패·성공을 검증할 수 있어야 한다.
4. 계층 분할: 필요할 때 기반 계층부터 소비 계층으로 얇게 나눈다.
5. 변경량 휴리스틱(경험에 근거한 판단 기준): 한 단위의 목표는 변경 400줄 이하다. 500줄 초과가 예상되면 재분할 이점을
   검토해 판단 근거를 계획에 기록한다. 줄 수만 맞추는 기계적 분할은 하지 않는다.

UI(User Interface, 사용자 화면) 작업은 레이아웃 구조의 컴포넌트(화면을 이루는 독립 구성 요소)
단위로 나누고, 배치와 상태 전파에 영향이 가장 큰 최상위 컴포넌트부터 하위로 진행한다.

근거: 단위가 작고 의도가 하나여야 실패 원인을 좁히고 위험한 변경만 되돌릴 수 있다.

### III. 실행과 독립 검증의 분리

- 실행 Agent(`task-executor`)와 검증 Agent(`task-verifier`)는 반드시 별도 인스턴스(따로 띄운 실행 개체)여야 한다. 같은 Agent가 구현과 최종 합격 판정을
  함께 맡아서는 안 된다.
- 실행 Agent는 승인된 한 작업 단위만 구현하고, 외부 의존성 없는 쉬운 검증만 수행한다.
- 검증 Agent는 read-only(읽기 전용)로 새 인스턴스에서 시작해 승인 계획과 현재 diff(변경 차이)를 읽고, 계획된
  모든 검증을 독립적으로 다시 실행한다. 계획된 검증을 실행할 수 없으면 통과로 간주하지 않고 이유를
  명시해야 한다.
- 검증 Agent는 명령, 결과, 증거, 누락·편차, 발견 사항과 판정을 검증 보고서로 반환한다.
- 조정 Agent(실행 Agent와 검증 Agent를 호출하는 오케스트레이터, 즉 여러 Agent의 작업을 조율하는 역할)는 승인, 역할 배정, 보고만 조율하며
  구현하거나 자기 결과에 합격 판정을 내리지 않는다.
- 검증 실패 루프: 검증 실패가 나면 조정 Agent가 발견 전체를 실행 Agent에 반환하고, 실행 Agent가
  승인 범위 안에서 모두 수정한 뒤, 동일한 검증 Agent 인스턴스가 계획된 모든 검증을 처음부터
  재실행한다. 계획 밖 변경이 필요하면 루프를 멈추고 재승인을 받는다.

근거: 구현자의 결론을 이어받지 않는 검증만이 합격 판정의 증거가 된다.

### IV. TDD

- 개발은 TDD(Test-Driven Development, 테스트 주도 개발)의 RED → GREEN → REFACTOR 순서로 진행한다.
  RED는 실패하는 테스트 확인, GREEN은 통과시키는 최소 구현, REFACTOR는 동작을 유지한 정리다.
- 코드 개발 계획에는 관찰할 동작, 정상·경계·실패 사례와 예상 결과를 포함한 Unit test(작은 코드
  단위의 동작을 확인하는 자동 테스트) 설계가 있어야 한다.
- 승인 계획에 테스트 설계가 있으면 실행 Agent는 그대로 사용한다. 테스트 관련 내용이 없을 때만
  스스로 설계할 수 있다.
- RED는 구현 부재로 인한 assertion(테스트의 기대 결과 검사) 실패를 실제로 확인한 경우만 인정한다.
  import·문법·fixture(테스트 준비 데이터·환경) 오류 같은 테스트 오류는 RED가 아니다.
- REFACTOR 뒤에는 같은 테스트가 계속 통과하는지 확인해야 한다.

근거: 구현 부재로 실패함을 먼저 확인해야 테스트가 해당 동작을 실제로 검증한다고 믿을 수 있다.

### V. 근거 재현성

- 이 원칙에서 재현은 근거를 다시 찾아 확인하거나 다시 실행할 수 있게 하는 재현 좌표를 근거와 함께
  제공하는 것이다.
- RDB(관계형 데이터베이스) 근거를 제외한 모든 근거는 어느 원본인지 식별하는 원본 경로, 자료에 제목
  구조가 있으면 그 제목 계층, 원문 위치(행 범위, 페이지, 시트·셀), 색인 세대(색인 실행 1회를 가리키는
  색인 run, 불변 revision), 내용 해시(내용에서 계산한 식별값)로 재현 가능해야 한다. 불변 revision은
  한 번 정해지면 바뀌지 않는 자료 시점 식별값이다.
- 현재 MVP(Minimum Viable Product, 최소 기능 제품)의 색인은 Git으로 유입한 자료의 revision으로
  commit SHA를 쓰고, 원본 경로로 저장소 기준 파일 경로를, 원문 위치로 원문 행 범위를 쓴다. commit SHA는
  Git 커밋 식별자이며, 이력 저장 기능이 아니라 인용 원문을 재현하는 좌표다. 위 일반화는
  `AGENTS.md`의 `다음 목표: 제조 자료 등록과 지식 그래프` 절에서 승인된 방향이며, 구현 전까지는 이
  항목이 현재 시스템의 사실이다.
- 검색 서비스의 응답인 근거 패키지(자연어 생성 답변이 아니라 인용과 재현 좌표를 담은 묶음)에는 위
  좌표와 함께 검색 순위, RRF(Reciprocal Rank Fusion, 순위 결합) 점수, 검색 정책 좌표
  `search_policy.policy_id`·`config_hash`를 포함한다. 조회 경로 모델(원칙 VII)의 식별자·revision·설정은
  검색 정책 식별값에 기록되므로, 검색 정책 좌표를 통해 어떤 모델·설정으로 채점·정렬했는지 식별하는 재현
  좌표의 일부가 된다. 호출 Agent는 이 근거 패키지로 최종 응답의
  요약과 직접 인용을 작성한다. 이 열거는 요약이며, 전체 좌표와 상세는 `AGENTS.md`의
  `사용자 인터페이스와 인증`, `Agent 조회 동작`, `Index identity와 search policy identity`,
  `다음 목표: 제조 자료 등록과 지식 그래프` 절을 따른다.
- 아래 세 항목은 `AGENTS.md`의 `다음 목표: 제조 자료 등록과 지식 그래프` 절에서 승인된 방향이며 새
  명세·계획·구현에 적용한다. 구현 전까지는 이 원칙의 현재 MVP 항목이 현재 시스템의 사실이다.
  - RDB 근거(MES 운영 DB에서 복제한 별도 DB `mes_mirror`의 조회 결과)의 재현 좌표는 실행한 SQL과
    데이터 기준 시각이다. 복제본은 계속 갱신되므로 같은 SQL을 다시 실행해도 같은 결과를 보장하지
    않는다. 응답에는 기준 시각·지연 시간·최신성 상태를 넣어야 한다.
  - RDB 조회 경로는 4겹 금지 조건(DB 권한, SQL 구조 검사, 실행 상한, 감사 기록)을 따른다. SQL이
    애매하거나, 검사 자체가 오류로 끝나거나, 판정할 수 없으면 그 SQL은 거부하고 실행해서는 안 된다
    (fail-closed, 판정할 수 없으면 차단). 상세 조건은 `AGENTS.md`의 같은 절을 따른다.
  - 같은 원본 revision에 같은 버전의 파서·스키마·사전·분할 규칙을 적용하면 항상 같은 chunk(검색
    단위로 나눈 조각)가 나와야 한다. 스키마·사전·분할 규칙은 불변 버전으로 관리하고 그 버전을 색인
    식별값(색인 결과를 구분하는 설정 묶음의 식별값)에 포함해야 한다.
- 현재 MVP의 색인은 커밋된 깨끗한 작업 트리(커밋하지 않은 변경이 없는 Git 작업 폴더)에서 수행한다.
- 완전히 같은 내용의 문서가 여러 경로에 있으면 모든 원본 경로를 보존한다.
- `확정기록`, `결정서`, `[확정]` 표기는 일반 조사 문서보다 우선한다. 같은 지위에서는 버전과 결정일을
  비교한다.
- 근거가 없으면 추측하지 않고 확인 가능한 근거가 없음을 명시해야 한다.
- 문서 충돌은 숨겨서는 안 된다. 위 우선 기준으로 우선 문서가 정해져도 지위가 낮아서 진 쪽 근거를
  숨기지 않고 양쪽 근거를 표시하며, 우선하는 쪽을 먼저 써야 한다. 위 기준으로도 남은 충돌은 하나를
  임의로 선택하지 않고 양쪽 근거와 충돌 내용을 공개해야 한다.

근거: 이 플랫폼의 산출물은 답변이 아니라 근거 패키지이므로, 재현 좌표가 없는 근거는 근거가 아니다.
원문 근거는 위 좌표로 같은 원문을 다시 찾아 내용 해시로 확인할 수 있어야 하고, RDB 근거는 실행 SQL과
기준 시각으로 어느 시점의 결과인지 밝혀야 한다.

### VI. 보안·데이터 경계

- 내부 원문과 인덱스(색인)는 사내 환경에 저장해야 한다.
- OMF 저장소(이 플랫폼의 첫 조회 대상 프로젝트의 설계 문서 저장소)는 읽기 전용 데이터 소스다. 수정이
  필요하면 별도 승인을 받아야 한다. 색인·검색·Agent 인터페이스·배포는 omf-retrieval 저장소가 소유한다.
- Codex API(사내 Agent가 쓰는 외부 LLM API, LLM은 대규모 언어 모델)에는 답변 생성에 필요한 최소
  근거만 전송할 수 있다. 원문 전체나 불필요한 주변 문맥을 외부 서비스에 전송해서는 안 된다.
- `docs/raw`와 기타 대외비 자료를 외부 서비스에 업로드해서는 안 된다.
- 비밀 토큰이나 관리자 인증정보 같은 비밀값을 저장소에 기록해서는 안 된다.
- 아래 항목은 `AGENTS.md`의 `다음 목표: 제조 자료 등록과 지식 그래프` 절에서 승인된 방향이며 새
  명세·계획·구현에 적용한다. 구현 전까지는 위 항목과 현재 MVP 공유 배포가 현재 시스템의 사실이다.
  - 외부 LLM(사내 밖에서 운영되는 LLM)으로 나가는 내용은 어느 외부 LLM이든 최소 근거로 한정해야 하며
    보안 검사 모듈을 거쳐야 한다. 이 항목은 전송 범위를 제한할 뿐 Codex API 외 외부 LLM으로의 전송을
    허용하지 않는다.
  - 보안 검사 모듈은 하나를 만들어 플랫폼 응답(A)과 외부 LLM 중계 서버(B, 외부 LLM으로 나가는 요청을
    받아 보안 검사 후 전달하는 사내 서버) 두 곳에 둔다. Agent의 외부 직접 접속 차단은 별도 운영
    결정이다.
  - 보안 검사 모듈은 개인정보·고객사명·구체 금액을 의미 손실을 줄이는 가명(민감 값을 대신하는 일관된
    대체 표기)·비율·구간으로 바꿔야 한다. 가명 대응표는 사내에 두어야 한다.
  - 보안 검사가 실패하면 외부로 보내서는 안 된다(fail-closed).
  - 관리자가 호출자마다 외부 LLM 사용 여부를 표시하며, 표시가 없는 호출자는 외부 LLM 사용으로
    간주한다.
  - 뷰(DB에 미리 정의한 조회용 가상 테이블)·열 이름과 설명은 외부 LLM으로 보낼 수 있다(사용자 승인
    2026-11-06).
  - 원본 파일 전체는 외부로 내보내서는 안 된다. 외부 사용으로 표시되었거나 표시가 없는 호출자에게는
    원본 읽기 권한을 줄 수 없다.

근거: 이 플랫폼은 대외비 원문을 다루며, 경계 밖으로 나간 데이터는 되돌릴 수 없다.

### VII. 조회 경로 모델의 역할 경계와 LLM 사용 경계

- 이 원칙은 `AGENTS.md`의 `다음 목표: 제조 자료 등록과 지식 그래프` 절에서 승인된 방향이며 새
  명세·계획·구현에 적용한다. 구현 전까지는 현재 MVP의 검색 경로가 현재 시스템의 사실이다.
- 질의를 무엇·왜·어떻게(질문 의도)로 분석하는 일은 호출 Agent가 맡고, 플랫폼은 호출 Agent가 보낸
  구조화된 요청을 실행하며, 조회 경로 모델의 채점을 제외한 처리(템플릿·SQL 검사와 실행, 키워드 검색,
  결과 결합)는 결정적으로(같은 입력에 항상 같은 처리로) 실행한다. 호출 Agent는 외부 LLM이든 내부
  LLM이든 같은 계약을 따른다.
- 조회 경로의 모델(임베딩 모델(글을 의미 벡터로 바꾸는 모델)·리랭커(검색 후보의 순위를 다시 매기는
  모델), LLM 기반 포함)은 후보 근거를 채점·정렬만 해야 한다. 근거 내용을 생성하거나 바꿔서는 안 되며,
  색인이나 RDB 조회 결과에 없는 근거를 만들어서는 안 된다. 응답의 근거 본문은 원문 그대로여야 한다.
  조회 경로 모델의 식별자·revision·설정은 검색 정책 식별값(조회 시점 결과를 바꾸는 설정 묶음의
  식별값)에 고정 기록해야 한다.
- 플랫폼 안의 LLM 사용은 다음 두 가지로 한정한다. (1) 적재 시점의 문서 분석 Agent(문서별 분할 규칙을
  만들고 엔티티·속성·관계를 추출하는 Agent)의 생성 사용, (2) 조회 경로 모델의 후보 근거 채점·정렬.
  두 사용 모두 사내 모델 서버의 내부 모델만 써야 한다.
- 파서(파일에서 글자·표·위치를 꺼내는 프로그램)의 글자 추출을 LLM에 맡겨서는 안 된다.
- 문서 분석 Agent가 만든 분할 규칙은 불변 버전으로 저장해야 하며, 실제 청킹(자료를 검색 단위로
  나누는 작업)은 프로그램이 저장된 규칙대로 결정적으로 실행해야 한다. LLM이 직접 청킹해서는 안 된다.

근거: 조회 경로 모델이 근거 내용을 만들거나 바꾸면 원문 인용과 원칙 V의 재현 좌표가 의미를 잃고,
chunk가 LLM의 비결정성에 좌우되면 재현성을 지킬 수 없다. 모델의 역할을 채점·정렬로 한정하고 그 식별값을
검색 정책 식별값에 고정해야 어떤 모델·설정이 순위를 정했는지 추적할 수 있다. 적재 시점 생성과 조회 경로
채점·정렬 두 LLM 사용을 모두 사내 모델로 한정해야 원문이 경계 밖으로 나가지 않는다.

3. 기존 설계서와 구현 계획(`docs/design/...`, `docs/superpowers/plans/...`)이 시스템 정본이다.

## 거버넌스

- 우선순위: 이 헌법과 `AGENTS.md`가 충돌하면 `AGENTS.md`가 우선한다. 충돌을 발견하면 임의로
  해석하지 않고 사용자에게 알린다. `AGENTS.md`의 규칙대로 직접적인 최신 사용자 지시가 `AGENTS.md`와
  충돌하면 최신 지시를 우선하고 충돌 사실을 알린다. Spec Kit 운영 규칙 2의 예외는 이 규칙에 근거한다.
- 개정 절차: 이 헌법의 개정은 원칙 I의 계획 보고와 사용자 승인을 거쳐야 한다.
- 버전 정책: 의미적 버전(MAJOR.MINOR.PATCH)을 따른다. MAJOR는 하위 호환되지 않는 원칙 삭제나
  재정의, MINOR는 원칙·절 추가나 지침의 실질적 확장, PATCH는 의미를 바꾸지 않는 문구 수정이다.
- 준수 확인: `speckit-plan`(Spec Kit의 계획 작성 스킬)의 Constitution Check(계획 단계의 헌법 준수 점검)와 작업 단위별 독립
  검증에서 이 헌법의 준수 여부를 확인한다. 위반을 발견하면 원칙 I에 따라 멈추고 보고한다.
