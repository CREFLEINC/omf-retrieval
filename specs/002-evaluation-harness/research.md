# Research: 평가 하네스 — 평가셋·지표·실험 기록·적용 관문(evaluation-harness)

**작성일**: 2026-11-10 | **입력**: [spec.md](./spec.md), [plan.md](./plan.md), [checklists/requirements.md](./checklists/requirements.md) | **상태**: 결정 요청 DR-01~DR-25 **승인(사용자 2026-11-10, 모두 권장안. DR-02·DR-03은 권장 A)**. spec 모호점 A-1·A-15도 같은 날 사용자 결정으로 해소했다(4.2절). **값 입력 대기**(결정 미승인이 아님, tasks 진행을 막지 않음): DR-04 운영 GPU 총 메모리 실측값(그 전 관문 시도는 `gate_setting_missing`으로 거부), DR-03 승인된 연구 자원의 구체 호스트·GPU 목록(그 전 실험은 시작 거부, fail-closed).

이 문서는 계획의 Phase 0 산출물이다. 저장소에서 확인한 사실(1절), 계획이 채택한 기술 판단(R-xx, 2절), 사용자 승인이 필요한 **결정 요청**(DR-xx, 3절), 범위 밖으로 확인한 사항(4절)을 정리한다. `AGENTS.md` `사용자 승인 필수 의사결정`에 해당하는 항목(외부 의존성, 데이터 모델·정본·버전·권한 정책, Agent 도구·외부 계약, 검색·랭킹 전략, 인증·보안·배포·운영 방식)은 결정하지 않고 DR로 올렸다.

## 2. 계획이 채택한 기술 판단(새 의존성·정책 변경 없음)

### R-01 정확 산술과 경계 비교

- **판단**: 비율 지표(Recall@5, MRR, 근거 완전성, 의도별 Recall@5, `no_evidence` 비율), 차이, 부트스트랩 통계값은 `fractions.Fraction`으로 계산하고 관문 비교도 분수로 한다. 기록에는 분수(분자/분모)와 10진 문자열(소수점 6자리 반올림, 표시용)을 함께 남긴다. 지연(ms)·시간(초)·메모리(MiB)는 정수로 측정·비교한다.
- **근거**: SC-007의 경계값(+3.0%p, 하한 0, 5.0%p, 2.0%p, 200ms, 8시간)이 부동소수점 오차로 뒤집히지 않게 한다. FR-031(같은 입력이면 같은 신뢰구간)을 플랫폼과 무관하게 만족한다.

### R-02 질의문 같음 판정

- **판단**: "같은 질의문"(FR-007)은 유니코드 NFC 정규화 → 앞뒤 공백 제거 → 연속 공백(줄바꿈 포함)을 공백 하나로 바꾼 문자열이 정확히 같을 때로 본다. 대소문자·문장부호는 바꾸지 않는다. 정규화 문자열을 질의와 함께 저장한다.
- **근거**: 보이지 않는 공백 차이로 중복 검사가 무력해지는 것을 막되, 의미 판정(유사 질의)은 하지 않아 결정적이다. 개발셋 제외(FR-007 후단)와 SC-006 측정에 같은 함수를 쓴다.
- **SC-006 유지(개발셋이 먼저 있는 경우)**: 개발셋 생성 때의 제외만으로는 개발셋이 생긴 뒤 시험셋에 추가된 질의를 막지 못한다. 그래서 세 지점에서 같은 함수로 확인한다. (1) 개발셋 생성: 평가 DB의 **모든 시험셋**의 현재 구성원(제거되지 않은 질의)과 같으면 제외. (2) 시험셋 접수: 평가 DB의 **모든 개발셋**의 현재 구성원과 같을 때의 처리. 사람이 쓴 시험 질의를 거부할지는 데이터 정책 선택이므로 **DR-23**으로 올렸다. DR-23은 권장안(`duplicate_query`(`in_dev_set`)로 거부, R-04 7단계)으로 승인됐다(사용자 2026-11-10). (3) 관문 사전 점검: 시험셋 스냅숏 구성원과 모든 개발셋 현재 구성원 사이에 같은 정규화 문이 하나라도 있으면 `dev_test_overlap`으로 거부(시도로 세지 않음, data-model 4.2). (3)은 DB 직접 수정 같은 예외 경로에 대한 방어다.

### R-03 한 번 검색하고 앞부분을 쓴다

- **판단**: 질의마다 비공개 평가 경로로 `limit = MRR 기준 길이(DR-11)`만큼 한 번 검색하고, Recall@5·근거 완전성·반환 근거 길이는 그 결과의 앞 5개로 계산한다.
- **근거**: `group_evidence`의 정렬은 `limit`과 무관하므로 앞 5개가 `limit=5` 결과와 같다(1절). U-PRIV-03이 이 성질을 고정한다.

### R-04 질의 접수 판정 순서

- **판단**: 질의 한 건은 아래 순서의 모든 단계를 확인하고, 어긋난 사유를 **전부** 이 순서로 돌려준다(첫 사유만이 아니라). 사유 코드는 FR-006의 7개와 같다.

| 순서 | 확인 | 사유 코드(FR-006) |
|---|---|---|
| 1 | 질의문·확인 기준 원본 자료 스냅숏·출처 구분 **키** 존재, 알 수 없는 항목 없음 | `missing_field`(항목 누락) |
| 2 | 의도 키가 있고 값이 `무엇`·`왜`·`어떻게` 중 하나 | `invalid_intent`(의도) |
| 3 | 정답 구분 키가 있고 값이 둘 중 하나, 정답 근거 목록(키가 없으면 빈 목록으로 봄)과의 짝(FR-005) | `invalid_answer_marking`(정답 표시) |
| 4 | 확인 기준 원본 자료 스냅숏이 목록(FR-003b)에 있음 | `unknown_source_snapshot`(확인 기준 스냅숏) |
| 5 | 정답 근거마다 (source, 자료 ID, revision)이 그 스냅숏에 있고, 좌표 종류가 형식에 맞으며, 위치가 revision 범위 안(FR-004) | `invalid_answer_coordinate`(정답 근거 좌표) |
| 6 | 작성자·작성일 키 존재·값 있음·형식, 출처 구분 값이 셋 종류와 맞음 | `invalid_authoring_info`(작성 정보) |
| 7 | 같은 평가셋의 현재 구성원·같은 파일 안에 같은 질의문 없음, 시험셋 제출이면 모든 개발셋의 현재 구성원에도 없음(R-02, 개발셋 부분은 DR-23) | `duplicate_query`(중복, 세부 `in_set`·`in_file`·`in_dev_set`) |

- 4번이 실패하면 5번은 확인할 수 없으므로 건너뛴다. 3번이 실패하면 5번은 있는 정답 근거만 확인한다.
- 키가 없을 때의 사유: spec 시나리오가 사유를 정한 항목은 그 사유를 쓴다(US1-4 의도, US1-5 정답 표시, US1-8 작성 정보). 즉 `의도` 키 없음 → `invalid_intent`, `정답 구분` 키 없음 → `invalid_answer_marking`(`invalid_status`), `정답 근거 목록` 키 없음 → 빈 목록으로 보고 3단계에서 판정(정답 있음이면 `answer_without_evidence`, 정답 없음이면 통과), `작성자`·`작성일` 키 없음 → `invalid_authoring_info`. 키가 없든 값이 비었든 같은 사유다. `missing_field`는 spec이 따로 사유를 두지 않은 필수 키(`질의문`, `확인 기준 원본 자료 스냅숏`, `출처 구분`)와 알 수 없는 키에만 쓴다. 이 해석은 spec 모호점 A-15의 권장안으로 사용자가 승인했다(2026-11-10). 결과로 정답 없음 질의의 `정답 근거 목록` 키 생략은 빈 목록으로 보아 접수한다(FR-003을 이 키에 한해 완화, spec FR-003 비고에 반영).
- **근거**: SC-003은 형식 오류 0건을 요구하므로 작성자가 한 번에 모두 고칠 수 있어야 한다. 출처 구분 값 오류와 작성자·작성일 누락을 같은 "작성 정보" 사유로 묶은 것은 spec이 출처 구분 사유를 따로 두지 않았기 때문이다(아래 4절 모호점 A-4).

### R-05 (결번 — DR-24로 승격)

- 관문 시도를 세는 시점은 spec Edge Case의 "결과가 산출" 해석이 필요한 정책 선택이라 기술 판단이 아니라 결정 요청 **DR-24**로 옮겼다. 실행 순서(사전 점검 → 색인 쪽 필수 검사 → 모델 적재·예열 → 실험 행 기록 → 질의)는 DR-24의 어느 안에서도 같다.

### R-06 평가 전용 설정 클래스

- **판단**: 평가 실행기 설정은 기존 `Settings`를 바꾸지 않고 새 `EvaluationSettings`(접두사 `OMF_EVAL_`)에 둔다: 평가 DB URL, 실행 자원 허용 목록·운영 GPU 식별값(DR-03), 관문 기준 버전 선택(DR-15), 평가 장치, 합성 경로 설정(DR-16).
- **근거**: `Settings`는 `extra="forbid"`이고 운영 API·색인이 공유한다. 운영 설정 변경을 피해 위험을 격리한다(헌법 II-2).

### R-07 불변 기록의 강제

- **판단**: 평가 테이블은 001·`0003` 관례대로 DB 트리거로 append-only를 강제한다. 실험 행에만 상태 전이 제한 트리거를 두어 다음 UPDATE만 허용한다. (1) `running → completed | failed` 한 번과 그때의 `finished_at`·`failure_code` 기록. (2) `status = 'running'`인 `gate` 행의 `attempt_number` NULL → 값 한 번(DR-24). (3) 중단된 실험 정리 경로의 `running → failed`(`failure_code = 'abandoned'`): 같은 트랜잭션에 중단 기록(data-model 3.16) 행이 있어야 한다(DR-25). 그 밖 UPDATE와 모든 DELETE는 거부한다. 또 질의별 결과와 결과 요약은 부모 실험이 `running`일 때만 INSERT할 수 있다(결과 가드, DR-25). 질의별 결과 행은 질의마다(DR-24), 결과 요약 행(data-model 3.14)은 실험 종료 트랜잭션에서 한 번 INSERT한다.
- **근거**: FR-029(기록 수정·삭제 불가), US5-3. 애플리케이션 버그로도 바꿀 수 없게 DB에서 막는다.

### R-08 실험 기록의 구성 펼침

- **판단**: 실험 기록은 두 구성마다 run id, 색인 식별값(`index_configs.config_hash`)과 그 다섯 snapshot 원문 전체, 검색 정책 `config_hash`와 13개 필드 snapshot 원문, 질의 임베딩 기술자(제공자·모델·revision·차원·정규화·라이브러리 버전)를 펼쳐 저장한다. `006`·`009`의 새 형식이 오면 그 기술자 6종을 같은 자리에 펼친다.
- **근거**: FR-028(모듈별 버전, 모델과 revision 포함), 설계서 13절("해시만 남기면 어떤 모듈이 바뀌었는지 알 수 없다").

### R-09 관문 시도의 정책 보정 상태

- **판단**: 관문 시도의 두 정책은 모두 `calibration_status = calibrated`여야 한다(사전 점검 거부 `policy_not_calibrated`). 개발셋 실험은 `calibration_pending` 정책도 받는다.
- **근거**: 운영 검색은 `calibrated`만 받으므로(1절), 관문을 통과해도 운영에 쓸 수 없는 후보가 관문 시도를 쓰는 일을 막는다. 개발셋에서는 보정 과정 자체를 실험해야 한다(설계서 15.3 4단계).

### R-10 run과 원본 자료 스냅숏의 일치 확인

- **판단**: 실험 사전 점검에서 두 run이 실험의 원본 자료 스냅숏으로 만든 것인지 확인한다. MVP 형식 run은 (run의 `commit_sha` = 스냅숏 `omf` 항목들의 revision) 그리고 (run의 occurrence 경로·내용 해시 집합 = 스냅숏의 `omf` 자료 ID·내용 해시 집합)일 때 일치다. 다르면 `run_snapshot_mismatch`로 거부한다.
- **근거**: FR-017, US2-3. 같은 스냅숏으로 만든 run끼리만 비교해야 적중 판정이 공정하다.

### R-11 외부 전송 금지의 강제

- **판단**: 평가 실행기는 (a) DB 연결, (b) 사내 합성 모델 서버(허용 목록 호스트, DR-16), (c) 로컬 GPU 외 네트워크 연결을 하지 않는다. 단위·계약 테스트는 socket 연결을 가로채 허용 목록 밖 연결 시도가 있으면 실패시킨다. 합성 클라이언트는 허용 목록에 없는 호스트·`https`가 아닌 외부 주소 설정이면 시작하지 않는다(fail-closed).
- **근거**: FR-034, SC-010, 헌법 VI·VII.

### R-12 계층 규칙과 생성물 격리

- **판단**: 새 코드는 domain(순수 규칙) → application(서비스·포트) → infrastructure(DB·git·GPU·HTTP 구현) → interfaces(CLI) 계층을 따른다. application 평가 모듈은 infrastructure와 `Settings`를 import하지 않는다. 또 색인(`application/indexing`, `infrastructure/source`)과 검색(`application/search`, `infrastructure/database/search.py`, `interfaces/api`) 모듈은 평가 모듈을 import하지 않고, 그 SQL은 `eval_` 테이블 이름을 포함하지 않는다(정적 테스트 U-ARCH-01·02).
- **근거**: 헌법 VII (3)(생성물은 색인·응답·근거에 넣지 않음), 설계서 16절(계층 위반을 새 코드에서 반복하지 않음). 구조로 격리해야 SC-010을 기록이 아니라 설계로 보장한다.

### R-13 마이그레이션 번호

- **판단**: 002의 마이그레이션은 두 개다. 계획 기준 이름은 `0006_evaluation_datasets`(평가셋·스냅숏), `0007_evaluation_experiments`(실험·관문)이며 `down_revision`은 각각 `0005_material_registration`, `0006_evaluation_datasets`다. 구현 시점의 실제 head가 다르면(다른 명세의 마이그레이션이 먼저 들어온 경우) 번호와 `down_revision`만 그 head 뒤로 바꾸고 내용은 바꾸지 않는다. 002 테이블은 001 테이블에 외래 키를 두지 않는다(revision은 문자열로 저장).
- **근거**: 001이 `0004`·`0005`를 예약했다. 병렬 진행 중인 다른 명세(예: `012`)의 번호 예약은 확인되지 않았다. 외래 키를 두지 않으면 OMF(commit SHA)와 factory(UUID) revision을 같은 열에 담을 수 있고 001 구현 순서와 독립이다.

### R-14 평가에서 조회 경로 오류의 처리

- **판단**: 비공개 평가 경로의 어떤 질의 오류(질의 임베딩 실패, DB 오류, 정책·run 짝 불일치, 이후 리랭커 실패)도 대체 동작 없이 실험 오류로 처리한다. 그 실험은 `failed`로 끝나고 지표와 판정을 만들지 않는다.
- **근거**: 설계서 D-06(승인: "평가 실행기에서는 대체하지 않고 실행 오류"). 대체를 허용하면 결정성 검사와 질의별 결과가 오염된다.

### R-15 이미지 묶음 정보 자료가 PDF인 경우

- **판단**: 체크리스트 이월 N4의 "이미지 묶음의 정보 자료가 PDF일 때의 좌표"는 생기지 않는다. 001이 정보 자료를 `text`·`markdown`만 허용하기로 승인했다(001 DR-15·R-04). 이미지 묶음 정답 근거는 정보 자료 파일의 행 범위로 적는다(파일 지정은 DR-07).
- **근거**: 001 승인 결정. 001 결정이 바뀌면 이 판단을 다시 연다.

### R-16 실험 실행 순서와 지연 측정

- **판단**: 한 실험에서 질의 목록은 질의 ID 순서로 처리하고, 질의마다 두 구성을 번갈아(홀수 번째 질의는 현재 → 후보, 짝수 번째는 후보 → 현재) 실행한다. 각 구성의 첫 질의 전에 같은 준비 질의 3건(평가셋 밖 고정 문장)을 실행해 지연 측정에서 뺀다. 지연은 비공개 평가 경로 호출 전후의 단조 시계(`time.perf_counter_ns`) 차이를 ms 정수(올림)로 기록한다.
- **근거**: FR-014("두 구성의 비용은 같은 측정 환경에서 잰다"). 실행 순서와 예열 차이가 한쪽 지연에만 쌓이지 않게 한다. 지연 비교는 운영 HTTP 지연이 아니라 같은 경로의 상대 비교이며, 이 점을 실험 기록의 측정 환경에 적는다.

### R-17 평가 경로의 `strict` 모드

- **판단**: 비공개 평가 경로는 `relevance_level = default`만 받는다.
- **근거**: `strict` 모드는 검색 정책 식별값에 들어 있지 않아(설계서 O-10, `009`) 실험 기록의 정책 `config_hash`만으로 재현할 수 없다. `009`가 정책에 넣으면 그 정책 필드로 받는다.

## 3. 결정 요청(사용자 승인 2026-11-10, 모두 권장안)

각 DR은 필요 이유, 의존하는 계획 부분, 권장안과 대안(안, 내용, 비용·복잡도, 향후 변경 가능성)을 적었다. **spec·체크리스트에서 넘어온 필수 항목**: GPU 메모리 한도(DR-04), 부트스트랩 세부(DR-05), 반환 근거 길이 단위(DR-06), 행 번호 기준(DR-07), 시험셋 보충 규칙(DR-08), 모듈 교체 건 단위(DR-09). 그 밖의 이월 항목(스냅숏 목록 방식과 기본 선택값, 연구 실행 자원, 버그 수정, O-11, O-8, O-13 ①)과 재검증에서 정책 선택으로 확인된 항목(DR-23 개발셋 겹침 처리, DR-24 시도를 세는 시점, DR-25 중단된 실험의 정리)도 DR로 올렸다. **2026-11-10 사용자가 DR-01~DR-25를 모두 권장안(DR-02·DR-03은 권장 A)으로 승인했다.** 각 DR 아래 `상태` 줄에 적었다.

### DR-01 평가 데이터 저장 위치와 방식

**상태**: 승인(사용자 2026-11-10, 권장안).

### DR-03 연구 실행 자원과 운영 GPU 차단 방식

**상태**: 승인(사용자 2026-11-10, 권장안 A). **값 입력 대기**: 승인된 연구 자원의 구체 목록(자원 이름·호스트·GPU UUID)은 사용자가 나중에 알려 준다. 값이 들어오기 전에는 허용 목록이 비어 있으므로 실험·관문 명령이 시작하지 않는다(fail-closed, `resource_not_allowed`). 결정 미승인이 아니라 설정값 입력 대기이며 tasks 진행을 막지 않는다.

필요 이유: FR-033, US2-8, SC-011. spec Out of Scope는 "연구 실행 자원의 구체 선택"이므로 어떤 장비를 쓸지는 정하지 않는다. 대신 실행기가 운영 GPU에서 돌지 않음을 어떻게 강제·기록하는지는 운영 방식 결정이다. 의존: P10(U-ENV-01·02), quickstart 5절, H-11.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장 A** | 허용 목록 방식. `EvaluationSettings`에 승인된 연구 자원 목록(자원 이름, 호스트 이름, GPU UUID 목록)과 운영 GPU UUID·운영 호스트 이름 목록을 둔다. 실행기는 시작 시 현재 호스트·GPU UUID를 읽어 (허용 목록에 있고) 그리고 (운영 목록에 없을) 때만 실험을 시작한다. 읽기 실패·목록 비어 있음은 거부(fail-closed). 측정 환경(자원 이름, 호스트, GPU 이름·UUID·총 메모리, CPU, 드라이버, Python·torch·라이브러리 버전)을 실험 기록에 남긴다. GPU가 없는 자원(CPU 전용)은 GPU UUID 없이 호스트로만 허용 가능 | 낮음. 표준 라이브러리와 `nvidia-smi` 호출(새 Python 의존성 없음). 자원 목록 관리가 운영 작업 | 높음 |

| 대안 C | 강제 없이 측정 환경 기록만, 점검은 사람이 | 가장 낮음. SC-011 "운영 GPU에서 실행된 건수 0"을 사후에만 확인 | 높음 |

### DR-04 운영 GPU 메모리 한도 값과 측정 방법(spec 이월)

**상태**: 승인(사용자 2026-11-10, 권장안). **값 입력 대기**: 운영 GPU 총 메모리 실측값(MiB)은 사용자가 나중에 알려 준다. 값이 정해지기 전 관문 시도는 사전 점검 `gate_setting_missing`으로 거부된다(시도로 세지 않음). 결정 미승인이 아니라 설정값 입력 대기이며 tasks 진행을 막지 않는다.

필요 이유: FR-018 ⑤ "GPU 메모리 최대 사용량이 운영 GPU 메모리 안에 들어감", spec Assumptions "운영 GPU 메모리 용량은 설정값, 값은 계획 단계에서 운영 환경을 확인해 정한다", 체크리스트 미충족 항목. 관문 수치(설정값)와 측정 방식. 의존: P3(관문 기준 상수), P10(비용 측정), U-GATE-03, DR-15.

권장안 내용:

1. **한도 값**: 운영 GPU의 총 메모리 실측값(사용자가 운영 서버에서 `nvidia-smi --query-gpu=name,uuid,memory.total --format=csv`로 확인해 알려 주는 값, MiB)에서 10%를 뺀 값을 관문 기준 설정값 `gpu_memory_limit_mib`로 둔다. `AGENTS.md` 기록상 운영 GPU는 RTX 4090(공칭 24 GiB)이지만 **실측값 확인 전에는 값을 정하지 않는다**. 값이 정해지기 전 관문 시도는 사전 점검 `gate_setting_missing`으로 거부한다(시도로 세지 않음).
2. **측정 대상**: 후보 구성의 **질의 처리 경로**(질의 임베딩, 이후 리랭커) 최대 사용량. 실험 프로세스는 구성마다 별도 하위 프로세스에서 모델을 올려 질의를 처리하고, 그 프로세스의 GPU 메모리를 `nvidia-smi --query-compute-apps=pid,used_memory` 100ms 간격 표본의 최댓값(MiB, CUDA 문맥 포함)으로 잰다. 색인(문서 임베딩) 최대 사용량은 콜드 빌드 기록(DR-14)에 있으면 함께 기록하고 둘 중 큰 값을 비교한다.
3. **비교**: `측정 최대값 <= gpu_memory_limit_mib`이면 통과(이하 통과, spec 경계값 규칙과 같은 방향).

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 위 1~3(실측 총 메모리 −10%, 질의 경로 하위 프로세스 측정, 색인 값 있으면 큰 값) | 중간. 구성별 하위 프로세스 실행, `nvidia-smi` 호출. 10% 여유는 운영 API의 다른 할당·단편화 대비 | 높음(여유 비율은 설정값) |
| 대안 1 | 한도 = 총 메모리 그대로, 측정은 `torch.cuda.max_memory_reserved()` | 낮음. CUDA 문맥(수백 MiB)이 빠져 과소 측정, 같은 프로세스에서 두 모델을 올리면 구분 어려움 | 높음 |
| 대안 2 | 한도 = 총 메모리 − 운영 API 상주 사용량(실측) − 여유, 즉 "운영 API와 함께 올라갈 수 있는가"로 판정 | 중간. 설계서 15.3 되돌리기의 동시 상주 위험까지 반영하지만 대부분의 후보가 불합격할 수 있음(관문이 엄격해짐) | 중간 |
| 대안 3 | 연구 자원 GPU가 운영 GPU와 다르면 측정하지 않고 모델 파라미터 크기로 추정 | 낮음. 추정 오차, 결정성은 높음 | 중간 |

### DR-05 부트스트랩 세부(spec 이월)

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: FR-018 ③, FR-031, spec Assumptions "부트스트랩 세부 방식은 계획 단계에서 정하고 관문 기준 설정에 포함해 기록". 검색 평가 전략(관문 판정 방식). 의존: P2(U-BOOT-01~04), DR-15, 실험 기록 필드.

권장안 내용:

- 통계값: 질의 i의 짝 차이 `d_i = hit5_후보(i) − hit5_현재(i)` ∈ {−1, 0, 1}(정답이 있는 질의만). 재표본 b의 통계값 = 뽑은 N개 `d`의 평균 × 100(%p), 분수로 계산(R-01).
- 재표본 수: 10,000(spec 기본값).
- 방법: 백분위 부트스트랩. 하한 = 정렬된 통계값의 `ceil(0.025 × B)`번째(1부터 셈, B=10,000이면 250번째), 상한 = `ceil(0.975 × B)`번째(9,750번째). 보간 없음.
- 난수: SHA-256 카운터 방식. 재표본 b의 j번째 추출 = `int.from_bytes(SHA-256(f"{seed}:{b}:{j}:{t}")[:8], "big")`에서 `2^64 − (2^64 mod N)` 이상이면 t를 1 올려 다시 뽑고(거절 표본추출, 치우침 0), 아니면 `mod N`. 질의 순서는 질의 ID 오름차순.
- 시드: 관문 기준에 고정값(권장 `20261108`, 기준 승인일)을 두고 **관문 시도는 그 값만 쓴다**(연구자가 시드를 바꿔 유리한 구간을 고르는 일 방지). 개발셋 실험은 시드를 지정할 수 있고 기록한다.
- 모든 질의에서 d가 0이면 구간은 [0, 0]이고 하한이 0보다 크지 않아 ③ 미통과(spec Edge Case).

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 위 내용(백분위, B=10,000, SHA-256 카운터 난수, 고정 시드) | 낮음. 표준 라이브러리만. 400질의 × 10,000회 = 400만 해시, 수 초~수십 초 | 높음(방식 이름·버전을 기준에 기록) |
| 대안 1 | Python `random.Random(seed)` 사용 | 가장 낮음. 표준 라이브러리 버전이 바뀌면 같은 시드의 추출이 달라질 수 있어 FR-031을 Python 버전에 묶음 | 중간 |
| 대안 2 | numpy `PCG64` + 백분위 | 낮음. numpy 직접 의존성 추가 결정 필요, 빠름 | 중간 |
| 대안 3 | BCa 방식 | 중간. 잭나이프 추가 계산, 0/±1 값에서 가속 추정 불안정 가능, 재계산 설명이 어려움 | 중간 |

### DR-06 반환 근거 평균 길이의 단위와 범위(spec 이월)

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |

### DR-11 적중·지표 계산 세부(설계서 O-11 포함)

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: FR-011·FR-012·FR-014, 설계서 13절·O-11("같은 내용이 여러 원본 경로에 있는 반환 근거에서 원본 중 하나라도 겹치면 적중을 `002`에 반영할지"). 검색 평가 전략. 의존: P1(U-HIT), P2(U-MET), DR-05.

권장안 내용:

1. **근거 단위와 순위**: 검색 응답의 근거 항목(parent 묶음)이 순위 단위다. 상위 5개 = 응답 순위 1~5.
2. **반환 근거의 위치**: 근거 항목의 child match마다의 행 범위(응답 `matches[].line_start..line_end`) × 그 항목의 **모든 origin**. parent 절 전체 범위가 아니다.
3. **다중 원본(O-11)**: 한 근거 항목의 origin 중 **하나라도** 정답 근거와 겹치면 적중(설계서 권장과 같음). MVP origin은 (source `omf`, 자료 ID = `source_path`, revision = run `commit_sha`)로 바꾼다(spec 임시 규칙).
4. **MRR 기준 길이**: MRR@20(검색 API 최대 `limit` 20). 20위 안에 적중이 없으면 0.
5. **근거 완전성**: 정답 근거가 2개 이상인 질의마다 상위 5개에서 적중한 정답 근거 수 ÷ 정답 근거 수, 그 평균. 해당 질의가 없으면 "해당 없음".
6. **p95**: nearest-rank. 질의별 지연(ms 정수)을 오름차순 정렬해 `ceil(0.95 × N)`번째 값(N = 그 구성의 전체 평가 질의 수, 문서에 없는 질의 포함). 관문 ⑤의 지연 증가 = 후보 p95 − 현재 p95.
7. **`no_evidence` 비율**: 문서에 없는 질의 중 응답 상태가 `no_evidence`인 비율.

|---|---|---|---|

### DR-12 평가셋 스냅숏과 원본 자료 스냅숏의 정합 규칙

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: FR-003(확인 기준 원본 자료 스냅숏), FR-017, US5-6, Edge Case(완전 삭제된 revision). 데이터 정합 정책. 의존: P5, P10 사전 점검(`basis_snapshot_mismatch`), data-model 4.2.

권장안 내용: 한 실험의 원본 자료 스냅숏 D는 그 평가셋 스냅숏의 **모든 질의의 확인 기준 원본 자료 스냅숏과 같아야** 한다. 원본 자료 스냅숏을 바꾸려면 작성자가 새 기준으로 질의를 다시 확인·접수해(새 질의 ID) 새 평가셋 스냅숏을 만든다. 정답 근거 revision이 001 완전 삭제로 사라지면 다음 평가셋 스냅숏부터 그 질의를 "평가 불가"로 표시하고 규모 계산(FR-002)에서 뺀다. 이미 남은 실험 기록은 바뀌지 않는다.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 단일 기준(모든 질의의 확인 기준 = 실험 스냅숏) | 낮음. 판정이 단순하고 "문서에 없음" 확인이 유효. 자료가 갱신되면 재확인 작업 필요 | 중간 |
| 대안 1 | 포함 규칙: 정답 있는 질의는 정답 revision이 D에 모두 있으면 허용, 문서에 없는 질의는 확인 기준 = D만 허용 | 중간. 재확인 부담 감소, 판정 규칙이 둘 | 높음 |
| 대안 2 | 어떤 D도 허용하고 맞지 않는 질의는 그 실험에서 평가 불가로 제외 | 낮음. 제외가 많아지면 규모 미달이 조용히 생김 | 높음 |

### DR-13 필수 검사 판정 세부(설계서 O-8 포함)

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: FR-016, FR-030, 설계서 13절(입력 정보)·O-8("GPU 리랭커·임베딩의 결정성 허용 기준", `002`·`012`·`014`). 필수 검사의 측정 방법이 정해져야 판정이 재현된다. 검색 평가 전략. 의존: P9(U-CHK-01~05), US2-4~6.

권장안 내용:

| 검사 | 판정 방법 | MVP 형식 run에서의 입력 |

| 결정성 | (a) 색인: 실험 시 해당 run의 파서·청커 기술자로 원본 자료 스냅숏을 다시 파싱·청킹(GPU·임베딩 없음)해 문서별 청크 해시 목록이 저장된 run과 같은지. 벡터는 비교하지 않음(O-8 결정 전). | 고아 청크 0 | 청크마다 (run의 occurrence → 내용 → 파싱 → 절 → 청크) 연결로 스냅숏 자료 ID·revision에 닿는지 | 기존 조인 |
| 구조 경계 위반 0 | 청킹 모듈의 경계 기록(설계서 6.3)이 있으면 그 위반 수. MVP 형식처럼 경계 기록이 없으면 평가 실행기가 같은 파서 블록(표, 목록 항목, 코드 펜스, 인용)을 보존 단위로 보고 청크 경계가 단위 안쪽을 가르는 경우를 센다. 단, 보존 단위 하나가 토큰 상한을 넘어 나눌 수밖에 없는 경우의 처리는 `003`(O-4) 결정 전까지 위반으로 센다 | markdown-it 블록 map |

- 현재 구성이 위반해도 기록만 하고(spec Edge Case), 후보는 5종 모두 통과해야 한다.
- `not_run`(입력 부족으로 검사 불가)은 통과가 아니다. 관문 시도에서 후보의 `not_run`은 ① 불합격이다.

|---|---|---|---|
| **권장** | 위 표(색인 결정성은 CPU 재청킹, 질의 결정성은 두 번 실행·정확 일치) | 중간. 실험 시간 약 2배(질의 두 번), 재청킹은 CPU 수십 초 수준 | 높음. O-8 허용 기준이 정해지면 질의 결정성 비교만 바꿈 |

### DR-14 재색인 소요 시간 측정 방법

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: FR-014, FR-018 ⑤("재색인 소요 시간이 8시간 이하"). 같은 DB에서 산출물을 재사용하면 재색인이 약 20초로 줄어든다(`AGENTS.md` 관찰값)는 사실 때문에 측정 정의가 필요하다. 운영·평가 방식. 의존: P10(비용 측정), `006`("빌드만"·재사용 끔 선택지).

권장안 내용: 재색인 소요 시간 = 실험과 **같은 측정 환경**에서 산출물 재사용 없이 실행한 **콜드 빌드** run의 `indexed_at − started_at`(초). 실험 요청에 구성마다 측정용 run id를 지정하고, 실행기는 그 run이 (같은 색인 식별값, 같은 원본 자료 스냅숏, 재사용 0건 기록, 같은 자원)인지 확인한다. 이 측정을 줄 수 있는 빌드 선택지는 `006`이 만든다. 그 전까지 관문 시도는 사전 점검 `cost_measurement_missing`으로 거부(시도로 세지 않음)되고, 개발셋 실험은 "측정 안 됨"으로 기록한다.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 위 내용(콜드 빌드 run 지정, 같은 환경, 없으면 관문 사전 점검 거부) | 중간. 후보마다 콜드 빌드 1회 필요 | 높음 |
| 대안 1 | 후보 run 자체의 `indexed_at − started_at`(재사용 포함) | 가장 낮음. 재사용 정도에 따라 20초~수 시간으로 흔들려 한도 판정이 무의미 | 높음 |
| 대안 2 | 표본 문서(예: 10%)의 콜드 빌드 시간 × 10으로 추정 | 낮음. 추정 오차, 결정적 표본 선택 규칙 필요 | 중간 |

### DR-21 시험셋 결과 노출 범위

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: FR-024("시험셋 질의와 그 결과는 튜닝과 후보 선정에 쓰지 않는다"). spec은 접근 통제를 요구하지 않지만, 질의별 시험셋 결과를 연구자에게 그대로 보여 주면 오염 경로가 된다. 보안·운영 정책. 의존: `eval gate attempt`·`eval experiment show` 출력 계약, SC-002 재계산.

권장안 내용: 관문 시도 출력과 `experiment show`는 시험셋에 대해 **조건별 사유(FR-020)와 집계 지표만** 보여 준다. 질의별 결과는 DB에 저장하되 출력하려면 `eval experiment export --per-query --actor A --reason R`을 써야 하고, 그 실행을 기록(실행자·시각·사유)에 남긴다. `eval gate recompute`는 질의별 결과를 읽어 다시 계산하지만 판정 일치 여부와 조건별 사유만 출력한다. 시험셋 질의문도 같은 방식으로 다룬다: `eval query show`는 시험셋 질의의 작성 정보·좌표만 출력하고, 질의문은 `--include-text --reason R --actor A`일 때만 출력하며 그 열람을 같은 기록 테이블(data-model 3.15 `eval_access_log`, `kind=test_query_text`)에 남긴다. 개발셋 결과와 개발셋 질의문은 제한 없이 보여 준다.

### DR-24 관문 시도를 세는 시점(spec 모호점 A-3)

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: FR-025("시험셋 결과가 일부라도 산출된 시도는 모두 센다"), spec Edge Case("시험셋 결과가 하나도 산출되기 전에 실패한 실행은 세지 않는다"), `012` US3-5(결과 없는 시도는 세지 않음). "산출"을 질의 실행으로 볼지 결과 저장으로 볼지가 정책 선택이다. 이전 판의 R-05는 첫 질의 직전에 세는 보수적 해석이었으나, 결과 없이 첫 질의에서 실패한 시도까지 세게 되어 Edge Case 문구와 어긋날 수 있다. 의존: data-model 3.12·3.13·4.2·4.3, plan `실험 흐름`, U-EXP-03, U-ATT-01, I-DB-02·03, contracts/eval-cli.md exit 4와 `gate attempt`.

공통(어느 안이든): 사전 점검 → 색인 쪽 필수 검사 → 모델 적재·예열 → 실험 행 기록 → 질의 순서. 사전 점검 거부와 실험 행 기록 전 오류는 세지 않는다.

권장안 내용: **첫 질의별 결과가 저장되는 순간부터 센다.** `gate` 실험 행은 `attempt_number` NULL로 기록하고, 질의마다 두 구성의 결과를 한 트랜잭션으로 저장·커밋한다. 첫 질의 결과를 저장하는 트랜잭션이 트랙별 advisory lock 아래 `attempt_number`(그 실험 행의 `generation`에서 값 있는 시도 수 + 1. 실행 중 새 세대가 열려도 시작 때 기록한 세대를 쓴다)를 정한다. 횟수는 `attempt_number`가 있는 `gate` 행 수다. 첫 결과 저장 전에 실패하면 `failed`, `attempt_number` NULL로 남고 세지 않는다. 결과가 하나라도 저장된 뒤 실패하면 센다. 진행 중 시도는 `attempt_number`가 NULL이어도 진행 중 유일 인덱스로 같은 트랙의 다른 시도를 막는다.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 첫 질의별 결과 저장 시점부터 셈(위 내용) | 중간. 결과를 질의마다 커밋, `attempt_number` 한 번 지정 트리거. 검색 경로가 결과를 돌려준 직후 저장 전에 프로세스가 죽으면 세지 않는 틈이 있으나, 관문 출력은 집계만 보여 주므로 그 틈으로 시험셋 결과를 보지는 못한다 | 높음 |
| 대안 1 | 첫 시험셋 질의 실행 직전부터 셈(이전 판 R-05) | 낮음. 결과가 하나도 없는 실패까지 세어 Edge Case 문구·`012` US3-5와 어긋남 | 높음 |
| 대안 2 | `completed`로 끝난 시도만 셈 | 낮음. 결과 일부를 낸 뒤 실패한 시도를 세지 않아 FR-025 "일부라도 산출되면 센다"와 충돌하고, 실패를 반복해 한도를 피할 수 있음. 비권장 | 높음 |

### DR-25 중단된 실험(`running`으로 남은 행)의 정리

**상태**: 승인(사용자 2026-11-10, 권장안).

필요 이유: 실험 행은 `running`으로 INSERT되고(DR-24), 프로세스가 강제 종료되거나 호스트가 멈추면 아무도 `failed`로 바꾸지 않는다. 그러면 트랙별 진행 중 유일 인덱스(data-model 3.12)와 사전 점검 9(`attempt_in_progress`)가 그 트랙의 이후 시도를 모두 막고, DELETE는 트리거로 금지되어 FR-026의 "고쳐서 다시 올리기"가 수동 SQL 없이는 불가능해진다. 기록 불변(FR-029)과 운영 절차에 걸친 결정이다. 의존: data-model 3.12·3.16·4.2·4.3, R-07, contracts/eval-cli.md 7절, U-EXP-02, I-EXP-03, C-CLI-06, P4b·P10·P11.

권장안 내용:

- **생존 잠금(시작 순서)**: 실행기는 실험 id(UUIDv4)를 **클라이언트에서 먼저 만들고**, 전용 DB 연결에서 그 id의 생존 잠금을 얻은 **뒤에** 실험 행을 INSERT·커밋한다. 그래서 행이 보이는 순간에는 이미 잠금이 있고, 정리 명령이 시작 직후의 살아 있는 실험을 끝낼 틈이 없다. 잠금은 실험이 끝날 때까지 유지한다.
- **새 실험의 잠금 획득(키 충돌 처리)**: 새 실험의 생존 잠금은 기다리는 `pg_advisory_lock`이 아니라 기다리지 않는 `pg_try_advisory_lock(EVAL_LIVENESS_CLASS, objid)`로 얻는다. `false`(다른 세션이 같은 (class, objid)를 쥠. 새 UUID의 objid가 다른 실험과 우연히 같은 경우)이면 그 UUID를 버리고 새 UUIDv4를 만들어 다시 시도한다. 최대 5회(코드 상수)까지 하고, 모두 실패하면 실험 행을 만들지 않고 exit 4 `liveness_lock_unavailable`(`detail.retryable: true`, 관문이면 `attempt_consumed: false`)로 끝난다. 이 코드는 실험 종류(`dev`·`gate`·`reproduction`·`transition_check`)와 무관하게 같고, 같은 트랙의 진행 중 시도를 뜻하는 `attempt_in_progress`(사전 점검 9, `gate` 전용)와 다르다. 전용 연결 자체의 오류는 일반 DB 오류로 exit 4다.
- **잠금 키**: PostgreSQL 두 정수 키 형식 `(classid int4, objid int4)`(함수 `pg_try_advisory_lock`·`pg_advisory_xact_lock`·`pg_try_advisory_xact_lock`의 두 인자 형태)을 쓰고 용도마다 고정 class ID를 둔다. 생존 잠금 = (`EVAL_LIVENESS_CLASS`, 실험 UUID의 SHA-256 앞 4바이트를 부호 있는 int4로), DR-24 트랙별 차수 지정 잠금 = (`EVAL_TRACK_CLASS`, `"<set_name>|<generation>|<track_id>"` SHA-256 앞 4바이트). 두 class ID는 서로 다르고 기존 색인 파이프라인 잠금(단일 bigint 키 형식)과도 키 공간이 다르다. 생존 잠금은 세션 잠금(전용 연결), 트랙 잠금은 트랜잭션 잠금(주 연결)이며 키가 달라 한 프로세스 안에서 서로 기다리지 않는다(자기 교착 없음). 생존 키 objid가 다른 실험과 우연히 같으면 정리 명령이 "살아 있음"으로 보고 거부하는 안전한 방향으로만 틀린다.
- **전용 연결**: 생존 잠금 연결은 SQLAlchemy 연결 풀을 거치지 않는 직접 psycopg 연결(또는 `NullPool`)이며 그 실험 동안 닫거나 재사용하지 않는다. 트랜잭션 단위로 서버 연결을 바꾸는 연결 풀러(예: PgBouncer transaction 모드)를 거치면 안 된다(세션 잠금이 다른 클라이언트 세션에 붙거나 풀림). 풀러 경유 여부는 실행기가 시작 시점에 믿을 만하게 판별할 수 없다(Docker 포트 매핑·SSH 터널처럼 URL 포트와 서버 `port` 설정이 정상적으로 다른 직접 연결이 있다. 예: 테스트 DB `127.0.0.1:55432 → 5432`). 그래서 시작 시 거부 검사는 두지 않고 다음 두 가지로 다룬다. (1) 설정 규칙: `OMF_EVAL_DATABASE_URL`은 평가 PostgreSQL에 직접 연결하는 주소여야 하고 트랜잭션 모드 풀러를 거치면 안 된다(quickstart 5절 배치 점검에서 사람이 확인). (2) 실행 중 검사: 생존 잠금을 얻을 때 전용 연결의 `pg_backend_pid()`를 기록하고, 이후 모든 자기 확인에서 값이 바뀌면 잠금 상실로 보고 아래 `liveness_lost` 처리로 끝낸다(풀러가 서버 연결을 바꾸면 안전한 방향으로 멈춤). 이 검사는 풀러를 "탐지"하는 것이 아니라 세션이 바뀐 결과를 잡는 것이며, 서버 연결을 바꾸지 않는 풀러 구성은 잡지 못한다(그 경우 세션 잠금은 그대로 유효하다). 시작 시 거부 코드는 두지 않는다. `eval experiment abandon`과 사전 점검 9는 트랜잭션 잠금만 쓰므로 이 검사를 하지 않는다.
- **연결 끊김 감지**: 전용 연결은 클라이언트 TCP keepalive(`keepalives=1`, `keepalives_idle=30`, `keepalives_interval=10`, `keepalives_count=3`)를 켜고, 평가 PostgreSQL 서버도 `tcp_keepalives_idle=30`, `tcp_keepalives_interval=10`, `tcp_keepalives_count=3`으로 둔다. 이 서버 설정과 아래 `idle_session_timeout=0`은 DR-02(승인, 권장 A)에 따라 **연구 자원에 둔 별도 평가 PostgreSQL에만** 적용하며 운영 PostgreSQL 설정은 바꾸지 않는다. 리눅스 기본값(약 2시간 11분)으로는 호스트 정지 감지가 2시간 넘게 늦어지기 때문이다. 이 설정으로 약 1분 안에 서버가 끊김을 알고 잠금을 푼다. 서버의 `idle_session_timeout`은 0(끔)이어야 한다(전용 연결은 잠금만 쥐고 쉰다).
- **잠금 상실 시 실행기 동작**: 실행기는 **모든 쓰기 트랜잭션(질의별 결과 트랜잭션과 완료 트랜잭션)을 커밋하기 직전마다** 전용 연결에서 자기 세션이 그 잠금을 쥐고 있는지 확인한다. 확인 조건은 `pg_locks`에서 `locktype = 'advisory'`, `database = (SELECT oid FROM pg_database WHERE datname = current_database())`, `classid = EVAL_LIVENESS_CLASS`, `objid = 생존 objid`, `objsubid = 2`(두 정수 키 형식), `pid = pg_backend_pid()`, `granted`인 행이 있는 것이다. `pg_locks`의 `classid`·`objid`는 부호 없는 32비트 `oid`로 보이므로, **클라이언트에서** 부호 있는 int4 키를 부호 없는 값으로 바꿔(`classid_u = classid & 0xFFFFFFFF`, `objid_u = objid & 0xFFFFFFFF`, 예: `-1 → 4294967295`) 바인드하고 `classid = CAST(:classid_u AS oid) AND objid = CAST(:objid_u AS oid)`로 비교한다(이 방식 하나로 고정. 바인드 변수에 `::` 캐스트를 붙이지 않는 저장소 관례 `CAST(:query_vector AS vector)`와 같은 형태). 또 `pg_backend_pid()`가 잠금 획득 때 기록한 값과 같아야 한다(위 전용 연결 (2)). 완료 직전에도 확인하는 이유: 결과 가드는 정리가 **커밋된 뒤**의 쓰기만 막는다. 정리 명령이 아직 오지 않았을 때 잠금을 잃은 실행기가 `completed`를 남기면 "잠금 없이 완료됨"인 기록이 생겨 생존 판정 규칙과 어긋나므로, 결과 가드만으로 충분하다고 보지 않고 완료 트랜잭션도 같은 확인을 한다. 연결 오류·잠금 없음이면 그 결과를 커밋하지 않고 질의 실행을 멈춘 뒤, 주 연결로 자기 실험을 `failed`(`failure_code = 'liveness_lost'`)로 바꾸려 시도하고(실패해도 무시) exit 4로 끝난다. 이미 정리 명령이 `failed`로 바꿨다면 아래 가드가 결과 저장을 막는다.
- **결과 가드**: 질의별 결과(data-model 3.13)와 결과 요약(3.14)에 BEFORE INSERT 트리거를 두어 부모 실험 행이 `running`일 때만 받는다. 트리거는 부모 행을 `FOR SHARE`로 읽으므로 같은 시점의 정리 명령 UPDATE와 직렬화된다. 정리가 먼저 커밋되면 그 뒤의 좀비 쓰기는 모두 거부된다. 결과 요약은 완료 트랜잭션에서 상태 전이(`running → completed`) **전에** INSERT한다.
- **트랜잭션 안 순서(잠금 승격 교착 방지)**: 결과 가드의 `FOR SHARE`를 먼저 쥔 뒤 같은 부모 행을 UPDATE하면 `FOR SHARE` → `FOR NO KEY UPDATE` 승격이 일어나고, 그 사이 정리 명령이 같은 행의 잠금을 기다리면 교착이 생길 수 있다. 그래서 실행기의 모든 쓰기 트랜잭션은 **부모 실험 행을 가장 먼저 `SELECT status FROM eval_experiments WHERE id = :id FOR NO KEY UPDATE`로 잠그고**, 그 뒤에만 자식 행을 INSERT한다. 같은 트랜잭션이 이미 더 강한 잠금을 쥐고 있으므로 가드 트리거의 `FOR SHARE`는 승격 없이 통과하고, `status`·`attempt_number`·`finished_at`·`failure_code`는 키 컬럼이 아니므로 UPDATE도 `FOR NO KEY UPDATE`로 충분하다(자식 행 외래 키 확인의 `FOR KEY SHARE`와도 충돌하지 않음).
  - 질의별 결과 트랜잭션: ① 부모 행 `FOR NO KEY UPDATE`, `running`이 아니면 커밋 없이 멈춤 → ② (`gate`의 첫 결과 트랜잭션만) 트랙 트랜잭션 잠금 `pg_advisory_xact_lock(EVAL_TRACK_CLASS, …)` → 값 있는 시도 수 계산 → `attempt_number` UPDATE → ③ 두 구성 결과(3.13) INSERT → ④ 생존 잠금 자기 확인 → ⑤ COMMIT.
  - 완료 트랜잭션: ① 부모 행 `FOR NO KEY UPDATE`, `running` 확인 → ② 결과 요약(3.14) INSERT → ③ 생존 잠금 자기 확인 → ④ `running → completed` UPDATE(`finished_at`) → ⑤ COMMIT.
  - 실행기가 스스로 `failed`(`liveness_lost` 또는 질의 오류)로 끝내는 트랜잭션도 ① 부모 행 잠금 → ② UPDATE 순서다.
  - 정리 명령(`abandon`) 트랜잭션: ① `pg_try_advisory_xact_lock(EVAL_LIVENESS_CLASS, objid)`, `false`면 exit 3 `experiment_alive` → ② 부모 행 `FOR NO KEY UPDATE`(실행기의 진행 중 쓰기 트랜잭션이 있으면 그것이 끝날 때까지 기다림), `running`이 아니면 exit 3 `not_running` → ③ 3.16 INSERT → ④ `running → failed`(`abandoned`) UPDATE → ⑤ COMMIT.
  - 모든 쓰기가 부모 행을 처음에 같은 세기로 잠그므로 잠금 승격이 없고, 정리 명령이 쥐는 생존 키 트랜잭션 잠금을 실행기의 자기 확인(`pg_locks` 읽기, 잠금 획득 없음)은 기다리지 않는다. 그래도 PostgreSQL이 교착(SQLSTATE `40P01`)을 보고하면 `abandon`은 트랜잭션을 되돌리고 exit 4 `lock_conflict`(`detail.retryable: true`)로 끝난다. 상태 변화와 3.16 기록은 없으며 같은 명령을 다시 실행하면 된다. 실행기 쪽에서 교착이 보고되면 R-14와 같이 그 실험의 오류로 처리한다.
- 위 장치로 정리 명령이 커밋된 뒤에는 이전 실행기가 결과를 더 쓸 수 없으므로, 같은 트랙의 새 시도와 이전 실행기가 동시에 기록을 남기는 일이 없다(FR-026).
- **진행 중 유일 인덱스 충돌**: 사전 점검 9를 통과한 같은 트랙의 두 관문 시도가 거의 동시에 실험 행을 INSERT하면 뒤쪽 INSERT가 진행 중 유일 인덱스 `eval_experiments_running_track_uq`(data-model 3.12)에서 유일성 위반(SQLSTATE `23505`)으로 실패한다. 실행기는 오류의 위반 제약 이름(`constraint_name`)이 `eval_experiments_running_track_uq`일 때만 이를 exit 3 `attempt_in_progress`로 바꾸고(실험 행 없음, 시도로 세지 않음, `attempt_consumed: false`), 이미 얻은 자기 생존 잠금은 풀고(`pg_advisory_unlock`, 또는 전용 연결 닫기) 끝난다. 다른 제약·인덱스의 `23505`는 예기치 않은 오류로 기존 내부 오류 경로(exit 4)를 따른다.
- 잠금이 있으면 "살아 있음", 없으면 "중단됨"이다. PostgreSQL은 연결이 끊기면(프로세스 종료, 호스트 정지 뒤 keepalive 시간 초과, DB 재시작) 세션 잠금을 자동으로 푼다.
- 사전 점검 9는 같은 트랙의 `running` 행이 있을 때 주 연결의 짧은 트랜잭션에서 `pg_try_advisory_xact_lock(EVAL_LIVENESS_CLASS, 그 실험의 objid)`로 그 잠금을 시험하고 바로 되돌려(얻었으면 트랜잭션 끝에 풀림), 살아 있으면 `attempt_in_progress`, 중단됐으면 `stale_attempt_in_progress`로 거부하고 `detail.next_step`에 정리 명령을 안내한다(둘 다 시도로 세지 않음).
- 새 명령 `eval experiment abandon ID --reason R --actor A`: 같은 트랜잭션에서 그 실험의 세션 잠금을 `pg_try_advisory_xact_lock`으로 얻을 수 있을 때만(살아 있는 프로세스가 없을 때만) `running → failed`(`failure_code = 'abandoned'`)로 바꾸고, 중단 기록(data-model 3.16: 실험 id, 사유, actor, 시각, 그 시점 `attempt_number`)을 INSERT한다. 잠금 확인은 명령이 같은 트랜잭션에서 하며 DB 제약으로 강제되지는 않는다(기록에 확인 여부 컬럼을 두지 않음). 잠금이 잡혀 있으면 exit 3 `experiment_alive`, `running`이 아니면 exit 3 `not_running`, 교착 보고면 exit 4 `lock_conflict`(재시도 가능, 상태 변화 없음). 단계 순서는 위 `트랜잭션 안 순서`.
- 시도 횟수는 DR-24를 그대로 따른다: `attempt_number`가 이미 정해졌으면(결과가 하나라도 저장됨) 중단돼도 센다. 정해지지 않았으면 세지 않는다. 정리 뒤 같은 트랙은 남은 횟수 안에서 다시 시도할 수 있다.
- 자동 정리는 하지 않는다. 정리는 사람이 명령으로 하고 사유가 기록에 남는다.
