## 용어

| 용어 | 뜻 |
|---|---|
| 평가 하네스 | 평가셋·지표·실험 기록·적용 관문을 묶은 공용 평가 체계. 이 명세의 대상이다. |
| RAG | 검색 기반 근거 조회. 원본 자료 내용을 검색해 근거로 돌려주는 방식이다. |
| LLM | 대규모 언어 모델. 글을 이해하고 생성하는 AI 모델이다. |
| 사내 모델 | 사내에서 운영하는 모델. 외부 서비스로 자료를 보내지 않는다. 특정 서버 하나로 한정하지 않는다(헌법 원칙 VII). |
| 헌법 | 이 저장소의 프로젝트 원칙 문서(`.specify/memory/constitution.md`, v2.1.0). `AGENTS.md`를 압축한 것이며 둘이 충돌하면 `AGENTS.md`가 우선한다. |
| 헌법 원칙 V | 헌법의 "근거 재현성" 원칙. 모든 원문 근거는 원본 경로, 원문 위치, revision, 내용 해시로 다시 찾아 확인할 수 있어야 한다는 규칙이다. |
| 헌법 원칙 VII (3) | 헌법의 "조회 경로 모델의 역할 경계와 LLM 사용 경계" 원칙에서 허용한 세 번째 LLM 용도. 평가 하네스의 개발셋 질의 합성과 연구용 학습 쌍(질의–근거 쌍) 생성이며, 생성물은 색인·조회 응답·근거에 넣지 않고 평가·연구 용도로만 쓴다. 사내에서 운영하는 모델만 쓴다. |
| GPU | 모델 계산에 쓰는 그래픽 처리 장치. GPU 메모리는 그 장치의 작업 메모리다. |
| 자료 | 플랫폼에 등록되어 검색 대상이 되는 문서 자료. 형식은 Excel, PDF, 이미지(사람이 쓴 정보 자료와 묶음), 텍스트 파일(Markdown 포함)이다. 등록은 명세 `001`이 다룬다. |
| source | 플랫폼이 다루는 자료 출처 단위. 현재 조회 대상은 `omf`이고 제조 자료용은 `factory`다. `001` 용어표의 정의를 따른다. |
| 자료 ID | 한 source 안에서 유일한 자료 식별값. source와 자료 ID가 함께 자료를 식별한다. `001` 용어표의 정의를 따른다. 아직 `001` 경로로 이관되지 않은 OMF Markdown의 자료 ID는 Assumptions의 임시 규칙을 따른다. |
| revision | 한 번 정해지면 바뀌지 않는 자료 시점 식별값(불변 revision). `001` 용어표의 정의를 따른다. 현재 Git 경로 자료는 commit SHA(Git 커밋 식별값)가 이 역할을 한다(헌법 원칙 V). |
| 위치 좌표 | revision 안에서 원문 위치를 가리키는 값. 자료 형식에 따라 페이지(PDF), 시트·셀 범위(Excel), 행 범위(Markdown을 포함한 텍스트 파일)로 표현한다(FR-004). |
| 근거 | 검색이 돌려주는 원문 조각과 그 재현 좌표(원본 식별, revision, 위치 좌표 등). |
| 청크 | 자료를 검색 단위로 나눈 조각. 청킹은 그 나누는 작업이다. |
| `no_evidence` | 검색 결과에 하한선을 넘는 근거가 없을 때 검색이 돌려주는 상태 값. 기존 검색 기능이 이미 쓰고 있다. |
| 의도 | 질문 의도. 무엇(사실·대상을 묻는 질의), 왜(이유·근거를 묻는 질의), 어떻게(방법·절차를 묻는 질의) 셋 중 하나다. |
| 평가 질의 | 평가셋에 든 질의 한 건. 질의문, 의도, 정답 근거 표시 등을 갖춘다(FR-003). |
| 질의 작성 형식 계약서 | 계획 단계에서 만든 `contracts/query-authoring-format.md`. 질의 작성자에게 제출 파일 형식, 키 이름, 위치 좌표 표기를 정해 주는 문서이며, SC-003에서 이 명세와 함께 작성자에게 주는 유일한 추가 문서다(사용자 결정 A-1). |
| 정답 근거 | 평가 질의에 답하는 원문 위치. revision과 위치 좌표로 식별한다. 한 질의에 여러 개일 수 있다. |
| 문서에 없는 질의 | 확인 기준 자료 어디에도 답이 없는 평가 질의. 정답 근거 대신 "정답 없음"으로 표시한다. |
| 평가셋 | 평가 질의의 모음. 시험셋과 개발셋으로 나뉜다. |
| 시험셋 | 사람이 작성한 평가 질의 모음. 정답이 있는 질의 400개 이상과 문서에 없는 질의 50개 이상, 모두 450개 이상으로 이루어진다(FR-002). 적용 관문 판정에만 쓰고 튜닝에 쓰지 않는다. |
| 질의 템플릿 | 빈칸이 있는 질문 틀(예: "[설비명]의 점검 주기는 무엇인가?")에 자료의 용어·값을 넣어 질의를 기계적으로 만드는 방식. 템플릿이라고도 쓴다. RDB 조회의 SQL 템플릿과는 다른 것이다. |
| 개발셋 | 질의 템플릿이나 사내 모델 합성으로 만든 평가 질의 모음. 튜닝과 후보 선정에 쓴다. 시험셋과 분리한다. |
| 합성 질의 | 사내 모델이 자료를 읽고 만들어 낸 평가 질의. 헌법 원칙 VII (3)이 허용한 LLM 용도다. |
| 튜닝 | 결과를 보고 구성의 설정·규칙·모델을 고르거나 조정하는 일. |
| 오염 | 시험셋 결과가 튜닝이나 후보 선정에 새어 들어가 시험셋이 더 이상 공정한 시험이 되지 못하는 상태. |
| 스냅숏 | 특정 시점의 내용을 고정해 다시 꺼낼 수 있게 한 사본과 그 식별값. 평가셋 스냅숏과 원본 자료 스냅숏이 있다. |
| 구성 | 평가 대상이 되는 검색 설정 묶음. 색인 식별값과 검색 정책 식별값의 조합으로 식별한다. |
| 색인 식별값 | 저장 문서·청크·벡터를 바꾸는 설정(자료 revision, 파서, 청킹 규칙, 문서 임베딩 모델·revision 등)의 묶음을 구분하는 식별값. `AGENTS.md` `Index identity와 search policy identity` 절의 index identity다. |
| 검색 정책 식별값 | 질의 시점 결과를 바꾸는 설정(질의 임베딩 모델·revision, 후보 수, 결합 방식, 하한선, 리랭커 등)의 묶음을 구분하는 식별값. 같은 절의 search policy identity다. |
| 현재 구성 | 비교 시점에 운영에 적용되어 있는 구성. 관문 판정의 비교 기준이다. |
| 후보 구성 | 연구나 모듈 교체로 적용을 제안하는 구성. |
| 활성 색인 | 운영 검색이 현재 사용하는 색인. |
| 나란히 색인 | 활성 색인을 건드리지 않고 후보 구성의 색인을 별도로 만들어 비교하는 방식. |
| 모듈 | 교체 가능한 검색 구성 요소. 파서, 영역 판별, 청킹 규칙, 검색용 텍스트 보강, 임베딩, 리랭커다. 모듈 경계는 "공통 모듈 구조 설계(작성 예정)"에서 정한다. |
| 파서 | 파일에서 글자·표·위치를 꺼내는 프로그램. |
| 영역 판별 | 문서 안의 영역(본문, 표, 머리말 등)의 종류를 판별하는 일. |
| 구조 보존 청킹 | 표·목록·제목 절 같은 문서 구조를 깨지 않게 나누는 청킹. |
| 검색용 텍스트 보강 | 원문은 바꾸지 않고 검색에만 쓰는 텍스트를 덧붙이는 일. |
| 임베딩 | 글을 의미 벡터(숫자 목록)로 바꾸는 일. 그 모델을 임베딩 모델이라 한다. |
| 리랭커 | 질의와 후보 근거를 함께 읽어 순위를 다시 매기는 모델. |
| 나이브 기본 구현 | 연구 결과가 적용되기 전 플랫폼이 쓰는 단순한 기본 모듈 구현. |
| 연구 트랙 | 병렬로 진행하는 검색 품질 연구 하나. ① 파싱·영역 판별·구조 보존 청킹(`013`), ② 리랭커(`012`), ③ 임베딩(`014`)의 세 트랙이 있다. 원문자 번호는 `AGENTS.md`의 연구 순서이고 명세 번호와 다르다. |
| 실험 | 같은 평가셋 스냅숏과 원본 자료 스냅숏으로 두 구성을 평가해 비교하는 한 번의 실행. |
| 실험 기록 | 실험의 입력 식별값·결과·판정을 불변으로 남긴 기록. |
| 적용 관문 | 후보 구성을 적용 권고할지 판정하는 기준. 이 명세의 기준 이름은 "개선 폭 기준 v1.0"(사용자 승인 2026-11-08)이다. |
| 관문 시도 | 후보 구성 하나를 시험셋으로 평가해 관문 판정을 받는 일 한 번. 같은 시험셋에서 연구 트랙(또는 모듈 교체 건)마다 최대 3회다. |
| 모듈 교체 건 | 연구 트랙 밖에서 제안하는 모듈 교체 하나. 관문 시도 한도는 연구 트랙과 같이 건별로 센다. |
| 적중 | 반환 근거의 위치가 정답 근거의 위치와 조금이라도 겹치는 것. 겹치면 그 정답 근거를 찾은 것으로 본다. |
| 토큰 | 모델이 글을 처리하는 최소 단위. 대개 단어나 단어 조각이다. |
| 반환 근거 평균 길이 | 검색이 돌려준 근거 원문의 평균 길이. 길이 단위(토큰 등)는 계획 단계에서 정하며 비교하는 두 구성에 같은 단위를 쓴다. |
| 설정값 | 기본값을 갖되 승인된 절차로 바꿀 수 있는 수치. 관문의 모든 수치는 설정값이다. |
| Recall@5 | 정답 근거가 검색 결과 상위 5개 안에서 하나라도 적중한 질의의 비율. 정답이 있는 질의만 대상으로 센다. 이 명세의 주 지표다. |
| MRR | 평균 역순위(Mean Reciprocal Rank). 질의마다 첫 정답 근거의 순위 역수(1위면 1, 2위면 1/2, 없으면 0)를 구해 평균한 값. 0~1 사이다. |
| 근거 완전성 | 정답 근거가 여러 개인 질의에서, 상위 5개 안에 찾은 정답 근거 수를 전체 정답 근거 수로 나눈 값의 평균. |
| `no_evidence` 비율 | 문서에 없는 질의 중 검색이 `no_evidence`를 돌려준 질의의 비율. |
| %p | 퍼센트포인트. 비율 사이의 차이를 나타내는 단위다. 60%에서 63%로 오르면 +3%p다. MRR과 근거 완전성처럼 0~1 값인 지표는 100을 곱한 값으로 읽어 0.02 차이를 2%p로 본다. |
| p95 | 95번째 백분위수. 질의 지연을 작은 순으로 늘어놓았을 때 95% 지점의 값이다. |
| 짝 비교 | 같은 질의에 대한 두 구성의 결과를 짝지어 질의 단위로 차이를 보는 비교. |
| 불일치율 | 짝 비교에서 두 구성 중 한쪽만 정답을 상위 5개에 넣은 질의의 비율. |
| 부트스트랩 | 질의 목록에서 같은 수만큼 복원 추출(뽑은 것을 되돌려 놓고 다시 뽑기)을 반복해 지표 차이의 흩어짐을 추정하는 통계 방법. 한 번의 추출을 재표본이라 한다. |
| 시드 | 무작위 추출의 출발값. 같은 시드면 같은 추출 순서가 나와 결과를 재현할 수 있다. |
| 신뢰구간 | 추정한 차이가 있을 법한 범위. 95% 신뢰구간의 하한이 0보다 크면 개선이 우연이 아닐 가능성이 높다고 본다. |
| 필수 검사 | 어기면 다른 지표와 관계없이 즉시 불합격시키는 검사. 결정성, 원문 커버리지, 근거 좌표 정확성, 고아 청크 0, 구조 경계 위반 0이다(FR-016). |
| 결정성 | 같은 입력과 같은 식별값이면 항상 같은 결과가 나오는 성질. |
| 원문 커버리지 | 색인 대상 원문이 빠짐없이 어떤 청크에 담겼는지 여부. |
| 고아 청크 | 원본 자료의 revision·위치와 연결되지 않은 청크. |
| 구조 경계 위반 | 분할 규칙이 보존하도록 정한 구조 단위(예: 표의 행, 목록, 제목 절)를 청크 경계가 가르는 일. |
| 비용 한도 | 후보 구성이 넘으면 안 되는 비용 상한. 질의 지연 p95 증가, 재색인 소요 시간, GPU 메모리, `no_evidence` 비율이다. |
| 재색인 | 원본 자료 스냅숏 전체로 색인을 처음부터 다시 만드는 일. |
| smoke | 기존 MVP 배포 때 기능이 동작하는지만 빠르게 확인한 고정 질의 6개(정상 5개, 문서에 없는 질의 1개). 정식 평가셋이 아니다. |
| 승인권자 | 이 프로젝트의 사용자. 관문 통과 후보의 실제 적용을 승인한다. |
| `001` | 문서 자료 등록·원본 보관·불변 revision·권한·스키마 사전을 다루는 명세. |
| `003` | 파서·전처리·문서 분석 Agent 분할 규칙·키워드 사전을 다루는 후속 명세. |
| `006` | RAG 적재 일반화와 OMF(첫 조회 대상 프로젝트) 문서 이관을 다루는 후속 명세. |
| `012` | 연구 트랙 ② 리랭커의 연구 내용을 다루는 후속 명세. |
| `013` | 연구 트랙 ① 파싱·영역 판별·구조 보존 청킹의 연구 내용을 다루는 후속 명세. 반환 근거 평균 길이의 증가 한도도 여기서 정한다. |
| `014` | 연구 트랙 ③ 임베딩의 연구 내용을 다루는 후속 명세. |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 질의 작성자가 명세만 보고 시험셋 질의를 작성한다 (Priority: P1)

질의 작성자는 다른 문서 없이 이 명세와 질의 작성 형식 계약서(`contracts/query-authoring-format.md`)만 읽고 평가 질의 한 건에 무엇을 적어야 하는지와 정답 근거를 어떻게 표시하는지 안다. 작성자는 질의문, 의도, 정답 근거 목록(또는 정답 없음)과 작성 정보를 갖춰 시험셋에 질의를 넣는다. 항목이 빠지거나 정답 표시가 틀린 질의는 시험셋에 들어가지 않는다.

**Why this priority**: 시험셋이 없으면 어떤 지표도 관문도 계산할 수 없다. 사람이 쓴 시험셋은 다른 모든 이야기의 입력이다.

**Independent Test**: 이 명세와 질의 작성 형식 계약서만 받은 작성자가 정답이 하나인 질의, 정답이 여러 개인 질의, 문서에 없는 질의를 각각 작성해 넣고, 형식이 맞는 질의만 받아들여지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 시스템이 보여 준 원본 자료 스냅숏과 그 안의 PDF·Excel 자료가 있고, **When** 작성자가 FR-003 질의 예시 A처럼 질의문, 의도 `무엇`, 정답 구분 "정답 있음", 정답 근거 2개(각각 source, 자료 ID, revision, 위치 좌표), 확인 기준 원본 자료 스냅숏, 작성자, 작성일, 출처 구분 "사람 작성"을 모두 갖춘 질의를 넣으면, **Then** 질의가 시험셋에 들어가고 시스템이 질의 ID를 매겨 돌려준다.
2. **Given** 답이 Excel 자료 두 곳에 나뉘어 있고, **When** 작성자가 정답 근거 두 개(각각 source, 자료 ID, revision, 시트·셀 범위)를 표시한 질의를 넣으면, **Then** 질의가 정답 근거 두 개를 가진 채 들어간다.
3. **Given** 확인 기준 자료 어디에도 답이 없는 질문이 있고, **When** 작성자가 FR-003 질의 예시 B처럼 의도를 적고 "정답 없음"으로 표시한 질의를 넣으면, **Then** 문서에 없는 질의로 들어간다.
4. **Given** 의도가 비었거나 무엇·왜·어떻게 밖의 값인 질의가 있고, **When** 넣으면, **Then** 의도 사유로 거부된다.
5. **Given** 정답 근거도 "정답 없음"도 없는 질의, 또는 둘 다 있는 질의가 있고, **When** 넣으면, **Then** 정답 표시 사유로 거부된다.
6. **Given** 정답 근거의 revision이 원본 자료 스냅숏에 없거나 위치 좌표가 그 revision 안에 없는 질의가 있고, **When** 넣으면, **Then** 정답 근거 좌표 사유로 거부된다.
7. **Given** 위치 좌표의 종류가 자료 형식과 맞지 않는 질의(예: 텍스트 파일에 시트·셀 범위)가 있고, **When** 넣으면, **Then** 정답 근거 좌표 사유로 거부된다.
8. **Given** 작성자나 작성일이 빠진 질의가 있고, **When** 넣으면, **Then** 작성 정보 사유로 거부된다.
9. **Given** 같은 시험셋에 같은 질의문이 이미 있고, **When** 같은 질의문을 다시 넣으면, **Then** 중복 사유로 거부된다.
10. **Given** 아직 `001` 경로로 이관되지 않은 OMF Markdown에 답이 있고, **When** 작성자가 source `omf`, 자료 ID로 저장소 기준 파일 경로, revision으로 고정 commit SHA, 위치 좌표로 행 범위를 적은 질의를 넣으면, **Then** 질의가 시험셋에 들어간다.
11. **Given** 시스템이 보여 준 목록에 없는 원본 자료 스냅숏 식별값을 적은 질의가 있고, **When** 넣으면, **Then** 확인 기준 스냅숏 사유로 거부된다(FR-006).

### User Story 2 - 연구자가 후보 구성을 현재 구성과 나란히 비교한다 (Priority: P1)

연구자는 후보 구성의 색인을 활성 색인과 별도로 만들고, 같은 평가셋 스냅숏과 원본 자료 스냅숏으로 현재 구성과 후보 구성을 평가해 주 지표, 보조 지표, `no_evidence` 비율, 비용, 필수 검사 결과를 얻는다. 이 비교는 운영 검색에 영향을 주지 않는다. 연구자는 개발셋으로 마음껏 튜닝하고, 시험셋은 관문 시도에서만 쓴다.

**Why this priority**: 연구 트랙 3건과 모듈 교체가 모두 이 비교로 결과를 낸다. 운영에 영향을 주면 비교 기능을 쓸 수 없다.

**Independent Test**: 표본 원본 자료 스냅숏과 개발셋으로 두 구성을 비교해 모든 지표와 필수 검사 결과가 나오는지, 비교 전후 운영 검색의 고정 질의 결과와 활성 색인이 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 현재 구성과 후보 구성, 개발셋 스냅숏, 원본 자료 스냅숏이 있고, **When** 실험을 실행하면, **Then** 두 구성 각각의 Recall@5, MRR, 근거 완전성, 의도별 Recall@5, `no_evidence` 비율, 질의 지연 p95, 재색인 소요 시간, GPU 메모리 사용량, 반환 근거 평균 길이와 필수 검사 5종의 결과를 받는다.
2. **Given** 실험이 진행 중이고, **When** 운영 검색이 고정 질의를 받으면, **Then** 실험 전과 같은 결과를 돌려주고 활성 색인은 바뀌지 않는다.
3. **Given** 두 구성의 평가셋 스냅숏이나 원본 자료 스냅숏이 서로 다른 비교 요청이 있고, **When** 실행하면, **Then** 비교 조건 불일치 사유로 거부된다.
4. **Given** 후보 구성의 청크 하나가 원본 revision·위치와 연결되지 않고, **When** 실험을 실행하면, **Then** 고아 청크 검사가 실패로 기록된다.
5. **Given** 후보 구성이 표의 한 행을 두 청크로 갈라 놓고, **When** 실험을 실행하면, **Then** 구조 경계 위반 검사가 실패로 기록된다.
6. **Given** 같은 구성과 같은 스냅숏으로 두 번 실행했는데 결과가 다르고, **When** 결정성 검사를 하면, **Then** 결정성 검사가 실패로 기록된다.
7. **Given** 개발셋 실험이 있고, **When** 연구자가 결과를 보고 설정을 바꿔 다시 실행하면, **Then** 횟수 제한 없이 실행되고 관문 시도로 세지 않는다.
8. **Given** 실험이 끝났고, **When** 실험 기록의 측정 환경을 확인하면, **Then** 실험을 실행한 자원이 기록되어 있고 그 자원이 운영 GPU가 아니다.

### User Story 3 - 관문이 후보 구성의 적용 권고 여부를 판정한다 (Priority: P1)

연구 트랙의 최종 후보는 시험셋으로 관문 시도를 받는다. 관문은 개선 폭 기준 v1.0의 다섯 조건을 모두 확인해 "적용 권고", "불합격", "유의한 차이 없음(현재 유지)" 중 하나로 판정하고 조건별 사유를 남긴다. 적용 권고를 받아도 실제 적용은 승인권자가 승인한 뒤에만 한다.

**Why this priority**: 연구 결과를 적용할지 정하는 유일한 객관 기준이다. 이 판정이 없으면 연구 결과를 근거 없이 적용하게 된다.

**Independent Test**: 경계값에 걸친 표본 결과(+3.0%p, 신뢰구간 하한 0, 의도별 하락 5.0%p 등)로 판정을 내려 기준표대로 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 필수 검사를 모두 통과하고 Recall@5가 +3.4%p, 신뢰구간 하한이 +0.6%p, 의도별 하락과 보조 지표 하락이 한도 안이며 비용 한도 안인 후보가 있고, **When** 관문 시도를 하면, **Then** "적용 권고"로 판정되고 조건별 통과 사유가 기록된다.
2. **Given** 다른 지표는 모두 좋지만 구조 경계 위반이 1건인 후보가 있고, **When** 관문 시도를 하면, **Then** "불합격"으로 판정되고 사유에 어긴 필수 검사가 남는다.
3. **Given** Recall@5 개선이 +2.5%p인 후보가 있고, **When** 관문 시도를 하면, **Then** 다른 조건과 관계없이 적용 권고가 나오지 않고 현재 구성을 유지한다.
4. **Given** Recall@5 개선이 +3.2%p지만 신뢰구간 하한이 0 이하인 후보가 있고, **When** 관문 시도를 하면, **Then** "유의한 차이 없음(현재 유지)"으로 판정된다.
5. **Given** 전체 Recall@5는 +4%p 올랐지만 의도 `왜`의 Recall@5가 5%p 이상 떨어진 후보가 있고, **When** 관문 시도를 하면, **Then** "불합격"으로 판정되고 사유에 해당 의도가 남는다.
6. **Given** 질의 지연 p95가 현재 구성보다 200ms를 넘게 늘었거나 재색인이 8시간을 넘거나 운영 GPU 메모리에 들어가지 않거나 `no_evidence` 비율이 줄어든 후보가 있고, **When** 관문 시도를 하면, **Then** "불합격"으로 판정되고 사유에 넘은 비용 한도가 남는다.
7. **Given** "적용 권고"를 받은 후보가 있고, **When** 승인권자가 아직 승인하지 않았으면, **Then** 운영 구성은 바뀌지 않는다.
8. **Given** 승인권자가 관문 설정값 하나를 바꿨고, **When** 이후 관문 시도를 하면, **Then** 바뀐 설정값과 관문 기준 버전이 실험 기록에 남는다.

### User Story 4 - 시험셋 오염을 막는다 (Priority: P2)

같은 시험셋에서 연구 트랙(또는 모듈 교체 건)마다 관문 판정은 최대 3회이고, 트랙은 한 번에 최종 후보 1개만 올린다. 불합격한 후보를 고쳐 그 트랙의 남은 횟수 안에서 다시 올릴 수 있다. 한도를 다 쓴 트랙은 시험셋을 보충한 뒤에 재개한다. 시험셋의 정답이 있는 질의가 400개에 이르기 전에는 개선 목적의 교체를 하지 않는다.

**Why this priority**: 시험셋을 반복해서 보면 관문이 결과에 맞춰진 기준이 되어 의미를 잃는다. 다만 관문 판정 자체(User Story 3)가 먼저 있어야 이 제한이 의미가 있으므로 P2다.

**Independent Test**: 한 시험셋에서 같은 트랙의 네 번째 관문 시도와 후보 2개를 한 번에 올리는 시도가 막히는지, 다른 트랙의 시도는 영향을 받지 않는지, 정답이 있는 질의가 400개 미만인 시험셋에서 개선 목적 관문 시도가 막히는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 한 시험셋에서 트랙 ②가 관문 시도를 3회 썼고, **When** 트랙 ②가 네 번째 시도를 하면, **Then** 시도 한도 사유로 거부되고 시험셋 보충이 필요하다는 안내를 받는다. 같은 시험셋에서 시도를 3회 쓰지 않은 트랙 ③의 시도는 받아들여진다.
2. **Given** 한 연구 트랙이 있고, **When** 같은 시험셋에 후보 2개를 한 번의 관문 시도로 올리면, **Then** 트랙당 후보 한도 사유로 거부되고 시도 횟수는 늘지 않는다.
3. **Given** 트랙 ①의 후보가 첫 관문 시도에서 불합격했고, **When** 고친 후보를 같은 시험셋에 다시 올리면, **Then** 두 번째 시도로 받아들여지고 남은 횟수는 1회가 된다.
4. **Given** 정답이 있는 질의가 400개 미만인 시험셋이 있고, **When** 개선 목적의 관문 시도를 하면, **Then** 시험셋 규모 사유로 거부된다.
5. **Given** 의도 하나의 정답이 있는 질의가 100개 미만이거나 문서에 없는 질의가 50개 미만인 시험셋이 있고, **When** 관문 시도를 하면, **Then** 시험셋 구성 사유로 거부된다.
6. **Given** 시험셋 질의와 같은 질의문이 개발셋 후보에 있고, **When** 개발셋을 만들면, **Then** 그 질의는 개발셋에서 빠진다.
7. **Given** 이미 기록된 관문 시도가 있고, **When** 같은 구성과 같은 스냅숏으로 재현 실행을 하면, **Then** 결과가 기록과 같고 관문 시도 횟수는 늘지 않는다.

### User Story 5 - 실험 기록만으로 판정을 다시 계산하고 실험을 재현한다 (Priority: P2)

검토자는 실험 기록만 보고 관문 판정을 다시 계산해 기록된 판정과 같은지 확인한다. 같은 식별값으로 실험을 다시 실행하면 같은 결과가 나온다.

**Why this priority**: 판정을 다시 확인할 수 없으면 관문 결과를 믿을 수 없다. 다만 기록이 쌓이는 것은 비교와 판정이 동작한 뒤이므로 P2다.

**Independent Test**: 표본 실험 기록에서 판정을 다시 계산하고, 같은 실험을 다시 실행해 질의별 결과와 지표가 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 끝난 실험 기록이 있고, **When** 검토자가 기록의 질의별 결과와 설정값만으로 관문 판정을 다시 계산하면, **Then** 기록된 판정과 사유가 같다.
2. **Given** 끝난 실험 기록이 있고, **When** 같은 구성 식별값, 평가셋 스냅숏, 원본 자료 스냅숏, 시드로 다시 실행하면, **Then** 질의별 결과와 품질 지표가 기록과 같다.
3. **Given** 끝난 실험 기록이 있고, **When** 기록을 수정하거나 지우려 하면, **Then** 거부되고 기록은 그대로다.
4. **Given** 같은 결과로 부트스트랩을 같은 시드로 두 번 계산하고, **When** 두 신뢰구간을 비교하면, **Then** 두 구간이 같다.
5. **Given** 평가셋 스냅숏 S1이 있고, **When** 평가셋에 질의를 더하거나 빼면, **Then** 새 스냅숏 S2가 생기고 S1의 질의와 내용은 그대로이며 S1을 쓴 실험 기록도 그대로다.
6. **Given** 원본 자료 스냅숏 D1이 있고, **When** 그 안의 자료에 새 revision이 등록되면, **Then** D1은 여전히 이전 revision을 가리키고, 새 revision을 쓰려면 새 원본 자료 스냅숏을 만든다.

### Edge Cases

- 두 구성이 모든 질의에서 같은 결과를 내면 불일치율이 0이고 신뢰구간이 0 하나로 모인다. 하한이 0보다 크지 않으므로 "유의한 차이 없음(현재 유지)"이다.
- 경계값 처리는 기본값이며 관문 설정값으로 바꿀 수 있다(FR-022). 기본값으로는 Recall@5 개선이 정확히 +3%p이면 ② 조건을 통과한다. 신뢰구간 하한이 정확히 0이면 ③ 조건을 통과하지 못한다. 의도별 하락이 정확히 5%p이거나 보조 지표 하락이 정확히 2%p이면 ④ 조건을 통과하지 못한다. 지연 p95 증가가 정확히 200ms이거나 재색인이 정확히 8시간이면 ⑤ 조건을 통과한다.
- 현재 구성이 이미 필수 검사 하나를 어기고 있어도 후보 구성은 필수 검사 5종을 모두 통과해야 한다. 현재 구성의 위반은 실험 기록에 남긴다.
- 정답이 여러 개인 질의가 시험셋에 없으면 근거 완전성은 계산할 수 없다. 이때 완전성 조건은 "해당 없음"으로 기록하고 그 사실을 판정 사유에 남긴다.
- 정답 근거가 가리키는 revision이 `001`의 완전 삭제로 사라지면 그 질의는 다음 평가셋 스냅숏부터 평가 불가로 표시한다. 이미 남은 실험 기록은 바뀌지 않는다.
- 시험셋 결과가 하나도 산출되기 전에 실패한 실행(예: 후보 색인 생성 실패)은 관문 시도로 세지 않는다. 시험셋 결과가 일부라도 산출되었으면 센다.
- 관문 시도에서 불합격한 후보를 고쳐 같은 시험셋에 다시 올리면 그 트랙의 다음 시도로 센다. 횟수는 트랙(또는 모듈 교체 건)별로 따로 세며, 한 트랙의 시도가 다른 트랙의 남은 횟수를 줄이지 않는다.
- 정답이 있는 질의 420개와 문서에 없는 질의 30개로 모두 450개인 시험셋은 FR-002를 채우지 못한다. 문서에 없는 질의가 50개 미만이기 때문이다. 정답이 있는 질의 390개와 문서에 없는 질의 60개인 시험셋도 같다.
- 같은 평가셋 안에서 정답 근거 좌표가 같은 revision의 다른 범위와 겹쳐도 오류가 아니다. 서로 다른 질의는 같은 원문을 정답으로 가질 수 있다.
- 문서에 없는 질의는 Recall@5, MRR, 근거 완전성의 분모에 넣지 않고 `no_evidence` 비율에만 쓴다.
- 연구 자원과 운영 자원의 사양이 달라 비용 측정값이 운영과 다를 수 있다. 측정 환경을 실험 기록에 남긴다.

## Requirements *(mandatory)*

### Functional Requirements

**평가셋과 평가 질의**

- **FR-001**: 시스템 MUST 평가셋을 시험셋과 개발셋으로 나누어 관리한다. 한 질의는 두 셋 중 하나에만 속한다.
- **FR-002**: 시험셋은 MUST 사람이 작성한 질의로만 구성하고 다음 규모를 갖춘다: 정답이 있는 질의 400개 이상(의도 무엇·왜·어떻게별 각 100개 이상)과, 이와 별도로 문서에 없는 질의 50개 이상, 모두 450개 이상. 문서에 없는 질의는 정답이 있는 질의 400개에 세지 않는다. 이 규모를 채우지 못한 시험셋으로는 관문 시도를 할 수 없다.
- **FR-003**: 평가 질의 한 건은 MUST 다음 항목을 모두 갖춘다. 작성자가 채우는 항목이 하나라도 빠지면 그 질의를 받지 않는다. 단, 정답 없음 질의의 정답 근거 목록은 비워 두는 항목이므로 적지 않아도 빈 목록으로 보고 빠진 것으로 보지 않는다(사용자 결정 A-15, 2026-11-10). 작성자가 채우는 항목이 적도록 시스템이 채울 수 있는 항목은 시스템이 채운다.

- **FR-003a**: 문서에 없는 질의도 MUST 의도를 가진다. 호출 Agent는 모든 질의를 무엇·왜·어떻게로 분석해 보내므로(`AGENTS.md` `다음 목표` 절) 평가 질의도 실제 요청과 같은 형태여야 하기 때문이다. 문서에 없는 질의의 의도 분포에는 규칙을 두지 않는다. 의도별 100개 이상(FR-002)은 정답이 있는 질의에만 센다.
- **FR-003b**: 시스템 MUST 질의 작성자에게 작성 기준으로 고를 수 있는 원본 자료 스냅숏의 식별값 목록을 보여 준다. 목록에 없는 식별값을 적은 질의는 거부한다.
- **FR-004**: 정답 근거의 위치 좌표는 MUST 자료 형식에 맞는 종류를 쓴다: PDF는 페이지, Excel은 시트와 셀 범위, Markdown을 포함한 텍스트 파일은 행 범위, 이미지 묶음은 묶인 정보 자료의 행 범위. 형식과 맞지 않는 종류나 revision 안에 없는 위치는 거부한다.
- **FR-005**: 정답 근거 목록이 1개 이상이면서 "정답 없음"인 질의와, 정답 근거 목록이 비었으면서 "정답 있음"인 질의는 MUST 거부한다.
- **FR-006**: 시스템 MUST 평가 질의를 거부할 때 작성자가 다음 사유를 구별해 고칠 수 있게 한다: 항목 누락, 의도, 정답 표시, 정답 근거 좌표, 확인 기준 스냅숏, 작성 정보, 중복. 확인 기준 스냅숏 사유는 확인 기준 원본 자료 스냅숏 식별값이 시스템이 보여 준 목록(FR-003b)에 없을 때 쓴다. 의도, 정답 구분, 정답 근거 목록, 작성자, 작성일이 빠진 질의는 항목 누락이 아니라 각각 의도·정답 표시·정답 표시·작성 정보·작성 정보 사유로 거부한다(User Story 1 시나리오 4·5·8). 정답 근거 목록이 빠지면 빈 목록으로 보므로 "정답 있음" 질의는 정답 표시 사유로 거부되고 "정답 없음" 질의는 받는다(FR-003). 항목 누락 사유는 질의문, 확인 기준 원본 자료 스냅숏, 출처 구분이 빠졌거나 알 수 없는 항목이 있을 때만 쓴다(사용자 결정 A-15, 2026-11-10).
- **FR-007**: 같은 평가셋에 같은 질의문을 두 번 넣을 수 없다. 개발셋을 만들 때 MUST 시험셋 질의와 같은 질의문은 개발셋에서 뺀다.
- **FR-008**: 개발셋은 MUST 질의 템플릿 또는 합성으로 만든 질의로 구성한다. 합성 질의 생성은 헌법 원칙 VII (3)이 허용한 평가·연구용 자료 생성이며, MUST 사내에서 운영하는 모델만 쓴다.
- **FR-008a**: 합성 질의와 그 생성 과정의 산출물(연구용 질의–근거 쌍 포함)은 MUST 색인, 조회 응답, 근거에 들어가지 않고 평가·연구 용도로만 쓴다(헌법 원칙 VII (3)). 개발셋 질의도 같다.
- **FR-009**: 평가셋은 MUST 스냅숏으로 고정할 수 있다. 질의를 더하거나 빼면 새 스냅숏이 되고, 이미 만든 스냅숏의 내용은 바뀌지 않는다.
- **FR-010**: 원본 자료도 MUST 스냅숏으로 고정할 수 있다. 원본 자료 스냅숏은 포함한 자료와 각 revision을 고정한다.

**지표**

- **FR-011**: 시스템 MUST 각 구성에 대해 주 지표 Recall@5를 계산한다. 분모는 정답이 있는 질의이며, 질의 하나는 정답 근거 중 하나라도 검색 결과 상위 5개에서 적중했으면 성공이다. 적중은 반환 근거의 위치가 정답 근거의 위치와 조금이라도 겹치는 것이다. 이 적중 판정은 Recall@5, MRR, 근거 완전성에 똑같이 적용한다.
- **FR-012**: 시스템 MUST 보조 지표로 MRR, 근거 완전성, 의도별 Recall@5를 계산한다. 근거 완전성은 정답 근거가 2개 이상인 질의만으로 계산한다.
- **FR-013**: 시스템 MUST 문서에 없는 질의에 대해 `no_evidence` 비율을 계산한다. 문서에 없는 질의는 Recall@5, MRR, 근거 완전성의 분모에 넣지 않는다.
- **FR-014**: 시스템 MUST 비용 지표로 질의 지연 p95, 재색인 소요 시간, GPU 메모리 최대 사용량을 측정한다. 두 구성의 비용은 같은 측정 환경에서 잰다.
- **FR-014a**: 시스템 MUST 실험마다 두 구성의 반환 근거 평균 길이를 기록하고 비교 결과에 지표와 함께 보여 준다. 겹침만으로 적중을 판정하므로 긴 근거를 돌려주는 구성이 유리해지는지 검토자가 볼 수 있게 하기 위해서다. 길이 증가 한도는 이 명세의 관문 조건이 아니며 `013`에서 정한다.
- **FR-015**: 시스템 MUST 질의마다 두 구성의 검색 결과 순위, 정답 근거 판정, 지연을 질의별 결과로 남긴다. 관문 판정의 재계산은 이 질의별 결과만으로 할 수 있어야 한다.

**필수 검사**

- **FR-016**: 시스템 MUST 각 구성에 대해 다음 필수 검사 5종을 실행한다. 하나라도 어기면 그 구성은 관문에서 즉시 불합격이다.
  - 결정성: 같은 원본 자료 스냅숏, 같은 색인 식별값과 검색 정책 식별값으로 두 번 실행한 청크와 질의별 결과가 같다.
  - 원문 커버리지: 색인 대상 원문 중 어느 청크에도 담기지 않은 부분이 없다. 의도적 제외 대상은 그 규칙을 정한 모듈(`003`)의 규칙을 따른다.
  - 근거 좌표 정확성: 모든 청크의 재현 좌표(revision, 위치 좌표)로 원본에서 찾은 원문이 청크 원문과 같다.
  - 고아 청크 0: 원본 revision·위치와 연결되지 않은 청크가 없다.
  - 구조 경계 위반 0: 분할 규칙이 보존하도록 정한 구조 단위를 청크 경계가 가르지 않는다.

**적용 관문(개선 폭 기준 v1.0)**

- **FR-017**: 관문은 MUST 후보 구성을 현재 구성과 같은 시험셋 스냅숏과 같은 원본 자료 스냅숏으로 비교해 판정한다.
- **FR-018**: 관문은 MUST 다음 다섯 조건을 모두 확인한다. 괄호 안은 기본값이며 모든 수치는 설정값이다.

| 조건 | 내용(기본값) |
|---|---|
| ① 필수 검사 회귀 없음 | 후보 구성이 필수 검사 5종을 모두 통과한다 |
| ② 주 지표 개선 | 시험셋 Recall@5가 현재 구성보다 +3%p 이상 높다 |
| ③ 개선의 유의성 | 질의 단위 짝 비교 부트스트랩(재표본 10,000회, 고정 시드)으로 구한 Recall@5 차이의 95% 신뢰구간 하한이 0보다 크다 |
| ④ 부분 하락 제한 | 모든 의도에서 Recall@5 하락이 5%p 미만이고, MRR과 근거 완전성 하락이 각각 2%p 미만이다 |
| ⑤ 비용 한도 | 질의 지연 p95 증가가 +200ms 이하, 재색인 소요 시간이 8시간 이하, GPU 메모리 최대 사용량이 운영 GPU 메모리 안에 들어감, 문서에 없는 질의의 `no_evidence` 비율이 현재 구성보다 낮지 않음 |

- **FR-019**: 관문은 MUST 판정을 다음 셋 중 하나로 내린다. "불합격": ①, ④, ⑤ 중 하나라도 어김. "유의한 차이 없음(현재 유지)": ①, ④, ⑤는 지켰지만 ② 또는 ③을 채우지 못함. "적용 권고": 다섯 조건을 모두 채움. "불합격"과 "유의한 차이 없음"이면 현재 구성을 유지하며, 나이브 기본 구현을 유지하는 것도 정상 결과다.
- **FR-020**: 관문 판정은 MUST 조건별 통과 여부, 측정값, 기준값을 사유로 남긴다.
- **FR-021**: "적용 권고"는 MUST 권고일 뿐이다. 후보 구성은 승인권자가 승인한 뒤에만 운영에 적용한다. 관문은 운영 구성을 바꾸지 않는다.
- **FR-022**: 관문 설정값과 관문 기준 버전은 MUST 승인권자의 승인으로만 바뀐다. 시스템은 각 관문 시도에 쓴 설정값과 기준 버전을 실험 기록에 남긴다.
- **FR-023**: 관문은 MUST 연구 트랙 3건의 결과와 플랫폼 모듈 6종(파서, 영역 판별, 청킹 규칙, 검색용 텍스트 보강, 임베딩, 리랭커)의 교체에 같은 기준으로 적용한다.

**시험셋 오염 방지**

- **FR-024**: 시험셋 질의와 그 결과는 MUST 튜닝과 후보 선정에 쓰지 않는다. 튜닝과 후보 선정은 개발셋으로만 한다. 예외로, 관문 판정의 조건별 사유를 보고 불합격 후보를 고쳐 다시 올리는 일은 FR-025·FR-026의 트랙(건)별 시도 한도 안에서만 허용한다. 시도 한도는 이 예외로 생기는 오염을 제한하기 위한 것이다.
- **FR-025**: 시스템 MUST 같은 시험셋에서 연구 트랙(또는 모듈 교체 건)별 관문 판정을 최대 3회로 제한한다. 횟수는 트랙(건)마다 따로 센다. 시험셋 결과가 일부라도 산출된 시도는 모두 센다. 이미 기록된 실험을 같은 식별값으로 재현하는 실행은 세지 않는다.
- **FR-026**: 시스템 MUST 연구 트랙(또는 모듈 교체 건)이 관문 시도 한 번에 최종 후보를 1개만 올리게 한다. 불합격한 후보를 고쳐 그 트랙(건)의 남은 횟수 안에서 다시 올릴 수 있다. 한도를 다 쓴 트랙(건)은 그 시험셋으로 관문 시도를 받지 않으며, 시험셋을 보충한 뒤에 재개한다.
- **FR-027**: 시험셋의 정답이 있는 질의가 400개(FR-002)에 이르기 전에는 MUST 개선 목적의 모듈 교체를 하지 않는다. 버그 수정은 이 제한의 예외다.

**실험 기록과 재현**

- **FR-028**: 시스템 MUST 실험마다 다음을 불변으로 기록한다: 비교한 두 구성의 색인 식별값과 검색 정책 식별값(모듈별 버전, 모델과 그 revision 포함), 평가셋 스냅숏 식별값, 원본 자료 스냅숏 식별값, 시드, 실행 시각, 측정 환경(실행 자원 포함), 질의별 결과, 지표 결과, 반환 근거 평균 길이, 필수 검사 결과, 관문 시도이면 연구 트랙 또는 모듈 교체 건·그 트랙(건)의 시도 차수·관문 설정값·기준 버전·판정과 사유.
- **FR-029**: 실험 기록은 MUST 수정하거나 삭제할 수 없다.
- **FR-030**: 같은 구성 식별값, 평가셋 스냅숏, 원본 자료 스냅숏, 시드로 실험을 다시 실행하면 MUST 질의별 결과와 품질 지표(Recall@5, MRR, 근거 완전성, 의도별 Recall@5, `no_evidence` 비율)와 필수 검사 결과가 같다. 비용 지표는 측정 환경에 따라 달라질 수 있으며 같음을 요구하지 않는다.
- **FR-031**: 같은 질의별 결과와 시드로 계산한 부트스트랩 신뢰구간은 MUST 같다.

**자원 분리와 데이터 취급**

- **FR-032**: 후보 구성의 색인은 MUST 활성 색인과 별도로 만들며(나란히 색인), 실험은 활성 색인과 운영 검색 결과를 바꾸지 않는다.
- **FR-033**: 연구와 실험 실행은 MUST 운영 GPU와 충돌하지 않도록 운영과 분리된 자원에서 한다. 구체 자원은 이 명세에서 정하지 않는다.
- **FR-034**: 평가셋, 원본 자료, 질의, 모델, 실험 기록과 그 밖의 실험 산출물은 MUST 사내 환경에 보관하고 외부 서비스로 전송하지 않는다. 대외비 자료 취급은 `AGENTS.md`의 `보안과 데이터 취급` 절을 따른다.

### Key Entities *(include if feature involves data)*

- **평가셋**: 평가 질의의 모음. 시험셋 또는 개발셋 중 하나다. 여러 스냅숏을 가진다.
- **평가 질의**: 질의 ID, 질의문, 의도, 정답 구분, 정답 근거 목록, 확인 기준 원본 자료 스냅숏, 작성자, 작성일, 출처 구분을 가진다.
- **정답 근거**: 자료 식별(source와 자료 ID), revision, 위치 좌표로 이루어진다. 한 평가 질의에 여러 개일 수 있다.
- **평가셋 스냅숏**: 특정 시점의 평가셋 내용을 고정한 것. 식별값을 가지며 내용이 바뀌지 않는다.
- **원본 자료 스냅숏**: 평가에 쓰는 자료와 각 revision을 고정한 것. 식별값을 가진다.
- **구성**: 색인 식별값과 검색 정책 식별값의 조합. 현재 구성과 후보 구성이 있다.
- **연구 트랙**: 트랙 ①~③. 모듈 교체 건과 함께 같은 시험셋에서 각각 관문 시도 최대 3회를 가지며, 한 번에 최종 후보 1개를 올린다.
- **실험**: 두 구성을 같은 스냅숏으로 비교한 실행 한 번. 개발셋 실험과 관문 시도가 있다.
- **질의별 결과**: 실험 안에서 질의마다 두 구성의 결과 순위, 적중 판정, 지연, 반환 근거 길이를 담는다.
- **실험 기록**: FR-028의 항목을 불변으로 담는다.
- **관문 기준**: 이름과 버전(개선 폭 기준 v1.0)과 설정값 묶음.
- **관문 시도**: 시험셋 스냅숏 하나에 대한 후보 구성의 평가 한 번. 연구 트랙 또는 모듈 교체 건, 그 트랙(건)의 시도 차수와 판정을 가진다.
- **관문 판정**: "적용 권고", "불합격", "유의한 차이 없음(현재 유지)" 중 하나와 조건별 사유.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 표본 실험 전부를 같은 식별값·스냅숏·시드로 다시 실행했을 때 질의별 결과, 품질 지표, 필수 검사 결과가 기록과 다른 건수가 0건이다.
- **SC-002**: 표본 실험 기록 전부에서 기록만으로 다시 계산한 관문 판정과 조건별 사유가 기록된 판정과 100% 일치하고, 재계산에 실험 재실행이 필요한 건수가 0건이다.
- **SC-003**: 정성 기준으로, 이 명세와 질의 작성 형식 계약서(`contracts/query-authoring-format.md`)만 받은 질의 작성자가 다른 문서나 질문 없이 질의 한 건의 항목과 정답 표시 방법을 알고 작성할 수 있다. 검토 표본(작성자별 20건 이상. 20건은 기본값이며 설정으로 바꿀 수 있다. 정답 하나·정답 여러 개·문서에 없는 질의 포함)에서 형식 오류로 거부된 질의가 0건이다. 합격 예시는 FR-003의 질의 예시 A(의도 무엇, 정답 2개)와 예시 B(문서에 없는 질의)처럼 작성자가 채우는 항목을 모두 갖춘 질의다. 불합격 예시는 정답 위치를 "운영 매뉴얼 3장 근처"처럼 revision과 위치 좌표 없이 적거나 확인 기준 원본 자료 스냅숏을 빠뜨린 질의다. 여기서 "다른 문서"에서 빠지는 것은 질의 작성 형식 계약서 한 파일뿐이며, 그 밖의 문서(계획서, 데이터 모델, 명령 계약 등)를 봐야 작성할 수 있으면 불합격이다(사용자 결정 A-1, 2026-11-10).
- **SC-004**: 같은 시험셋에서 한 트랙(또는 모듈 교체 건)의 네 번째 관문 시도와 한 번에 후보 2개 이상을 올린 시도의 성공이 0건이고, 한 트랙의 시도 때문에 다른 트랙의 남은 횟수가 줄어든 건수가 0건이다.
- **SC-005**: FR-002의 규모 조건(정답이 있는 질의 400개 이상, 그중 의도별 100개 이상, 문서에 없는 질의 50개 이상) 중 하나라도 채우지 못한 시험셋으로 관문 판정이 나온 건수가 0건이다. 표본은 세 조건을 각각 하나씩만 어긴 시험셋 3개를 포함한다.
- **SC-006**: 시험셋과 개발셋에 같은 질의문이 함께 든 건수가 0건이다.
- **SC-007**: User Story 3과 Edge Cases의 경계값 표본(+3.0%p, 신뢰구간 하한 0, 의도별 하락 5.0%p, 보조 지표 하락 2.0%p, 지연 증가 200ms, 재색인 8시간) 전부에서 판정이 FR-018·FR-019대로 나온다.
- **SC-008**: 실험 전후로 운영 검색의 고정 질의 결과가 달라진 건수와 활성 색인이 바뀐 건수가 0건이다.
- **SC-009**: 승인권자의 승인 없이 "적용 권고" 후보가 운영에 적용된 건수가 0건이다.
- **SC-010**: 평가셋, 원본 자료, 질의, 실험 산출물이 외부 서비스로 전송된 건수가 0건이고, 합성 질의 생성에 사내에서 운영하는 모델 밖의 모델을 쓴 건수가 0건이며, 합성 질의나 그 생성 산출물이 색인·조회 응답·근거에 들어간 건수가 0건이다.
- **SC-011**: 표본 실험 기록 전부에 실행 자원이 기록되어 있고, 실험이 운영 GPU에서 실행된 건수가 0건이다. 계획 단계의 자원 배치 점검으로 운영 자원과 실험 자원이 분리되어 있음을 확인한다.

## Assumptions

- 주 사용자는 시험셋 질의를 쓰는 질의 작성자, 연구 트랙과 모듈 교체를 맡는 연구자, 관문 판정을 확인하는 검토자, 적용을 승인하는 승인권자다.
- 확정(사용자 승인 2026-11-08): 관문 기준은 개선 폭 기준 v1.0이며 FR-018의 기본값을 쓴다. 수치는 설정값으로 둔다.
- 정답 근거는 자료 revision과 위치 좌표로 식별하므로 이 평가 체계가 채점하는 근거는 등록 자료의 원문 근거다. RDB 조회 결과나 지식 그래프 관계를 정답으로 삼는 평가는 이 명세에서 정하지 않는다.
- 현재 Git 경로로 색인한 OMF 문서는 commit SHA를 revision으로, 행 범위를 위치 좌표로 쓴다(헌법 원칙 V). `001`·`006` 이후 등록 자료는 `001`의 불변 revision을 쓴다.
- 임시 규칙(OMF Markdown의 자료 식별): `001`은 자료 ID를 등록자가 전달하는 값으로만 정하고, OMF 문서를 `001` 경로로 옮길 때 자료 ID를 무엇으로 할지는 `006`(OMF 이관)에서 정하며 아직 정해지지 않았다. 그때까지 OMF Markdown 정답 근거는 source `omf`, 자료 ID로 저장소 기준 파일 경로(예: `design/wiki/...md`), revision으로 고정 commit SHA, 위치 좌표로 행 범위를 적는다. `006`이 다른 자료 ID를 정하면 이 규칙으로 쓴 질의는 새 평가셋 스냅숏으로 옮겨 적으며, 이미 남은 실험 기록은 바뀌지 않는다.
- 질의 ID는 시스템이 매기고(FR-003), 원본 자료 스냅숏 목록은 시스템이 작성자에게 보여 준다(FR-003b). 목록을 보여 주는 방식과 기본 선택값을 둘지는 계획 단계에서 정한다.
- 확정(사용자 결정 2026-11-09): 관문 시도 한도는 같은 시험셋에서 연구 트랙(또는 모듈 교체 건)별 3회다. 불합격 후보를 고쳐 남은 횟수 안에서 다시 올릴 수 있고, 한도를 다 쓴 트랙은 시험셋 보충 후 재개한다.
- 확정(사용자 승인 2026-11-09, 헌법 v2.1.0): 개발셋 질의 합성과 연구용 질의–근거 쌍 생성은 헌법 원칙 VII (3)의 허용 용도다. 생성물은 색인·조회 응답·근거에 넣지 않는다(FR-008a).
- 확정(사용자 결정 2026-11-09): 시험셋은 정답이 있는 질의 400개 이상(의도별 100개 이상)과 별도의 문서에 없는 질의 50개 이상, 모두 450개 이상이다.
- 확정(사용자 결정 2026-11-09): 적중은 반환 근거의 위치가 정답 근거 위치와 조금이라도 겹치는 것이다. 긴 근거가 유리해지는 문제는 반환 근거 평균 길이를 기록·표시해 드러내고(FR-014a), 길이 증가 한도는 `013`에서 정한다.
- 시험셋 보충의 구체 조건(더할 새 질의 수, 이전 질의 재사용 범위, 보충 뒤 시도 횟수를 다시 세는 기준)과 모듈 교체 건을 하나의 건으로 묶는 기준은 계획 단계에서 사용자 승인으로 정한다.
- 열린 항목(검증 필요): 부록 A의 불일치율 10% 가정은 실제 데이터로 확인해야 한다. 시험셋 첫 관문 시도에서 측정한 불일치율을 실험 기록에 남기고, 가정과 크게 다르면 관문 설정값의 재검토를 승인권자에게 보고한다. 이 확인이 끝나기 전에도 v1.0 기본값으로 판정한다.
- 열린 항목: 트랙 ①의 영역 판별 전용 관문 기준은 정하지 않았다. 그 전까지 영역 판별 교체에도 FR-018의 공통 관문을 적용한다. 전용 기준이 정해지면 공통 관문과의 관계는 그때 승인권자가 정한다.
- 버그 수정의 정의와 버그 수정에 관문을 적용하는지는 이 명세에서 정하지 않는다. 변경 계획에서 버그 수정임을 밝히고 `AGENTS.md`의 계획 승인 절차를 따른다.
- 경계값 처리(Edge Cases, 이상·이하는 통과, 미만·초과 기준은 같은 값이면 미통과)와 SC-003의 검토 표본 수 20건은 기본값이며 설정으로 바꿀 수 있다. 변경은 FR-022에 따라 승인권자가 승인한다.
- 근거 완전성의 "해당 없음" 처리(Edge Cases)와 문서에 없는 질의를 Recall 분모에서 빼는 처리는 지표 정의에서 따른 합리적 기본값이다.
- 부트스트랩 신뢰구간을 구하는 세부 방식은 계획 단계에서 정하고, 정한 방식을 관문 기준 설정에 포함해 기록한다.
- 운영 GPU 메모리 용량은 설정값으로 두며 값은 계획 단계에서 운영 환경을 확인해 정한다.
- 기존 MVP의 6개 smoke 질의(용어표)는 정식 평가셋이 아니다(`AGENTS.md`). 이 명세는 smoke 검증을 바꾸지 않는다.
- 연구 중 플랫폼은 나이브 기본 구현을 쓴다. 이 명세는 그 구현을 바꾸지 않는다.
- 기존 설계서와 구현 계획이 시스템 정본이며, 이 명세는 기능 완료 시 정본에 반영한다.

## Out of Scope

- 연구 내용 자체: 트랙 ② 리랭커(`012`), ① 파싱·영역 판별·구조 보존 청킹(`013`), ③ 임베딩(`014`).
- 반환 근거 평균 길이의 증가 한도: 청킹 연구 명세 `013`에서 정한다. 이 명세는 길이를 기록하고 비교 결과에 보여 주기만 한다(FR-014a).
- 모듈 경계 정의: 공통 모듈 구조 설계(작성 예정)에서 다룬다.
- 실제 시험셋 질의 작성 작업. 이 명세는 질의 형식과 규칙만 정한다.
- 트랙 ①의 영역 판별 전용 관문 기준(열린 항목, Assumptions 참조).
- 결과를 보여 주는 대시보드 화면.
- 생성형 답변 품질 평가.
- 연구 실행 자원의 구체 선택.
- 승인된 후보의 실제 운영 적용 절차. 적용은 `AGENTS.md`의 승인·배포 절차를 따른다.

## 부록 A. 관문 수치의 근거

- 짝 비교에서 Recall@5 차이의 95% 신뢰구간 반폭은 대략 1.96 × √(불일치율 / N)이다.
- N은 정답이 있는 질의 수다. 문서에 없는 질의 50개 이상은 Recall@5 계산에 들어가지 않으므로 N에 포함하지 않는다.
- 불일치율을 10%로 가정하면 N=400에서 반폭은 약 3.1%p다. 그래서 주 지표 개선 기준을 +3%p로 두고, 신뢰구간 하한이 0보다 클 것을 따로 요구한다.
- 의도별 표본 N≈133(정답이 있는 질의 400/3)에서 같은 가정의 표준편차는 약 2.7%p다. 우연한 흔들림으로 불합격하지 않도록 의도별 하락 한도를 5%p로 여유 있게 둔다.
- 불일치율 10%는 가정이며 실제 데이터로 확인해야 하는 열린 항목이다(Assumptions).
