# Contract: 평가 질의 작성 형식과 개발셋 템플릿 형식 — spec 002

**상태**: 승인(사용자 2026-11-10). DR-07(좌표 표기·행 번호 기준), DR-10(JSON, spec 항목 이름 키, 파일 단위 원자 접수, 기본 선택값 없음), DR-23 권장안과 spec 모호점 A-15 해소안 기준이다. 사용자 결정 A-1에 따라 이 계약서는 spec SC-003에서 "다른 문서"로 세지 않는 유일한 문서다(작성자는 spec과 이 계약서만 받는다). 작성자는 이 문서와 spec만으로 작성할 수 있어야 한다. 이 상태 줄과 본문의 `[참고: …]` 표시는 결정 출처 기록일 뿐 **비규범**이며, 작성자가 그 문서를 읽을 필요는 없다.

## 용어

| 용어 | 뜻 |
|---|---|
| DR·R·A 번호 | `DR-07`, `R-02`, `A-15`처럼 상태 줄과 `[참고: …]` 표시에 나오는 번호. 계획 문서에서 그 규칙이 정해진 출처를 적은 기록이며 작성에 필요 없다. 작성 규칙은 모두 이 문서와 spec에 있다. |
| 질의 파일 | 작성자가 `eval query add`로 제출하는 UTF-8 JSON 파일. 최상위는 질의 객체의 배열이다. |
| 질의 객체 | 평가 질의 한 건. 키 이름은 spec FR-003 표의 항목 이름 그대로다. |
| 정답 근거 객체 | 정답 근거 한 건(source, 자료 ID, revision, 위치). 파일 번호는 적지 않는다. |
| 위치 객체 | 좌표 하나. 종류는 `행 범위`, `페이지`, `셀 범위`. |
| A1 표기 | Excel 셀 주소(열 문자 + 행 번호). `B14`는 한 셀, `B14:D14`는 직사각형 범위. |
| 원본 자료 스냅숏 목록 | `eval source-snapshot list`·`show --materials` 출력. 작성자는 여기서 스냅숏 ID, 자료 ID, revision, 행 수·페이지 수·시트 이름을 확인한다. |
| 정규화 질의문 | 중복 판정에 쓰는 문자열. 질의문을 NFC(유니코드 정규화 형식의 하나, 한글 음절을 합친 형태)로 바꾸고, 앞뒤 공백을 지우고, 줄바꿈을 포함한 연속 공백을 공백 하나로 바꾼 것이다. 대소문자와 문장부호는 바꾸지 않는다. [참고: research R-02, 비규범] |
| 줄 끝 | 행을 끝내는 `\r\n`(하나로 셈), `\n`, 단독 `\r`. 줄 끝 문자는 그 행에 속하고, 마지막 줄 끝 뒤의 빈 조각은 행으로 세지 않는다(빈 파일은 0행). 검색 결과의 행 번호와 같은 기준이다. |

## 1. 작성 순서

1. `eval source-snapshot list`로 확인 기준 원본 자료 스냅숏 ID를 고른다. 기본값은 없으므로 반드시 적는다.
2. `eval source-snapshot show <ID> --materials`로 정답이 있는 자료의 자료 ID, revision, 형식, 행 수(페이지 수, 시트 이름)를 확인한다. OMF Markdown은 자료 ID가 저장소 기준 파일 경로이고 revision이 고정 commit SHA다(spec 임시 규칙).
3. 아래 형식으로 질의 파일을 쓰고 `eval query add --set <시험셋> --file <파일> --actor <이름>`으로 제출한다.
4. 거부되면 출력의 배열 위치별 사유를 모두 고쳐 같은 파일을 다시 제출한다(한 건이라도 거부되면 아무것도 접수되지 않는다).

## 2. 질의 객체

| 키 | 필수 | 값 |
|---|---|---|
| `질의문` | 예 | 1~1000자 문자열. 공백만 불가 |
| `의도` | 예(문서에 없는 질의 포함) | `무엇`, `왜`, `어떻게` 중 하나 |
| `정답 구분` | 예 | `정답 있음` 또는 `정답 없음` |
| `정답 근거 목록` | 예 | 배열. `정답 있음`이면 1개 이상, `정답 없음`이면 빈 배열 `[]` |
| `확인 기준 원본 자료 스냅숏` | 예 | 원본 자료 스냅숏 목록의 ID |
| `작성자` | 예 | 1~100자 |
| `작성일` | 예 | `YYYY-MM-DD` 형식의 실제 날짜 |
| `출처 구분` | 예 | 시험셋은 `사람 작성`만 |

`질의 ID`는 시스템이 매기므로 적지 않는다. 위 표에 없는 키가 있으면 거부한다.

## 3. 정답 근거 객체와 위치 객체

| 키 | 필수 | 값 |
|---|---|---|
| `source` | 예 | `omf` 또는 `factory` |
| `자료 ID` | 예 | 스냅숏의 자료 ID와 정확히 같은 문자열 |
| `revision` | 예 | 스냅숏의 그 자료 revision과 정확히 같은 문자열 |
| `위치` | 예 | 아래 위치 객체 |

| 위치 종류 | 형식 | 쓸 수 있는 자료 형식 | 기준 |
|---|---|---|---|
| 행 범위 | `{"종류":"행 범위","시작":12,"끝":30}` | `markdown`, `text`, 묶음의 정보 자료 | 1부터 세고 양 끝 포함. 1 ≤ 시작 ≤ 끝 ≤ 행 수. 행은 줄 끝(`\r\n`, `\n`, 단독 `\r`)으로 나눈 단위이며 `show --materials`의 행 수와 같은 기준 |
| 페이지 | `{"종류":"페이지","시작":7,"끝":7}` | `pdf` | 1부터 세는 물리 페이지 순번, 양 끝 포함, 끝 ≤ 페이지 수 |
| 셀 범위 | `{"종류":"셀 범위","시트":"보증현황","범위":"B14:D14"}` | `xlsx` | 시트 이름 정확 일치. 범위는 그 시트의 사용 범위 안 |

이미지 파일 자체에는 좌표를 적지 않는다(OCR 없음). 묶음 revision에서 어느 파일인지는 시스템이 revision의 구성(`composition`, `eval source-snapshot show --materials`에 표시)과 좌표 종류로 정한다[참고: research DR-07, 비규범]: 행 범위 → 정보 자료(`info`, 묶음에 하나뿐). 페이지·셀 범위 → `embedded_image_bundle`(그림 포함 PDF·Excel 묶음)의 대상 파일. `image_bundle`(대상이 이미지·전체 스캔 PDF, 전체 스캔 PDF가 하나뿐이어도)의 정답은 정보 자료의 행 범위로만 적는다.

## 5. 거부 사유(FR-006)

질의 객체마다 아래 순서로 모두 확인하고 어긋난 사유를 전부 돌려준다[참고: research R-04, 비규범]. 출력 예: `{"code":"query_rejected","detail":{"entries":[{"index":1,"reasons":[{"code":"invalid_answer_marking","rule":"no_answer_with_evidence"}]}]}}`. 질의문·자료 내용은 출력하지 않는다.

| 순서 | 사유 코드 | FR-006 사유 | 세부 `rule` 예 | 대표 사례 |
|---|---|---|---|---|
| 1 | `missing_field` | 항목 누락 | `missing:<키>`, `unknown_field:<위치>` | `질의문`·`확인 기준 원본 자료 스냅숏`·`출처 구분` 키 없음, `질의 ID`·`파일 번호`를 적음, 알 수 없는 키 |
| 2 | `invalid_intent` | 의도 | `missing`, `empty`, `not_allowed` | `의도` 키 없음, 빈 의도, `언제`(US1-4) |
| 3 | `invalid_answer_marking` | 정답 표시 | `answer_without_evidence`, `no_answer_with_evidence`, `invalid_status` | 정답 있음 + 빈 목록 또는 `정답 근거 목록` 키 없음, 정답 없음 + 근거 1개, `정답 구분` 키 없음(US1-5) |
| 4 | `unknown_source_snapshot` | 확인 기준 스냅숏 | `not_listed` | 목록에 없는 ID(US1-11) |
| 5 | `invalid_answer_coordinate` | 정답 근거 좌표 | `material_not_in_snapshot`, `revision_mismatch`, `kind_format_mismatch`, `ambiguous_file`, `out_of_range`, `invalid_cell_range`, `sheet_not_found`, `source_not_supported` | 스냅숏에 없는 revision(US1-6), 텍스트에 셀 범위(US1-7), 이미지 묶음에 페이지, 행 수 초과 |
| 6 | `invalid_authoring_info` | 작성 정보 | `author_missing`, `date_missing`, `date_invalid`, `origin_not_allowed` | `작성자`·`작성일` 키가 없거나 값이 빔(US1-8), 시험셋에 `템플릿` |
| 7 | `duplicate_query` | 중복 | `in_set`, `in_file`, `in_dev_set` | 평가셋에 같은 정규화 질의문(US1-9), 같은 파일 안 중복, 시험셋 제출이 개발셋 현재 구성원과 같음(SC-006, `in_dev_set`) |

- 4가 실패하면 5는 확인하지 않는다(기준 스냅숏이 없어 범위를 모른다).
- 키가 없는 경우의 사유는 spec 시나리오를 따른다[spec FR-003·FR-006 비고. 참고: research A-15, 사용자 결정 2026-11-10, 비규범]: `의도` → `invalid_intent`(US1-4), `정답 구분` 또는 `정답 근거 목록` → `invalid_answer_marking`(US1-5, `정답 근거 목록` 키 없음은 빈 목록으로 보고 판정. 정답 없음 + 키 없음은 통과), `작성자`·`작성일` → `invalid_authoring_info`(US1-8). 그 밖의 필수 키(`질의문`, `확인 기준 원본 자료 스냅숏`, `출처 구분`)가 없으면 `missing_field`. 키가 없든 값이 비었든 같은 사유다. research R-04.
- 파일 자체가 JSON 배열이 아니거나 UTF-8이 아니면 질의 단위 판정 전에 exit 2 `invalid_file`.
- 접수된 질의의 질의문은 바뀌지 않는다. 고치려면 제거 후 새로 제출한다(새 질의 ID).

## 6. 개발셋 템플릿 파일(FR-008)

```json
{
  "템플릿 이름": "점검-주기-v1",
  "확인 기준 원본 자료 스냅숏": "SNAP-20261120-01",
  "의도": "무엇",
  "질의 틀": "[설비명]의 점검 주기는 무엇인가?",
  "채움 목록": [
    {"설비명": "3호 사출기",
     "정답 근거 목록": [{"source": "omf", "자료 ID": "design/wiki/…md",
       "revision": "a8f46f23cd3fb9c5f7042e987dff8103d23f0fa2",
       "위치": {"종류": "행 범위", "시작": 40, "끝": 44}}]}
  ]
}
```

- `질의 틀`의 `[이름]` 자리마다 `채움 목록` 항목의 같은 이름 값으로 바꿔 질의 하나를 만든다(결정적, 목록 순서대로). 자리 이름이 항목에 없거나 남는 자리가 있으면 그 항목은 `missing_field`로 거부.
- 각 생성 질의의 `출처 구분`은 `템플릿`, `작성자`는 실행 `--actor`, `작성일`은 실행일(KST). 정답 구분은 `정답 근거 목록`이 비었으면 `정답 없음`이다.
- 생성 질의도 2·3·5절 규칙으로 검사하고, 시험셋과 같은 정규화 질의문은 거부가 아니라 제외로 처리해 건수만 보고한다(FR-007 후단).
