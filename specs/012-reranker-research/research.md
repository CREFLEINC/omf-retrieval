| 상한 차이 | Recall@최대(후보 목록) − Recall@5(후보 목록). 리랭커가 후보를 완벽하게 정렬해도 얻을 수 있는 개선의 위쪽 한계에 가까운 값이다. |

| 공개 벤치마크 | 외부에 공개된 한국어 검색 평가 데이터. 사내로 반입해 "우리 리랭커 구현이 모델 카드 수치를 재현하는지" 확인에만 쓴다(사용자 결정 2026-11-12). |

## 3. 계획이 채택한 기술 판단(새 의존성·정책 변경 없음)

### R-01 점수 척도 통일

- **판단**: 모든 리랭커 구현은 리랭크 점수를 0~1의 확률 척도로 낸다. cross-encoder는 출력 logit에 sigmoid(0~1로 바꾸는 단조 함수)를, yes/no logit 방식은 마지막 위치의 ("yes", "no") 두 logit에 softmax를 적용한 P(yes)를 쓴다. 두 변환 모두 단조라 순위를 바꾸지 않는다.
- **근거**: 결정성 기준의 점수 허용 범위(FR-028, DR-03)를 모델과 무관한 하나의 절대값으로 정할 수 있다. 실험 기록의 점수를 모델 간에 읽기 쉽다. 변환 방식은 리랭커 기술자의 설정 원문에 남는다.

### R-02 결정적 배치 구성

- **판단**: 리랭커 입력은 RRF 순서 그대로 고정 크기 배치(설정값, 기술자 설정에 포함)로 나눠 계산한다. 배치 구성(어떤 후보끼리 함께 계산되는지)과 패딩(길이를 맞추려고 채우는 빈 토큰)이 점수에 미세한 차이를 줄 수 있어서다. 계산 정밀도(dtype, 예: bfloat16)도 기술자 설정에 넣는다. 추론은 평가 모드·기울기 계산 끔으로 하고, 결정성에 영향을 주는 torch 설정(예: cuDNN 자동 튜닝 끔)은 고정해 실험 기록 환경에 남긴다. 엄격 결정 모드(torch 결정적 알고리즘 강제) 사용 여부는 구현 재현 확인(G-REPRO-01) 단계에서 동작과 속도를 보고 DR-03 안에서 정한다.
- **근거**: FR-028, SC-004. 같은 연구 장비·같은 구성에서 두 번 실행한 순위가 같아야 한다.

### R-03 런타임 불변 검사

- **판단**: 리랭크 결과를 만드는 순수 함수는 호출마다 (a) 출력 후보 집합 = 입력 후보 집합, (b) 중복 없음, (c) 점수 수 = 리랭크 대상 수, (d) 모든 점수가 유한한 0~1 값임을 확인한다. 하나라도 어기면 계약 오류다. 운영 경로에서는 "리랭크 미적용(오류)"로, 평가 경로에서는 실행 오류로 처리한다(D-06).
- **근거**: SC-002는 "개발셋 실험과 관문 시도의 모든 질의별 결과"에서 집합이 다른 질의가 0건이기를 요구한다. `002` 질의별 결과는 후보 목록을 저장하지 않으므로(1절) 사후 비교 대신 매 호출 검사로 보장하고, 위반은 실험 실패로 드러난다(C-11).

### R-04 근거 본문·좌표 불변의 구조적 보장

- **판단**: 백엔드(모델을 실제로 돌리는 부분)는 문자열 쌍만 받고 점수 목록만 돌려준다. 출력 후보 목록은 입력 `FusedCandidate` 객체를 그대로 재배치해 만들고, 리랭크 점수·순위는 별도 필드로 붙인다. 백엔드가 만든 글(생성 토큰)은 어디에도 저장하거나 전달하지 않는다.
- **근거**: FR-008, FR-012, 헌법 VII. 본문을 바꿀 수 있는 경로가 코드에 없게 한다.

### R-05 시간 초과의 실행 방식

- **판단**: 리랭크 호출은 단일 작업 스레드에서 실행하고 호출 쪽은 시간 초과 한도까지만 기다린다. 소요 시간은 단조 시계로 잰다. GPU 계산은 도중에 멈출 수 없으므로, 시간 초과 뒤에도 그 계산은 끝까지 돌 수 있다. 그래서 운영 경로에서는 앞선 리랭크가 아직 돌고 있으면 다음 요청을 기다리게 하지 않고 바로 "리랭크 미적용(시간 초과)"로 처리하는 방식을 제안한다(운영 경로의 최종 방식은 `009`가 정한다). 평가 경로에서는 시간 초과가 실행 오류다.
- **근거**: FR-019·FR-020·FR-021. 시간 초과 뒤 밀린 GPU 작업이 다음 요청의 지연으로 번지는 것을 막는다.

### R-06 후보 검색 정책의 구성 방법

- **판단**: 후보 검색 정책은 그 시점 현재 정책을 복사하고 리랭커 기술자와 후보 깊이(와 DR-01 결과에 따라 입력 구성·자르기 규칙·시간 초과 한도)만 바꾼다. 질의 임베딩, 후보 수, RRF, 하한선과 보정 상태(`calibrated`)는 그대로다.
- **근거**: 리랭커는 하한선 뒤 단계라 하한선 값을 바꾸지 않는다(설계서 15.1 3·5단계). 관문 시도는 두 정책 모두 `calibrated`를 요구한다(`002` R-09). 비교하는 두 구성의 차이가 리랭커 설정뿐이어야 결과를 리랭커에 귀속할 수 있다(FR-026).

### R-07 개발셋 탐색 순서(선별 → 격자 → 상한 참고)

- **판단**: 탐색 개발셋에서 세 단계로 비교한다. 모든 단계의 비교 상대는 현재 구성(통과 모듈)이다.
  1. **선별**: 적용 후보 4개 × 후보 깊이 비교값 3개 중 가운데 값 × 입력 구성 "제목 계층 + 원문". 실험 4개. Recall@5와 비용(지연 p95 증가·GPU 메모리)으로 상위 2개 모델을 고른다. 비용 한도를 넘는 모델은 제외한다.
  2. **격자**: 상위 2개 모델 × 후보 깊이 3개 × 입력 구성 3개 = 실험 18개. yes/no 방식 모델이 남으면 instruction 후보 2개(DR-07)를 그 모델의 최선 조합에 추가로 비교한다(실험 2개).
  3. **상한 참고**: Qwen3-Reranker-4B를 격자 최선 조합의 깊이·입력 구성으로 1회 실행한다. 결과는 "더 큰 모델이면 얼마나 오르는가"의 참고값이며 최종 후보가 될 수 없다(사용자 결정 2026-11-12).
  4. 최종 후보 1개를 고른다: 비용 한도 안에서 탐색 개발셋 Recall@5가 가장 높은 조합. 차이가 1%p 안이면 지연 p95가 낮은 쪽.
- **근거**: spec Assumptions(후보 모델 1개 이상, 2~3개 권장), FR-018(깊이 3개 이상), FR-014(입력 구성 비교). 처음부터 4 × 3 × 3 = 36개를 모두 돌리는 것보다 실험 수를 25개(선별 4 + 격자 18 + instruction 2 + 상한 참고 1)로 약 31%(11개) 줄인다. instruction·상한 참고를 빼고 같은 범위(모델 × 깊이 × 입력 구성)만 비교하면 36개 대 22개로 약 39% 줄어든다. 개발셋 실험은 횟수 제한이 없으므로(FR-023) 필요하면 단계를 되돌려 추가 실행할 수 있다.

### R-08 개발셋 구성과 분할

- **판단**: 개발셋 두 개를 `002` 평가셋으로 만든다. 탐색 개발셋(정답 있음 1,000, 의도별 약 333·333·334, 문서에 없음 100)과 확인 개발셋(정답 있음 500, 의도별 약 167·167·166, 문서에 없음 50). 합성은 내부 모델 서버의 Kanana로만 한다(`002` DR-16, 헌법 VII (3)). 두 셋 사이에 정규화 질의문(`002` R-02)이 같은 질의가 0건이도록, 생성 뒤 겹치는 질의를 확인 개발셋에서 제거한다. 두 셋의 정답 원문 구간이 겹치는 비율은 연구 결과 요약에 기록한다(구간 겹침은 금지하지 않는다. 같은 문서 집합을 쓰기 때문이다). 합성물은 평가 DB의 `eval_` 테이블에만 있고 색인·응답·근거에 들어가지 않는다(`002` FR-008a).
- **근거**: 사용자 결정 2026-11-12(U-3). 확인 개발셋이 튜닝에 새지 않게 질의 단위로 분리한다. 의도별 배분과 문서에 없는 질의의 합성 방법은 `002` 합성 기능에 의존하므로 DR-11에 넣었다.

### R-09 Recall@N(후보 목록)의 계산

- **판단**: 정답 있는 질의마다 근거 묶기 전 후보 목록(하한선·RRF 뒤, `strict` 미사용)의 상위 min(N, 후보 수)개 청크 중 하나라도 정답 근거와 위치가 겹치면 적중이다. 겹침 판정은 `002` DR-11의 2·3번 규칙(청크 행 범위 × 그 청크의 모든 원본, 원본 중 하나라도 겹치면 적중)을 청크 단위로 그대로 쓴다. N은 5·10·20·30·50·최대. 질의별 후보 수 분포(최소·중앙값·최대)도 기록한다. 비교용으로 같은 실험의 `002` 주 지표(근거 항목 단위 Recall@5)를 함께 보고한다.
- **근거**: 사용자 결정 2026-11-12(U-4). 근거 항목 단위 Recall@5는 대부분 청크 단위 Recall@5보다 같거나 크다(상위 5개 근거 항목은 보통 상위 5개 청크를 모두 포함한다). 예외가 하나 있다: 5위 경계에서 RRF 점수가 같은 청크가 서로 다른 상위 절에 있으면, 후보 목록은 청크 id 순서로, 근거 묶기는 상위 절 id 순서로 동점을 가르므로 후보 목록 5위 안의 청크가 근거 항목 6위 이하로 밀릴 수 있다. 그런 질의에서는 근거 항목 단위가 청크 단위보다 작을 수 있으며, 두 값을 함께 보고할 때 이런 질의 수를 같이 적는다. 그래서 청크 단위 상한 차이는 근거 항목 단위로 본 개선 여지보다 크게 나올 수 있다. 진행 판단은 사용자 결정대로 청크 단위로 하되 두 값을 함께 보고한다(C-05의 해석 확인). 실험 구조 (가)(사용자 결정 2026-11-13)에서 첫 측정은 S1에서 만든 고정 파일 A의 후보 목록으로 계산한다(R-15).

### R-10 통과 모듈의 동작

- **판단**: 통과 모듈은 입력 후보 목록을 그대로 돌려주고 리랭크 점수·순위를 내지 않는다. 모델을 올리지 않으며 시간이 걸리지 않는다. 리랭크 적용 상태는 DR-04 값이다. 후보 깊이 설정은 결과에 영향이 없다(FR-018).
- **근거**: 설계서 6.6(나이브 기본 구현), FR-011(통과 모듈은 점수 요구에서 제외), FR-013a ②.

### R-11 yes/no 방식의 점수 계산

- **판단**: Qwen3-Reranker 계열은 모델 카드 공식 예제의 입력 형식(시스템 지시문, `<Instruct>`·`<Query>`·`<Document>` 틀, 답변 위치 접미사)을 그대로 쓰고, 마지막 위치의 "yes"·"no" 토큰 logit으로 R-01의 P(yes)를 계산한다. KURE-Reranker-base는 반입 시 모델 카드의 공식 사용법을 확인해 같은 방식으로 구현하며, 공식 사용법이 sentence-transformers의 로딩 경로라면 그 경로를 그대로 쓴다. 공식 형식 문자열은 반입 시 모델 카드 원문과 대조해 contracts/reranker-module.md 6절에 고정한다.
- **근거**: 구현 재현 확인(G-REPRO-01)이 공식 예제와 점수 일치를 요구한다. 형식 문자열이 한 글자라도 다르면 점수가 달라진다.

### R-12 `strict` 모드

- **판단**: 이 연구의 모든 실험은 `strict` 모드를 쓰지 않고(`002` 비공개 평가 경로는 `default`만 받음, `002` R-17), 실험 기록에 "strict 미사용"을 남긴다.
- **근거**: FR-010. 두 구성에 같은 값을 쓴다.

### R-13 GPU 메모리의 사전 추정

- **판단**: 측정 전 대략값으로 가중치 크기(파라미터 수 × 2바이트, bfloat16 가정)만 적는다. KURE-base 약 3.4GB, Qwen3-0.6B 약 1.2GB, bge-v2-m3 약 1.1GB, KURE-nano 약 0.3GB, Qwen3-4B 약 8.0GB. 활성값(계산 중간 결과)·CUDA 문맥은 빠져 있어 실제 최대 사용량은 이보다 크다. 관문 판정은 `002` DR-04 방식의 실측값만 쓴다. 질의 임베딩 모델(Qwen3-Embedding-0.6B)과 함께 잰다(FR-027).
- **근거**: 선별 단계에서 운영 GPU(기록상 24GB급)에 명백히 맞지 않는 조합을 미리 거르기 위한 참고다. 추정값은 판정 근거가 아니다.

### R-14 코드 배치와 계층

- **판단**: 순서 규칙·실행 경계·입력 구성·결정성 비교는 application 계층의 순수 함수로(`application/search/rerank*.py`), 모델 백엔드·무결성 확인·오프라인 로딩은 infrastructure 계층으로(`infrastructure/reranking/`), 레지스트리 조립은 interfaces 계층에서만 한다(설계서 14절, D-08). 012는 운영 `SearchService`, 검색 정책 형식, 공개 API, 감사 테이블을 바꾸지 않는다. 그 삽입은 `009`가 한다. `002` DR-18의 `rank_evidence`가 먼저 구현되면 삽입 지점은 그 함수 안이 되며, 012의 순수 함수(`apply_rerank`, 근거 항목 순서 제안 식)는 순수하게 유지하고 시간이 걸리는 백엔드 호출은 실행 경계(P2)에만 둔다(C-13).
- **근거**: spec Out of Scope(위치·정책 형식·응답 필드의 구현은 `009`), 헌법 II-2(위험 격리).

### R-15 고정 파일 기반 오프라인 실험의 근거 항목 재계산(실험 구조 (가))

- **판단**: S2의 오프라인 실험은 고정 파일의 후보 목록으로 리랭크 순서 규칙(P1)을 돌린 뒤, 근거 항목과 근거 항목 단위 지표를 운영·평가 경로와 **같은 순수 묶기 함수**(`group_evidence`, `002` DR-18 구현 뒤에는 `rank_evidence`의 묶기 부분, C-13)로 다시 계산한다. 리랭커가 통과 모듈이면 고정 파일로 다시 계산한 근거 항목이 S1 검색 때의 근거 항목과 같아야 한다(U-FRZ-02의 통과 모듈 사례). 고정 파일의 후보 객체를 `FusedCandidate`로 되살리는 변환과 깊이 자르기는 012의 순수 함수(P8)로, 파일 생성·식별값 대조·확인 개발셋 사용 제한·실험 기록은 `002` ⑨로 둔다(DR-11).
- **근거**: 사용자 결정 2026-11-13(U-6). 검색을 한 번만 돌려 후보를 고정하면 S2 실험 사이 차이가 리랭커 설정뿐임이 구조로 보장되고(FR-026), 같은 묶기 함수를 쓰면 오프라인 근거 항목 지표가 실제 검색 경로와 같은 정의가 된다. 후보 목록은 색인 run·현재 정책이 같으면 질의마다 결정적이므로(검색 결정성) 파일 식별값으로 그 전제를 확인한다.

### R-16 참고 지표 MRR@3·nDCG@3(사용자 결정 2026-11-13)

- **상태**: 사용자 결정 2026-11-13(옵션 (1)).
- **정의**: MRR@3 = 정답 있는 질의마다 상위 3개 근거 항목 중 첫 적중 순위의 역수(3위 안 적중이 없으면 0)의 평균. nDCG@3 = 이진 관련도 DCG@3 ÷ 이상적 DCG@3. DCG@3은 순위 r(1~3)의 근거 항목이 아직 적중하지 않은 정답 위치와 겹치면 이득 1, 할인 1/log2(r+1)을 곱해 더한다. 정답 위치 하나는 한 번만 센다(근거 항목 하나가 여러 정답과 겹쳐도 아직 적중하지 않은 첫 정답 하나에만 센다). 이상적 DCG@3 = 1위부터 min(정답 위치 수, 3)개 순위의 할인 합. 적중 판정은 `002` 겹침 규칙(`002` FR-011·DR-11)이고, 근거 묶기 뒤 근거 항목 단위(Recall@5와 같음)로 계산한다. 문서에 없는 질의는 분모에서 뺀다. 관련도는 이진이다(`002` `relevance_level`은 `default`만). 정답 있는 질의가 0개면 값 대신 `not_applicable`을 기록한다.
- **쓰임**: S2 탐색 실험(파일 A)·확인 실험(파일 B)의 오프라인 기록과 관문 시도 보고에 기록·보고만 한다. 후보 선정(R-07)과 관문 판정에는 쓰지 않는다(관문은 개선 폭 기준 v1.0 그대로이며 `002`의 MRR@20 기록도 그대로). 산술: MRR@3은 `002` R-01 정확 산술(분수)로 계산한다. nDCG@3은 log2가 들어가 분수로 표현할 수 없으므로 배정밀도 부동소수점으로 계산하고 10진 표기(소수점 6자리)와 계산 정밀도를 함께 기록하는 것을 `002`에 제안한다(최종 방식은 `002`).
- **근거**: 리랭커는 상위 몇 개의 순서를 바꾸므로 Recall@5만으로는 1~3위 개선이 보이지 않는다. 참고 지표로만 두어 관문 기준 v1.0과 후보 선정 규칙을 바꾸지 않는다. 계산·저장은 `002` 연동 변경 ②(DR-11)에 요청하고, 기대값은 plan U-RMET-01이다.

### R-17 개선 목표(사용자 결정 2026-11-16)

- **상태**: 사용자 결정 2026-11-16(옵션 (1)).
- **내용**: 임시 목표는 리랭커 적용 대 미적용(현재 구성) 차이 +5%p이며 Recall@5·MRR@3·nDCG@3 세 지표에 같은 값을 쓴다(MRR@3·nDCG@3은 0~1 값의 차이에 100을 곱해 %p로 읽는다, `002` 용어와 같음). S1 첫 측정 뒤 목표를 max(+3%p, G × 30%)로 다시 정하고(G = 상한 차이 = Recall@최대(후보 목록) − Recall@5(후보 목록), 탐색 개발셋), 세 지표에 같은 값을 쓰며 사용자에게 보고해 확인받는다. S2 요약·확인 개발셋 확인·관문 시도 보고에 지표별 달성/미달을 적는다(차이 ≥ 목표면 달성). 목표는 관문 기준이 아니며(관문은 개선 폭 기준 v1.0: Recall@5 +3%p, 신뢰구간 하한 0 초과 등 그대로) 후보 선정 규칙도 아니다. 관문을 통과했지만 목표에 못 미치면 판정은 그대로 "적용 권고"이고 "목표 미달"로 기록하며, 미세 조정 재검토 판단(plan `진행 판단 규칙` 3, C-12)의 입력으로 쓴다.
- **예시**: 예: Recall@5(후보 목록) 70%, Recall@최대(후보 목록) 88% → G = 18%p → 목표 max(3, 5.4) = +5.4%p. G = 8%p → 2.4%p → 목표 +3%p. G = 10%p → 3.0%p → 목표 +3%p(두 값이 같음).
- **경계와 예외**: G를 계산할 수 없으면(정답 있는 질의 0개) 목표는 임시 +5%p로 두고 그 사실을 표시해 보고한다. G가 0 이하면 G × 30%가 0 이하라 목표는 +3%p다. 달성 판정 산술: 목표 계산과 Recall@5·MRR@3의 달성 판정은 `Fraction`으로 한다(차이 × 100 ≥ 목표면 달성). nDCG@3의 달성 판정은 R-16의 정밀도 방식(부동소수점, 정밀도 기록)을 따라 0~1 척도에서 비교한다: 부동소수점 차이 Δ가 Δ ≥ float(목표/100) − 1e-9이면 달성(허용 오차 1e-9는 R-16 U-RMET-01의 제안값과 같음). Δ는 `002` ②가 계산하므로 이 비교 방식은 `002`에 제안하는 것이며 최종 방식은 `002`가 정한다. 지표 값이 `not_applicable`(정답 있는 질의 0개)이면 그 지표의 달성 여부도 `not_applicable`이다. `target_shortfall`(목표 미달)은 판정이 "적용 권고"인 관문 시도에서 `not_applicable`이 아닌 지표만 보고 정한다: 그중 하나라도 미달이면 참, 모두 달성이면 거짓, 세 지표가 모두 `not_applicable`이면 `not_applicable`. 판정이 "적용 권고"가 아니면 거짓.
- **쓰는 곳**: plan `진행 판단 규칙` 1(S1 뒤 재설정·보고)·8(보고)·3(미세 조정 재검토 입력), data-model 15절, quickstart 4~6절. 계산 함수는 012 P7(U-TGT-01).

### DR-03 결정성 기준: 리랭크 점수 허용 범위와 측정 방법(FR-028, 설계서 O-8, `002` DR-13 정합)

**상태**: 승인(사용자 2026-11-13, 권장안).

권장안 내용:

1. **순위**: `002` DR-13 필수 검사 그대로(근거 항목 순위 정확 일치)가 관문 판정 기준이다. 012는 여기에 더해 근거 묶기 전 후보 목록의 리랭크 순위도 질의마다 정확히 같은지 확인한다.

3. **판정 위치**: 1의 근거 항목 순위는 `002` 필수 검사(관문 ①). 1의 후보 목록 순위와 2의 점수는 SC-004의 연구 기록 항목이며, 어긋나면 그 후보 구성은 관문에 올리지 않고 원인을 조사한다(관문 판정 자체는 `002` 기준을 바꾸지 않는다).
4. **측정 환경 고정**: R-02의 배치 크기·계산 정밀도·torch 설정을 고정한다. 서로 다른 하드웨어 사이의 일치는 요구하지 않는다(spec Assumptions).

| 대안 1 | 점수 완전 일치(비트 단위) | 중간. torch 결정적 알고리즘 강제가 필요할 수 있고 일부 연산에서 느려지거나 오류 | 높음 |
| 대안 2 | 점수 절대 차이 1e-3 이하 | 낮음. 느슨하지만 순위 요구는 같으므로 실질 차이는 작음 | 높음 |

### DR-04 리랭크 적용 상태 값(통과 모듈일 때 포함)

### DR-05 후보 깊이 비교값 선정 규칙(FR-018, 첫 측정 결과 기반)

**상태**: 승인(사용자 2026-11-13, 권장안).

필요 이유: FR-018은 개발셋에서 후보 깊이 값 3개 이상을 비교하라고 하고, 사용자 결정(2026-11-12, U-4)은 첫 측정의 Recall@N(후보 목록)을 비교값 3개의 선정 근거로 삼게 했다. 같은 측정값이면 같은 3개가 나오도록 규칙을 미리 정해야 결과를 보고 값을 고르는 일(사후 선택)을 막을 수 있다. 검색·랭킹 전략 결정이다. 의존: S1 끝, S2 격자.

권장안 내용: 탐색 개발셋에서 g(N) = Recall@N(후보 목록) − Recall@5(후보 목록), G = g(최대)로 둔다. 후보 격자 {10, 20, 30, 50, 최대}에서

- N₁ = g(N) ≥ 0.5 × G를 처음 만족하는 가장 작은 N
- N₂ = g(N) ≥ 0.8 × G를 처음 만족하는 가장 작은 N
- N₃ = g(N) ≥ 0.95 × G를 처음 만족하는 가장 작은 N

셋 중 같은 값이 생기면 뒤의 값을 격자에서 다음으로 큰 값으로 올린다. "최대"는 질의마다 후보 전체(최대 100개)다.

예시: Recall@5·10·20·30·50·최대가 0.62·0.70·0.76·0.78·0.80·0.81이면 G = 0.19. 0.5G = 0.095 → g(20) = 0.14가 처음 → N₁ = 20. 0.8G = 0.152 → g(30) = 0.16 → N₂ = 30. 0.95G = 0.1805 → g(50) = 0.18은 미달, g(최대) = 0.19 → N₃ = 최대. 비교값은 {20, 30, 최대}.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 상한 차이의 50%·80%·95% 도달 지점 | 낮음. 데이터가 정하는 값이라 사후 선택이 없음. 꼬리가 길면 "최대"가 들어가 지연 비용이 큼(관문 ⑤가 걸러 냄) | 높음 |
| 대안 1 | 고정값 {10, 20, 40}(spec SC-011 예시) | 가장 낮음. 첫 측정을 쓰지 않아 사용자 결정 U-4 ①과 맞지 않음 | 높음 |
| 대안 2 | {20, 50, 최대}(설계서 D-07 대안 B의 "전체" 포함) | 낮음. 큰 깊이 위주라 지연 비용 큼 | 높음 |
| 대안 3 | 비용 우선: 예상 지연이 한도의 절반 이하인 값 중 가장 큰 셋 | 중간. 측정 전 지연 추정이 필요 | 중간 |

### DR-06 입력 구성 후보와 자르기 규칙(FR-014·FR-015)

**상태**: 승인(사용자 2026-11-13, 권장안).

필요 이유: 입력 구성은 개발셋 비교로 정해 검색 정책 식별값에 기록한다(FR-014). 자르기 규칙도 식별값에 들어간다(FR-015). 비교할 후보와 자르기의 구체 규칙은 랭킹 전략 결정이다. 의존: P3, S2 격자.

권장안 내용:

1. **입력 구성 후보 3개**(모두 색인 저장 내용, FR-014): (a) 원문 = 청크 `raw_text`. (b) 제목 계층 + 원문 = `heading_path`를 " > "로 이은 한 줄 + 줄바꿈 + 원문. (c) 제목 계층 + 원문 + 상위 절 문맥 = (b) 뒤에 줄바꿈 두 개와 상위 절 본문(`sections.body`). `search_text`는 쓰지 않는다(키워드 lane용 보강 텍스트라 연구 3 대상이 섞이기 때문).
2. **자르기 규칙**(각 모델 자기 토크나이저로 센다): 질의 상한 Q = 256토큰, 문서 쪽 상한 D = 1,024토큰. 질의가 Q를 넘으면 앞쪽 Q토큰만 남긴다. 문서 쪽이 D를 넘으면 상위 절 문맥 → 원문 끝부분 순서로 뒤에서부터 잘라 D에 맞춘다. 제목 계층은 자르지 않는다(D를 넘는 제목 계층은 끝부분을 자른다). 자르기는 채점용 입력에만 적용하고 응답 근거 본문은 그대로다.
3. 모델 입력 상한(8,192 또는 32K)은 Q + D + 템플릿보다 훨씬 커서 자르기는 지연을 묶는 장치다.

예시: 청크는 최대 800토큰(임베딩 토크나이저 기준)이라 (a)·(b)는 대개 자르지 않는다. 상위 절 본문이 3,000토큰인 (c)는 원문 뒤에 상위 절 본문 앞부분 약 200토큰만 남는다.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | (a)·(b)·(c) 비교, Q 256 / D 1,024, 상위 절 문맥부터 자름 | 낮음. 지연 상한이 모델과 무관하게 비슷 | 높음(상한은 기술자 설정) |
| 대안 1 | D = 모델 입력 상한까지 | 낮음. (c)에서 지연·메모리가 크게 늘어 비용 한도 위험 | 높음 |
| 대안 2 | D = 512 | 낮음. 긴 청크(최대 800)가 잘려 (a)도 원문 손실 | 높음 |
| 대안 3 | (c)의 상위 절 문맥을 "청크 주변 창"(기존 `ParentContextBuilder` 방식, 상한 1,200)으로 | 중간. 문맥 품질이 좋을 수 있지만 색인 쪽 코드 재사용·검증이 더 필요 | 중간 |

### DR-07 yes/no 방식 모델의 instruction 문구(입력 구성의 일부, 정책 식별값에 포함)

**상태**: 승인(사용자 2026-11-13, 권장안).

필요 이유: Qwen3-Reranker 계열(적용 후보 0.6B, 상한 확인 4B)은 instruction을 입력으로 받고, 문구가 점수를 바꾼다. 문구는 입력 구성의 일부로 정책 식별값에 들어간다(DR-01). KURE-Reranker-base는 Qwen3 기반 yes/no 방식이지만 instruction을 받는지는 반입 시 모델 카드로 확인한다(이 계획은 외부 조회를 하지 않았다). cross-encoder 2개(KURE-nano, bge)는 instruction이 없다. 의존: P3, S2 격자 3단계.

권장안 내용: 두 문구를 개발셋에서 비교한다. 모델 카드가 영어 instruction을 권장하므로 둘 다 영어로 둔다.

- I-1(모델 기본 문구): `Given a web search query, retrieve relevant passages that answer the query` (Qwen3-Reranker 모델 카드 예제의 기본값. 반입 시 원문과 대조해 한 글자라도 다르면 원문을 쓴다)
- I-2(도메인 문구): `Given a question about the design documents of a manufacturing execution system (MES), retrieve the passage of the design documents that answers the question`

KURE-base는 모델 카드에 instruction 사용법이 있으면 같은 두 문구를, 없으면 모델 카드의 공식 형식을 그대로 쓴다.

예시: 격자 최선 조합이 Qwen3-0.6B·깊이 30·입력 (b)이면 I-1과 I-2로 실험 2개를 더 돌려 Recall@5가 높은 쪽을 최종 후보에 쓴다.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | I-1·I-2 비교(영어) | 낮음(실험 2개 추가) | 높음 |
| 대안 1 | I-1만(모델 기본값 고정) | 가장 낮음. 도메인 지시 효과를 확인하지 못함 | 높음 |
| 대안 2 | 한국어 문구 추가 비교(예: "제조 실행 시스템(MES) 설계 문서에 관한 질문에 답하는 설계 문서 단락을 찾으시오") | 낮음(실험 1개 추가). 모델 카드 권장과 다름 | 높음 |

### DR-08 의존성 버전(sentence-transformers 등)

**상태**: 승인(사용자 2026-11-13, 권장안).

필요 이유: 사용자가 KURE 요구(sentence-transformers>=5.6.1)에 따른 업그레이드 여부를 결정 요청으로 올리라고 했다. 외부 의존성 선택·변경은 사용자 승인 사항이다(헌법 I). 의존: P4·P5, G-REPRO-01.

권장안 내용: **업그레이드하지 않는다.** 현재 고정 버전 sentence-transformers 5.7.0(`>=5.7.0,<5.8`)이 이미 5.6.1 이상이다(1절). transformers 5.15.0, torch 2.11.0도 그대로 둔다. 새 Python 의존성을 추가하지 않는다. 공식 예제가 별도 라이브러리(예: bge의 FlagEmbedding)를 쓰는 경우, 구현 재현 확인은 모델 카드의 transformers 또는 sentence-transformers 예제로 한다. 반입 시 어느 후보가 현재 버전에서 로딩되지 않으면(예: 새 모델 구조 미지원) 그 후보만 중단하고 보고한다.

예시: KURE-nano가 skt/A.X-Encoder-base 구조를 transformers 5.15.0에서 원격 코드 없이 열 수 있으면 진행한다. 원격 코드가 필요하면 DR-10의 원격 코드 금지로 반입 단계에서 거부되고 보고된다.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 현재 버전 유지, 새 의존성 없음 | 가장 낮음. 운영 이미지·잠금 파일 변경 없음 | 높음 |
| 대안 1 | 재현 비교용 공식 라이브러리(FlagEmbedding 등)를 연구 장비의 별도 임시 가상환경에만 설치(프로젝트 의존성에는 넣지 않음) | 낮음. 공식 예제와 정확히 같은 코드로 비교 가능. 연구 장비에 외부 패키지 반입 승인 필요 | 높음 |
| 대안 2 | 최신 버전으로 일괄 업그레이드 | 중간. 기존 임베딩 경로 회귀 확인 필요(운영 영향) | 중간 |

### DR-09 공개 벤치마크 데이터셋 선택·라이선스·재현 허용 오차

**상태**: 승인(사용자 2026-11-13, 권장안).

필요 이유: 사용자 결정 2026-11-12(U-3)는 한국어 공개 벤치마크를 사내로 반입해 구현 재현 확인에만 쓰고, 구체 데이터셋과 라이선스는 결정 요청으로 올리게 했다. 외부 데이터 반입과 허용 오차는 사용자 승인 사항이다. 의존: O2 단계.

권장안 내용:

1. **선택**: KURE 모델 카드가 평균을 낸 9개 한국어 벤치마크 중 **라이선스가 사내 업무 사용을 허용하고 평가 절차(1단계 후보 집합 구성 방식)가 공개된 것 2개**를 고른다. 이 계획은 외부 조회를 하지 않아 9개 목록과 각 라이선스를 확인하지 못했다. 반입 전 단계에서 모델 카드 목록·라이선스·평가 절차를 확인해 표로 사용자에게 보고하고 그 표를 승인받는다.
2. **보관**: 연구 장비의 별도 디렉터리. 색인·평가 DB·시험셋·개발셋과 섞지 않는다. 우리 자료를 외부로 보내지 않는다.
3. **두 단계 확인**: (가) 같은 입력쌍 점수 일치(G-REPRO-01): 공식 예제 코드와 우리 구현의 점수 차이 절댓값 ≤ 1e-3(같은 장비·같은 정밀도), 쌍 20개의 순위 동일. 이 단계가 구현 정확성의 주 기준이다. (나) 벤치마크 재현: 데이터셋별 nDCG@10이 모델 카드 값 ±0.02 안. 벗어나면 평가 절차 차이인지 구현 문제인지 조사해 보고한다. (가)를 통과하고 (나)만 벗어나면 그 후보를 막지 않고 차이를 기록한다(벤치마크는 선정 근거가 아니다).

예시: KURE-nano의 데이터셋 X nDCG@10이 카드 0.876 근처(9개 평균이 아니라 데이터셋별 값과 비교)에서 우리 측정 0.861이면 ±0.02 안이라 재현으로 기록한다. 0.80이면 조사 대상이다.

### DR-10 모델 가중치 반입·보관·SHA 검증·오프라인 로딩

**상태**: 승인(사용자 2026-11-13, 권장안).

필요 이유: 후보 모델은 사내에 고정 revision으로 보관해야 하고(FR-005), 승인 목록 밖 모델이나 revision 불일치는 시작 거부여야 한다(fail-closed, 단위 테스트 설계). 보관·검증·네트워크 사용 방식은 보안·운영 결정이다. Hugging Face에서 받는 것은 사내로 들이는 것이며 자료 유출이 아니다(spec Assumptions). 의존: P4, O1, contracts/model-intake.md.

권장안 내용:

1. **반입 지점**: 외부 다운로드가 허용된 사내 지점(연구 장비 자체 또는 사용자가 정하는 반입용 장비)에서 승인 목록의 (모델, revision)만 `snapshot_download(revision=고정 SHA)`로 받는다. 다른 파일·모델을 받지 않는다.
2. **검증**: 받은 직후 (a) 받은 스냅숏의 커밋 SHA = 승인 목록 revision, (b) 파일마다 SHA-256을 계산해 무결성 매니페스트 작성, (c) Hugging Face가 제공하는 LFS 파일 SHA-256과 대조(반입 시 API로 얻음), (d) 설정에 원격 코드 지정(`auto_map` 등)이 있으면 반입 거부, (e) 허용 확장자 밖 파일이 있으면 중단·보고.
3. **보관**: 연구 장비의 사내 모델 저장소(쓰기 권한은 반입 담당자만). 매니페스트와 함께 보관. 운영 서버의 운영 배포 경로(운영 API가 읽는 모델 위치)에는 관문 "적용 권고"와 사용자 승인 뒤 최종 후보 1개만, 같은 매니페스트로 복사·대조한다(S4). 운영 개시 전 예외 기간에 운영 서버를 연구 장비로 쓰면 연구용 반입 모델은 운영 서버의 `/home/phoebe-deploy/experiments` 아래에 두고 운영 배포 경로와 섞지 않는다(`002` FR-033 "운영 개시 전 예외", 사용자 결정 2026-11-13, 조건 ⑤).
4. **로딩**: 로딩 전에 매 시작마다 매니페스트와 파일 SHA-256을 대조하고(기존 임베딩 방식 재사용·일반화), `local_files_only=True`, Hugging Face 오프라인 환경변수 설정, `trust_remote_code=False`로 연다. 하나라도 어긋나면 시작 거부.
5. **상한**: 기존 매니페스트 상한(합계 8 GiB)은 Qwen3-Reranker-4B(bfloat16 약 8.0GB ≈ 7.5 GiB)에 근접한다. 리랭커 매니페스트는 모델별 상한을 승인 목록에 적어 둔다(예: 4B는 합계 10 GiB). 상한을 넘는 파일 구성이면 반입 중단·보고.

예시: KURE-base 반입 결과 스냅숏 커밋이 `0ca23195dc2c37177e7458330e2286e2f9fa04b3`이 아니면 매니페스트를 만들지 않고 실패한다. 반입 뒤 누군가 `model.safetensors`를 바꾸면 다음 시작에서 SHA-256 불일치로 거부된다.

### DR-12 실험 단계별 장비·DB

**상태**: 승인(사용자 결정 2026-11-13, 2026-11-12 결정 '별도 연구 장비'를 대체). 근거 조항은 `002` FR-033 "운영 개시 전 예외"(사용자 결정 2026-11-13)다. 연구와 운영 분리(사용자 결정 2026-11-10)는 운영 개시 뒤 다시 원칙이 된다.

### DR-13 근거 항목 순서 식(FR-013a) 제안과 012 구현 범위

**상태**: 승인(사용자 2026-11-13, 권장안). 식의 최종 확정은 `009`의 몫이다(spec FR-013a).

필요 이유: 단위 테스트 설계는 FR-013a ③④ 근거 항목 순서 규칙과 ② 통과 모듈 동일성을 검증하게 하지만, 정확한 식은 `009`가 정한다. 012가 무엇을 만들지(제안 함수인지 검사기만인지)를 정해야 범위가 분명하다. 랭킹 전략 결정이다. 의존: P6, S2(평가 경로가 근거 항목을 만들려면 식이 필요).

권장안 내용: 012는 (1) FR-013a 조건 ①~④를 확인하는 **조건 검사기**와 (2) **제안 식**을 구현한 순수 함수를 만든다. 제안 식의 근거 항목 정렬 키는 (리랭크된 일치 조각 보유 여부 내림차순, 보유하면 그 항목의 최고 리랭크 점수 내림차순·아니면 최고 RRF 점수 내림차순, 같으면 상위 절 식별값 오름차순)이다. 점수가 같을 때 RRF 순위로 먼저 가르는 안은 통과 모듈의 RRF 동점에서 현재 순서(상위 절 식별값 순)와 달라져 FR-013a ②를 어기므로 쓰지 않는다. 일치 조각 순서는 (리랭크 여부 내림차순, 리랭크 점수 내림차순, RRF 점수 내림차순, 청크 식별값). 통과 모듈이면 모든 조각이 "리랭크되지 않음"이라 현재 `group_evidence` 키 (최고 RRF 점수 내림차순, 상위 절 식별값)와 같아진다. `009`는 이 함수를 채택하거나 다른 식으로 바꾸되 조건 검사기를 통과해야 한다.

예시(spec User Story 3 시나리오 10): 3위·12위 청크(상위 절 P, 리랭크 점수 0.91·0.40)와 5위 청크(상위 절 Q, 0.85) → P의 최고 리랭크 점수 0.91 > Q의 0.85이므로 P 항목이 Q 항목보다 앞, P 항목 안 일치 조각은 0.91, 0.40 순서.

### DR-14 확인 개발셋 사용 규칙과 결과 처리

**상태**: 승인(사용자 2026-11-13, 권장안). 사용 횟수 규칙(아래 1)은 사용자 결정 2026-11-13(F-4 (1), G-2 (가) 1:1)으로 "관문 시도마다 1회"에서 "관문 시도와 따로 세어 모두 3회, 관문 시도마다 앞선 확인 1회"로 바뀌었다. 결과 처리(2)·기록(3)은 그대로다. `002` 개정 정렬(사용자 결정 2026-11-16, `002` DR-28): 확인 대상에 리랭커 교체 건 포함, 확인 횟수는 시험셋 세대마다 3회(새 세대에서 0부터), 소진은 사전 점검 ① 실행 자원·② 평가 DB 확인 직후(①·②에서 거부되면 소진 없음), 탐색·확인 개발셋 겹침은 자동 제외.

필요 이유: 사용자 결정 2026-11-12(U-3)는 확인 개발셋으로 "최종 후보를 관문 시도 직전에 한 번만 확인"하게 했다. 불합격 후 고친 후보를 다시 올릴 때의 사용 횟수와, 확인 결과가 나쁠 때 관문 시도를 할지가 정해지지 않았다. 평가 정책 결정이다. 의존: S2 끝, S3 시작, DR-11 ④.

권장안 내용:

1. 확인 개발셋 실험(확인)은 관문 시도와 따로 세며 트랙 ②(리랭커 교체 건 `swap-reranker-*`도 같은 규칙)에서 시험셋 세대마다 3회까지 한다(새 세대가 열리면 0부터, 이전 세대에 만들어져 아직 소진되지 않은 확인도 대조 키(파일 B SHA-256 포함)가 맞으면 새 세대 관문 시도에 쓸 수 있고, 새 세대 횟수에 다시 더하지 않음[결정 2026-11-16], 세대별로 세는 것은 사용자 결정 2026-11-16). 관문 시도마다 그 시도에 보내는 후보(FR-025 세 식별값이 같은 후보)로 확인을 1회 먼저 해야 한다. 4회째 확인부터는 사용자 승인이 있어야 한다(사용자 결정 2026-11-13, F-4 (1)). 확인 기록과 관문 시도는 1:1이다. 확인 기록 하나는 관문 시도 하나에만 쓰이고, 같은 후보로 관문 시도를 다시 하려면 새 확인이 필요하다(확인 3회 중 1회를 쓴다). 관문 시도 사전 점검이 ① 실행 자원·② 평가 DB 확인을 통과한 직후 맞는 확인 기록을 찾으면 그 시점에 그 시도와 연결해 소진한다. 그 뒤 사전 점검 오류 등으로 판정 없이 끝나면 관문 시도 차수는 쓰지 않지만(`002` 규칙) 확인 기록은 소진된 채로 남는다. 이미 연결된 확인 기록을 다시 쓰려 하면 거부한다(제안 코드 `holdout_check_already_used`). 대조 키는 FR-025 세 식별값과 확인에 쓴 파일 B의 SHA-256(`holdout_file_sha256`, 파일 식별값을 통해 색인 run까지 정함)이다. 색인이 바뀌어 고정 파일을 다시 만들면 이전 확인 기록은 대조되지 않는다(사용자 결정 2026-11-13 G-2 (가), G-1). 확인 결과로 후보를 고치지 않는다. 실험 구조 (가)(사용자 결정 2026-11-13)에서 이 실험은 고정 파일 B를 읽는 오프라인 실험이며, 파일 B는 이 용도 밖에서 쓰지 않는다(DR-11 ④⑨).
2. 확인 결과는 판정이 아니라 보고다. 다만 (a) 확인 개발셋 Recall@5(근거 항목 단위) 차이가 0 이하이거나 (b) 비용 한도(`002` FR-018 ⑤)를 넘으면 관문 시도 전에 사용자에게 보고하고 지속 여부를 묻는다. 그 밖이면 바로 관문 시도로 간다.
3. 탐색 개발셋 개선 폭과 확인 개발셋 개선 폭의 차이를 연구 결과 요약에 기록한다(과적합 정도).

예시: 탐색 +4.1%p, 확인 +3.2%p → 보고만 하고 관문 시도. 탐색 +4.1%p, 확인 −0.5%p → 관문 시도 전에 사용자에게 묻는다(관문 시도 1회를 아낄 수 있음).

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **승인(사용 횟수는 사용자 결정 2026-11-13 F-4 (1))** | 확인은 관문 시도와 따로 세어 시험셋 세대마다 3회, 관문 시도마다 보내는 후보로 확인 1회 선행(확인과 시도 1:1, 재시도는 새 확인, G-2 (가)), 4회째부터 사용자 승인. 0 이하·비용 초과면 사용자 확인 | 낮음 | 높음 |
