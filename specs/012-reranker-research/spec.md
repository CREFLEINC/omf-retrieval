# Feature Specification: 리랭커 연구 — 하이브리드 후보 재정렬의 근거 순위 개선 검증(reranker-research)

**Feature Branch**: `012-reranker-research` (명세 식별 이름이다. 별도 git 브랜치는 만들지 않았고 `001-data-registration` 브랜치에서 작성했다.)

**Created**: 2026-11-10

**Status**: Draft

**Revised**: 2026-11-10 (사용자 결정 반영: FR-016의 입력 구성·자르기 규칙·시간 초과 한도를 검색 정책 식별값에 넣는 것, FR-009a의 D-05 원칙 리랭커 적용, FR-030 적용 전 확인 필수화와 합격 기준을 확정; 검증 반영: FR-011 점수 요구에서 통과 모듈 제외)

**Input**: User description: "검색 품질 연구 트랙 ② 리랭커의 명세를 쓴다. 연구 질문은 하이브리드 검색 후보에 리랭커를 더하면 비용 한도 안에서 `002` 관문 기준으로 근거 순위가 개선되는가이다. 후보는 사내 GPU에서 돌릴 수 있는 모델로 한정하고 자료·모델·GPU를 모두 사내에 두며 외부로 보내지 않는다. 리랭커는 헌법 원칙 VII (2)에 따라 후보 근거를 채점·정렬만 하고 근거를 만들거나 바꾸지 않으며, 모델과 revision은 검색 정책 식별값에 고정한다. 튜닝은 개발셋으로만 하고 시험셋은 관문 시도에만 쓰며, 같은 시험셋에서 트랙당 관문 시도는 최대 3회이고 불합격 후보는 고쳐 다시 올릴 수 있다. 성공은 관문 판정을 얻는 것이며 리랭커 없는 현재 구성 유지도 정상 결과다. 적용은 관문 통과와 사용자 승인 뒤에만 한다. 산출물은 실험 기록, 최종 후보 1개, 공통 모듈 구조 설계서 6.6을 따르는 구현이다. 후보 깊이 값은 이 연구에서 정하고(D-07), 실패·시간 초과 동작은 D-06을 따르며, 비용(지연·GPU 메모리) 한도는 `002` 설정값을 따른다. 연구 GPU는 운영과 분리한다."

## 용어

| 용어 | 뜻 |
|---|---|
| 리랭커 | 질의와 후보 근거를 함께 읽어 순위를 다시 매기는 모델. 이 명세의 연구 대상이다. 채점·정렬만 하고 근거 내용을 만들거나 바꾸지 않는다. |
| 리랭크 | 리랭커로 후보의 순위를 다시 매기는 일. |
| 리랭크 점수 | 리랭커가 후보 하나에 매긴 점수. 순위를 정하는 데만 쓴다. |
| AI | 인공지능(Artificial Intelligence). 사람처럼 글을 읽고 판단하는 프로그램을 통틀어 이르는 말이다. |
| LLM | 대규모 언어 모델. 글을 이해하고 생성하는 AI 모델이다. |
| Agent | 사람 대신 작업을 맡아 수행하는 AI 프로그램. |
| 호출 Agent | 플랫폼에 검색을 요청하고 받은 근거로 최종 답변을 쓰는 Agent. |
| 근거 패키지 | 검색 응답. 자연어 답변이 아니라 근거 항목들과 재현 좌표·검색 정책 좌표를 담은 묶음이다. |
| GPU | 모델 계산에 쓰는 그래픽 처리 장치. GPU 메모리는 그 장치의 작업 메모리다. |
| 운영 GPU | 운영 검색 서비스가 쓰는 GPU. 연구·실험은 이 GPU를 쓰지 않는다(`002` FR-033). |
| 연구 자원 | 운영과 분리된, 연구와 실험에 쓰는 사내 계산 자원. 구체 자원은 운영 결정이다. |
| 사내 모델 | 사내 환경에 보관하고 사내 자원에서 실행하는 모델. 질의·근거를 외부 서비스로 보내지 않는다. |
| 헌법 | 이 저장소의 프로젝트 원칙 문서(`.specify/memory/constitution.md`, v2.1.0). `AGENTS.md`를 압축한 것이며 둘이 충돌하면 `AGENTS.md`가 우선한다. |
| 헌법 원칙 VII (2) | 헌법의 "조회 경로 모델의 역할 경계와 LLM 사용 경계" 원칙에서 허용한 두 번째 LLM 용도. 조회 경로 모델(임베딩 모델·리랭커, LLM 기반 포함)은 후보 근거를 채점·정렬만 하고, 모델의 식별자·revision·설정을 검색 정책 식별값에 고정 기록한다. |
| 헌법 원칙 V | 헌법의 "근거 재현성" 원칙. 모든 원문 근거는 원본 경로, 원문 위치, revision, 내용 해시로 다시 찾아 확인할 수 있어야 한다. |
| revision | 한 번 정해지면 바뀌지 않는 식별값. 자료에서는 자료 시점 식별값이고, 모델에서는 모델 가중치의 고정 버전 식별값이다. |
| 근거 | 검색이 돌려주는 원문 조각과 그 재현 좌표(원본 식별, revision, 위치 좌표 등). |
| 근거 본문 | 근거에 담긴 원문 텍스트. 응답에서 원문 그대로여야 한다. |
| 청크 | 자료를 검색 단위로 나눈 조각. 청크 식별값은 청크마다 붙은 고유 값이다. |
| 하이브리드 검색 | 키워드 검색과 의미(벡터) 검색 두 가지를 함께 쓰고 결과를 합치는 현재 검색 방식. |
| lane | 하이브리드 검색의 한 갈래. 현재 키워드 lane과 벡터 lane 두 개가 있다. |
| 하한선 | lane별로 후보가 되려면 넘어야 하는 원시 점수 기준. 두 lane 모두 하한선을 넘는 후보가 없으면 `no_evidence`다. |
| RRF | Reciprocal Rank Fusion, 순위 결합. 두 lane의 순위를 합쳐 하나의 순서를 만드는 방식이다. 리랭커가 없을 때는 이 순서가 최종 순서다. |
| RRF 순서 | 하한선과 RRF 결합(과 `strict` 모드면 교집합 필터)을 거친 후보의 순서. 리랭커의 입력 순서이자 리랭커가 없거나 실패했을 때의 순서다. |
| `strict` 모드 | 현재 검색 서비스에 있는 선택 동작. 두 lane 모두에서 나온 후보만 남기는 교집합 필터이며 RRF 결합 뒤, 리랭커 앞에 있다(설계서 10절). 검색 정책 식별값에 넣을지는 열린 항목 O-10이다. |
| 후보 목록 | 근거 묶기 전 청크 단위 후보의 순서 있는 목록. 리랭커의 입력과 출력은 이 목록이다. |
| 근거 묶기 | 후보 목록의 청크들을 상위 절 단위로 묶어 근거 항목을 만들고, 근거 항목의 순서를 정한 뒤 응답 근거 수만큼 자르는 단계. 리랭커 다음에 있다(설계서 10절). |
| 근거 항목 | 응답에 담기는 근거 하나. 상위 절 하나와, 그 절에 속한 일치 청크(일치 조각) 하나 이상으로 이루어진다. |
| 일치 조각 | 근거 항목 안에 들어 있는, 후보 목록에서 온 청크 하나. 자기 원문·재현 좌표·RRF 순위·점수를 가진다. |
| 응답 근거 수 | 응답에 담을 근거 항목의 최대 수. 검색 요청의 선택적 `limit` 값이며 기본값과 최대값이 정해져 있다. 근거 묶기 뒤에 적용한다. |
| `no_evidence` | 검색 결과에 하한선을 넘는 근거가 없을 때 검색이 돌려주는 상태 값. 기존 검색 기능이 이미 쓰고 있다. |
| 후보 깊이 | 리랭커에 넘기는 후보 수 N. RRF 순서 상위 N개를 리랭크한다. 설정값이다(설계서 D-07). |
| 입력 구성 | 리랭커에 후보마다 무엇을 넘기는지의 묶음. 예: 원문, 제목 계층, 상위 절 문맥. |
| 상위 절 문맥 | 청크가 속한 상위 제목 절의 원문. 현재 검색은 작은 청크로 찾고 상위 절 문맥을 함께 제공한다. |
| 길이 상한 | 리랭커 모델이 한 번에 읽을 수 있는 입력 길이의 한계. |
| 자르기 규칙 | 입력이 길이 상한을 넘을 때 채점용 입력만 줄이는 고정 규칙. 응답의 근거 본문은 줄이지 않는다. |
| 시간 초과 한도 | 리랭크 한 번이 끝나야 하는 최대 시간. 설정값이다. |
| 리랭크 적용 상태 | 응답과 감사 기록에 남기는 값. 리랭크가 적용되었는지, "리랭크 미적용"인지(리랭커 오류·시간 초과) 등을 나타낸다. |
| 리랭크 미적용 | 운영 검색에서 리랭커가 실패하거나 시간 초과되어 RRF 순서로 응답했음을 뜻하는 리랭크 적용 상태(설계서 D-06). |
| 통과 모듈 | 입력 순서를 그대로 돌려주는 리랭커 구현. 리랭커의 나이브 기본 구현이며 현재 구성의 리랭커다. "리랭커 없음"과 같은 결과를 낸다. |
| 나이브 기본 구현 | 연구 결과가 적용되기 전 플랫폼이 쓰는 단순한 기본 모듈 구현. |
| 모듈 | 교체 가능한 검색 구성 요소. 파서, 영역 판별, 청킹 규칙, 검색용 텍스트 보강, 임베딩, 리랭커의 6종이다(설계서). |
| 모듈 기술자 | 모듈 구현이 내놓는 자기 설명 묶음. 종류, 구현 이름, 버전, 설정 해시, 모델 식별자·revision으로 이루어진다(설계서 5절). |
| 색인 식별값 | 저장 문서·청크·벡터를 바꾸는 설정의 묶음을 구분하는 식별값. 리랭커는 여기에 들어가지 않는다. |
| 검색 정책 식별값 | 질의 시점 결과를 바꾸는 설정(질의 임베딩, 후보 수, 결합 방식, 하한선, 리랭커 기술자, 후보 깊이 등)의 묶음을 구분하는 식별값. 설정 내용에서 계산한 해시(`config_hash`)로 식별한다. |
| 검색 정책 등록 기록 | 검색 정책 하나를 불변으로 등록한 기록(설계서의 manifest). 한 번 등록하면 바뀌지 않고 추가만 된다. |
| 구성 | 평가 대상이 되는 검색 설정 묶음. (색인, 검색 정책)의 쌍이다. |
| 현재 구성 | 비교 시점에 운영에 적용되어 있는 구성. 관문 판정의 비교 기준이다. 이 명세 작성 시점에는 리랭커가 통과 모듈이다. |
| 후보 구성 | 적용을 제안하는 구성. 이 연구에서는 현재 구성과 같은 색인에 후보 검색 정책을 붙인 것이다. |
| 최종 후보 | 연구 트랙이 관문 시도에 올리는 후보 구성 하나. |
| 활성 색인 | 운영 검색이 현재 사용하는 색인. |
| 평가 하네스 | 평가셋·지표·실험 기록·적용 관문을 묶은 공용 평가 체계. 명세 `002`가 정한다. |
| 평가 실행기 | 평가 하네스에서 실험을 실행하는 부분. 공개 검색 경로를 거치지 않는 비공개 평가 경로로 질의한다(설계서 D-04). |
| 평가셋·시험셋·개발셋 | `002`의 정의를 따른다. 시험셋은 사람이 작성한 질의로 관문 판정에만 쓰고, 개발셋은 템플릿·합성 질의로 튜닝과 후보 선정에 쓴다. |
| 튜닝 | 결과를 보고 구성의 설정·규칙·모델을 고르거나 조정하는 일. |
| 실험·실험 기록 | `002`의 정의를 따른다. 실험은 두 구성을 같은 스냅숏으로 비교하는 한 번의 실행이고, 실험 기록은 그 입력 식별값·결과·판정을 불변으로 남긴 기록이다. |
| 적용 관문 | 후보 구성을 적용 권고할지 판정하는 `002`의 기준 "개선 폭 기준 v1.0"(사용자 승인 2026-11-08). 판정은 "적용 권고", "불합격", "유의한 차이 없음(현재 유지)" 중 하나다. |
| 관문 시도 | 최종 후보 하나를 시험셋으로 평가해 관문 판정을 받는 일 한 번. 같은 시험셋에서 연구 트랙마다 최대 3회다(`002` FR-025). |
| 관문 판정을 얻음 | 관문 시도가 끝나 세 판정 중 하나가 실험 기록에 남은 상태. 이 연구의 성공 기준이다. |
| Recall@5 | 정답 근거가 검색 결과 상위 5개 안에 하나라도 든 질의의 비율. `002`의 주 지표다. |
| MRR | 평균 역순위. 질의마다 첫 정답 근거 순위의 역수를 평균한 값이다. `002`의 보조 지표다. |
| p95 | 95번째 백분위수. 질의 지연을 작은 순으로 늘어놓았을 때 95% 지점의 값이다. |
| 비용 한도 | 후보 구성이 넘으면 안 되는 비용 상한. `002` FR-018 ⑤의 설정값(질의 지연 p95 증가, 재색인 소요 시간, GPU 메모리, `no_evidence` 비율)을 따른다. |
| 결정성 | 같은 입력과 같은 식별값이면 항상 같은 결과가 나오는 성질. `002`의 필수 검사 중 하나다. |
| 결정성 기준 | 리랭커의 결정성을 판정하는 구체 규칙(무엇을 비교하고 어떤 차이를 허용하는지). 설계서 열린 항목 O-8을 이 명세에서 정한다. |
| 감사 기록 | 검색 요청마다 남기는 운영 기록. 원문이나 비밀값은 담지 않는다. |
| MVP | Minimum Viable Product, 최소 기능 제품. 현재 운영 중인 첫 검색 서비스다. |
| API | Application Programming Interface, 프로그램 간 호출 규약. |
| `crefle-doc` | 사람이 읽는 설계서·보고서를 쓸 때 사용하는 CREFLE 문서 작성 스킬(Agent가 불러 쓰는 작업 절차 묶음). |
| smoke | 기존 MVP 배포 때 기능이 동작하는지만 빠르게 확인한 고정 질의 6개(정상 5개, 문서에 없는 질의 1개). 정식 평가셋이 아니다. |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 연구자가 승인된 사내 리랭커 후보를 개발셋으로 비교해 최종 후보 하나를 고른다 (Priority: P1)

연구자는 승인권자가 승인한 후보 모델 목록 안에서 사내에 보관한 모델로 리랭커 후보 구성을 만든다. 각 후보 구성은 현재 구성과 같은 색인에 후보 검색 정책(리랭커 모델·revision, 후보 깊이, 입력 구성 등)을 붙인 것이다. 연구자는 개발셋으로 현재 구성(통과 모듈)과 후보 구성들을 횟수 제한 없이 비교하며 모델, 후보 깊이, 입력 구성을 고르고, 지표와 비용을 함께 보고 최종 후보 하나를 정한다. 모든 실험은 운영과 분리된 연구 자원에서 하며 운영 검색에 영향을 주지 않는다.

**Why this priority**: 관문 시도에 올릴 최종 후보와 후보 깊이 값이 모두 이 단계에서 나온다. 이 단계 없이는 관문 판정도, `009`에 넘길 후보 깊이 값도 없다.

**Independent Test**: 승인 목록의 후보 모델 하나와 후보 깊이 값 3개로 개발셋 실험을 실행해 각 후보 구성의 지표·비용·리랭크 소요 시간이 실험 기록에 남는지, 실험 기록의 실행 자원이 운영 GPU가 아닌지, 실험 전후 운영 검색의 고정 질의 결과와 활성 색인이 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 승인 목록에 있는 후보 모델이 고정 revision으로 사내에 보관되어 있고, **When** 연구자가 그 모델로 만든 후보 구성과 현재 구성을 개발셋으로 비교하면, **Then** 두 구성의 `002` 지표, 비용 지표, 리랭크 소요 시간이 실험 기록에 남고, 후보 구성의 검색 정책 식별값에 모델 식별자와 revision이 들어 있다.
2. **Given** 승인 목록에 없는 모델이나 revision이 고정되지 않은 모델로 만든 후보 구성이 있고, **When** 연구자가 실험을 실행하려 하면, **Then** 그 후보 구성은 실험에 쓰이지 않고 사유가 남는다.
3. **Given** 질의나 후보 근거를 사내 밖으로 보내 채점하는 후보가 있고, **When** 후보 범위를 확인하면, **Then** 그 후보는 후보 범위 밖으로 제외된다.
4. **Given** 같은 모델로 후보 깊이만 다른 후보 구성 3개가 있고, **When** 개발셋 실험을 하면, **Then** 각 후보 구성은 서로 다른 검색 정책 식별값으로 평가 전에 불변 등록되고 결과가 따로 기록된다.
5. **Given** 개발셋 실험 결과가 있고, **When** 연구자가 결과를 보고 후보 깊이나 입력 구성을 바꿔 다시 실행하면, **Then** 횟수 제한 없이 실행되고 관문 시도로 세지 않는다.
6. **Given** 개발셋 비교가 끝났고, **When** 연구자가 최종 후보를 정하면, **Then** 최종 후보는 하나이고, 선정 근거는 개발셋 실험 기록만 가리킨다.
7. **Given** 실험이 진행 중이고, **When** 운영 검색이 고정 질의를 받으면, **Then** 실험 전과 같은 결과를 돌려주고 활성 색인과 운영 검색 정책은 바뀌지 않는다.

### User Story 2 - 최종 후보가 관문 판정을 받고, 판정에 따라 적용하거나 현재 구성을 유지한다 (Priority: P1)

연구자는 최종 후보 하나를 시험셋 관문 시도에 올린다. 관문은 `002`의 개선 폭 기준 v1.0으로 "적용 권고", "불합격", "유의한 차이 없음(현재 유지)" 중 하나를 판정한다. 어느 판정이든 판정을 얻으면 이 연구는 성공이다. "적용 권고"를 받은 후보는 승인권자가 승인한 뒤에만 운영에 적용하고, 다른 판정이면 리랭커 없는 현재 구성(통과 모듈)을 유지한다. 불합격한 후보는 고쳐 같은 시험셋의 남은 시도 안에서 다시 올릴 수 있다.

**Why this priority**: 리랭커를 적용할지 정하는 유일한 객관 기준이다. 판정을 얻지 못하면 연구가 끝나지 않는다.

**Independent Test**: 표본 시험셋과 표본 후보로 관문 시도를 해 판정이 실험 기록에 남는지, 판정이 "유의한 차이 없음"일 때 운영 구성이 그대로이고 연구가 "현재 유지"로 종결되는지, 네 번째 시도가 막히는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개발셋으로 고른 최종 후보가 있고 시험셋이 `002`의 규모 조건을 채웠고, **When** 관문 시도를 하면, **Then** 세 판정 중 하나와 조건별 사유가 실험 기록에 남고 트랙 ②의 시도 차수가 1 늘어난다.
2. **Given** 판정이 "유의한 차이 없음(현재 유지)"이고, **When** 연구 결과를 정리하면, **Then** 운영 구성은 통과 모듈 그대로이고 연구 결과는 "현재 유지"로 기록되며 이는 정상 종결이다.
3. **Given** 판정이 "불합격"이고 트랙 ②의 남은 시도가 있고, **When** 연구자가 판정 사유를 보고 고친 후보를 다시 올리면, **Then** 다음 시도로 받아들여지고 남은 횟수가 1 줄어든다.
4. **Given** 같은 시험셋에서 트랙 ②가 관문 시도를 3회 썼고, **When** 네 번째 시도를 하면, **Then** 시도 한도 사유로 거부되고 시험셋 보충이 필요하다는 안내를 받는다. 트랙 ①·③의 남은 횟수는 줄지 않는다.
5. **Given** 질의 지연 p95가 현재 구성보다 비용 한도(`002` 기본값 +200ms)를 넘게 늘어난 후보가 있고, **When** 관문 시도를 하면, **Then** "불합격"으로 판정되고 사유에 넘은 비용 한도가 남는다.
6. **Given** "적용 권고"를 받은 후보가 있고, **When** 승인권자가 아직 승인하지 않았으면, **Then** 운영 검색 정책은 바뀌지 않는다.
7. **Given** 승인권자가 "적용 권고" 후보를 승인했고, **When** 운영에 적용하면, **Then** 관문 시도에 쓴 바로 그 검색 정책 식별값이 운영에 쓰이고, 색인 식별값과 활성 색인은 바뀌지 않으며 재색인·재임베딩이 없다.
8. **Given** 정답이 있는 질의가 400개 미만인 시험셋이 있고, **When** 관문 시도를 하면, **Then** 시험셋 규모 사유로 거부된다(`002` FR-027). 개발셋 실험은 이 제한과 관계없이 할 수 있다.

### User Story 3 - 리랭커는 후보를 채점·정렬만 하고 근거를 만들거나 바꾸지 않는다 (Priority: P1)

호출 Agent는 리랭커가 적용된 응답에서도 원문 그대로의 근거와 재현 좌표를 받는다. 리랭커는 근거 묶기 전 후보 목록에서 RRF 순서 상위 N개 후보에 점수와 새 순위를 매길 뿐이며, 후보를 더하거나 빼지 않고 근거 본문을 바꾸지 않는다. 응답과 검색 정책 식별값으로 어떤 리랭커 모델·revision·설정이 순위를 정했는지 알 수 있다.

**Why this priority**: 헌법 원칙 V·VII를 어기는 리랭커는 지표가 좋아도 쓸 수 없다. 이 계약이 깨지면 근거 패키지의 재현 좌표가 의미를 잃는다.

**Independent Test**: 고정된 후보 목록을 리랭커에 넣어 근거 묶기 전 출력 후보 목록의 집합이 입력과 같은지, 동점과 후보 깊이 밖 후보의 순서가 규칙대로인지 확인한다. 이어 그 목록을 근거 묶기에 넣어 근거 항목 순서와 응답 근거 수 자르기가 FR-013a대로인지, 근거 본문이 원문과 글자 단위로 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 하한선을 통과한 후보 30개와 후보 깊이 20이 있고, **When** 리랭크하면, **Then** RRF 순서 상위 20개만 리랭커에 넘어가고, 근거 묶기 전 출력 후보 목록은 그 20개를 새 순위로 먼저 두고 나머지 10개를 원래 RRF 순서대로 뒤에 둔다.
2. **Given** 리랭크 결과가 있고, **When** 근거 묶기 전 출력 후보 목록의 집합을 입력 후보 집합과 비교하면, **Then** 두 집합이 같다. 입력에 없던 후보가 나오거나 입력 후보가 빠지는 일이 없다.
3. **Given** 리랭크 결과가 있고, **When** 응답의 근거 본문과 재현 좌표를 원본과 비교하면, **Then** 원문과 글자 단위로 같고 좌표도 리랭크 전과 같다.
4. **Given** 리랭크 점수가 같은 후보 둘이 있고, **When** 리랭크하면, **Then** RRF 순위가 높은 쪽이 앞서고, RRF 순위도 같으면 청크 식별값 순서로 정한다.
5. **Given** 하한선을 통과한 후보가 후보 깊이보다 적고, **When** 리랭크하면, **Then** 통과한 후보 전부가 리랭크된다.
6. **Given** 두 lane 모두 하한선을 통과한 후보가 없고, **When** 검색하면, **Then** 리랭커를 부르지 않고 지금처럼 `no_evidence`를 돌려준다.
7. **Given** 리랭크가 적용된 응답이 있고, **When** 근거 항목의 일치 조각을 보면, **Then** 리랭크된 일치 조각에는 리랭크 점수와 리랭크 순위가, 후보 깊이 밖의 일치 조각에는 리랭크되지 않았다는 표시가 있다. 모든 일치 조각의 기존 RRF 순위·점수와 재현 좌표, 응답의 검색 정책 좌표도 그대로 있다.
8. **Given** 길이 상한을 넘는 후보 원문이 있고, **When** 리랭크하면, **Then** 채점용 입력만 고정된 자르기 규칙으로 줄고 응답의 근거 본문은 줄지 않는다.
9. **Given** LLM 기반 리랭커 후보가 있고, **When** 리랭크하면, **Then** 리랭커가 만든 글은 근거나 응답에 들어가지 않고 점수와 순위만 쓰인다.
10. **Given** 출력 후보 목록에서 같은 상위 절에 속한 리랭크된 청크가 3위와 12위에 있고 다른 상위 절의 리랭크된 청크가 5위에 있으며, 3위 청크의 리랭크 점수가 5위 청크보다 높고, **When** 근거 묶기를 하면, **Then** 3위·12위 청크는 한 근거 항목의 일치 조각이 되고, 그 근거 항목은 5위 청크의 근거 항목보다 앞선다(FR-013a ④).
11. **Given** 후보 깊이 밖 청크만으로 이루어진 근거 항목이 있고, **When** 근거 묶기를 하면, **Then** 그 근거 항목은 리랭크된 청크를 하나라도 가진 어떤 근거 항목보다도 앞서지 않는다(FR-013a ③).
12. **Given** 통과 모듈 구성에서 서로 다른 상위 절에 속한 두 청크의 RRF 점수가 같고(예: 하나는 키워드 lane에서만 2위, 다른 하나는 벡터 lane에서만 2위), **When** 근거 묶기를 하면, **Then** 두 근거 항목은 지금과 같이 상위 절 식별값 순서로 놓이고, 근거 항목 순서 전체가 리랭커 도입 전 동작과 같다(FR-013a ②).
13. **Given** 근거 항목이 12개 만들어졌고 응답 근거 수가 5이고, **When** 응답을 만들면, **Then** 근거 항목 순서의 상위 5개만 응답에 담긴다. 응답에 담기지 않은 후보가 있어도 FR-011 위반이 아니다. FR-011은 근거 묶기 전 후보 목록에 대한 요구이기 때문이다.

### User Story 4 - 리랭커가 실패하거나 시간 초과되어도 운영 검색은 근거를 돌려주고, 평가는 오염되지 않는다 (Priority: P2)

운영 검색에서 리랭커가 오류를 내거나 시간 초과 한도를 넘기면 검색은 실패하지 않고 RRF 순서로 근거를 돌려주며 응답에 "리랭크 미적용"을 표시한다(설계서 D-06). 평가 실행기에서는 대신 RRF 순서를 쓰지 않고 실행 오류로 처리해 실험 결과가 섞이지 않게 한다.

**Why this priority**: 리랭커 장애가 검색 장애가 되면 안 되고, 평가에서 몰래 대체하면 결정성 검사와 질의별 결과가 오염된다. 다만 리랭커가 실제로 적용되기 전에는 운영 영향이 없으므로 P2다.

**Independent Test**: 리랭커가 오류를 내거나 응답을 지연하도록 만든 표본으로 운영 검색 경로와 평가 경로를 각각 실행해 동작과 기록을 확인한다.

**Acceptance Scenarios**:

1. **Given** 운영 검색에서 리랭커가 오류를 내고, **When** 검색하면, **Then** 검색은 성공하고 근거를 RRF 순서로 돌려주며 응답의 리랭크 적용 상태가 "리랭크 미적용"이다. 응답에 내부 오류 정보나 원문 일부가 오류 사유로 들어가지 않는다.
2. **Given** 운영 검색에서 리랭크가 시간 초과 한도를 넘기고, **When** 검색하면, **Then** 시나리오 1과 같이 RRF 순서와 "리랭크 미적용"으로 응답한다.
3. **Given** 운영 검색에서 리랭크가 적용되지 않았고, **When** 감사 기록을 보면, **Then** 리랭크 적용 상태, 실패 구분(오류 또는 시간 초과)과 리랭크 소요 시간이 남고 원문은 남지 않는다.
4. **Given** 평가 실행기에서 리랭커가 오류를 내거나 시간 초과되고, **When** 실험을 실행하면, **Then** 그 실행은 실행 오류로 끝나고 RRF 순서가 리랭크 결과로 기록되지 않는다.
5. **Given** 관문 시도가 시험셋 결과를 하나도 산출하기 전에 리랭커 오류로 끝났고, **When** 시도 횟수를 세면, **Then** 관문 시도로 세지 않는다. 시험셋 결과가 일부라도 산출된 뒤 끝났으면 센다(`002` Edge Cases, FR-025).

### User Story 5 - 검토자가 리랭커의 결정성과 연구 결과를 기록만으로 확인한다 (Priority: P2)

검토자는 실험 기록과 연구 결과 요약만 보고 어떤 후보를 시험했는지, 최종 후보를 왜 골랐는지, 후보 깊이 값과 그 근거, 결정성 기준, 비용, 관문 판정을 확인한다. 같은 구성을 같은 자원에서 다시 실행하면 질의별 순위가 같다.

**Why this priority**: 판정과 선택 근거를 확인할 수 없으면 연구 결과를 믿을 수 없다. 다만 기록은 비교와 판정이 동작한 뒤 쌓이므로 P2다.

**Independent Test**: 표본 후보 구성을 같은 연구 자원에서 두 번 실행해 질의별 순위를 비교하고, 연구 결과 요약만 받은 검토자가 아래 정성 기준의 질문에 답할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 후보 구성과 같은 스냅숏이 있고, **When** 같은 연구 자원에서 두 번 실행하면, **Then** 모든 질의의 결과 순위가 같다.
2. **Given** 리랭크 점수가 두 실행에서 아주 조금 다르지만 순위는 같고, **When** 결정성을 판정하면, **Then** 차이가 결정성 기준의 점수 허용 범위 안이면 통과로 기록되고 허용 범위와 측정값이 함께 남는다.
3. **Given** 두 실행에서 한 질의라도 순위가 다르고, **When** 결정성을 판정하면, **Then** 결정성 검사가 실패로 기록되고 그 후보 구성은 관문에서 불합격이다(`002` FR-016).
4. **Given** 연구가 끝났고, **When** 검토자가 연구 결과 요약을 읽으면, **Then** 시험한 후보 모델·revision 목록, 최종 후보와 선정 근거(개발셋 실험 기록 참조), 후보 깊이 값과 비교한 값들, 입력 구성, 결정성 기준, 비용 측정값, 관문 판정과 시도 차수를 다른 문서 없이 확인할 수 있다.
5. **Given** "적용 권고" 후보가 승인되었고, **When** 적용 전에 운영 하드웨어에서 관문을 통과한 검색 정책 식별값 그대로 하한선 재확인과 smoke를 하면, **Then** 값은 바뀌지 않고 FR-030의 합격 기준별 결과가 기록된다. 기준 하나라도 채우지 못하면 적용하지 않는다.

### Edge Cases

- 통과 모듈 구성은 동점 처리까지 포함해 근거 항목 순서와 응답이 현재 구성과 같다(FR-013a ②). 실제 리랭커가 모든 질의에서 후보 목록의 RRF 순서를 그대로 유지해도 근거 항목 순서는 리랭크 점수 기준(FR-013a ④)이라 동점 처리 같은 작은 차이만 생길 수 있다. 이런 결과는 대개 `002`의 판정 규칙대로 "유의한 차이 없음(현재 유지)"이며 정상 결과다.
- 리랭커는 후보를 버리지 않으므로 `no_evidence`가 나오는 질의 집합은 현재 구성과 같아야 한다. 같은 스냅숏에서 `no_evidence` 질의가 하나라도 달라지면 FR-013 위반으로 기록하고 원인을 조사한다.
- 후보 깊이가 1이면 순서가 바뀔 수 없으므로 통과 모듈과 결과가 같다. 개발셋 비교 대상에 넣을 수는 있지만 최종 후보로는 의미가 없다.
- 하한선을 통과한 후보가 하나뿐이면 리랭크해도 순서가 같다. 리랭크 적용 상태는 "적용"으로 기록한다.
- 같은 내용이 여러 원본 경로에 있어 하나로 묶인 후보는 리랭크에서 후보 하나로 다루며 모든 원본 경로를 그대로 보존한다.
- 질의문 자체가 길이 상한을 넘으면 질의도 자르기 규칙을 따른다. 자르기 규칙은 검색 정책 식별값에 들어간다.
- 연구 자원과 운영 GPU의 사양이 달라 지연과 GPU 메모리 측정값이 운영과 다를 수 있다. 측정 환경을 실험 기록에 남기고, 적용 전 확인(FR-030)에서 운영 하드웨어로 다시 확인한다.
- 다른 연구 트랙(`013` 청킹, `014` 임베딩)의 결과가 먼저 적용되어 현재 구성이 바뀌면, 이전 현재 구성에서 만든 개발셋 결과는 새 현재 구성에 대한 근거가 아니다. 관문 시도는 시도 시점의 현재 구성과 비교하므로, 최종 후보는 새 현재 구성 위에 다시 구성해 새 검색 정책 식별값으로 등록하고 개발셋으로 다시 확인한 뒤 올린다. 트랙 ②의 시도 횟수는 이어서 센다.
- 리랭커와 새 임베딩 모델(`014`)이 함께 운영 GPU에 올라가면 둘의 메모리 합이 운영 GPU 메모리를 넘을 수 있다. 비용 한도의 GPU 메모리는 시도 시점 구성 전체(질의 임베딩과 리랭커 포함)로 잰다.
- 후보 모델의 길이 상한이 상위 절 문맥을 넣기에 부족하면 그 입력 구성은 자르기 규칙의 영향을 크게 받는다. 개발셋 비교에서 입력 구성별 결과를 따로 기록한다.
- 운영에서 "리랭크 미적용"이 반복되면 같은 검색 정책 식별값으로 다른 순위가 나온다(설계서 D-06 주의). 응답과 감사 기록의 리랭크 적용 상태가 이를 구분하는 재현 좌표다.

## Requirements *(mandatory)*

### Functional Requirements

**연구 질문과 결과**

- **FR-001**: 이 연구는 MUST 다음 질문에 답한다: "하한선과 RRF 결합을 거친 하이브리드 검색 후보에 사내 리랭커를 더하면, 비용 한도 안에서 `002` 적용 관문 기준으로 근거 순위가 개선되는가?" 답은 최종 후보의 관문 판정으로 낸다.
- **FR-002**: 연구의 성공은 MUST 최종 후보 하나에 대한 관문 판정을 얻는 것이다. "불합격"이나 "유의한 차이 없음(현재 유지)"으로 리랭커 없는 현재 구성(통과 모듈)을 유지하는 것도 정상 결과다.
- **FR-003**: 연구는 MUST 다음 산출물을 낸다: ① 개발셋 실험과 관문 시도의 실험 기록(`002` 형식), ② 관문 시도에 올린 최종 후보 1개(불변 등록된 검색 정책 식별값), ③ 설계서 6.6·10절 계약을 따르는 리랭커 구현, ④ 후보 깊이 값과 그 근거(FR-018), ⑤ 결정성 기준(FR-028), ⑥ 연구 결과 요약(User Story 5 시나리오 4의 항목).
- **FR-004**: 후보 구성은 MUST "적용 권고" 판정과 승인권자의 승인을 모두 받은 뒤에만 운영에 적용한다. 연구와 관문은 운영 구성을 바꾸지 않는다.

**후보 범위와 데이터 경계**

- **FR-005**: 리랭커 후보는 MUST 사내 자원에서 실행할 수 있고 고정 revision으로 사내에 보관한 모델로 한정한다. 질의나 후보 근거를 사내 밖 서비스로 보내 채점하는 후보는 범위 밖이다.
- **FR-006**: 후보 모델 목록(모델 식별자와 revision)은 MUST 모델을 들여오거나 실험에 쓰기 전에 승인권자의 승인을 받는다. 외부 의존성의 선택·추가는 사용자 승인 사항이기 때문이다(헌법 원칙 I). 승인 목록 밖의 모델은 실험에 쓰지 않는다.
- **FR-007**: 질의, 후보 근거, 평가셋, 원본 자료, 모델, 실험 기록과 그 밖의 연구 산출물은 MUST 사내 환경에 두고 외부 서비스로 보내지 않는다(`AGENTS.md` `보안과 데이터 취급` 절, `002` FR-034).
- **FR-008**: LLM 기반 리랭커는 MUST 헌법 원칙 VII (2)의 채점·정렬 용도로만 쓴다. 리랭커가 만든 글은 근거, 응답, 색인에 들어가지 않는다.
- **FR-009**: 연구와 실험은 MUST 운영 GPU와 분리된 연구 자원에서 하고, 실험 기록에 실행 자원을 남긴다(`002` FR-033).

**리랭커 동작 계약(설계서 6.6·10절)**

- **FR-009a**: 평가 실행기는 MUST 후보 검색 정책마다 그 정책이 가리키는 리랭커 구현을 코드에 적은 명시적 목록에서 골라 쓰고(설계서 D-08), 여러 후보 모델을 함께 올리는 일은 연구 자원의 평가 실행기에서만 한다. 공개 검색은 운영 검색 정책의 리랭커 하나만 쓴다. 이는 설계서 D-05(임베딩 모델에 대해 승인된 원칙)를 리랭커에 같은 방식으로 적용하는 것이며, 그 적용은 사용자 승인으로 확정했다(2026-11-10).
- **FR-010**: 리랭커는 MUST 질의문과, 하한선 → RRF 결합 → (`strict` 모드면 두 lane 교집합 필터)를 거친 근거 묶기 전 후보 목록의 RRF 순서 상위 N개(후보 깊이)만 입력으로 받는다(설계서 10절). 그 후보가 N개보다 적으면 전부를 받는다. `strict` 모드를 검색 정책 식별값에 넣을지는 설계서 O-10으로 `009`에서 정하며, 이 연구의 실험은 실험 기록에 `strict` 모드 사용 여부를 남기고 비교하는 두 구성에 같은 값을 쓴다.
- **FR-011**: 리랭커는 MUST 입력 후보마다 리랭크 점수와 새 순위를 낸다. 통과 모듈은 리랭크 점수를 내지 않으므로 이 점수·순위 요구에서 빠진다(FR-013a). 후보 집합 보존 요구는 통과 모듈에도 적용된다. 리랭커가 내놓는 근거 묶기 전 후보 목록에는 입력에 없던 후보가 들어가지 않고 입력 후보가 빠지지 않는다. 응답 근거 수에 따른 자르기(FR-013a)는 이 요구와 별개다. 리랭크 점수로 후보를 버리는 기능(리랭크 점수 하한선, 설계서 O-7)은 이 연구 범위에 넣지 않는다.
- **FR-012**: 응답의 근거 본문과 재현 좌표는 MUST 리랭크 전과 같다. 리랭커는 순서와 리랭크 점수·순위만 바꾼다.
- **FR-013**: 리랭커가 내놓는 근거 묶기 전 후보 목록의 순서는 MUST 리랭크한 N개를 새 순위대로 먼저 두고, 후보 깊이 밖의 후보를 원래 RRF 순서대로 뒤에 둔다. 리랭크 점수가 같으면 RRF 순위, 그다음 청크 식별값 순서로 정한다. 두 lane 모두 하한선을 통과한 후보가 없으면 리랭커를 부르지 않고 `no_evidence`를 돌려준다. 리랭커는 `no_evidence` 여부를 바꾸지 않는다.
- **FR-013a**: 근거 묶기와 응답 근거 수 자르기는 MUST 리랭커 뒤에, 리랭커가 내놓은 후보 목록 순서를 입력으로 해서 한다. 응답 근거 수는 묶기 뒤에 적용하므로 응답에는 후보 목록의 일부만 담길 수 있다. 이 연구는 현재 근거 묶기 규칙을 바꾸지 않는다. 현재 규칙은 근거 항목을 그 항목에서 RRF 점수가 가장 높은 일치 조각의 점수 내림차순으로 놓고, 점수가 같으면 상위 절 식별값 순으로 놓는다. 후보 목록 자체는 RRF 점수 내림차순, 같으면 청크 식별값 순이므로, RRF 점수가 같은 경우에는 근거 항목 순서가 "후보 목록에서 가장 앞선 일치 조각의 위치" 순서와 다를 수 있다(가중치가 같으면 키워드 lane에서만 2위인 후보와 벡터 lane에서만 2위인 후보처럼 동점이 흔하다). 리랭크된 경우의 근거 항목 순서 규칙은 다음 조건을 모두 지켜야 한다.
  - ① 결정적이다: 같은 후보 목록과 리랭크 점수면 항상 같은 근거 항목 순서가 나온다.
  - ② 통과 모듈이면 현재 규칙과 같다: 동점 처리(같은 점수면 상위 절 식별값 순)까지 포함해 근거 항목 순서가 지금과 같다.
  - ③ 리랭크된 일치 조각을 하나라도 가진 근거 항목은 후보 깊이 밖 일치 조각만 가진 근거 항목보다 앞선다.
  - ④ 리랭크된 일치 조각을 가진 근거 항목끼리는 각 항목에서 가장 높은 리랭크 점수의 내림차순이다. 후보 깊이 밖 일치 조각만 가진 근거 항목끼리는 현재 규칙(가장 높은 RRF 점수 내림차순)을 따른다. 어느 쪽이든 점수가 같으면 고정된 식별값 규칙으로 정한다.

  위 조건을 만족하는 정확한 식(예: (리랭크된 일치 조각 보유 여부, 해당 점수의 내림차순, 상위 절 식별값))과, 근거 항목 안 일치 조각의 순서, 근거 항목 하나를 대표하는 점수·순위 필드(예: 리랭크된 일치 조각이 여러 개일 때, 리랭크되지 않은 일치 조각만 있을 때)는 `009`가 정한다. 통과 모듈은 리랭크 점수를 내지 않으므로 모든 일치 조각이 "리랭크되지 않음"이 되어 ③·④가 현재 규칙으로 돌아간다.
- **FR-014**: 리랭커의 입력 구성(후보 원문, 제목 계층, 상위 절 문맥 포함 여부 등)은 MUST 색인에 저장된 내용으로만 만들고, 연구에서 개발셋 비교로 정해 검색 정책 식별값에 기록한다.
- **FR-015**: 입력이 리랭커 모델의 길이 상한을 넘으면 MUST 고정된 자르기 규칙으로 채점용 입력만 줄인다. 자르기 규칙은 검색 정책 식별값에 들어가고, 응답의 근거 본문은 줄이지 않는다.
- **FR-016**: 리랭커 모델 식별자·revision, 구현 이름·버전, 후보 깊이, 입력 구성, 자르기 규칙, 시간 초과 한도는 MUST 검색 정책 식별값에 들어간다. 이 중 하나라도 바뀌면 새 검색 정책 식별값이 된다. 리랭커는 색인 식별값에 들어가지 않으며, 리랭커만 바꾼 후보 구성은 재색인·재임베딩을 요구하지 않는다. 앞의 세 묶음(모델 식별자·revision, 구현 이름·버전, 후보 깊이)은 설계서 7.1의 "리랭커 기술자·후보 깊이"에 해당한다. 뒤의 세 항목(입력 구성, 자르기 규칙, 시간 초과 한도)은 설계서 7.1을 구체화하는 추가이며, 검색 정책 식별값의 구성은 사용자 승인 사항(헌법 원칙 I)이므로 사용자 승인으로 확정했다(2026-11-10).
- **FR-016a**: FR-016의 뒤 세 항목을 리랭커 기술자의 설정 해시 안에 넣을지, 검색 정책의 별도 필드로 둘지는 이 명세에서 정하지 않는다. `012` 계획과 `009`에서 권장안·대안을 제시하고 승인권자 승인으로 정한다. 어느 쪽이든 세 값이 바뀌면 검색 정책 식별값이 바뀌어야 한다.
- **FR-016b**: 시간 초과 한도가 검색 정책 식별값에 들어가므로, 관문을 통과한 뒤 운영 하드웨어(연구 자원과 다를 수 있음)에 맞춰 시간 초과 한도를 바꾸면 MUST 새 후보로 본다. 새 후보는 FR-030대로 개발셋 확인, 관문 시도(트랙 ②의 시도 1회를 쓴다), 승인을 다시 거친다. 그래서 시간 초과 한도는 첫 관문 시도 전에 운영 하드웨어의 예상 지연을 고려해 정한다(FR-020).
- **FR-017**: 리랭크가 적용된 응답은 MUST 근거 항목 안의 일치 조각마다 리랭크 점수와 리랭크 순위를 담고, 후보 깊이 밖이라 리랭크되지 않은 일치 조각에는 리랭크되지 않았다는 표시를 담으며, 응답에 리랭크 적용 상태를 담는다. 기존 RRF 순위·점수, 재현 좌표, 색인 좌표와 검색 정책 좌표는 그대로 둔다. 근거 항목 단위의 대표 점수·순위는 FR-013a대로 `009`가 정한다. 응답·감사 필드 자체는 `009`가 만들고, 이 연구의 구현은 그 값을 채운다.

**후보 깊이(설계서 D-07)**

- **FR-018**: 후보 깊이는 MUST 설정값이다. 이 연구는 개발셋에서 후보 깊이 값을 3개 이상(기본값이며 설정으로 바꿀 수 있다) 비교해 비용 한도 안에서 최종 후보의 후보 깊이 값을 정하고, 비교한 값과 결과를 실험 기록에, 정한 값과 근거를 연구 결과 요약에 남긴다. 정한 값은 `009`에 넘겨 검색 정책의 기본값으로 확정한다. 리랭커가 통과 모듈이면 후보 깊이는 결과에 영향이 없다.

**실패와 시간 초과(설계서 D-06)**

- **FR-019**: 운영 검색에서 리랭커가 오류를 내거나 시간 초과 한도를 넘기면 MUST 검색을 실패시키지 않고 RRF 순서로 근거를 돌려주며, 응답의 리랭크 적용 상태를 "리랭크 미적용"으로 표시한다. 응답에는 내부 오류 정보나 원문 일부를 오류 사유로 넣지 않는다.
- **FR-020**: 시간 초과 한도는 MUST 설정값이며 검색 정책 식별값에 들어간다(FR-016). 값은 비용 한도(`002` FR-018 ⑤의 지연 한도)와 운영 하드웨어의 예상 지연을 함께 고려해 계획 단계에서 승인권자 승인으로 정하고, 첫 관문 시도 전에 고정한다. 관문 통과 뒤 값을 바꾸면 FR-016b의 새 후보다.
- **FR-021**: 평가 실행기에서 리랭커가 오류를 내거나 시간 초과되면 MUST RRF 순서로 대체하지 않고 실행 오류로 처리한다. 그 질의의 RRF 순서를 리랭크 결과로 기록하지 않는다. 관문 시도 횟수는 `002`의 규칙대로 센다.
- **FR-022**: 운영 검색의 감사 기록은 MUST 요청마다 리랭크 적용 상태, 실패 구분(오류 또는 시간 초과)과 리랭크 소요 시간을 남기고 원문과 비밀값은 남기지 않는다.

**평가와 관문(`002`)**

- **FR-023**: 튜닝과 최종 후보 선정은 MUST 개발셋으로만 한다. 시험셋은 관문 시도에만 쓰며 시험셋 질의와 결과를 튜닝에 쓰지 않는다. 예외로, 불합격 판정의 조건별 사유를 보고 후보를 고쳐 다시 올리는 일은 FR-024의 한도 안에서만 허용한다(`002` FR-024).
- **FR-024**: 트랙 ②는 MUST 같은 시험셋에서 관문 시도를 최대 3회만 하고, 시도 한 번에 최종 후보 1개만 올린다. 불합격 후보를 고쳐 남은 횟수 안에서 다시 올릴 수 있다. 한도를 다 쓰면 시험셋을 보충한 뒤에 재개한다(`002` FR-025·FR-026).
- **FR-025**: 개발셋 실험과 관문 시도에 쓰는 모든 후보 검색 정책은 MUST 평가 전에 불변으로 등록하고, 실험 기록은 그 식별값을 참조한다(설계서 D-11). 운영에 적용할 때는 관문 시도에 쓴 바로 그 등록 식별값을 쓴다. 이 등록은 운영 검색 정책을 바꾸지 않는다.
- **FR-026**: 비교는 MUST (현재 구성의 색인, 현재 검색 정책)과 (같은 색인, 후보 검색 정책)의 쌍으로 한다. 이 연구는 활성 색인과 운영 검색 정책을 바꾸지 않는다(`002` FR-032).
- **FR-027**: 비용은 MUST `002` FR-018 ⑤의 설정값을 한도로 쓴다. 질의 지연 p95 증가는 리랭크 시간을 포함한 전체 질의 지연으로, GPU 메모리 최대 사용량은 리랭커를 포함한 질의 경로 구성 전체로 잰다. 리랭크 소요 시간은 따로도 기록한다.
- **FR-028**: 이 연구는 MUST 첫 관문 시도 전에 리랭커의 결정성 기준을 정해 기록한다(설계서 O-8). 기준은 `002`의 결정성 필수 검사와 맞아야 한다: 같은 연구 자원에서 같은 구성으로 두 번 실행한 질의별 결과 순위가 모두 같아야 하고, 리랭크 점수에는 허용 범위(설정값)를 둘 수 있다.
- **FR-029**: 관문 시도는 MUST `002`의 시험셋 규모 조건(FR-002, FR-027)을 채운 시험셋으로만 한다. 개발셋 실험은 이 조건과 관계없이 할 수 있다.

**적용 전 확인과 되돌리기**

- **FR-030**: 승인된 후보를 적용하기 전에 MUST 운영 하드웨어에서 관문을 통과한 검색 정책 식별값 그대로 하한선 재확인과 smoke 확인을 한다. 이 확인은 값을 바꾸지 않는다. 합격 기준은 다음을 모두 채우는 것이다: ① 기존 smoke 합격 기준(정상 질의 5개 모두 허용 근거가 상위 5위 안, 문서에 없는 질의는 `no_evidence`), ② 리랭커가 불리는 정상 질의 5개 모두 리랭크 적용 상태가 "적용"이고 "리랭크 미적용"(오류·시간 초과)이 0건이다. 문서에 없는 질의는 FR-013대로 리랭커를 부르지 않으므로 ②에서 빼고 ①의 `no_evidence`만 본다. 시간 초과는 "리랭크 미적용(시간 초과)"으로 ②에서 드러나므로 별도 지연 기준을 두지 않는다. 확인할 때는 정상 질의 5개의 리랭크 소요 시간도 기록한다. 설계서 15절은 이 확인을 승인 대상인 설계 권고로 두었으며, 이 확인을 필수(MUST)로 두는 것과 위 합격 기준은 사용자 승인으로 확정했다(2026-11-10). 확인이 실패하면 적용하지 않으며, 값을 바꿔야 하면 새 후보로 보고 개발셋 확인, 관문 시도(남은 횟수 안), 승인을 다시 거친다. 확인의 실행 시점과 운영 GPU 사용 방식은 `009` 계획과 설계서 O-13에서 정한다.
- **FR-031**: 적용과 되돌리기는 MUST 검색 정책만 바꿔서 한다. 되돌리기는 이전 검색 정책 식별값으로 돌아가며 색인과 활성 색인은 건드리지 않는다.

### Key Entities *(include if feature involves data)*

- **후보 모델**: 승인 목록에 오른 리랭커 모델. 모델 식별자, 고정 revision, 사내 보관 위치, 길이 상한, 승인 일자를 가진다.
- **리랭커 구현**: 설계서 6.6 계약을 따르는 구현. 모듈 기술자(종류 리랭커, 구현 이름, 버전, 설정 해시, 모델 식별자·revision)를 낸다. 통과 모듈도 리랭커 구현 하나다.
- **후보 검색 정책**: 현재 검색 정책에 리랭커 구현, 후보 깊이, 입력 구성, 자르기 규칙, 시간 초과 한도를 더한 검색 정책. 평가 전에 불변 등록되며 검색 정책 식별값을 가진다.
- **후보 구성**: (현재 구성의 색인, 후보 검색 정책)의 쌍.
- **최종 후보**: 관문 시도에 올리는 후보 구성 하나. 시도 차수를 가진다.
- **리랭크 결과**: 질의 하나에 대해 후보마다 리랭크 점수, 리랭크 순위, 원래 RRF 순위를 담는다.
- **리랭크 적용 상태**: 응답과 감사 기록의 값. 적용, 리랭크 미적용(오류), 리랭크 미적용(시간 초과) 등을 구분한다. 통과 모듈일 때의 값은 계획 단계에서 정한다.
- **결정성 기준**: 순위 동일 요구와 리랭크 점수 허용 범위를 담는다.
- **연구 결과 요약**: 시험한 후보 목록, 최종 후보와 선정 근거, 후보 깊이 값과 근거, 입력 구성, 결정성 기준, 비용 측정값, 관문 판정과 시도 차수를 담는다. 실험 기록을 참조한다.
- **실험 기록·관문 판정**: `002`의 정의를 따른다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 트랙 ②의 최종 후보에 대한 관문 판정이 실험 기록에 1건 이상 남고, 같은 시험셋에서 트랙 ②의 관문 시도는 3회 이하다. 판정이 "적용 권고"가 아니어도 이 기준을 채운다.
- **SC-002**: 개발셋 실험과 관문 시도의 모든 질의별 결과에서, 근거 묶기 전 리랭커 출력 후보 목록의 집합이 리랭커 입력 후보 집합과 다른 질의가 0건이고, 근거 항목 순서가 FR-013a의 순서 규칙과 다른 질의가 0건이고, 응답 근거 본문이 원문과 글자 단위로 다르거나 재현 좌표가 리랭크 전과 다른 근거가 0건이다.
- **SC-003**: 같은 스냅숏에서 후보 구성과 현재 구성의 `no_evidence` 질의 집합이 다른 건수가 0건이다. 또 통과 모듈 구성의 응답 근거 항목 순서가 리랭커 도입 전 동작과 다른 질의가 0건이며, 이 표본에는 RRF 점수가 같은 상위 절이 있는 질의가 1건 이상 들어 있다.
- **SC-004**: 같은 연구 자원에서 같은 후보 구성을 두 번 실행했을 때 질의별 결과 순위가 다른 질의가 0건이고, 리랭크 점수 차이가 결정성 기준의 허용 범위를 넘은 건수가 0건이다.
- **SC-005**: 리랭커 오류와 시간 초과를 일부러 일으킨 운영 경로 표본(오류·시간 초과 각 1건 이상) 전부에서 검색이 성공하고 RRF 순서와 "리랭크 미적용"이 응답·감사 기록에 남으며, 평가 경로의 같은 표본 전부에서 RRF 순서가 리랭크 결과로 기록된 건수가 0건이다.
- **SC-006**: 튜닝·후보 선정에 쓴 실험 중 시험셋을 쓴 실험이 0건이고, 최종 후보의 선정 근거가 가리키는 실험 기록이 모두 개발셋 실험이다.
- **SC-007**: 모든 실험 기록에 비교한 두 구성의 검색 정책 식별값과 리랭커 모델 식별자·revision, 후보 깊이, 입력 구성, 자르기 규칙, 시간 초과 한도가 빠짐없이 있고, 등록되지 않은 검색 정책으로 평가한 실험이 0건이다.
- **SC-008**: 승인 목록 밖 모델을 쓴 실험, 질의·후보 근거·연구 산출물을 외부 서비스로 보낸 건수, 운영 GPU에서 실행한 실험이 각각 0건이다.
- **SC-009**: "적용 권고"와 승인권자 승인을 모두 받지 않은 리랭커가 운영에 적용된 건수가 0건이고, 리랭커 적용·되돌리기로 색인 식별값이나 활성 색인이 바뀐 건수가 0건이다.
- **SC-010**: 최종 후보의 후보 깊이 값은 개발셋에서 비교한 3개 이상의 값 중 하나이며, 비교한 값마다 지표와 비용이 실험 기록에 있다.
- **SC-011**: 정성 기준으로, 연구 결과 요약만 받은 검토자가 다른 문서나 질문 없이 다음 다섯 질문에 답할 수 있다: 무엇을 시험했는가, 왜 이 후보를 골랐는가, 후보 깊이는 얼마이고 왜인가, 비용은 한도 안인가, 관문 판정은 무엇이고 몇 번째 시도인가. 합격 예시: "승인 목록의 후보 모델 2개를 개발셋에서 후보 깊이 10·20·40으로 비교했고, 모델 B·깊이 20이 개발셋 Recall@5가 가장 높으면서 지연 증가가 한도 안이라 골랐다(실험 기록 식별값 제시). 첫 관문 시도에서 '유의한 차이 없음(현재 유지)'이었다." 불합격 예시: "리랭커를 넣으니 결과가 좋아졌다"처럼 비교 대상, 후보 깊이, 실험 기록 식별값, 판정 없이 결론만 적은 요약.

## Assumptions

- 주 사용자는 리랭커 후보를 시험하는 연구자, 실험 기록과 판정을 확인하는 검토자, 후보 모델 목록과 적용을 승인하는 승인권자, 그리고 리랭커가 적용된 근거 패키지를 받는 호출 Agent다.
- 확정(설계서 v0.3, 사용자 승인 2026-11-09): 리랭커 위치는 하한선 → RRF 결합 → 리랭커 → 근거 묶기 순서이고, 실패 시 운영은 RRF 순서와 "리랭크 미적용", 평가는 오류다(D-06). 후보 깊이는 정책 설정값이며 수치는 이 연구에서 정해 `009`에서 확정한다(D-07). 후보 검색 정책은 평가 전에 불변 등록한다(D-11). 평가 실행기는 비공개 평가 경로로 질의한다(D-04).
- 확정(사용자 승인 2026-11-08): 관문 기준은 `002`의 개선 폭 기준 v1.0이며 이 명세는 그 설정값을 그대로 쓴다. 이 연구만의 별도 관문 기준을 두지 않는다.
- 확정(사용자 승인 2026-11-10): ① FR-016의 입력 구성·자르기 규칙·시간 초과 한도를 검색 정책 식별값에 넣는 것(설계서 7.1의 구체화), ② FR-009a의 D-05 원칙을 리랭커에 적용하는 것, ③ FR-030의 적용 전 확인을 필수로 두는 것과 그 합격 기준(설계서 15절은 승인 대상인 권고로 둠). FR-016a의 배치(기술자 설정 해시 안 또는 별도 정책 필드)는 `012` 계획·`009`에서 승인으로 정한다.
- 근거 묶기 기본값: 이 연구는 현재 근거 묶기 규칙(상위 절 단위 묶기, 가장 높은 RRF 점수의 내림차순·같으면 상위 절 식별값 순, 응답 근거 수는 묶기 뒤 적용)을 바꾸지 않는다. 통과 모듈이면 동점 처리까지 지금과 같아야 하고, 리랭크된 경우의 순서 규칙은 이 규칙으로 돌아가는 결정적 규칙이어야 한다(FR-013a ①~④). 정확한 식은 그 조건 아래 `009`가 정한다. 이 밖에 근거 묶기 규칙을 바꾸는 제안은 범위 밖이며 별도 승인 대상이다.
- 후보 범위 기본값: 후보는 플랫폼 검색 경로 안에서 리랭커 구현으로 실행할 수 있는 모델로 한정한다. 다른 사내 모델 서버(예: 내부 생성 모델 서버)를 검색 경로에서 원격으로 불러 채점하는 방식은 서비스 경계를 바꾸므로 이 연구에 넣지 않으며, 필요하면 별도 승인을 받는다.
- 후보 수 기본값: 개발셋 비교에는 통과 모듈(현재 구성) 외에 승인 목록의 후보 모델을 1개 이상 쓰며, 2~3개를 권장한다. 구체 모델 목록은 계획 단계에서 권장안·대안과 함께 승인권자에게 제시한다.
- 모델 사용 조건 기본값: 후보 모델의 라이선스는 사내 업무 사용을 허용해야 하며, 계획 단계에서 모델 목록과 함께 확인한다. 모델 가중치를 들여오는 일은 사내로 받는 것이며 자료를 밖으로 보내는 일이 아니다.
- 미세 조정 기본값: 이 연구는 후보 모델의 가중치를 사내 자료로 다시 학습(미세 조정)하지 않고, 승인된 고정 revision을 그대로 쓴다. 튜닝은 모델·후보 깊이·입력 구성·자르기 규칙의 선택을 뜻한다. 미세 조정이 필요하면 학습 쌍 생성(헌법 원칙 VII (3))을 포함한 별도 계획과 승인을 받는다.
- 리랭크 점수 하한선(설계서 O-7) 기본값: 이 연구는 리랭크 점수로 후보를 버리지 않는다. 그래서 `no_evidence` 판정은 지금처럼 lane 하한선만으로 정해지고 `002` 비용 한도의 `no_evidence` 비율 조건은 구조적으로 지켜진다. 하한선을 두자는 제안은 별도 승인 대상이다.
- 결정성 기준 기본값: 같은 연구 자원에서 질의별 결과 순위가 완전히 같아야 하고, 리랭크 점수의 허용 범위는 설정값으로 둔다. 허용 범위 값은 계획 단계에서 정하고 첫 관문 시도 전에 기록한다(FR-028). 서로 다른 하드웨어 사이의 순위 동일은 요구하지 않고 적용 전 확인(FR-030)으로 대신한다.
- 비용 측정 기본값: GPU 메모리 최대 사용량은 질의 임베딩 모델과 리랭커를 함께 올린 질의 경로 구성 전체로 잰다. 운영 GPU 메모리 용량은 `002`의 설정값이다.
- 시간 초과 한도와 통과 모듈일 때의 리랭크 적용 상태 값은 계획 단계에서 승인권자 승인으로 정한다(FR-020, Key Entities).
- 후보 깊이 비교 값 3개 이상은 기본값이며 설정으로 바꿀 수 있다. 값의 범위는 현재 lane별 후보 수 상한 안에서 계획 단계에 정한다.
- 연구 결과 요약은 `specs/` 산출물이 아니라 사람이 읽는 보고서이므로 작성할 때 `crefle-doc` 스킬 규칙을 따른다(`AGENTS.md` `문서 작성` 절).
- 연구 중 플랫폼은 나이브 기본 구현(리랭커는 통과 모듈)을 쓴다. 이 명세는 그 상태를 바꾸지 않는다.
- 기존 설계서와 구현 계획이 시스템 정본이며, 이 명세는 기능 완료 시 정본에 반영한다.

## Dependencies

- **`002` 평가 하네스**: 개발셋·시험셋, 지표, 실험 기록, 적용 관문, 트랙별 관문 시도 한도, 비용 한도 설정값, 결정성 필수 검사. 관문 시도는 `002`가 구현되고 시험셋이 규모 조건(정답이 있는 질의 400개 이상 등)을 채운 뒤에만 할 수 있다. 기록이 남는 개발셋 실험은 `002`의 개발셋·실험 실행이 준비되고, 아래 `009`의 검색 정책 새 형식·등록 경로와 검색 경로 안 리랭커 실행 위치가 생긴 뒤에 할 수 있다(FR-025).
- **설계서 v0.3**: 리랭커 모듈 계약(6.6), 식별값 배치(7.1), 위치와 계약(10), 교체 절차(15.1), 결정 D-04·D-05·D-06·D-07·D-08·D-11, 열린 항목 O-7·O-8·O-10·O-13. FR-016의 입력 구성·자르기 규칙·시간 초과 한도는 7.1을 구체화하는 추가이며 사용자 승인으로 확정했다(2026-11-10). FR-009a는 D-05를 리랭커에 적용하는 것이며 사용자 승인으로 확정했다(2026-11-10).
- **`009` 통합 조회 API**: 다음이 `009`에서 먼저 만들어져야 한다.
  - 검색 정책 새 형식: 리랭커 기술자와 후보 깊이 필드(설계서 7.1, D-02), 그리고 FR-016의 입력 구성·자르기 규칙·시간 초과 한도를 담을 자리(FR-016a에서 정하는 배치에 따름). 그 형식의 등록 경로와 마이그레이션(설계서 15.1 0단계, D-07·D-11). **FR-025의 후보 검색 정책 등록은 이 형식이 있어야 할 수 있으므로, 이 형식이 생기기 전에는 기록이 남는 개발셋 실험도 시작할 수 없다.**
  - 검색 경로 안의 리랭커 실행 위치(근거 묶기 앞). 평가 실행기는 비공개 평가 경로로 같은 검색 서비스를 부르므로(D-04), 이 위치가 없으면 평가 경로에서도 리랭커를 돌릴 수 없다.
  - 근거 항목 단위의 리랭크 대표 점수·순위와 일치 조각 순서의 정의(FR-013a), 응답의 리랭크 점수·순위·적용 상태 필드, 감사 기록의 리랭크 상태·소요 시간 필드.
  - `strict` 모드를 검색 정책 식별값에 넣을지(O-10).
  - 후보 깊이 기본값은 이 연구의 결과를 받아 `009`에서 확정한다.
- **`002` 평가 실행기 계획**: 평가 실행기가 후보 검색 정책마다 리랭커 구현을 골라 여러 후보 모델을 올리는 방식(FR-009a)과 리랭커 실패를 실행 오류로 처리하는 방식(FR-021).
- **`013` 파싱·영역 판별·구조 보존 청킹(트랙 ①)**: 청크 경계와 길이가 바뀌면 리랭커 입력과 결과가 바뀐다. `013`이 먼저 적용되면 이 연구의 최종 후보는 새 현재 구성 위에서 다시 확인한다(Edge Cases).
- **`014` 임베딩(트랙 ③)**: 질의·문서 임베딩이 바뀌면 리랭커에 들어오는 후보 집합과 GPU 메모리 사용량이 바뀐다. `014`가 먼저 적용되면 같은 방식으로 다시 확인한다. 두 트랙이 모두 적용 권고를 받으면 나중에 적용하는 쪽은 먼저 적용된 쪽을 포함한 현재 구성과 비교한 판정이어야 한다.
- **연구 자원**: 운영 GPU와 분리된 사내 GPU 자원. 구체 자원은 운영 결정이며 계획 단계에서 확인한다.

## Out of Scope

- 리랭크 점수 하한선(후보를 점수로 버리기, 설계서 O-7).
- 키워드 lane 교체, 세 번째 lane 추가, RRF 결합 방식 교체.
- 검색 정책 새 형식, 응답·감사 필드, 리랭커 위치의 구현 자체(`009`). 이 연구는 그 틀에 들어갈 리랭커 구현을 만든다.
- 다른 사내 모델 서버를 검색 경로에서 원격으로 불러 채점하는 방식(Assumptions).
- 리랭커 모델의 학습·미세 조정. 이 연구는 승인 목록의 모델을 사내에 보관한 고정 revision 그대로 쓴다(FR-005·FR-006).
- 근거 묶기 규칙의 변경(FR-013a의 일반화 외). 근거 항목 대표 점수·순위 필드의 정의는 `009`의 몫이다.
- 생성형 답변과 그 품질 평가.
- 평가 환경의 DB 분리와 운영 적용 절차(설계서 O-13).
- 승인된 후보의 실제 운영 배포 실행. 배포는 `AGENTS.md`의 승인·배포 절차를 따른다.
- 연구 자원의 구체 선택.
