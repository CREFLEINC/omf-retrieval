## Summary

이 연구는 "하한선과 RRF를 거친 하이브리드 후보에 사내 리랭커를 더하면 비용 한도 안에서 `002` 관문 기준으로 근거 순위가 개선되는가"에 관문 판정으로 답한다(FR-001). 사용자 결정(2026-11-12)에 따라 후보 모델은 승인 목록의 적용 후보 4개(KURE-Reranker-base, KURE-Reranker-nano, Qwen3-Reranker-0.6B, bge-reranker-v2-m3)와 연구 장비 전용 상한 확인 1개(Qwen3-Reranker-4B)로 한정하고, 미세 조정은 하지 않는다.

작업은 **지금 할 수 있는 것**과 **선행 조건을 기다리는 것**으로 나눈다. 이 계획 승인 직후 바로 할 수 있는 것은 설계서 6.6·10절 계약을 따르는 리랭커 모듈 코드와 단위 테스트(개발 PC, DB·GPU 없음, 작은 가짜 모델로 순서 규칙 검증)다. DR-01~DR-14는 모두 승인되었으므로(사용자 2026-11-13) DR 때문에 미루는 테스트는 없다(`단계 구분` S0 행).

연구 장비는 사용자가 운영 개시를 알릴 때까지 운영 서버 `192.168.1.185`(RTX 4090)다(DR-12, `002` FR-033 "운영 개시 전 예외", 사용자 결정 2026-11-13). 장비 쪽 첫 조건은 **운영 서버 첫 접속 승인(배포 하네스) → GPU UUID·총 메모리 실측 → 허용 목록에 예외 표시 등록**이다. 그 뒤 승인 목록 모델의 반입과 SHA(해시) 검증(O1), 공식 예제 대비 구현 재현과 공개 벤치마크 재현(O2)을 하고, 실제 모델이 필요한 P5 완료 검증도 O2에서 한다.

실험은 실험 구조 (가)(사용자 결정 2026-11-13)를 따른다. S1에서 `002` 구현과 연동 변경[DR-11 ①②⑥⑦⑨]을 기다려 개발셋을 합성하고 현재 구성 run으로 검색을 **한 번만** 돌려 후보 목록을 고정 파일 A(탐색)·B(확인)로 저장한 뒤, 파일 A로 Recall@N(후보 목록)을 재서 진행 여부와 후보 깊이 비교값을 정한다. S2의 모든 탐색 실험(약 25건)·최종 후보 선택·결정성 확인은 파일 A만 읽는 오프라인 실험이라 검색·색인 DB와 `009`가 필요 없다. 확인 개발셋 확인(파일 B)은 관문 시도마다 그 시도에 보내는 후보로 1회 먼저 하며, 관문 시도와 따로 세어 시험셋 세대마다 3회까지다(4회째부터 사용자 승인, 새 세대에서 0부터, 사용자 결정 2026-11-16). `009`(검색 정책 새 형식·등록 경로·검색 경로 안 리랭커 위치·근거 항목 순서 식)와 `006` 새 형식 run은 S3에만 필요하다. 시험셋 400개 이상이 준비되면 실제 검색 경로 전체 + 리랭커로 관문 시도를 하고(최대 3회), 시험셋은 이 관문 시도에만 쓴다. "적용 권고"와 사용자 승인 뒤에만 운영 하드웨어에서 적용 전 확인(FR-030, S4)을 하며, 이 확인은 연구 평가가 아니라 운영 개시 전 예외로 하는 일이 아니다. 운영 서버에서 연구를 하는 동안에도 운영 DB·운영 컨테이너·활성 색인·운영 검색 정책은 읽지도 바꾸지도 않는다.

기술 접근은 기존 스택 재사용이다(Python 3.12, sentence-transformers 5.7.0, transformers 5.15.0, torch 2.11.0). 새 의존성을 두지 않는 것을 제안한다[DR-08]. 리랭커는 순수 함수로 순서 규칙·집합 보존을 강제하고(R-03·R-04), 모델 백엔드는 문자열 쌍을 받아 0~1 점수만 돌려준다(R-01). 운영 검색 서비스·검색 정책 형식·공개 API는 012에서 바꾸지 않는다(삽입은 `009`).

## 진행 판단 규칙

1. **첫 측정 뒤 진행 판단**(사용자 결정 U-4): S1에서 탐색 개발셋(고정 파일 A)의 상한 차이 G = Recall@최대(후보 목록) − Recall@5(후보 목록)를 잰다. **G < 3%p이면** 리랭커 실험을 계속할지 사용자에게 다시 묻는다. 근거 항목 단위 Recall@5(`002` 주 지표) 기준 차이도 함께 보고한다(R-09, C-05). C-01은 기록만 해 두고 그때 결정한다(사용자 2026-11-13): 사용자는 spec 개정(FR-002에 "사용자 결정에 의한 중단"을 정상 결과로 추가)과 관문 시도 1회 중에서 고른다. G ≥ 3%p이면 DR-05 규칙으로 비교값 3개를 정하고 S2로 간다. 같은 측정에서 개선 목표를 max(+3%p, G × 30%)로 다시 정하고(임시 +5%p를 대체, 세 지표 공통, R-17, 사용자 결정 2026-11-16), 계산 근거와 함께 사용자에게 보고해 확인받는다. 예: G = 18%p → +5.4%p, G = 8%p → +3%p. G를 계산할 수 없으면 임시 +5%p를 유지하고 표시해 보고한다.
2. **확인 개발셋 사용과 결과 처리**[DR-14, 사용자 결정 2026-11-13 F-4 (1)·G-2 (가)]: 관문 시도마다 그 시도에 보내는 후보로 파일 B 오프라인 실험(확인)을 1회 먼저 한다. 확인 하나는 관문 시도 하나에만 쓰고, 같은 후보로 다시 시도하면 새 확인을 한다. 판정 없이 끝난 시도도 그 확인은 소진된다. 확인 횟수는 관문 시도와 따로 세어 트랙 ②(리랭커 교체 건 `swap-reranker-*`도 같은 규칙)에서 시험셋 세대마다 3회까지이며(새 세대가 열리면 0부터, 이전 세대에 만들어져 아직 소진되지 않은 확인도 대조 키(파일 B SHA-256 포함)가 맞으면 새 세대 관문 시도에 쓸 수 있고, 새 세대 횟수에 다시 더하지 않음[결정 2026-11-16]), 4회째부터는 사용자 승인을 받는다. 확인은 관문 요청이 사전 점검 ① 실행 자원·② 평가 DB 확인을 통과한 직후 소진되며 ①·②에서 거부되면 소진되지 않는다(사용자 결정 2026-11-16, `002` DR-28). 색인이 바뀌어 파일 B를 다시 만들면 이전 확인은 쓸 수 없다(G-1). 근거 항목 단위 Recall@5 차이 0 이하 또는 비용 한도 초과면 관문 시도 전에 사용자에게 묻는다. 그 밖이면 관문 시도.
3. **미세 조정 재검토 조건**(사용자 결정 U-1): 공개 모델 최종 후보가 관문에서 "불합격" 또는 "유의한 차이 없음"을 받고, **그리고** 탐색 개발셋 상한 차이가 컸으면, 미세 조정을 포함하는 spec 개정을 제안한다(학습 쌍 생성은 헌법 VII (3)과 별도 계획·승인). "컸다"의 기준값은 제안(승인 대기) **G ≥ 10%p**다(C-12). 관문 시도 보고의 "목표 미달"(R-17, 관문은 통과했지만 개선 목표에 못 미침) 여부도 이 판단의 입력으로 함께 적는다(사용자 결정 2026-11-16). 기준값 G ≥ 10%p는 C-12로 그대로 사용자 확인 대상이다.
4. **시간 초과 한도 사전 점검**[DR-02]: 첫 관문 시도 전 탐색 개발셋(파일 A)에서 잰 최종 후보 리랭크 시간 p99가 한도의 80%(400ms)를 넘으면 사용자에게 보고한다. 운영 개시 전 예외 기간에는 운영 서버에서 잰 실측값을 쓰고, 운영 개시 뒤 다른 장비로 옮긴 경우에만 DR-02 2의 추정값을 쓴다.
5. **결정성**[DR-03]: 같은 연구 장비에서 같은 고정 파일 A와 같은 구성으로 두 번 실행해 후보 목록 리랭크 순위가 다르거나 점수 차이가 허용 범위(1e-4)를 넘으면 그 후보는 관문에 올리지 않고 원인을 조사한다.
6. **시험셋 사용 범위와 관문 불합격 뒤 원인 분석**(실험 구조 (가), 승인 사용자 2026-11-13): 시험셋은 S3 관문 시도에만 쓰고 S1·S2에는 쓰지 않는다. 관문 불합격 뒤 원인 분석은 개발셋(파일 A의 탐색 결과, 해당 시도의 파일 B 확인 결과)으로만 한다. 시험셋에서는 관문 출력의 조건별 수치와 불합격 사유만 본다(승인, 사용자 2026-11-13). `002`와의 관계: `002` spec FR-024는 시험셋 질의와 결과를 튜닝·후보 선정에 쓰지 않되 "관문 판정의 조건별 사유를 보고" 고쳐 다시 올리는 것만 허용하고, `002` research DR-21은 관문 출력을 조건별 사유·집계 지표로 제한하며 질의별 결과는 `eval experiment export --per-query --reason --actor`로만 꺼내고 그 실행을 `eval_access_log`에 남긴다. 이 규칙은 그 범위 안의 더 좁은 운용이며 충돌하지 않는다. 012 트랙은 시험셋 질의별 내보내기를 하지 않는다(승인, 사용자 2026-11-13). 시험셋에 대해서도 관문 보고에 참고 지표(MRR@3·nDCG@3) 집계값과 개선 목표 달성/미달을 적지만, 이것들도 원인 분석에는 쓰지 않는다.
7. **참고 지표 MRR@3·nDCG@3**(사용자 결정 2026-11-13, R-16): S2 탐색 실험(파일 A)·확인 실험(파일 B)과 관문 시도 보고에 현재·후보 구성 값과 차이를 함께 적는다. 후보 선정(R-07 4의 "Recall@5가 가장 높은 조합")과 관문 판정에는 쓰지 않는다. 연구 결과 요약에도 참고로만 적는다.
8. **개선 목표 달성 보고**(사용자 결정 2026-11-16, R-17): S2 요약, 확인 개발셋 확인, 관문 시도 보고에 Recall@5·MRR@3·nDCG@3 각각의 차이(%p)와 그때의 목표, 지표별 달성/미달(차이 ≥ 목표면 달성. Recall@5·MRR@3은 분수, nDCG@3은 허용 오차 1e-9의 부동소수점 비교, 값이 `not_applicable`이면 `not_applicable`. R-17)을 적는다. 목표는 관문 기준(개선 폭 기준 v1.0)도 후보 선정 규칙(R-07)도 아니다. 관문 "적용 권고"인데 목표에 못 미치면 판정은 바꾸지 않고 "목표 미달"로 기록해 `진행 판단 규칙` 3에 넘긴다.

### 리랭커가 들어갈 흐름(설계서 10절, 삽입은 `009`)

```text
질의 → 질의 임베딩 → 키워드·벡터 후보(각 최대 50)
 → 하한선(lane별, 이상 통과)
 → RRF 결합(정렬: RRF 점수 내림차순, 청크 id)           = 후보 목록(최대 100)
 → (strict면 교집합, 이 연구 실험에서는 사용 안 함 R-12)
 → [후보 0개] → no_evidence, 리랭커 호출 0회, 상태 skipped_no_candidates
 → [실행 경계 P2]  ※ `002` DR-18 구현 뒤에는 위·아래가 순수 함수 rank_evidence 안이라 분할이 필요(C-13)
     리랭커 = 통과 모듈 → 후보 목록 그대로, 상태 passthrough
     리랭커 = 모델     → 상위 N개(후보 깊이)만 입력 구성·자르기(P3) → 백엔드 점수(P5)
                         → 순서 규칙(P1): 새 순위 N개 + 깊이 밖 RRF 순서, 불변 검사(R-03)
                         → 성공: 상태 applied
                         → 오류·계약 위반·시간 초과:
                             운영: 후보 목록 그대로 + not_applied_error / not_applied_timeout
                             평가: 평가 오류(대체 없음, 실험 failed)
 → 근거 묶기(제안 식 P6 / 009 확정) → 응답 근거 수(limit) 자르기
```

실험 구조 (가)(사용자 결정 2026-11-13): S1에서 위 흐름의 "후보 목록"까지를 개발셋마다 한 번만 실행해 고정 파일 A·B로 저장한다(`002` ⑨). S2 오프라인 실험은 고정 파일에서 후보 목록을 읽어 "[실행 경계 P2]"부터 아래만 실행하고(P8이 레코드를 리랭크 입력으로 바꿈), 근거 묶기는 같은 순수 함수로 다시 계산한다(R-15). S3 관문 시도는 질의부터 전체 흐름을 실제 검색 경로로 실행한다.

## `002` 연동

- 012가 쓰는 `002` 기능: 평가셋·개발셋 관리, 합성(Kanana), 정책 등록(`eval policy register`, S3 준비), 개발셋 실험(S1 첫 측정, S2 오프라인 실험), 관문 시도, 트랙 `track-2-reranker`, 결정성 필수 검사, 비용 측정, 사전 점검(실행 자원 허용 목록과 운영 개시 전 예외 표시, 운영 DB 주소 거부).
- `002`에 요청하는 추가 변경 ①~⑨는 [DR-11]과 [contracts/eval-linkage-request.md](./contracts/eval-linkage-request.md)에 있다(DR-11 승인 2026-11-13, ⑨는 실험 구조 (가)로 추가). **012는 `002` 문서·코드를 바꾸지 않았다.** `002` 계획 개정은 별도 작업 단위이며 012는 의존만 기록한다. 단계별 필요: S1 ①②⑥⑦⑨, S2 ②(참고 지표)③④⑨(⑤의 오류 코드 목록 포함), S3 ②(참고 지표)⑤⑧.
- `002` 설정값: DR-03의 운영 서버 항목(호스트·GPU UUID, 예외 표시)과 DR-04 한도(실측 총 메모리 −10%)는 운영 서버 첫 접속 때 실측해 정한다(사용자 결정 2026-11-13, D2·D3). 이 첫 접속 승인이 O1~S3의 장비 쪽 시작 조건이다. 운영 개시 뒤 쓸 다른 연구 장비 목록만 사용자 입력 대기다.

## MVP 검색 기능 영향

- **012는 운영 검색 결과를 바꾸지 않는다.** 새 코드는 새 파일에만 있고 운영 `SearchService`·정책·API·마이그레이션을 import 경로로도 바꾸지 않는다. 운영 경로 삽입은 `009`의 계획·승인·검증을 따른다.
- 기존 검색 단위·계약 테스트를 수정 없이 통과해야 한다(검증 Agent 전체 검증).
- **되돌리기**: 012 코드는 새 파일이라 커밋 단위로 되돌릴 수 있다. 운영 적용 뒤 되돌리기는 이전 검색 정책으로 바꾸고 API만 재시작한다(FR-031, 설계서 15.1 7).

### 원칙

- TDD(헌법 IV): 각 Phase는 아래 사례로 테스트를 먼저 쓰고 구현 부재로 인한 assertion 실패(RED)를 확인한 뒤 최소 구현(GREEN), 정리(REFACTOR) 순서로 진행한다. 실행 Agent는 이 설계를 그대로 쓴다.
- 아래 표의 "사용자 승인 설계" 사례는 계획 승인 시 받은 Unit test 설계를 그대로 옮긴 것이다. "보조" 사례는 그 설계가 다루지 않는 구성 요소(기술자·입력 템플릿·어댑터)를 위해 더한 것이다.
- 단위 테스트는 개발 PC에서 DB·네트워크·GPU 없이 돈다. 가짜 백엔드는 (질의, 문서) 문자열에서 결정적으로 0~1 점수를 만들고, 오류·지연을 주입할 수 있다. 시간 초과는 가짜 시계로 시험한다(실제 대기 없음).
- 원문 비노출 검사는 알려진 표식 문자열을 후보 원문과 예외 메시지에 심고 결과 객체·로그 문자열에서 찾는 방식으로 한다.
- 실제 모델 테스트(G-xx)는 `gpu` 표식이며 O2에서 연구 장비(운영 개시 전에는 운영 서버)로 실행한다. 실행 Agent의 쉬운 검증에는 넣지 않는다.
- U-RMET-01은 참고 지표(R-16, 사용자 결정 2026-11-13)의 기대값이며 `002` ②가 구현한다. `002` plan의 U-MET-01~07과 헷갈리지 않게 ID를 U-RMET로 붙였다.
- U-FRZ-01~04는 실험 구조 (가)(사용자 결정 2026-11-13)의 고정 파일 사례다. U-FRZ-02·03은 012 P8이 구현·실행하고, U-FRZ-01·04는 `002` ⑨ 구현이 그대로 쓰도록 012가 기대값만 제공한다(012의 쉬운 검증 대상 아님).

- 500줄 초과 예상 Phase는 없다. P1·P4는 400줄 근처라 실행 중 초과가 보이면 멈추고 재분할을 보고한다.

- 각 Phase의 실행 Agent 쉬운 검증: `uv run ruff check src tests`와 해당 Phase의 `tests/unit/reranking` 테스트(외부 의존 없음).
- 각 Phase의 검증 Agent 전체 검증: ruff, 전체 `tests/unit`·`tests/contract`(기존 검색 테스트 무수정 통과 포함), `git diff`가 그 Phase 범위 밖 파일(특히 `application/search/service.py`·`policy.py`·`evidence.py`, `interfaces/api/`, `migrations/`)을 바꾸지 않았는지. P5는 연구 장비에서 G-REPRO-01·G-DET-01을 다시 실행한다. P5의 실행 Agent 쉬운 검증은 U-AD-01·02까지이며, P5 완료 판정은 O1(모델 반입) 뒤 O2에서 한다. 그 전에는 P5를 "코드 작성 완료, 완료 검증 대기"로 보고한다.
- 비코드 단계(O1·O2·S1~S5)도 실행 Agent와 검증 Agent를 나눈다. 검증 Agent는 quickstart의 해당 절 확인을 다시 수행한다.

```text
    ├── model_store.py            # P4 매니페스트 대조·원격 코드 금지·오프라인 로딩·반입 도구
    ├── registry.py               # P4 (reranker, 이름, 버전) → 생성 함수, 통과 모듈 포함
    ├── cross_encoder.py          # P5 KURE-nano, bge-reranker-v2-m3

tests/
├── unit/reranking/               # U-* (가짜 백엔드·토크나이저·시계)
└── server/reranking/             # G-* (gpu 표식, 연구 장비)
```

**Structure Decision**: 기존 단일 프로젝트의 계층 구조(domain → application → infrastructure → interfaces)를 따른다. 순수 규칙은 `application/search/rerank*.py` 새 파일에, 모델 의존 부분은 새 `infrastructure/reranking/` 패키지에 둔다. 기존 임베딩 매니페스트 코드는 import해 재사용하되 바꾸지 않는다(바꿔야 하면 멈추고 보고). 운영 검색·정책·API·마이그레이션 파일은 바꾸지 않는다. 레지스트리를 운영·평가 조립 지점에 연결하는 일은 `009`·`002`의 몫이다.
