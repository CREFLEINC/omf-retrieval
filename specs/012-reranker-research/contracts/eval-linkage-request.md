**상태**: 승인(사용자 2026-11-13, DR-11 권장 A). ⑨는 사용자 결정 2026-11-13(실험 구조 (가))으로 추가했다. 이 문서는 `002` 계획(기존 승인 2026-11-10)에 대한 **추가 변경 요청서**다. 012 작업은 `002` 문서·코드를 바꾸지 않았다. `002` 계획 개정(계획 보고와 승인 절차)은 별도 작업 단위로 하며 012는 의존만 기록한다. 개정이 반영되면 `002`의 계약 문서(`private-evaluation-path.md`, `eval-cli.md`, `data-model.md`)가 정본이 된다. 모든 항목은 기존 동작을 바꾸지 않는 추가(additive)다. **`002` 반영(2026-11-16)**: ①~⑧은 `002` 계획 개정(DR-26~DR-28, R-18~R-21, 사용자 승인 2026-11-16)에 반영되어 그쪽 계약이 정본이다. ④는 사용자 결정 2026-11-16으로 바뀐 점(리랭커 교체 건 포함, 시험셋 세대별 횟수, H-1 확정)을 아래에 맞춰 적었다. ⑨는 다음 `002` 개정 단위다.

## ① 근거 묶기 전 후보 목록 반환(S1)

`EvaluationSearchPort.search` 결과에 선택 필드 `candidates[]`를 더한다(요청 인자 `include_candidates=True`일 때만, 기본은 지금과 같음).

| 필드 | 뜻 |
|---|---|
| `position` | 후보 목록 안 1부터 위치(리랭커가 있으면 리랭크 뒤 순서) |
| `chunk_id`, `parent_id`, `line_start`, `line_end`, `origins[]` | 기존 후보 좌표 |
| `keyword_rank`, `vector_rank`, `rrf_rank`, `rrf_score` | 결합 정보 |
| `rerank_score`, `rerank_rank`, `reranked` | 리랭커가 있을 때(③과 같은 값) |

최대 100개. 원문(`excerpt`)은 프로세스 안에서만 쓰고 기록에는 넣지 않는다.

## ② Recall@N(후보 목록) 진단 지표(S1)와 참고 지표(S2·S3)

- `eval_query_results`에 선택 열: `candidate_hit_position`(정답과 겹치는 첫 후보 위치 또는 NULL), `candidate_count`.
- `eval_experiment_results.metrics`에 `diagnostic.recall_at_n_candidates`(N = 5·10·20·30·50·max), `diagnostic.candidate_count`(최소·중앙값·최대). 정확 산술(`002` R-01) 표기.
- 겹침 판정은 `002` DR-11의 2·3번 규칙을 청크 단위로 쓴다.
- 관문 판정·관문 기준 해시에는 넣지 않는다.
- **참고 지표 MRR@3·nDCG@3(S2·S3, 사용자 결정 2026-11-13)**: 근거 항목 단위로 계산해 S2 오프라인 실험(⑨) 결과와 관문 시도 결과의 `metrics`에 현재·후보 값과 차이로 저장한다(이름 예: `reference.mrr_at_3`, `reference.ndcg_at_3`, 최종 이름은 `002`). 정의는 012 research.md R-16: MRR@3 = 정답 있는 질의마다 상위 3개 근거 항목 중 첫 적중 순위의 역수(3위 안 적중이 없으면 0)의 평균. nDCG@3 = 이진 관련도 DCG@3 ÷ 이상적 DCG@3. DCG@3은 순위 r(1~3)의 근거 항목이 아직 적중하지 않은 정답 위치와 겹치면 이득 1, 할인 1/log2(r+1)을 곱해 더한다. 정답 위치 하나는 한 번만 센다(근거 항목 하나가 여러 정답과 겹쳐도 아직 적중하지 않은 첫 정답 하나에만 센다). 이상적 DCG@3 = 1위부터 min(정답 위치 수, 3)개 순위의 할인 합. 적중 판정은 `002` 겹침 규칙(`002` FR-011·DR-11)이고, 근거 묶기 뒤 근거 항목 단위(Recall@5와 같음)로 계산한다. 문서에 없는 질의는 분모에서 뺀다. 관련도는 이진이다(`002` `relevance_level`은 `default`만). 정답 있는 질의가 0개면 값 대신 `not_applicable`을 기록한다. 관문 판정·관문 기준 해시·후보 선정에는 쓰지 않는다. 산술은 MRR@3 분수(`002` R-01), nDCG@3은 배정밀도 부동소수점 + 10진 표기와 정밀도 기록(제안, 최종 방식은 `002`). 기대값은 012 plan U-RMET-01. 담당 `002`.

## ③ 리랭크 기록(S2 오프라인 실험, S3)

- `eval_query_results.evidence`의 일치 조각에 `rerank_score`, `rerank_rank`, `reranked`.
- 질의별 `rerank_ms`, `rerank_status`(012 data-model 7절 값).
- 결정성 비교(012 DR-03)의 점수 차이는 1·2회차 기록으로 계산한다.

## ④ 확인 개발셋(S2 끝)

- 개발셋에 역할 `exploration`·`holdout`(만들 때 지정, 불변).
- `holdout` 개발셋 실험(파일 B 오프라인 실험)은 목적 `holdout_check`만 허용한다. 탐색 목적 실험에 파일 B를 쓰면 거부(제안 코드 `holdout_not_allowed`).
- 확인 횟수는 관문 시도 차수와 따로 세며 트랙별(리랭커 교체 건 `swap-reranker-*` 포함)로 시험셋 세대마다 3회까지 허용한다(새 세대에서 0부터, 이전 세대에 만들어져 아직 소진되지 않은 확인도 대조 키(파일 B SHA-256 포함)가 맞으면 새 세대 관문 시도에 쓸 수 있고, 새 세대 횟수에 다시 더하지 않음[결정 2026-11-16], 세대별로 세는 것은 `002` DR-28 확정, 사용자 결정 2026-11-16). 4회째부터는 사용자 승인 참조가 있어야 하고, 없으면 사전 점검 거부(제안 코드 `holdout_check_limit_exceeded`, 시도로 세지 않음).
- 관문 시도 사전 점검은 그 시도에 보내는 후보의 미연결 확인 실험 기록을 찾는다. 대조 키는 FR-025 세 식별값과 확인에 쓴 파일 B의 SHA-256이다(G-1). 색인이 바뀌어 파일 B를 다시 만들면 이전 확인 기록은 맞지 않는다. 맞는 기록이 없으면 거부(제안 코드 `gate_without_holdout_check`, 시도로 세지 않음).
- 확인 기록과 관문 시도는 1:1이다(사용자 결정 2026-11-13 G-2 (가)). 사전 점검이 기록을 찾으면 그 시점에 연결해 소진하고(`consumed_at`, 한 번만), 그 뒤 판정 없이 끝나도 시도 차수는 쓰지 않지만 기록은 소진된다. 이미 연결된 기록을 다시 쓰면 거부(제안 코드 `holdout_check_already_used`, 시도로 세지 않음). 같은 후보로 다시 시도하려면 새 확인(3회 중 1회)이 필요하다.
- **H-1 확정(`002` DR-28, 사용자 결정 2026-11-16 (b))**: 확인 기록은 관문 시도 요청이 사전 점검 ① 실행 자원(허용 목록·GPU UUID·운영 개시 전 예외 표시)·② 평가 DB 확인을 통과한 직후, 다른 사전 점검(시험셋 규모, GPU 메모리 한도, 측정 run 등)보다 먼저 연결·소진된다(`002` 사전 점검 2a). ①·②에서 거부되면 소진되지 않는다. 그 뒤 어느 사전 점검이 실패해도 소진은 같다. 012 plan U-FRZ-04는 이 규칙을 따른다.
- 이전 안의 `holdout_already_used`(같은 관문 시도 차수의 두 번째 사용 거부)는 쓰지 않고 위 `holdout_check_already_used`로 바꾼다. 코드 이름 확정은 `002` ⑨·④ 개정에서 한다(사용자 결정 2026-11-13 F-4 (1)·G-2 (가)).
- 012 DR-14가 다른 안으로 승인되면 이 규칙도 따라 바뀐다.

## ⑤ 평가 경로의 리랭커 준비·오류(S3. 오류 코드 목록은 ⑨ 오프라인 실험에도 씀)

- `prepare`가 후보 정책의 리랭커 기술자로 012 레지스트리에서 리랭커를 만든다(설계서 D-08, spec 012 FR-009a). 여러 모델을 올리는 일은 평가 실행기에서만 한다.
- 새 오류 코드(대체 없음, D-06)는 [reranker-module.md](./reranker-module.md) 5.1절 정본 목록 10개다. 준비 단계 7개(`reranker_not_registered`, `reranker_model_not_approved`, `reranker_role_not_allowed`, `reranker_model_not_prepared`, `reranker_model_integrity_failed`, `reranker_remote_code_refused`, `reranker_settings_invalid`)는 실험 행 없이 끝나고 시도로 세지 않는다. 질의 단계 3개(`rerank_failed`, `rerank_timeout`, `rerank_contract_violation`)는 실험 `failed`다.
- 이 연결은 `009`의 정책 새 형식과 검색 경로 안 리랭커 위치가 생긴 뒤에 한다(S3에 필요). S2 오프라인 실험(⑨)은 이 연결 없이 리랭커 기술자로 같은 레지스트리에서 리랭커를 만들고 같은 오류 코드 목록을 쓴다.

## ⑥ 문서에 없는 질의 합성과 의도별 배분(S1)

- `eval dev synthesize`에 모드 `no_answer`: 원본 자료 스냅숏의 제목 목록만 내부 모델 서버(Kanana)에 주고 범위 밖 MES 주제 질문을 만들게 한다. 정답 구분 "정답 없음", 출처 구분 "합성".
- 현재 구성의 검색 결과로 거르지 않는다(현재 구성에 유리한 편향 방지). 연구자가 무작위 20개를 읽어 실제로 문서에 없는 비율을 기록한다.
- 합성 요청이 의도별 목표 수(무엇·왜·어떻게)를 인자로 받는다.

## ⑦ 단일 구성 진단(S1)

현재·후보 자리에 같은 구성을 넣은 개발셋 실험을 허용하거나(사전 점검이 같은 구성을 거부하지 않음을 명시), 별도 단일 구성 진단 실행을 둔다. 권장은 전자(새 명령 없음).

## ⑧ 정책만 다른 후보의 재색인 측정 공유(S3)

두 구성의 run이 같으면 같은 콜드 빌드 측정 run 하나를 양쪽에 쓰도록 허용한다. 리랭커 후보는 색인을 바꾸지 않으므로 재색인 시간이 같다. 측정 run 자체는 여전히 필요하다(`002` DR-14).

## ⑨ 후보 목록 고정 파일 생성과 오프라인 실험 실행(S1·S2, 사용자 결정 2026-11-13)

- **생성(S1)**: 현재 구성 run·현재 정책으로 탐색·확인 개발셋 검색을 한 번 돌려(①의 후보 목록 사용) 파일 A·B를 만든다. 내용은 012 data-model 14절(질의 레코드, 후보의 원문·제목 계층·상위 절 본문·좌표·lane 순위·RRF 순위·점수, 정답 좌표, S1 근거 항목). 파일 식별값 4개(색인 run id, 정책 `config_hash`, 개발셋 스냅숏 id, 파일 SHA-256)를 실험 기록에 남긴다. 원문은 연구 장비 파일에만 있고 DB 기록에는 넣지 않는다.
- **오프라인 실행(S2)**: 실험 요청이 파일 식별값 4개와 후보 구성(리랭커 기술자 설정 원문, 후보 깊이)을 받는다. 검색을 실행하지 않고 색인 DB를 읽지 않는다. 012 레지스트리로 리랭커를 만들고 012 P8 함수로 레코드를 리랭크 입력으로 바꾼 뒤, 근거 항목은 운영·평가 경로와 같은 순수 묶기 함수로 다시 계산해 ③ 형식으로 기록한다.
- **거부**: 파일 식별값이 하나라도 다르면 고정 코드(제안 `frozen_candidates_identity_mismatch`)로 거부하고 실험 행·결과를 남기지 않는다. 파일 B 사용 제한(확인 횟수 시험셋 세대마다 3회, 관문 앞 확인)은 ④.
- **기대값**: 012 plan U-FRZ-01(식별값 대조)·U-FRZ-04(파일 B 사용 제한·확인 횟수·관문 앞 확인)를 이 항목 구현의 테스트로 쓴다.
- **다시 만들기**: 색인이 바뀔 때만(예: `006` 새 형식 run). 새 파일은 새 식별값을 가진다.
- **식별(spec 012 FR-025·SC-007 개정, 사용자 결정 2026-11-13, C-15 (1))**: 오프라인 실험 기록마다 세 식별값(고정 파일 식별값의 현재 정책 `config_hash`, 리랭커 기술자 설정 원문·해시, 후보 깊이)을 필수로 남긴다. 하나라도 빠진 요청은 거부한다. 관문 시도 정책은 시도 전에 `eval policy register`로 불변 등록한다.
