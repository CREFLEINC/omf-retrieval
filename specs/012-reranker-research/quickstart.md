# Quickstart: 리랭커 연구 검증 안내(spec 012)

**작성일**: 2026-11-12 | **상태**: 초안(2026-11-13 갱신). 각 절의 시작 조건은 [plan.md](./plan.md) `단계 구분`과 같다. 아직 없는 명령·파일은 "(구현 뒤)"로 표시했다. `[DR-xx]`는 승인된 결정(사용자 2026-11-13)에 의존한다는 표시다. 연구 장비는 운영 개시 전까지 운영 서버이고(DR-12), 실험 구조는 (가)(후보 목록 고정 파일, 사용자 결정 2026-11-13)다.

## 4. S1 개발셋·후보 고정·Recall@N 첫 측정 — 운영 서버(운영 개시 전 예외) + 평가 DB(조건: `002` 구현, DR-11 ①②⑥⑦⑨, 운영 서버 첫 접속·예외 표시 등록)

구분: 연구 준비 + 연구 평가(관문 아님). 내부 모델 서버는 합성 호출에만 쓴다. 서버 작업마다 배포 하네스 승인을 받는다.

순서(`002` quickstart 6절을 따름):

1. 평가 DB(운영 DB와 다른 컨테이너·포트·볼륨) 마이그레이션, OMF 고정 commit 원본 자료 스냅숏, 현재 구성 run(평가 DB 재구성).
2. 개발셋 2개 생성: 탐색(정답 있음 1,000·문서에 없음 100), 확인(500·50). 확인 개발셋 역할 `holdout`(DR-11 ④).
3. 두 셋의 정규화 질의문 겹침 0건 확인, 겹치면 확인 개발셋에서 제거(R-08).
4. **후보 목록 고정**: 현재 구성 run·현재 정책으로 두 개발셋 검색을 한 번만 돌려 고정 파일 A(탐색)·B(확인)를 `/home/phoebe-deploy/experiments` 아래에 만들고 파일 식별값 4개를 기록한다(DR-11 ⑨, data-model 14절).
5. 파일 A로 현재 구성 진단 실험(DR-11 ⑦ 방식) → `diagnostic.recall_at_n_candidates`. 이 실험 기록의 색인 쪽 필수 검사 결과는 S2 첫 단계(C-14)에서 읽는다.
6. 개선 목표 재설정: G로 max(+3%p, G × 30%)를 계산해(임시 +5%p 대체, 세 지표 공통) 계산 근거와 함께 사용자에게 보고하고 확인받는다(R-17, 사용자 결정 2026-11-16).

| 확인 | 기대 결과 |
|---|---|
| 개발셋 규모 | 탐색 정답 있음 1,000(의도별 약 333)·문서에 없음 100, 확인 500(약 167)·50. 부족하면 추가 합성 |
| 합성 경계 | 합성 호출 호스트가 `192.168.1.167:8000`뿐, 합성물은 `eval_` 테이블에만(`002` H-10 관례) |
| 평가 DB 분리 | 평가 DB가 운영 DB와 다른 컨테이너·포트·볼륨, 평가 설정에 운영 DB 주소를 넣으면 시작 거부 |
| 고정 파일 | 파일 A 1,100질의·파일 B 550질의 레코드, 질의마다 후보 0~100개, 파일 식별값 4개 기록, 두 파일 모두 연구용 디렉터리 안 |
| 첫 측정 출력 | 파일 A에서 N = 5·10·20·30·50·max 값, 후보 수 분포, 근거 항목 단위 Recall@5 |
| 진행 판단 | 상한 차이 G < 3%p면 사용자에게 지속 여부를 묻는 보고 작성(plan `진행 판단 규칙` 1, C-01은 그때 결정) |
| 개선 목표 | 목표 값·근거(`g_based`, G 값) 기록과 사용자 확인 요청. 예: G = 18%p → +5.4%p, G = 8%p → +3%p. G 계산 불가면 +5%p 유지와 `g_not_computable` 표시 |
| 비교값 | DR-05 규칙 계산표(아래 예시 형식) |
| 실행 자원 | 실험 기록 `resource_name` "운영 서버(운영 개시 전 예외)" |

계산 예시(DR-05): Recall@5·10·20·30·50·최대 = 0.62·0.70·0.76·0.78·0.80·0.81 → G = 0.19 → 0.5G 도달 20, 0.8G 도달 30, 0.95G 도달 최대 → 비교값 {20, 30, 최대}.

## 5. S2 후보 비교(오프라인) — 운영 서버(운영 개시 전 예외) GPU, 고정 파일만(조건: S1 "지속", 고정 파일 A·B, DR-11 ③④⑨, S0·O1·O2. `009`·`006`을 기다리지 않음)

구분: 연구 평가(관문 아님). 모든 실험은 고정 파일만 읽는 오프라인 실험이며 검색을 실행하지 않고 색인 DB를 읽지 않는다.

1. S1 첫 측정 실험 기록에서 현재 run의 색인 쪽 검사(4종+색인 결정성) 결과를 점검하고 위반이 있으면 보고한다(C-14 (가)).
2. 후보 구성마다 리랭커 기술자(DR-01 설정 원문·해시)와 후보 깊이를 정하고 파일 A 식별값을 실험 요청에 적는다. 정책 불변 등록은 S3 준비에서 관문 시도 정책(최종 후보)만 한다(spec FR-025 개정, 사용자 결정 2026-11-13, C-15 (1)).
3. 선별 4 → 격자 18 → instruction 2 → 상한 참고 1(R-07). 각 실험은 파일 A 오프라인 실험(`002` ⑨ 방식, 명령 이름은 `002` 개정에서 정함).
4. 최종 후보 선택, 같은 장비·같은 파일 A 두 실행 결정성 확인[DR-03], 리랭크 시간 p99 사전 점검[DR-02].
5. 확인 개발셋 실험(파일 B): 관문 시도에 보낼 후보로 1회. 확인 하나는 관문 시도 하나에만 쓰며, 같은 후보로 다시 시도하려면 새 확인을 한다. 확인 횟수는 관문 시도와 따로 세어 시험셋 세대마다 3회까지(새 세대에서 0부터), 4회째부터 사용자 승인[DR-14, 사용자 결정 2026-11-13 F-4 (1)·G-2 (가), 2026-11-16]. 확인 실험 요청에 `--test-set`(관문 시도할 시험셋)을 적는다. 관문 요청이 사전 점검 ① 실행 자원·② 평가 DB를 통과하면 그 뒤 거부돼도 확인은 소진되므로, 규모·측정 run·GPU 한도를 먼저 확인한 뒤 요청한다(`002` DR-28).

| 평가 경로 대체 없음 | 리랭커 오류가 난 실험은 `failed`, RRF 결과 기록 0건(SC-005 평가 쪽) |
| `no_evidence` 집합 | 같은 파일에서 현재·후보 구성의 `no_evidence` 질의 집합 차이 0건(SC-003). 빈 후보 레코드는 `skipped_no_candidates` |
| 깊이 비교 | 비교값 3개 각각의 지표·비용 기록 존재(SC-010) |
| 참고 지표 | 탐색·확인 실험 기록마다 MRR@3·nDCG@3의 현재·후보 값과 차이가 있음(정답 있는 질의 0개면 `not_applicable`). 선정 근거 설명에 참고 지표를 쓰지 않음(R-16) |
| 목표 달성 | S2 요약과 확인 실험 기록에 Recall@5·MRR@3·nDCG@3별 차이(%p)·목표·달성/미달이 있음. 선정 근거에 목표 달성 여부를 쓰지 않음 |
| 튜닝 데이터 | 선정 근거 실험이 모두 파일 A(탐색 개발셋)(SC-006). 시험셋 사용 0건 |
| 시간 초과 사전 점검 | 최종 후보 리랭크 시간 p99(운영 서버 실측) 기록, 400ms 초과면 사용자 보고 |
| 확인 개발셋 | 확인 기록마다 확인 횟수가 있고 승인 없는 4회째 확인 0건, 탐색 목적의 파일 B 사용 0건(U-FRZ-04), DR-14 조건이면 사용자 보고 |

## 6. S3 관문 시도 — 운영 서버(운영 개시 전 예외) + 평가 DB(조건: 시험셋 400+ 등, `002` DR-04 한도, `009`·`006`, DR-11 ⑤, 콜드 빌드 측정 또는 DR-11 ⑧)

구분: 연구 평가(관문). 실제 검색 경로 전체 + 리랭커로 시험셋에서 실행한다.

준비: 최종 후보 정책을 현재 정책 복사 + 리랭커 기술자·후보 깊이로 만들어 `eval policy register`로 불변 등록한다(R-06). S1 뒤 색인이 바뀌었으면 고정 파일을 다시 만들고 Recall@N을 다시 재며 새 파일 A로 최종 후보를 다시 확인한다(C-05).

```bash
uv run omf-retrieval eval gate attempt --spec gate.json --track track-2-reranker --actor A   # (002 구현 뒤)
```

| 확인 | 기대 결과 |
|---|---|
| 사전 점검 | 시험셋 규모·GPU 메모리 한도(첫 접속 실측 −10%)·측정 run이 없으면 거부(시도로 안 셈) |
| 관문 앞 확인 | 관문 시도마다 보내는 후보(FR-025 세 식별값 + 지금 파일 B SHA-256이 같음)의 미연결 확인 기록 1건이 연결되어 있음. 확인 없는 시도 0건, 한 확인 기록이 두 시도에 연결된 경우 0건(U-FRZ-04) |
| 참고 지표 | 관문 시도 보고에 MRR@3·nDCG@3 현재·후보 값이 있고, 판정 사유에는 들어가지 않음(R-16) |
| 목표 달성 | 관문 보고에 지표별 달성/미달이 있고 판정에 영향 없음. "적용 권고"이면서 미달이면 "목표 미달" 기록(미세 조정 재검토 입력) |
| 정책 등록 | 관문 시도에 쓴 후보 정책이 시도 전에 `eval policy register`로 등록되어 있고 기록이 그 식별값을 참조함. 미등록 정책 평가 0건(spec FR-025·SC-007) |
| 판정 | 세 판정 중 하나, 조건별 사유, 시도 차수, 남은 횟수(SC-001) |
| 한도 | 트랙 ② 네 번째 시도 거부 |
| 시간 초과 한도 | 첫 시도 전 DR-02 사전 점검 기록(리랭크 시간 p99 실측 대 한도) |
| 시험셋 사용 | 시험셋은 이 관문 시도에만 쓰임. 불합격 뒤 원인 분석은 개발셋으로만 하고 시험셋은 조건별 수치·사유만 봄(plan `진행 판단 규칙` 6, 승인 사용자 2026-11-13). 012 트랙의 시험셋 질의별 내보내기 0건 |

## 7. S4 운영 적용 전 확인 — 운영 서버의 운영 구성(조건: "적용 권고" + 사용자 승인, `009` 계획·O-13)

구분: 운영 적용 전 확인(연구 평가 아님). 운영 개시 전 예외로 하는 일이 아니며, 같은 운영 서버를 쓰더라도 연구 평가 기록과 따로 기록한다(`002` FR-033, 사용자 결정 2026-11-13). 배포 실행은 `AGENTS.md` 배포 하네스를 따른다.

| 확인 | 기대 결과 |
|---|---|
| 정책 | 관문을 통과한 정책 `config_hash` 그대로(값 변경 없음) |
| 모델 | 최종 후보 1개만 운영 반입, 매니페스트 대조 통과 |

## 8. S5 연구 결과 요약 점검(SC-011)

연구 결과 요약은 `crefle-doc`으로 작성한다(작성자·작성일시·버전·열람 대상을 사용자에게 확인). 검토자는 요약만 읽고 plan `정성 평가 기준`의 다섯 질문에 답할 수 있는지 판정한다.

| 확인 | 기대 결과 |
|---|---|
| 산출물(FR-003) | 실험 기록 id 목록, 최종 후보 정책 `config_hash`, 구현 위치, 후보 깊이 값과 근거, 결정성 기준, 요약 |

| 공개 벤치마크 | 재현 결과는 참고로만, 선정 근거로 쓰지 않았음이 명시됨 |
