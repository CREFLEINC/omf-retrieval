# Research: 문서 자료 등록·원본 보관·불변 revision·권한·스키마 사전(data-registration)

**작성일**: 2026-11-09 | **개정**: 2026-11-09(독립 검증 FAIL 지적 M-1~M-6, L-1~L-6 반영), 2026-11-10(DR-04 안전 상한 수치·xlsx ZIP 경계 승인, 같은 바이트 파일 이름 대응 참고, 의존성·DR 승인 상태 문구 갱신) | **입력**: [spec.md](./spec.md), [plan.md](./plan.md) | **상태**: 결정 요청 DR-01~DR-24 전부 사용자 승인(2026-11-10). 대안 표는 검토 기록으로 남긴다.

## 2. 계획이 채택한 기술 판단(새 의존성 없음)

아래는 새 의존성·서비스 경계·데이터 모델 정책을 바꾸지 않는 구현 판단이다. 계획 승인 때 함께 검토받는다. 이전 초안의 R-01(계약 형식)·R-02(같은 앱 안 실행 구조)·R-03(권한 저장 구조)은 외부 API 계약·서비스 경계·데이터 모델 정책에 해당하므로 결정 요청 DR-20·DR-21·DR-22로 옮겼다(번호는 결번으로 둔다).

### R-04 판정 순서(결정적)

- **판단**: 등록 요청은 아래 순서로 판정하고, 앞 단계에서 거부되면 뒤 단계 사유는 나오지 않는다. 같은 단계 안에서 여러 파트가 어긋나면 **요청 안 `file` 파트 순서(0부터) → `info` 파트** 순으로 첫 위반의 사유를 낸다.

| 단계 | 판정 | 필요 정보 | 거부 코드 |
|---|---|---|---|
| ① | Bearer 인증 | 헤더 | `invalid_token`(401) |
| ② | `source` 질의 매개변수 존재(빈 문자열 포함 없음으로 봄) | 질의 | `source_required` |
| ③ | REST 등록 대상 source + 활성 쓰기 권한 | 질의, DB | `write_access_denied` |
| ④ | `material_id` 규칙 | 질의 | `invalid_material_id` |
| ⑤ | `schema_id` 규칙(매개변수가 있을 때, 빈 문자열 포함) | 질의 | `invalid_schema_id` |
| ⑥ | 본문 수신과 크기 계수, multipart 해석 | 본문 | `file_too_large`, 해석 불가는 `invalid_request_composition` |
| ⑦ 구성 1차 | 파트 개수·이름만 판정(아래 표 A) | 파트 목록 | `invalid_request_composition` |
| ⑧ 형식·내용 | `file` 파트마다 빈 파일 → 서명 판정 → 선언 대조 → (xlsx) 용기·항목 수·패키지 판정 → 손상·암호(순서는 아래 `file` 파트별 확인 순서), 그다음 `info` 파트(빈 정보 자료 판정 → 형식 판정) | 파일 바이트 | `unsupported_file_format`, `unreadable_content`, `info_material_missing`(빈 `info`), `invalid_info_material_format` |
| ⑨ 구성 2차 | 형식 판정 결과로 정보 자료 필요 여부·대상 파일 종류 판정(아래 표 B) | 형식 판정 결과 | `info_material_missing`, `invalid_request_composition` |
| ⑩ | 텍스트·Markdown 단일 파일의 스키마 지정 금지 | ⑧ 결과, 질의·파트 | `text_schema_not_allowed` |
| ⑪ | 스키마 입력 표(FR-012), 구조 검증, 예약 접두사, 충돌 | 스키마 파트, 사전 | `schema_missing`, `invalid_schema_id`, `incomplete_schema`, `schema_id_conflict` |
| ⑫ | 스키마 맞음 판정 | ⑧의 구조 값 | `schema_mismatch` |
| ⑬ | 저장(트랜잭션) | — | 내부 실패 `registration_unavailable`(503) |

- **표 A(구성 1차, 내용 불필요)**: `file` 파트 0개, `info` 파트 2개 이상, 알 수 없는 파트 이름, 255자를 넘는 파트 파일 이름, `info` 없이 `file` 2개 이상, `info`와 함께 `file` 21개 이상, `info` 없이 `info_human_authored`만 있음, `schema`·`info_human_authored` 파트 2개 이상 → 모두 `invalid_request_composition`.
- **⑧의 `file` 파트별 확인 순서**(사용자 승인 2026-11-10, DR-03·DR-04. 세부 순서·CFB 규칙 사용자 승인 2026-11-10): 각 `file` 파트를 아래 순서로 확인하고 첫 위반의 사유를 낸다. 기존 "형식 판정 → 선언 대조 → 손상" 순서를 세분한 것이다. 확인 시간 상한(30초)은 모든 단계에 걸쳐 적용한다.
  1. 빈 파일: 0바이트 → `unreadable_content`(FR-005).
  2. 서명 판정: 앞부분 바이트로 형식 계열을 정한다(ZIP 서명 `PK\x03\x04`, CFB, `%PDF-`, PNG는 8바이트 서명 + 첫 청크 IHDR, JPEG는 SOI `FF D8`, UTF-8 텍스트). 형식 계열은 이 나열 순서대로 확인하고 처음 맞는 계열로 정한다(예: `%PDF-`로 시작하는 압축 없는 ASCII PDF는 올바른 UTF-8이어도 PDF다). 어느 것도 아니면 `unsupported_file_format`. PNG 서명 뒤 첫 청크가 IHDR가 아니면 PNG로 판정하지 않는다(`unsupported_file_format`). 끝 표지(PNG IEND, JPEG EOI)는 여기서 보지 않는다.
  3. 선언 대조: 선언(확장자·Content-Type)과 서명 계열이 맞지 않으면 `unsupported_file_format`. 예: ZIP 서명인데 선언이 `.zip`·`.png`면 여기서 끝난다. 선언이 `.xlsx`인데 CFB면 암호화 패키지(`EncryptionInfo`·`EncryptedPackage` 스트림)일 때만 `unreadable_content`이고 그 밖(`.xls` 등)은 `unsupported_file_format`.
  4. 용기 해석(선언 xlsx + ZIP 서명만): 중앙 디렉터리를 읽을 수 없으면 `unreadable_content`.
  5. 항목 수 상한: 중앙 디렉터리의 항목 수로, 어떤 항목도 풀기 전에 판정한다. 10,000개 초과 → `unreadable_content`. 따라서 `.xlsx`로 선언한 OOXML 아닌 일반 ZIP이 항목 10,001개면 6단계에 가기 전에 `unreadable_content`다.
  6. 패키지 판정(OOXML): `[Content_Types].xml`의 workbook 주 파트 선언과 `xl/workbook.xml`을 확인한다. 없으면 `unsupported_file_format`. 이 단계부터 항목을 풀며, 풀 때마다 압축 해제 총량·항목별 비율 상한을 실제로 센 바이트로 판정한다(초과 → 즉시 중단, `unreadable_content`).
  7. 손상·구조 확인(모든 형식): xlsx는 시트 XML, drawing 관계 등(총량·비율 계수는 계속된다). PNG는 필수 청크와 끝 표지 IEND, JPEG는 끝 표지 EOI `FF D9`. 없거나 깨졌으면 `unreadable_content`. 예: IEND 없는 PNG, EOI 없는 JPEG → `unreadable_content`(형식 사유가 아님).
  - PDF는 2단계 `%PDF-`와 선언 `.pdf`가 맞은 뒤 페이지 트리 해석 실패·암호 → `unreadable_content`, 페이지 트리의 페이지 수가 2,000 초과면 페이지별 확인 전에 `unreadable_content`. 잘린 `.pdf`는 xlsx ZIP 경계가 아니라 이 PDF 규칙을 따른다.
- **⑧의 `info` 파트 규칙**(US5-4, FR-018): `file` 파트를 모두 확인한 뒤 `info` 파트를 다음 순서로 판정한다. ⑧-i `info`가 0바이트이거나, UTF-8로 해석되고 BOM을 뺀 내용이 공백 문자(유니코드 공백·줄바꿈)뿐이면 `info_material_missing`. 이 경우는 FR-005의 빈 파일(`unreadable_content`)의 예외다. ⑧-ii 그 밖에 형식 판정 결과가 `text`·`markdown`이 아니면(다른 허용 형식, 알 수 없는 형식, UTF-8 해석 실패, 손상 모두) `invalid_info_material_format`.
- **표 B(구성 2차, 형식 판정 결과 사용)**, 위에서부터 첫 해당 행:

| 순서 | 조건 | 결과 |
|---|---|---|

- **프레임워크 선언 검증과의 관계**: 새 경로는 매개변수와 multipart 필드를 문자열·문자열 목록·원시 요청으로만 받고 pattern·길이·개수·필수 여부를 선언하지 않는다. 그래서 기존 `app.py`의 `RequestValidationError` → 422 `invalid_request` 처리기는 새 경로에서 ①보다 먼저 실행될 일이 없다. 규칙 검증은 모두 핸들러 안에서 위 순서로 한다. 기존 처리기와 `/v1/search`의 422 동작은 바꾸지 않는다. 계약 파일에도 같은 형태로 적었다(DR-05 의존).

### R-05 원자성·동시성

- **판단**: 한 등록 요청은 DB 트랜잭션 하나에서 스키마 등록, revision·파일·원본 바이트·관계·등록 기록 저장, 현재본 갱신을 함께 커밋한다. 같은 (source, 자료 ID)는 트랜잭션 범위 advisory lock으로 직렬화하고, 새 스키마 ID는 PRIMARY KEY 충돌 후 내용 비교로 판정한다.
- **근거**: FR-007, Edge Case(동시 등록, 동시 스키마 등록, 전송 중단, 저장 공간 부족). 기존 색인 파이프라인의 advisory lock 관례를 재사용한다. DR-01은 A(PostgreSQL `bytea`)로 승인되었다. 나중에 B·C로 바꾸면 2단계 쓰기로 바뀐다.

### R-06 revision 동일성 판정(FR-038)

- **판단**: revision마다 `manifest_hash = SHA-256(canonical JSON{파일마다 (역할, 형식 판정 결과, 내용 해시), 묶음 연결, 스키마 ID})`를 저장한다. 같은 자료 ID의 **현재본** `manifest_hash`와 같을 때만 기존 revision을 돌려준다. 파일 이름은 넣지 않는다(FR-024). 묶음 대상 파일은 (형식 판정 결과, 내용 해시) 순으로 정렬해 제출 순서와 무관하게 한다(DR-15). 형식 판정 결과를 넣으므로 같은 바이트라도 `text`와 `markdown`으로 판정되면 다른 revision이다(DR-23).
- **근거**: Edge Case "같은 파일이라도 스키마가 다르면 같은 내용이 아니다". 형식 판정 결과는 이후 파서 선택(설계서 6.1 파서 입력 "형식")을 바꾸므로 revision의 불변 내용에 포함해야 재현된다. 기존 `hashing.canonical_json`·`config_hash`를 재사용한다.

### R-07 원본 되찾기 응답

- **판단**: 파일 본문은 항상 `application/octet-stream`, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment; filename*=UTF-8''<RFC 5987 인코딩>`로 돌려준다. `X-Content-SHA256` 헤더에 내용 해시를 싣는다.
- **근거**: 등록자가 보낸 이름·내용을 브라우저가 해석해 실행하지 않게 한다(Edge Case: 파일 이름 경로 문자, 매크로 미실행). 헤더 주입을 막으려면 이름을 그대로 넣지 않고 인코딩한다. 이 헤더는 원본 읽기 권한 경로에만 있다.

### R-08 거부 운영 기록

- **판단**: 거부는 DB에 남기지 않고 구조화 애플리케이션 로그 한 줄(`request_id`, 호출자 `key_id`(인증 성공 시), 사유 코드, 시각)로만 남긴다. 파일 이름·자료 ID·스키마 내용·토큰은 남기지 않는다.
- **근거**: FR-007, FR-034. 보관 위치·기간은 DR-17.

### R-09 등록 경로는 LLM·외부 호출을 하지 않는다

- **판단**: 등록 경로는 내부 모델 서버를 포함한 어떤 네트워크 서비스도 호출하지 않는다. 내용 확인기는 결정적 프로그램이며 OCR을 하지 않는다. 스키마 맞음 판정을 위해 시트 이름·스키마가 지정한 셀 값·정보 자료의 제목 줄을 읽어 비교하지만, 그 값을 저장·색인·응답·로그에 남기지 않는다. 문서 전체 글자 추출과 청킹은 하지 않는다.
- **근거**: 헌법 VI·VII, FR-013, FR-017, FR-033, FR-034, spec Out of Scope(`003`).

### R-10 내용 확인기 버전 기록

- **판단**: revision에 `inspector_version`(내용 확인기 동작 버전 문자열)을 기록한다. 색인 식별값에는 넣지 않는다.
- **근거**: 형식 판정 결과, 포함 이미지 관계 정보, 글자 층 판정은 확인기 동작에 따라 달라지므로 등록 기록의 재현 좌표가 필요하다. 설계서 5절의 모듈 6종에는 등록 시점 확인기가 없고, 확인기 결과는 청크·벡터를 직접 바꾸지 않는다. 다만 형식 판정 결과는 파서 입력이 되므로 revision 내용(R-06)에 들어간다. 설계서와의 관계는 [plan.md](./plan.md) `설계서 정합` 절.

### R-11 응답 필드의 원본 내용 비노출

- **판단**: 원본 읽기 권한이 필요 없는 응답(등록 결과, 거부 응답, 스키마 조회, 현재본 조회)에는 파일 안에서 읽은 값(시트 이름, 셀 값, 문서 제목, 정보 자료 문장, 글자)을 넣지 않는다. 위치는 PDF 페이지 번호와 Excel 시트 순번(0부터) 같은 내용 비노출 좌표로만 낸다. 원본 읽기 권한 경로(등록 기록·원본 파일)만 등록자가 제출한 파일 이름을 돌려준다. 거부 `detail.schema_mismatch_part`는 고정 키 이름과 배열 위치 번호만 쓰고(예 `mapping.entities[2].attributes[0].source`) 사용자가 정의한 이름·값을 넣지 않는다.
- **알려진 예외(FR-016 요구)**: 스키마 조회 응답은 등록자가 스키마에 적은 시트 이름·머리글 값·엔티티 이름을 그대로 담는다. 이 값은 원본 파일에서 읽은 것이 아니지만 원본 구조를 반영할 수 있다. FR-016·FR-031에 따라 어느 source든 쓰기 권한이 있으면 외부 LLM 사용 표시가 `외부`이거나 없는 호출자도 받는다. 001은 spec대로 두고 이 사실을 노출 점검표에 명시한다. 제한이 필요하면 spec 변경 사항이다.
- **근거**: FR-034, FR-031, 헌법 VI. 쓰기 권한만 가진 호출자(US2-6)에게 원본 내용이 새지 않아야 한다. 점검 결과는 [plan.md](./plan.md) `응답 필드 내용 노출 점검`.

## 3. 결정 요청(사용자 승인 대상, 2026-11-10 전부 승인)

모든 항목은 권장안과 대안 2~3개를 같은 표 형식(안, 내용, 비용·복잡도, 향후 변경 가능성)으로 적고, 필요 이유와 이 결정에 의존하는 계획 부분을 밝힌다. 하위 항목이 있는 DR(DR-11, DR-12)은 하위 항목마다 표를 둔다. DR-17만 예외로, 001에서 정하지 않고 운영 결정으로 넘기는 이월 목록이다. 2026-11-10 모든 DR이 승인되어 의존 Phase를 시작할 수 있다. 각 DR 머리에 승인 표시를 두고 대안 표는 검토 기록으로 남긴다.

### DR-03 허용 형식 상세

**승인(2026-11-10): 권장안.** 추가 사용자 결정: ZIP과 모든 압축 파일은 001에서 받지 않는다(아래 "추가 결정").

| 대안 3 | 텍스트에 CP949 허용, 호출자가 부호화 선언 | 중간. 선언 매개변수·판정 규칙 추가, "해석 불가" 정의가 선언에 의존 | 중간 |

**추가 결정(2026-11-10, 사용자): ZIP·압축 파일 미허용**

- `.zip`과 모든 압축 파일은 001에서 받지 않는다. 묶음 용기(이미지 여러 장을 압축해 보내기)로도, 여러 문서 일괄 등록으로도 쓰지 않는다. 거부 코드는 다른 미허용 형식과 같은 `unsupported_file_format`이다.
- 사유: 압축 폭탄(작은 파일이 거대하게 풀림), 경로 조작(`../` 같은 항목 이름), 항목마다 형식·크기·내용 확인을 반복해야 하는 판정 복잡도. 묶음은 이미 multipart 파트로 받을 수 있다.
- 판정: 실제 내용이 ZIP 서명이어도 `.xlsx` 판정 조건(OOXML workbook 파트)을 만족하지 않으면 `xlsx`가 아니며, 다른 허용 형식도 아니므로 `unsupported_file_format`이다. 이름을 `.xlsx`로 바꾼 ZIP도 같다. ZIP으로 해석조차 할 수 없는 파일과의 경계는 DR-04의 "xlsx의 ZIP 경계" 표를 따른다. 정보 자료(`info`) 파트로 온 ZIP은 ⑧-ii에 따라 `invalid_info_material_format`이다.
- 여러 문서 일괄 등록은 향후 기능 후보로 남긴다(001 범위 밖, 별도 명세와 승인 필요).
- 테스트: U-INSP-01(ZIP·7z·tar.gz·`.xlsx`로 이름만 바꾼 ZIP → `unsupported_file_format`), C-API-02(ZIP 단일 등록 → 415 `unsupported_file_format`), R-04 예시 표.

**공통 안전 조건(사용자 승인 2026-11-10: 권장 수치)**: 내용 확인기는 아래 상한을 설정값으로 두고, 상한을 넘으면 `unreadable_content`로 거부한다. 상한과 같은 값은 통과한다(초과만 거부). 기본값은 다음과 같다.

| 상한 | 기본값 | 적용 대상 |
|---|---|---|
| 압축 해제 총량 | 파일당 512 MiB(536,870,912바이트) 이하 | xlsx의 ZIP 항목 해제 크기 합 |
| 항목별 압축 비율 | 100배 이하. 설정값은 양의 정수(1 이상)다. 판정식은 항목마다 `해제 바이트 ≤ 100 × 압축 바이트`(나눗셈 없음). 압축 0바이트 항목은 해제 0바이트일 때만 통과(빈 파트·디렉터리 항목의 0/0은 통과) | xlsx의 ZIP 항목 하나하나 |
| 파트 수 | 파일당 10,000개 이하(ZIP 항목 수) | xlsx |
| PDF 페이지 수 | 파일당 2,000쪽 이하 | PDF |
| 확인 시간 | 파일당 30초 이하 | 모든 형식 |

- 비율·총량은 ZIP 중앙 디렉터리에 적힌 크기만 믿지 않고 실제로 풀면서 센 바이트로 판정한다(풀린 양이 상한을 넘는 즉시 중단). 압축 0바이트라고 적혔는데 실제로 바이트가 풀리면 비율식 위반이자 CRC·크기 불일치로 `unreadable_content`다.
- 항목 수는 중앙 디렉터리에서 풀기 전에, 총량·비율은 푸는 동안 판정한다(판정 위치는 R-04 ⑧ `file` 파트별 확인 순서 5·6단계).
- 확인 시간: 내용 확인기는 생성 시 시각 공급원 `clock`(단조 증가 시각을 돌려주는 함수, 기본 `time.monotonic`)을 받는다. 파일 확인 시작 시각을 기록하고, ⑧ 확인 순서의 각 단계 시작, ZIP 항목 하나를 풀기 전, PDF 페이지 하나를 확인하기 전에 경과 시간을 확인해 30초를 넘으면 중단하고 `unreadable_content`를 낸다. 경과가 정확히 30초면 통과한다.
- 테스트: U-INSP-02. 상한을 작은 값으로 주입한 설정으로 각 상한의 "같으면 통과, 넘으면 거부"를 확인하고(실제 512 MiB를 풀지 않음), 기본 설정값이 위 표의 값과 같은지 따로 확인한다.

**xlsx의 ZIP 경계(사용자 승인 2026-11-10)**: 이 표는 **선언 형식이 xlsx**(`.xlsx` 확장자 또는 xlsx Content-Type)인 `file` 파트에만 적용한다. 선언이 `.zip` 등 다른 형식인 ZIP은 DR-03 규칙대로 `unsupported_file_format`이고, 잘린 `.pdf`는 PDF 규칙을 따른다. 확인 순서는 R-04 ⑧ `file` 파트별 확인 순서(4~7단계)이며 항목 수 상한(5단계)이 OOXML 패키지 판정(6단계)보다 먼저다. 형식 판정과 내용 확인 불가를 다음 세 단계로 나눈다.

| 상태 | 결과 | 예 |
|---|---|---|
| ZIP 서명(`PK\x03\x04`)으로 시작하지만 ZIP 용기로 전혀 해석할 수 없음(중앙 디렉터리 없음·잘림, 항목 헤더 손상) | `unreadable_content` | 끝이 잘린 `.xlsx` |
| ZIP으로는 해석되지만 유효한 OOXML(xlsx) 패키지가 아님(`[Content_Types].xml`의 workbook 주 파트 선언 또는 `xl/workbook.xml`이 없음) | `unsupported_file_format` | 이름만 `.xlsx`인 일반 ZIP, workbook 선언은 있으나 `xl/workbook.xml`이 없는 ZIP |
| 위 판정 조건을 갖춰 `xlsx`로 판정된 뒤 안쪽 파트가 손상(시트 XML 해석 불가, drawing 관계 끊김) | `unreadable_content` | 시트 XML이 깨진 xlsx |

ZIP 서명이 없는 알 수 없는 바이트는 `.xlsx`로 선언했어도 지금처럼 `unsupported_file_format`이다. CFB(OLE 복합 문서) 안에 암호화된 xlsx는 암호 사유로 `unreadable_content`다(U-INSP-02). 테스트: U-INSP-01(경계·실패), U-INSP-02(실패).

**추가 결정(2026-11-10, 사용자)**

- **여러 이미지는 순서 없는 집합이다.** 제출 순서를 순번으로 저장하지 않는다. `manifest_hash`는 지금처럼 (형식 판정 결과, 내용 해시)로 정렬해 제출 순서를 무시한다(R-06). `file_index`는 revision 안 파일 식별용 번호이며 제출 순서가 아니라 결정적 정렬 순서((역할, 형식 판정 결과, 내용 해시))로 매긴다. 되찾기·등록 기록 응답도 이 순서로 파일을 나열하며, 계약은 이 순서가 의미(쪽 순서 등)를 갖지 않는다고 밝힌다. 같은 바이트의 파일이 둘 이상이면 정렬 키가 같으므로 그 안에서는 요청의 multipart 파트 순서(제출 순서)로 안정 정렬해 번호를 매긴다. 제출 순서 자체는 저장하지 않으며, 이 번호 차이는 의미가 없다.
- **같은 바이트 파일의 제출 이름 대응(참고)**: 한 묶음에 바이트가 똑같은 파일이 둘 이상 있으면, 등록 기록의 제출 파일 이름(`registration_event_files.submitted_filename`) 가운데 어느 이름이 어느 `file_index`에 붙는지는 그 등록 요청의 multipart 파트 순서로 정한다(정렬 키가 같은 파일끼리의 안정 정렬). 결정적이지만 의미 없는 선택이다(위 "순서 없는 집합" 규칙의 결과). 재등록(`reused`)이면 그 요청의 파트 순서로 기존 revision의 번호에 대응시킨다. 호출자는 이 대응에 의미를 두지 않아야 한다. 파일 이름은 `manifest_hash`에 들어가지 않으므로(R-06) 이 선택은 revision 동일성 판정에 영향이 없다.
- **여러 쪽 문서는 PDF 하나로 합쳐 등록한다.** 이는 등록 안내이며 거부 규칙이 아니다(시스템은 이미지가 문서의 쪽인지 사진인지 구별할 수 없다). quickstart와 계약의 등록 설명에 적는다.
- 기각한 안(검토 기록):

| 안 | 내용 | 비용·복잡도 | 기각 사유 |
|---|---|---|---|
| 순번 보존 저장 | 제출 순서를 순번으로 저장하고 `manifest_hash`에 넣음 | 중간. 같은 이미지 집합의 순서만 다른 등록이 다른 revision이 됨 | 변수가 늘어남. 쪽 순서가 필요하면 PDF 하나로 합치는 안내로 충분 |
| 정보 자료에 쪽 대응 기록 | 사용자 제안. 정보 자료 안에 "이미지 n = n쪽" 같은 대응을 적음 | 중간 | 기계가 읽거나 검증할 수 없는 자유 서술이라 판정·재현에 쓸 수 없음. 변수를 줄이는 쪽을 택함 |

### DR-23 텍스트와 Markdown 구분(형식 판정 결과)

**승인(2026-11-10): 권장안.**

필요 이유: 설계서 6.1은 파서 입력 형식을 텍스트·PDF·Excel·Markdown으로 구분한다. 바이트만으로는 Markdown과 일반 텍스트를 결정적으로 구별할 수 없다. FR-004("이름이 아니라 실제 내용 기준")와의 관계를 정해야 한다. 의존: P4a, data-model 3.8, 계약 `detected_format`.

권장안 내용: 실제 내용으로 "UTF-8 텍스트"임을 판정한 뒤(FR-004 충족), 텍스트 안의 하위 형식은 선언으로 정한다. `.md` 확장자 또는 `text/markdown` → `markdown`, `.txt` 또는 `text/plain` → `text`. 확장자와 Content-Type이 서로 다른 텍스트 하위 형식을 가리키면 `unsupported_file_format`. 판정 결과는 revision 파일 기록과 `manifest_hash`에 들어가 불변이다(R-06). 두 하위 형식 모두 기본 스키마(`target_format: text`)를 쓴다. 이유: 파서 선택(`003`, 현재 `MarkdownItParser`)과 `006` OMF 이관이 하위 형식을 알아야 하고, 이를 등록 때 고정하지 않으면 같은 revision이 파서 구현에 따라 다르게 해석될 수 있다.

| 안 | 내용 | 비용·복잡도 | 향후 변경 가능성 |
|---|---|---|---|
| **권장** | 위 내용(내용으로 텍스트 판정 + 선언으로 하위 형식, 결과를 revision에 고정) | 낮음 | 높음. 하위 형식 추가 가능 |
| 대안 1 | 구분 없이 `text` 하나, 하위 형식은 `003`·`006`이 파일 이름으로 추정 | 가장 낮음. 같은 revision의 해석이 후속 구현에 좌우됨(설계서 6.1과 불일치) | 낮음 |
| 대안 2 | 내용 휴리스틱(제목 기호 `#` 등)으로 Markdown 판정 | 중간. 비결정적 경계 사례, 오판 시 고칠 수 없음(불변) | 낮음 |
