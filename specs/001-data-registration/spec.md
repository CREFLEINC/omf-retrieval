# Feature Specification: 문서 자료 등록·원본 보관·불변 revision·권한·스키마 사전(data-registration)

**Feature Branch**: `001-data-registration`

**Created**: 2026-11-03

**Status**: Draft

**Revised**: 2026-11-09 (2026-11-06: `AGENTS.md` 방향 개정 반영: 등록 대상을 RDB에 보관되지 않는 문서 자료로 한정, 후속 명세 번호 재배열, 호출자별 외부 LLM 사용 표시와 원본 읽기 권한 제한 추가; 2026-11-09: 평가 하네스 명세 `002` 삽입에 따라 명세 번호 참조를 한 칸씩 이동)

**Input**: User description: "RDB에 보관되지 않는 문서 자료(Excel, PDF, 이미지, 텍스트 파일. 예: MES 운영 매뉴얼, 설비 납품 계약서, 자재 발주서, 자재 납품 거래명세서)를 REST API로 등록한다. MES DB 데이터는 이 기능으로 등록하지 않는다. 자료는 스키마와 함께 등록하고, 원본은 재현 가능하게 보관하며, 등록 결과는 불변 revision으로 식별한다. 쓰기 권한은 기존 Bearer 토큰·source grant 체계와의 관계를 정의한다. 등록된 스키마는 스키마 사전에 불변 버전으로 보관한다. 관리자는 호출자마다 외부 LLM 사용 여부를 표시하고, 외부 사용으로 표시되었거나 표시가 없는 호출자에게는 원본 읽기 권한을 줄 수 없다." (2026-11-06 방향 개정 반영)

## 용어

| 용어 | 뜻 |
|---|---|
| RAG | 검색 기반 근거 조회. 원본 자료 내용을 검색해 근거로 돌려주는 방식이다. |
| MES | 제조 실행 시스템. 공장의 생산 실행 데이터를 다루는 시스템이다. MES DB 데이터는 이 명세로 등록하지 않으며, 별도 명세 `004`의 복제본 연결로 다룬다. |
| RDB | 관계형 데이터베이스. 표 형태로 데이터를 보관하는 DB이며 MES DB가 그 예다. |
| LLM | 대규모 언어 모델. 글을 이해하고 생성하는 AI 모델이다. |
| 외부 LLM | 사내 밖에서 운영되는 LLM. |
| OMF | 이 플랫폼의 첫 조회 대상 프로젝트. OMF 저장소는 그 설계 문서 저장소다. |
| 자료 | RDB에 보관되지 않는 문서 자료로서 이 플랫폼에 등록하는 파일. 예: MES 운영 매뉴얼, 설비 납품 계약서, 자재 발주서, 자재 납품 거래명세서. 형식은 Excel, PDF, 이미지, 텍스트 파일로 제한한다. MES DB 데이터는 자료가 아니다. |
| 스키마 | DB 스키마가 아니라 자료를 해석·분할하는 규칙을 담은 등록용 정의. 개념 설명, 분할 규칙, 엔티티·속성·관계 매핑으로 구성한다. |
| 분할 규칙 | 자료를 검색 단위로 나누는 방법을 프로그램이 그대로 실행할 수 있게 정형으로 적은 규칙. 규칙이 적용되는 파일 형식도 분할 규칙의 일부로 밝힌다. 이 명세는 규칙의 존재와 적합성만 다루며 실행은 하지 않는다. |
| 엔티티 | 자료에 등장하는 개별 대상. 속성은 그 대상의 특성, 관계는 대상 사이의 연결이다. |
| 매핑 | 자료의 어떤 부분이 어떤 엔티티·속성·관계에 해당하는지 정한 대응 규칙. |
| 스키마 ID | 스키마를 재사용하려고 지정하는 식별 문자열. 1~20자이며 영문·숫자·`-`·`_`만 쓰고 대소문자를 구분한다. 플랫폼 전체에서 유일하다. 한 ID는 하나의 내용만 가지므로 스키마 ID가 곧 불변 버전 식별값이다. |
| 스키마 사전 | 등록된 스키마를 불변으로 보관하는 플랫폼 공용 저장소. |
| 기본 스키마 | 텍스트 파일에 쓰는, 플랫폼이 미리 갖춘 스키마. |
| 자료 ID | 등록자가 전달하는, 한 source 안에서 유일한 자료 식별값. source와 자료 ID가 자료의 원본 식별값이다. |
| 현재본 | 한 자료 ID에서 가장 최근에 만들어진 revision. 그 revision이 삭제되면 그 자료는 현재본 없음 상태가 된다. |
| 불변 revision | 한 번 정해지면 바뀌지 않는 자료 시점 식별값. revision이라고도 쓴다. |
| 원본 | 등록 요청으로 받은 파일 그대로의 내용. |
| 내용 해시 | 내용에서 계산한 식별값. 내용이 같으면 값도 같다. |
| 스캔 PDF | 글자 층(프로그램이 읽을 수 있는 문자 정보)이 없는 PDF. 모든 페이지에 글자 층이 없으면 전체 스캔 PDF라고 쓴다. |
| 포함 이미지 관계 정보 | 그림 내용 대신 "해당 파일에 포함된 이미지"라는 사실만 담은 기록. |
| OCR | 이미지 속 글자를 프로그램이 읽어 문자로 바꾸는 이미지 문자 인식. 이 플랫폼은 쓰지 않는다. |
| 이미지 규칙 | 이미지에 OCR을 쓰지 않고, 사람이 작성한 정보 자료와 묶어 등록하며, 정보 자료가 없으면 거부하는 규칙. 이미지 파일과 전체 스캔 PDF에 적용한다. Excel·PDF 안의 그림은 FR-020을 따른다. |
| 정보 자료 | 이미지나 스캔 내용을 사람이 글로 설명한 자료. |
| 호출자 | Bearer 토큰으로 REST API를 호출하는 사람 또는 프로그램. |
| REST API | HTTP 기반 웹 API. 프로그램이 웹 요청으로 기능을 호출하는 규약이다. |
| Bearer 토큰 | 요청에 실어 호출자를 증명하는 비밀 문자열. 기존 조회 기능이 이미 쓰고 있다. |
| source | 플랫폼이 다루는 자료 출처 단위. 현재 조회 대상은 `omf`이고, 제조 자료용 source는 `factory`이다. 이 명세의 REST API 등록 대상은 `factory`뿐이다. |
| source grant | 특정 호출자에게 특정 source의 검색을 허가한 기존 기록. 이 명세의 검색 권한이며 검색만 허용한다. |
| 원본 읽기 권한 | 호출자와 source의 조합마다 revision의 원본과 등록 기록을 되찾도록 허가한 기록. 이 명세에서 새로 만든다. |
| 쓰기 권한 | 호출자와 source의 조합마다 등록을 허가한 기록. 검색 권한, 원본 읽기 권한, 쓰기 권한은 서로 독립이며 각각 부여·회수한다. |
| 외부 LLM 사용 표시 | 관리자가 호출자마다 그 호출자가 외부 LLM을 쓰는지 정한 표시. 값은 `내부`(외부 LLM을 쓰지 않음)와 `외부`(외부 LLM을 씀) 둘이다. 표시가 없는 호출자는 `외부`로 간주한다. source별이 아니라 호출자 단위다. |
| 관리자 | source를 만들고 호출자의 source별 권한을 부여·회수하고 호출자의 외부 LLM 사용 표시를 정하며 완전 삭제를 수행하는 운영 주체. |
| 서버 관리 경로 | 호출자 권한과 무관하게 관리자가 서버에서 수행하는 관리 수단. 구체 형태는 계획 단계에서 정한다. |
| 등록자 | 대상 source에 쓰기 권한을 가진 호출자. |
| Git 색인 경로 | 고정 commit(Git 커밋 식별값으로 지정한 원본 시점)의 문서를 읽어 색인(검색용으로 가공해 저장)하는 현재 경로. |
| 문서 분석 Agent | 적재 시점에 내부 LLM으로 동작하며 문서별 분할 규칙을 만들고 엔티티·속성·관계를 추출하는 Agent. 이 명세에서는 다루지 않으며 `003`과 `007` 범위다. |
| `002` | 평가 하네스(평가셋·지표·실험 기록·적용 관문)를 다루는 후속 명세. |
| `003` | 파서·전처리·문서 분석 Agent 분할 규칙·키워드 사전을 다루는 후속 명세. |
| `004` | MES 복제본 연결(MES 운영 DB의 필요한 테이블을 플랫폼의 별도 DB로 한 방향 복제)을 다루는 후속 명세. |
| `005` | 보안 검사 모듈과 플랫폼 응답(A) 적용을 다루는 후속 명세. |
| `006` | RAG 적재 일반화와 OMF 문서 이관을 다루는 후속 명세. |
| `007` | 지식 그래프를 다루는 후속 명세. |
| `008` | RDB 조회를 다루는 후속 명세. |
| `009` | 통합 조회 API를 다루는 후속 명세. |
| `010` | 외부 LLM 중계 서버(B, 외부 LLM으로 나가는 요청을 받아 보안 검사 후 전달하는 사내 서버)를 다루는 후속 명세. |
| `011` | Git 경로 제거를 다루는 후속 명세. |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스키마와 함께 자료를 등록하고 원본을 재현한다 (Priority: P1)

등록자는 Excel 또는 글자 층이 있는 PDF를 자료 ID, 스키마와 함께 등록하고 revision을 받는다. 효력을 가진 원본 읽기 권한이 있는 호출자(FR-031, FR-047)는 나중에 그 revision의 원본을 그대로 되찾는다. 파일 형식이 허용되지 않거나 스키마가 파일과 맞지 않으면 등록은 실패하고 원본, 정보 자료, 스키마, revision이 남지 않는다. 거부 사실을 적은 운영 기록만 남을 수 있다.

**Why this priority**: 이후 모든 명세의 입력이 되는 최소 기능이다. 원본을 재현할 수 없으면 이후 단계의 근거도 재현할 수 없다.

**Independent Test**: 표본 Excel과 PDF를 맞는 스키마로 등록한 뒤 revision으로 되찾아 원본과 대조하고, 허용되지 않은 파일과 맞지 않는 스키마의 거부를 확인한다. 이 결과만으로 재현 가능한 원본 보관의 가치를 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 등록자와 파일에 맞는 스키마가 있고, **When** 자료 ID를 전달해 Excel 파일을 등록하면, **Then** 등록이 성공하고 revision, 스키마 ID, 파일별 내용 해시를 받는다.
2. **Given** 등록이 끝난 revision과 원본 읽기 권한이 있고, **When** 그 revision으로 원본을 되찾으면, **Then** 되찾은 파일이 등록한 파일과 완전히 같다.
3. **Given** 이미 등록한 자료의 수정본이 있고, **When** 같은 자료 ID로 등록하면, **Then** 새 revision을 받고 그 revision이 현재본이 되며, 이전 revision으로는 이전 원본을 그대로 되찾는다.
4. **Given** 허용 형식이 아닌 파일이 있고, **When** 등록하면, **Then** 형식 사유로 거부되고 원본, 스키마, revision 중 어느 것도 남지 않는다.
5. **Given** 이름만 Excel처럼 바꾼 다른 형식의 파일이 있고, **When** 등록하면, **Then** 형식 사유로 거부된다.
6. **Given** 파일 구조와 맞지 않는 새 스키마가 있고, **When** 등록하면, **Then** 스키마 불일치 사유로 거부되고 그 스키마는 스키마 사전에 남지 않는다.
7. **Given** 손상되었거나 암호가 걸렸거나 비어 있는 파일이 있고, **When** 등록하면, **Then** 내용 확인 불가 사유로 거부된다.
8. **Given** 크기 한도를 넘는 파일이 있고, **When** 등록하면, **Then** 크기 사유로 거부된다.
9. **Given** 등록이 끝난 revision이 있고, **When** 등록 기록을 확인하면, **Then** source, 자료 ID, 등록자, 등록 일시, 제출된 파일 이름, 파일별 내용 해시, 스키마 ID를 확인한다.
10. **Given** 등록이 끝난 revision이 있고, **When** 후속 등록을 하고 서비스를 재시작한 뒤 되찾으면, **Then** 원본과 기록이 그대로이고 그 내용을 고칠 수단이 없다. 삭제는 FR-026에서 결정한 대로 처리된다.
11. **Given** 자료 등록이 끝났고, **When** 기존 호출자가 같은 질의로 검색하면, **Then** 등록 전과 같은 결과를 받고 Git 색인 경로의 색인은 그대로다.
12. **Given** 자료 ID의 현재본과 파일, 정보 자료, 스키마가 모두 같은 등록이 있고, **When** 다시 등록하면, **Then** 기존 revision을 돌려받고 새 revision은 생기지 않으며, 이 재등록도 등록 기록에 남는다.
13. **Given** 자료 ID가 없는 요청이 있고, **When** 등록하면, **Then** 자료 ID 사유로 거부된다.
14. **Given** 같은 자료 ID가 다른 source에 있고, **When** 이 source에 등록하면, **Then** 서로 다른 자료로 처리된다.
15. **Given** 효력을 가진 원본 읽기 권한이 있는 호출자(FR-031, FR-047)와 revision이 여러 개인 자료 ID가 있고, **When** source와 자료 ID로 확인하면, **Then** 현재본 revision을 받는다.
16. **Given** revision A 다음 revision B가 현재본인 자료 ID가 있고, **When** A와 같은 내용을 다시 등록하면, **Then** 새 revision이 만들어지고 그 revision이 현재본이 된다.
17. **Given** 현재본 revision이 관리자에게 삭제된 자료 ID가 있고, **When** 원본 읽기 권한자가 현재본을 확인하면, **Then** 현재본 없음 상태를 받고 직전 revision은 현재본으로 올라가지 않는다. 같은 자료 ID로 다시 등록하면 새 revision이 현재본이 된다.
18. **Given** 모든 revision이 삭제된 자료 ID가 있고, **When** 같은 자료 ID로 등록하면, **Then** 등록이 성공하고 새 revision이 현재본이 된다.
19. **Given** 묶음이 아닌 파일 2개를 담은 요청이 있고, **When** 등록하면, **Then** 요청 구성 사유로 거부된다.

### User Story 2 - source별 권한을 가진 호출자만 등록하고 원본을 되찾는다 (Priority: P1)

관리자는 제조 자료용 source `factory`를 만들고, 호출자와 source의 조합마다 쓰기 권한과 원본 읽기 권한을 따로 준다. 검색 권한, 원본 읽기 권한, 쓰기 권한은 서로 독립이다. 검색 권한만 가진 기존 호출자는 지금처럼 검색할 수 있지만 등록하거나 원본을 되찾을 수 없다. 쓰기 권한만 가진 호출자는 등록할 수 있지만 원본을 되찾을 수 없다. 관리자는 호출자마다 외부 LLM 사용 표시를 정하며, 표시가 `외부`이거나 없는 호출자는 원본 읽기 권한을 받을 수 없고 원본을 되찾을 수 없다. 원본 파일 전체가 외부 LLM으로 나가지 않게 하기 위해서다. 완전 삭제는 관리자만 서버 관리 경로로 한다.

**Why this priority**: 내부 대외비 자료가 들어오는 입구이므로 권한 없는 쓰기를 막지 못하면 등록 기능을 공개할 수 없다.

**Independent Test**: 검색 권한만 가진 호출자, 다른 source의 쓰기 권한자, 무효 토큰, 대상 source 쓰기 권한자로 같은 등록을 시도해 마지막 경우만 성공하는지 확인한다. 같은 revision을 검색 권한자, 쓰기 권한자, 원본 읽기 권한자로 되찾아 마지막 경우만 성공하는지 확인한다. 외부 LLM 사용 표시가 `외부`인 호출자와 표시가 없는 호출자에게 원본 읽기 권한 부여를 시도해 모두 거부되는지, 표시가 `내부`에서 `외부`로 바뀐 호출자의 되찾기가 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** source grant(검색 권한)만 가진 기존 호출자가 있고, **When** 등록하거나 revision의 원본을 되찾으려 하면, **Then** 등록은 권한 사유로 거부되고, 원본 되찾기는 FR-043에 따라 없는 revision과 같은 응답을 받으며, 같은 호출자의 기존 검색은 그대로 동작한다.
2. **Given** 다른 source에만 쓰기 권한이 있는 호출자가 있고, **When** 대상 source에 등록을 시도하면, **Then** 권한 사유로 거부된다.
3. **Given** 토큰이 없거나 틀렸거나 만료·비활성·폐기된 호출자가 있고, **When** 등록을 시도하면, **Then** 인증 사유로 거부된다.
4. **Given** 등록 이력이 있는 호출자의 쓰기 권한을 회수했고, **When** 다시 등록을 시도하면, **Then** 권한 사유로 거부되고 이미 등록된 revision은 그대로 남는다.
5. **Given** 대상 source에 권한이 없는 호출자가 있고, **When** 있는 source와 없는 source에 각각 등록을 시도하면, **Then** 두 응답을 구별할 수 없다.
6. **Given** 쓰기 권한만 있고 원본 읽기 권한이 없는 호출자가 있고, **When** revision의 원본이나 기록을 되찾으려 하면, **Then** 거부된다.
7. **Given** 대상 source를 지정하지 않은 요청이 있고, **When** 등록하면, **Then** 대상 source 미지정 사유로 거부된다.
8. **Given** 성공하거나 거부된 등록이 있고, **When** 등록 응답과 운영 기록을 확인하면, **Then** 비밀값과 원본 내용이 없고, 원본 내용이 외부 서비스로 전송된 기록도 없다.
9. **Given** 대상 source의 원본 읽기 권한만 있는 호출자가 있고, **When** revision의 원본을 되찾으면, **Then** 성공한다. 같은 호출자의 등록은 거부되고, 원본 읽기 권한을 회수하면 이후 되찾기도 거부된다.
10. **Given** 쓰기 권한이 전혀 없는 호출자가 있고, **When** 스키마 내용을 조회하면, **Then** 거부된다.
11. **Given** 원본 읽기 권한이 없는 호출자가 있고, **When** 있는 revision과 없는 revision을 각각 되찾으려 하면, **Then** 두 응답을 구별할 수 없다.
12. **Given** 쓰기 권한이 없는 호출자가 있고, **When** 이미 있는 스키마 ID로 다른 내용을 보내면, **Then** 스키마 ID 충돌이 아니라 권한 사유로 거부된다.
13. **Given** `factory`가 아직 없고, **When** 관리자 아닌 호출자가 `factory`에 등록을 시도하면, **Then** 거부되고 `factory`는 생기지 않는다. 관리자가 `factory`를 만들고 쓰기 권한을 부여하면 해당 호출자의 등록이 성공한다.
14. **Given** revision이 있고, **When** 관리자가 서버 관리 경로로 그 revision을 완전 삭제하면, **Then** 원본, 정보 자료, 관계 정보가 사라지고, 이후 되찾기는 없는 revision과 같은 응답을 받으며, 원본 내용 없는 삭제 기록이 남고, 연결된 스키마는 남는다. 그 revision의 등록 기록에서 파일 이름은 더 보이지 않고 source, 자료 ID, revision, 등록자, 등록 일시는 남는다.
15. **Given** 쓰기 권한이나 원본 읽기 권한을 가진 호출자가 있고, **When** revision 삭제를 시도하면, **Then** 삭제할 수 없고 revision은 그대로다. 삭제 기록도 볼 수 없다.
16. **Given** `omf`에 대한 권한이 있는 호출자가 있고, **When** `omf`를 대상으로 REST API 등록을 시도하면, **Then** 없는 source와 같은 응답으로 거부되고 기존 Git 경로는 그대로다.
17. **Given** 관리자가 있고, **When** 호출자에게 `factory`의 쓰기 권한만 부여하면, **Then** 그 호출자의 검색 권한과 원본 읽기 권한은 바뀌지 않는다.
18. **Given** 외부 LLM 사용 표시가 `외부`인 호출자가 있고, **When** 관리자가 그 호출자에게 `factory`의 원본 읽기 권한 부여를 시도하면, **Then** 외부 LLM 사용 표시 사유로 거부되고 원본 읽기 권한은 생기지 않으며 그 호출자의 다른 권한은 바뀌지 않는다.
19. **Given** 외부 LLM 사용 표시가 없는 호출자가 있고, **When** 관리자가 그 호출자에게 `factory`의 원본 읽기 권한 부여를 시도하면, **Then** 표시가 `외부`인 경우와 같이 거부되고 원본 읽기 권한은 생기지 않는다.
20. **Given** 외부 LLM 사용 표시가 없는 호출자가 있고, **When** 관리자가 표시를 `내부`로 정한 뒤 원본 읽기 권한을 부여하면, **Then** 부여가 성공하고 그 호출자는 revision의 원본을 되찾는다.
21. **Given** 표시가 `내부`이고 `factory`의 원본 읽기 권한을 가진 호출자가 있고, **When** 관리자가 표시를 `외부`로 바꾸거나 없앤 뒤 그 호출자가 revision의 원본이나 등록 기록을 되찾으려 하면, **Then** 기존 원본 읽기 권한은 효력을 잃어 FR-043에 따라 없는 revision과 같은 응답을 받고, 이미 등록된 revision과 원본은 그대로다.
22. **Given** 외부 LLM 사용 표시가 `외부`이거나 없는 호출자가 있고, **When** 그 호출자가 자기 표시를 `내부`로 바꾸려 하면, **Then** 거부되고 그 호출자의 표시와 모든 권한은 바뀌지 않는다.

### User Story 3 - 등록한 스키마를 ID로 재사용한다 (Priority: P2)

등록자는 같은 양식의 자료를 반복 등록할 때 스키마 파일을 다시 보내지 않고 스키마 ID만 전달한다. 같은 ID의 내용이 몰래 바뀌는 일은 없다.

**Why this priority**: 반복 등록의 부담을 줄이고 같은 양식이 같은 규칙으로 처리되게 한다. 다만 스키마를 매번 보내도 등록 자체는 되므로 P1 다음이다.

**Independent Test**: 새 스키마를 ID와 함께 등록한 뒤 같은 ID만으로 다른 파일을 등록하고, 같은 ID에 다른 내용을 보내 거부되는지와 사전 내용이 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 스키마 사전에 있는 ID가 있고, **When** 맞는 파일을 그 ID만으로 등록하면, **Then** 등록이 성공하고 revision에 그 스키마 ID가 기록된다.
2. **Given** 사전에 있는 ID가 있고, **When** 같은 ID로 내용이 다른 스키마 파일을 보내면, **Then** ID 충돌 사유로 거부되고 사전 내용은 바뀌지 않는다.
3. **Given** 사전에 있는 ID가 있고, **When** 같은 ID로 완전히 같은 내용의 스키마 파일을 보내면, **Then** 거부되지 않고 기존 스키마를 재사용한다.
4. **Given** 사전에 없는 ID이고 스키마 파일도 없고, **When** 등록하면, **Then** 스키마 없음 사유로 거부된다.
5. **Given** 21자이거나 허용되지 않은 문자가 든 ID가 있고, **When** 등록하면, **Then** ID 규칙 위반 사유로 거부된다.
6. **Given** 1자 ID와 20자 ID가 있고 각각 규칙에 맞는 문자만 쓰였고, **When** 맞는 스키마 파일과 함께 등록하면, **Then** 둘 다 ID 규칙으로 거부되지 않는다.
7. **Given** Excel 또는 PDF 파일이 있고, **When** 스키마 ID도 스키마 파일도 없이 등록하면, **Then** 스키마 없음 사유로 거부된다.
8. **Given** 개념 설명, 분할 규칙, 매핑 중 하나가 빠졌거나 분할 규칙이 정형이 아닌 스키마가 있고, **When** 등록하면, **Then** 스키마 구성 사유로 거부된다.
9. **Given** 등록에 쓰인 스키마가 있고, **When** 등록자가 스키마 ID로 조회하면, **Then** 등록 당시 내용을 그대로 받는다.
10. **Given** 스키마 파일은 있고 스키마 ID가 없고, **When** 등록하면, **Then** 스키마 ID 규칙 위반 사유로 거부되고 그 스키마는 사전에 남지 않는다.
11. **Given** 빈 문자열(0자) 스키마 ID가 있고, **When** 등록하면, **Then** 스키마 ID 규칙 위반 사유로 거부된다.
12. **Given** 매핑 대상을 "대상 없음"으로 명시한 스키마가 있고, **When** 맞는 파일과 등록하면, **Then** 스키마 구성 사유로 거부되지 않는다.
13. **Given** 다른 source의 쓰기 권한자가 등록한 스키마 ID가 있고, **When** 이 source의 등록자가 그 ID로 맞는 파일을 등록하면, **Then** 스키마가 재사용된다.

### User Story 4 - 텍스트 파일을 기본 스키마로 등록한다 (Priority: P2)

등록자는 텍스트 파일을 스키마를 만들지 않고 등록한다. 텍스트 파일에는 항상 플랫폼의 기본 스키마가 적용되고, revision에서 그 스키마 ID를 확인할 수 있다.

**Why this priority**: 가장 단순한 자료의 등록 부담을 없애고, `006`의 Markdown(기호로 구조를 표시하는 텍스트 형식) 문서 이관 입구가 된다.

**Independent Test**: 스키마 ID와 스키마 파일 없이 표본 텍스트 파일을 등록해 revision과 기본 스키마 ID 기록을 확인하고 원본을 대조한다.

**Acceptance Scenarios**:

1. **Given** 텍스트 파일이 있고, **When** 스키마 ID와 스키마 파일 없이 등록하면, **Then** 등록이 성공하고 revision에 기본 스키마 ID가 기록된다.
2. **Given** 줄바꿈과 문자 부호화(문자를 파일에 저장하는 방식)가 일정하지 않은 텍스트 파일이 있고, **When** 등록 후 되찾으면, **Then** 원본과 완전히 같다.
3. **Given** 문자로 해석할 수 없는 내용을 텍스트 파일로 선언했고, **When** 등록하면, **Then** 형식 사유로 거부된다.
4. **Given** 텍스트 파일이 있고, **When** 스키마 ID나 스키마 파일을 지정해 등록하면, **Then** 텍스트 파일 스키마 지정 사유로 거부된다.

### User Story 5 - 이미지를 사람이 쓴 정보 자료와 묶어 등록한다 (Priority: P2)

등록자는 설비 사진이나 전체 스캔 문서처럼 글자를 읽을 수 없는 자료를 사람이 쓴 설명과 묶어 등록한다. 플랫폼은 이미지의 글자를 읽지 않으며, 설명이 없으면 등록을 받지 않는다. Excel·PDF 안의 그림은 등록을 막지 않고, 그림이 포함되었다는 사실만 기록한다.

**Why this priority**: OCR 없이 이미지를 쓸 수 있는 유일한 경로다. 설명 없는 이미지를 받으면 찾을 수 없는 자료만 쌓인다.

**Independent Test**: 이미지와 전체 스캔 PDF를 정보 자료와 함께, 그리고 정보 자료 없이 각각 등록해 묶음 기록과 거부를 확인하고, 그림이 든 Excel을 정보 자료 없이 등록해 관계 정보 기록을 확인한다.

**Acceptance Scenarios**:

1. **Given** 이미지와 사람이 쓴 정보 자료, 맞는 스키마, 원본 읽기 권한이 있고, **When** 함께 등록하면, **Then** 등록이 성공하고 revision으로 이미지와 정보 자료 원본을 모두 되찾으며 둘의 묶음을 확인한다.
2. **Given** 이미지만 있고, **When** 등록하면, **Then** 정보 자료 없음 사유로 거부된다.
3. **Given** 전체 스캔 PDF만 있고, **When** 등록하면, **Then** 정보 자료 없음 사유로 거부된다.
4. **Given** 내용이 비었거나 공백뿐인 정보 자료가 있고, **When** 이미지와 함께 등록하면, **Then** 정보 자료 없음 사유로 거부된다.
5. **Given** 묶음 등록이 끝났고, **When** 등록 기록을 확인하면, **Then** 정보 자료가 사람이 쓴 설명임을 알 수 있다.
6. **Given** 맞는 스키마와 그림이 든 Excel 또는 글자 층이 있는 PDF가 있고, **When** 정보 자료 없이 등록하면, **Then** 등록이 성공하고 그림 내용은 만들어지지 않으며 등록 기록에 포함 이미지 관계 정보가 남는다.
7. **Given** 사람이 쓴 설명이라는 표시가 없는 정보 자료가 있고, **When** 이미지와 함께 등록하면, **Then** 정보 자료 없음 사유로 거부된다.
8. **Given** 글자가 찍힌 이미지가 묶음으로 등록됐고, **When** 등록 기록을 확인하면, **Then** 이미지 속 글자를 읽어 만든 정보가 없다.
9. **Given** 일부 페이지에만 글자 층이 없는 PDF가 있고, **When** 정보 자료 없이 등록하면, **Then** 시나리오 6과 같이 등록되고 관계 정보가 남는다.
10. **Given** 텍스트 파일이 아닌 정보 자료(예: PDF)가 있고, **When** 이미지와 함께 등록하면, **Then** 정보 자료 형식 사유로 거부된다.

### Edge Cases

- 같은 자료 ID의 현재본과 같은 내용을 다시 등록하면 거부 사유가 아니다. 기존 revision을 돌려주고, 이 재등록도 등록 기록에 남으며, 앞선 등록 기록은 바뀌지 않는다.
- 같은 파일이라도 스키마가 다르면 같은 내용이 아니다. revision은 적용 스키마를 고정하기 때문이다.
- 내용이 같은 파일을 다른 자료 ID로 등록하면 각각 보존한다. 어느 자료 ID로 등록됐는지 잃지 않는다.
- 같은 자료 ID로 동시에 들어온 등록은 각각 전부 성공하거나 전부 실패하며, 마지막으로 성공한 등록이 현재본이다.
- 이미 있는 source를 다시 만들려는 요청은 거부되며 기존 source는 바뀌지 않는다.
- 삭제된 revision의 내용을 다시 등록하면 FR-038을 따른다. 현재본과 같으면 그 현재본 revision을 돌려주고, 그 밖의 경우는 새 revision을 만든다. 삭제된 revision을 돌려주는 일은 없다.
- 완전 삭제는 이 명세의 보관 원본에만 적용된다. `006` 이후의 색인에 이미 들어간 내용으로 삭제를 전파하는 일은 `006`에 의존한다.
- 두 등록자가 같은 새 스키마 ID를 동시에 등록하면 먼저 저장된 내용이 그 ID의 내용이 된다. 뒤의 요청은 내용이 같으면 재사용하고 다르면 ID 충돌로 거부한다.
- 새 스키마를 포함한 등록이 다른 사유로 실패하면 그 스키마도 사전에 남지 않는다.
- 스키마 ID의 대소문자가 다르면 서로 다른 ID다.
- 일부 페이지에만 글자 층이 없는 PDF는 그 페이지를 PDF 안의 그림과 같이 다룬다(FR-020).
- 전송이 중간에 끊긴 등록은 실패로 처리하며 부분 결과가 남지 않는다.
- 쓰기 권한은 있지만 스키마 ID만 보낼 때 그 ID가 파일과 맞지 않으면 스키마 불일치로 거부하며, 사전 내용은 바뀌지 않는다.
- 저장 공간 부족 같은 내부 실패는 성공으로 응답하지 않으며 부분 결과가 남지 않는다. 이 경우 호출자가 다시 시도해도 기존 revision은 영향을 받지 않는다.
- 파일 이름에 경로 문자가 있어도 이름은 기록 정보일 뿐이며 저장 위치나 다른 자료에 영향을 주지 않는다.
- 등록한 Excel의 매크로(파일 안에 든 자동 실행 명령)나 PDF의 내장 실행 내용은 등록 과정에서 실행되지 않는다.
- 외부 LLM 사용 표시가 바뀐 직후 진행 중이던 원본 되찾기의 처리와, 표시가 `외부`에서 `내부`로 돌아온 호출자의 기존 원본 읽기 권한이 다시 효력을 얻는지는 정하지 않았다. Assumptions의 미결 항목을 따른다.

## Requirements *(mandatory)*

### Functional Requirements

**등록 요청과 거부**

- **FR-001**: 시스템 MUST 인증된 호출자가 REST API로 자료를 등록할 수 있게 한다.
- **FR-002**: 등록 요청은 MUST 대상 source를 하나 지정한다. 지정이 없으면 거부한다. 없는 source와 REST API 등록 대상이 아닌 source는 쓰기 권한이 없는 source와 구별되지 않게 거부하고, 등록 요청으로 source를 자동 생성하지 않는다.
- **FR-003**: 시스템 MUST Excel, PDF, 이미지, 텍스트 파일만 받고 그 외 형식은 거부한다.
- **FR-004**: 형식 판정은 MUST 파일 이름이나 호출자의 선언이 아니라 실제 내용을 기준으로 한다. 선언과 실제가 다르면 거부한다.
- **FR-005**: 시스템 MUST 손상, 암호 설정, 빈 파일처럼 내용을 확인할 수 없는 파일을 거부한다.
- **FR-006**: 시스템 MUST 파일 크기 한도를 넘는 파일을 거부한다. 한도 값은 Assumptions를 따른다.
- **FR-007**: 하나의 등록 요청은 MUST 전부 성공하거나 전부 실패한다. 실패한 요청의 원본, 정보 자료, 새 스키마, revision은 남지 않는다. 거부 사실을 적은 운영 기록은 예외이며 FR-034를 따른다.
- **FR-008**: 거부 응답은 MUST 호출자가 다음 16개 사유를 구별해 고칠 수 있게 한다: 인증, 권한, 대상 source 미지정, 요청 구성, 자료 ID 누락 또는 규칙 위반, 파일 형식, 내용 확인 불가, 크기, 스키마 없음, 스키마 ID 규칙 위반, 스키마 구성 불완전, 스키마 ID 충돌, 스키마 불일치, 텍스트 파일 스키마 지정, 정보 자료 없음, 정보 자료 형식.

**스키마 지정과 검증**

- **FR-009**: 모든 등록은 MUST 하나의 스키마와 연결된다. 텍스트 파일(FR-014)을 제외하면 스키마 ID도 새 스키마 파일도 없는 요청은 거부한다.
- **FR-010**: 스키마는 MUST 개념 설명, 정형 분할 규칙, 엔티티·속성·관계 매핑을 모두 갖춘다. 분할 규칙은 적용 대상 파일 형식을 밝힌다. 하나라도 빠지거나 분할 규칙이 정형이 아니면 거부한다. 매핑 대상이 없는 자료는 매핑을 빼지 않고 "대상 없음"으로 명시하며, 이를 유효로 본다.
- **FR-011**: 스키마 ID는 MUST 1~20자이고 영문·숫자·`-`·`_`만 쓴다. 빈 문자열을 포함해 벗어나면 거부한다. 대소문자가 다르면 다른 ID다.
- **FR-012**: 시스템 MUST 텍스트 파일이 아닌 등록 요청의 스키마 입력을 다음 표대로 처리한다.

| 스키마 ID | 새 스키마 파일 | 사전 상태 | 결과 |
|---|---|---|---|
| 있음 | 없음 | ID 있음 | 기존 스키마 재사용 |
| 있음 | 없음 | ID 없음 | 거부(스키마 없음) |
| 있음 | 있음 | ID 없음 | 해당 ID로 새 스키마 등록 |
| 있음 | 있음 | ID 있음, 내용 같음 | 기존 스키마 재사용 |
| 있음 | 있음 | ID 있음, 내용 다름 | 거부(스키마 ID 충돌) |
| 없음 | 있음 | 해당 없음 | 거부(스키마 ID 규칙 위반). 플랫폼은 ID를 발급하지 않음 |
| 없음 | 없음 | 해당 없음 | 거부(스키마 없음) |

- **FR-013**: 시스템 MUST 스키마가 등록 파일과 맞는지 등록 시점에 판정하고, 맞지 않으면 등록을 실패시킨다. 맞지 않음은 분할 규칙이 밝힌 대상 파일 형식이 등록 파일과 다르거나 스키마가 가리키는 구조가 파일에 없는 경우를 포함한다.
- **FR-014**: 텍스트 파일은 MUST 항상 기본 스키마로 등록한다. 텍스트 파일에 스키마 ID나 스키마 파일을 지정하면 거부한다.

**스키마 사전**

- **FR-015**: 시스템 MUST 등록된 스키마와 기본 스키마를 플랫폼 공용 스키마 사전에 불변으로 보관한다. 스키마 ID는 플랫폼 전체에서 유일하고 하나의 내용만 가지며 그 자체가 불변 버전 식별값이다. 내용을 바꾸려면 새 ID로 등록한다. 등록 후 내용을 수정하거나 삭제할 수 없다.
- **FR-016**: 어느 source든 쓰기 권한이 있는 호출자는 MUST 스키마 ID로 스키마를 재사용하고 그 내용을 등록 당시 그대로 확인할 수 있다.

**이미지 규칙**

- **FR-017**: 시스템 MUST 이미지 내용을 OCR로 읽어 등록 정보를 만들지 않는다.
- **FR-018**: 이미지는 MUST 사람이 쓴 정보 자료와 묶어 등록한다. 정보 자료가 없거나 내용이 비었거나 공백뿐이면 정보 자료 없음으로 거부한다. 정보 자료는 텍스트 파일만 받으며, 텍스트 파일이 아니면 정보 자료 형식으로 거부한다. 묶음은 스키마 입력에 FR-009를 그대로 따르며, FR-013의 맞음 판정은 정보 자료를 기준으로 한다.
- **FR-019**: 전체 스캔 PDF는 MUST 이미지 규칙을 적용한다.
- **FR-020**: 그림이 든 Excel·PDF와 일부 페이지에만 글자 층이 없는 PDF는 MUST 정보 자료가 없어도 거부하지 않고 등록한다. 시스템은 그림 내용을 만들지 않고 포함 이미지 관계 정보를 등록 기록에 남긴다. 그런 파일을 정보 자료와 함께 제출하면 FR-021에 따라 묶음도 기록한다.
- **FR-021**: 시스템 MUST 어떤 이미지가 어떤 정보 자료와 묶였는지와, 등록자가 그 정보 자료를 사람이 쓴 설명으로 표시했음을 기록한다. 이 표시가 없는 정보 자료는 인정하지 않는다.

**불변 revision과 원본 보관**

- **FR-022**: 성공한 등록은 MUST 불변 revision으로 식별된다. 시스템은 성공 응답에 revision, 스키마 ID, 파일별 내용 해시를 포함한다. 한 번 발급한 revision이 가리키는 내용은 바뀌지 않으며, 재현이 멈추는 경우는 FR-026의 완전 삭제뿐이다.
- **FR-023**: 시스템 MUST 원본과 정보 자료를 받은 그대로 보관하고, 효력을 가진 원본 읽기 권한이 있는 호출자(FR-031, FR-047)가 revision으로 파일 내용까지 완전히 같게 되찾을 수 있게 한다.
- **FR-024**: 시스템 MUST 각 등록에 source, 자료 ID, 등록자, 등록 일시, 제출된 파일 이름, 파일별 내용 해시, 스키마 ID를 기록하고, revision으로 확인할 수 있게 한다. 새 revision을 만들지 않은 재등록도 등록 기록에 남긴다. 원본 식별값은 source와 자료 ID이며 파일 이름은 참고 기록이다.
- **FR-025**: 후속 등록과 서비스 재시작은 MUST 기존 revision, 원본, 등록 기록을 바꾸거나 잃지 않는다.
- **FR-026**: 등록된 원본과 revision은 MUST 내용을 수정할 수 없다. 관리자만 서버 관리 경로로 revision을 완전 삭제할 수 있고, 호출자 권한으로는 삭제할 수 없다. 완전 삭제는 그 revision의 원본, 정보 자료, 포함 이미지 관계 정보를 지운다. 완전 삭제는 그 revision의 등록 기록에서 제출된 파일 이름처럼 내용을 짐작하게 하는 항목도 지우고, source, 자료 ID, revision, 등록자, 등록 일시, 스키마 ID는 남긴다. 시스템은 삭제자, 삭제 일시, source, 자료 ID, revision, 내용 해시를 담은 삭제 기록을 남기며, 삭제 기록에는 원본 내용을 남기지 않는다. 삭제 기록은 관리자가 확인한다. 삭제된 revision은 재현할 수 없고, 되찾기 요청은 FR-043의 없는 revision과 같은 응답을 받는다. 스키마는 삭제 대상이 아니다.

**권한**

- **FR-027**: 등록, 스키마 쓰기, 원본 되찾기는 MUST 기존 Bearer 토큰으로 인증하며, 호출자 구분도 이 토큰을 따른다. 토큰이 없거나 틀렸거나 만료·비활성·폐기된 호출자는 거부한다.
- **FR-028**: 검색 권한, 원본 읽기 권한, 쓰기 권한은 MUST 서로 독립이며 각각 명시적으로 부여·회수한다. 원본 읽기 권한은 예외적으로 FR-046·FR-047의 외부 LLM 사용 표시 제한을 받는다. 기존 source grant는 검색 권한이며 검색만 허용한다. 원본 되찾기나 등록을 허용하지 않고, 다른 권한으로 자동 전환되지 않는다.
- **FR-029**: 쓰기 권한과 원본 읽기 권한은 MUST 호출자와 source의 조합 단위로 부여한다. 호출자는 대상 source에 쓰기 권한이 있을 때만 등록할 수 있다.
- **FR-030**: 쓰기 권한이나 원본 읽기 권한을 회수하면 MUST 이후 해당 요청이 거부되고, 다른 권한과 이미 등록된 revision과 원본은 그대로 유지된다.
- **FR-031**: revision의 원본과 등록 기록은 MUST 해당 source의 원본 읽기 권한이 효력을 가진 호출자에게만 제공한다. 쓰기 권한이나 검색 권한만으로는 되찾을 수 없다. 외부 LLM 사용 표시가 `외부`이거나 없는 호출자에게는 원본 읽기 권한 기록이 있어도 제공하지 않는다(FR-047). 스키마 내용은 MUST 어느 source든 쓰기 권한이 있는 호출자에게만 제공한다.

**보안과 데이터 취급**

- **FR-032**: 원본, 정보 자료, 스키마, 등록 기록은 MUST 사내 환경에 저장한다. 등록 호출로는 관찰할 수 없으므로 인수는 계획 단계의 저장 위치 점검으로 한다.
- **FR-033**: 등록 과정에서 원본과 정보 자료의 내용을 MUST 외부 서비스로 전송하지 않는다. 대외비 자료 취급은 `AGENTS.md`의 `보안과 데이터 취급` 절을 따른다.
- **FR-034**: 등록 응답과 운영 기록은 MUST 비밀값과 원본 내용을 드러내지 않으며, 저장소에 비밀값을 기록하지 않는다.

**기존 기능 보존**

- **FR-035**: 등록된 자료는 MUST `006`이 완료되기 전까지 검색 결과에 나타나지 않는다. 기존 조회 기능의 요청, 응답, 인증, 검색 결과는 바뀌지 않는다.
- **FR-036**: Git 색인 경로와 현재 색인은 MUST 이번 명세로 바뀌지 않으며, OMF 저장소(첫 조회 대상 프로젝트의 설계 문서 저장소)도 변경하지 않는다.

**자료 식별과 source 관리**

- **FR-037**: 등록 요청은 MUST 자료 ID를 전달한다. 없으면 거부한다. 자료 ID는 source 안에서 유일하다. 시스템은 자료 ID를 발급하지 않는다.
- **FR-038**: 같은 source와 자료 ID에 등록하면 MUST 다음과 같이 처리한다. 현재본과 파일, 정보 자료, 스키마가 모두 같으면 새 revision을 만들지 않고 기존 revision을 돌려준다. 그 밖의 경우는 과거 revision과 같은 내용이어도 새 revision을 만들고 그 revision이 현재본이 된다. 현재본 없음 상태이거나 모든 revision이 삭제된 자료 ID도 같은 규칙으로 새 revision을 만들며, 자료 ID는 재사용할 수 있다.
- **FR-039**: 효력을 가진 원본 읽기 권한이 있는 호출자(FR-031, FR-047)는 MUST source와 자료 ID로 현재본 revision을 확인할 수 있다. 현재본이 삭제되었으면 현재본 없음 상태를 받으며, 시스템은 직전 revision을 자동으로 현재본으로 올리지 않는다.
- **FR-040**: 관리자는 MUST source를 만들 수 있다. 제조 자료용 source는 하나이며 이름은 `factory`이다. 이 명세의 REST API 등록, 원본 되찾기, 쓰기·원본 읽기 권한 부여 대상은 `factory`뿐이다. `omf`에는 REST API 등록을 받지 않고 기존 Git 경로를 유지한다.
- **FR-041**: 관리자는 MUST 호출자의 `factory` 쓰기 권한과 원본 읽기 권한을 각각 부여하고 회수할 수 있다. 원본 읽기 권한 부여는 FR-046을 따른다.
- **FR-042**: 시스템 MUST 인증과 권한 검사를 파일 형식과 스키마 판정, 스키마 ID 충돌 판정보다 먼저 수행한다.
- **FR-043**: 없는 revision과 권한 없는 revision을 되찾는 요청은 MUST 같은 응답을 받는다.
- **FR-044**: 하나의 등록 요청은 MUST 파일 1개 또는 묶음 1개만 담는다. 이를 벗어난 요청은 요청 구성 사유로 거부한다.

**외부 LLM 사용 표시와 원본 읽기 권한**

- **FR-045**: 관리자는 MUST 호출자마다 외부 LLM 사용 표시를 `내부` 또는 `외부`로 정하고 바꾸거나 없앨 수 있다. 표시는 source별이 아니라 호출자 단위다. 시스템은 MUST 표시가 없는 호출자를 `외부`로 간주한다. 호출자는 자기 표시를 바꿀 수 없다.
- **FR-046**: 시스템 MUST 외부 LLM 사용 표시가 `외부`이거나 없는 호출자에게 원본 읽기 권한을 부여하려는 시도를 거부하고, 관리자가 거부 사유가 외부 LLM 사용 표시임을 알 수 있게 한다. 거부된 시도는 어떤 권한도 만들거나 바꾸지 않는다. 원본 파일 전체를 외부로 내보내지 않기 위한 규칙이다.
- **FR-047**: 원본 읽기 권한을 가진 호출자의 표시가 `내부`에서 `외부`로 바뀌거나 없어지면 MUST 그 원본 읽기 권한은 효력을 잃는다. 이후 그 호출자의 원본·등록 기록 되찾기는 FR-043의 없는 revision과 같은 응답을 받는다. 그 호출자의 검색 권한과 쓰기 권한, 이미 등록된 revision과 원본은 이 변경으로 바뀌지 않는다.

### Key Entities *(include if feature involves data)*

- **자료**: source와 자료 ID로 식별되는 대상. 여러 revision을 가지며 가장 최근에 만들어진 revision이 현재본이다. 현재본이 삭제되면 현재본 없음 상태가 된다.
- **source**: 자료 출처 단위. 관리자가 만든다.
- **원본 파일**: revision을 이루는 개별 파일. 제출된 이름, 형식, 내용 해시를 가지며 내용은 받은 그대로다. 제출된 이름은 식별값이 아니다.
- **정보 자료 묶음**: 이미지 또는 스캔 내용과 사람이 쓴 정보 자료의 연결. 사람이 쓴 설명이라는 표시를 가진다.
- **포함 이미지 관계 정보**: Excel·PDF 파일과 그 안의 이미지 사이의 관계 기록. 그림 내용은 담지 않는다.
- **revision**: 한 자료의 불변 시점 식별값. 파일 묶음, 스키마 ID, 등록 기록을 찾는 기준이다. 구성 방식은 이 명세에서 정하지 않는다.
- **스키마**: 개념 설명, 분할 규칙, 매핑으로 이루어진 불변 정의. 스키마 ID를 가지며 플랫폼 공용 스키마 사전에 속한다. 여러 revision이 재사용할 수 있다.
- **등록 기록**: source, 자료 ID, 등록자, 일시, 파일 이름, 내용 해시, 스키마 ID를 담는다.
- **삭제 기록**: 삭제자, 일시, source, 자료 ID, revision, 내용 해시를 담는다. 원본 내용은 담지 않으며 관리자가 확인한다.
- **쓰기 권한**: 호출자와 source의 조합에 등록을 허가하는 기록.
- **원본 읽기 권한**: 호출자와 source의 조합에 원본과 등록 기록 되찾기를 허가하는 기록.
- **검색 권한**: 기존 source grant. 검색만 허가한다. 세 권한은 서로 독립이다.
- **호출자**: Bearer 토큰으로 구분되는 사람 또는 프로그램. 외부 LLM 사용 표시를 하나 가지거나 표시가 없다.
- **외부 LLM 사용 표시**: 관리자가 호출자마다 정하는 `내부` 또는 `외부` 값. 표시가 없으면 `외부`로 간주한다. `외부`이거나 없으면 원본 읽기 권한을 받을 수 없고 기존 원본 읽기 권한도 효력이 없다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 네 가지 허용 형식의 표본 등록이 모두 성공하고, 되찾은 원본 중 등록한 파일과 내용이 다른 파일이 0건이다.
- **SC-002**: FR-008의 16개 거부 사유 표본이 모두 해당 사유로 거부되고, 거부된 요청이 남긴 원본, 정보 자료, 스키마, revision이 0건이다.
- **SC-003**: 권한 없는 쓰기 시도(인증 실패, 검색 권한만 보유, 원본 읽기 권한만 보유, 다른 source 권한, 회수된 권한)와 원본 읽기 권한 없는 되찾기 시도(검색 권한만 보유, 쓰기 권한만 보유 포함)의 성공이 0건이다.
- **SC-004**: 같은 스키마를 쓰는 연속 등록에서 두 번째 등록부터 스키마 파일을 다시 보낼 필요가 없고, 같은 ID에 다른 내용을 보낸 시도로 사전 내용이 바뀐 건수가 0건이다.
- **SC-005**: 후속 등록 10회와 서비스 재시작 1회 뒤에도 기존 revision의 원본, 내용 해시, 등록 기록이 달라진 건수가 0건이다.
- **SC-006**: 정보 자료 없이 등록한 이미지와 전체 스캔 PDF의 성공이 0건이고, 묶음 등록의 정보 자료 전부에서 사람이 쓴 설명임을 확인할 수 있으며, 정보 자료 없이 등록한 그림 포함 Excel·PDF 표본 전부에 포함 이미지 관계 정보가 있다.
- **SC-007**: 자료 등록 전후로 같은 색인과 같은 고정 질의에서 기존 조회 결과가 달라진 건수가 0건이고, 기존 조회 호출자가 바꿔야 할 항목이 0건이다.
- **SC-008**: 등록 과정에서 외부 서비스로 전송된 원본 내용이 0건이고, 응답과 운영 기록 표본에서 비밀값과 원본 내용 노출이 0건이다.
- **SC-009**: 정성 기준으로, 검토자가 거부 응답만 읽고 다른 문서 없이 무엇을 고쳐 다시 보낼지 판단할 수 있다. 합격 예시는 "스키마 ID가 21자라 20자 이하로 줄여야 한다"는 것을 알 수 있는 응답이다. 불합격 예시는 "등록 실패"만 알려 주는 응답이다.
- **SC-010**: 같은 자료 ID의 수정본과 과거 revision 내용 재등록 표본 전부에서 현재본이 새 revision으로 바뀌고, 현재본과 같은 내용의 재등록으로 새 revision이 생긴 건수가 0건이며, 현재본 삭제 뒤 직전 revision이 자동으로 현재본이 된 건수가 0건이다.
- **SC-011**: 관리자의 완전 삭제 표본 전부에서 삭제 후 되찾기 성공이 0건이고 원본 내용 없는 삭제 기록이 있으며, 호출자 권한으로 삭제에 성공한 건수가 0건이고 스키마 삭제 건수가 0건이다.
- **SC-012**: 외부 LLM 사용 표시가 `외부`이거나 없는 호출자에게 원본 읽기 권한을 부여하려는 시도 표본의 100%가 거부되고, 그 시도로 생기거나 바뀐 권한이 0건이다. 표시가 `내부`인 호출자에 대한 부여 표본은 모두 성공한다. 호출자가 자기 표시를 바꾸려는 시도 표본의 성공이 0건이고, 그 시도로 바뀐 표시와 권한이 0건이다.
- **SC-013**: 외부 LLM 사용 표시가 `외부`이거나 없는 호출자의 원본·등록 기록 되찾기 시도(표시가 `내부`에서 바뀐 뒤 남은 원본 읽기 권한 기록으로 시도한 경우 포함)의 성공이 0건이고, 그 응답이 없는 revision 응답과 구별되는 건수가 0건이다.

## Assumptions

- 주 사용자는 RDB에 보관되지 않는 문서 자료를 등록하는 담당자와 이를 대신하는 프로그램, source와 권한을 관리하는 관리자다.
- 확정: 파일 크기 한도를 두고 초과 시 거부한다. 값은 대표 자료를 확인한 뒤 계획 단계에서 사용자 승인으로 정한다.
- 정확한 허용 확장자와 이미지 세부 형식, 매크로 포함 Excel의 허용 여부는 계획 단계에서 사용자 승인으로 정한다. 텍스트 파일에는 Markdown을 포함한다. `006`의 OMF 문서 이관에 필요하기 때문이다.
- 파일 형식 제한은 등록 자료에 적용한다. 스키마 파일 자체의 형식은 계획 단계에서 정한다.
- FR-013의 판정, 스캔 PDF 식별, Excel·PDF 안의 그림 확인은 등록 시점에 필요한 최소 확인으로서 이 명세에 포함한다. 자료를 처리 가능한 구조로 변환하는 일은 `003` 범위다.
- 스키마의 "같은 내용"은 완전히 같은 내용을 뜻한다. 공백 하나만 달라도 다른 내용이다. 내용이 같은 스키마를 다른 ID로 등록하는 것은 막지 않는다.
- 확정: 스키마 사전은 플랫폼 공용이고 스키마 ID는 전역 유일하며, 쓰기 권한 보유자가 사용한다.
- 확정: 스키마 ID는 대소문자를 구분한다.
- 확정(사용자 승인): 스키마는 삭제할 수 없다. revision 재현에 필요하기 때문이다. FR-026의 삭제는 원본과 revision에만 적용한다.
- 기본 스키마의 구체 내용과 갱신 방식은 계획 단계에서 정한다. 기본 스키마도 FR-010의 구성을 갖추고 사전에 자기 스키마 ID로 보관한다.
- 이미지와 그림 포함 파일의 묶음은 텍스트 정보 자료를 포함해도 FR-014를 쓰지 않는다. 등록 대상이 텍스트 파일이 아니기 때문이다.
- 확정: 정보 자료는 텍스트 파일만 받는다. 사람이 썼는지를 시스템이 판별할 수 없으므로, 등록자의 표시를 기록하고 진위는 검증하지 않는다.
- 확정: 한 번의 등록 요청은 파일 1개 또는 묶음 1개를 다룬다. 여러 이미지를 한 정보 자료로 설명하는 묶음의 세부 제한은 계획 단계에서 정한다.
- 자료 ID의 길이와 문자 규칙은 승인되지 않았다. 계획 단계에서 사용자 승인으로 정한다.
- 분할 규칙의 정형 판정 기준은 스키마 파일 형식 결정에 의존하므로 계획 단계로 넘긴다.
- 확정: 과거 revision과 같은 내용의 재등록은 새 revision이 되고, 현재본 삭제 시 현재본 없음 상태가 되며, 완전 삭제는 관리자만 서버 관리 경로로 한다.
- 포함 이미지 관계 정보의 단위(파일당 하나인지 그림마다 하나인지)는 계획 단계에서 정한다.
- 확정(사용자 승인 2026-11-04): 완전 삭제 때 그 revision의 등록 기록에서 제출된 파일 이름처럼 내용을 짐작하게 하는 항목만 지운다. source, 자료 ID, revision, 등록자, 등록 일시는 남긴다. 스키마 ID도 남긴다. 스키마는 삭제 대상이 아니고 스키마 ID는 자료 내용이 아니라 플랫폼 전체의 식별값이기 때문이다. 내용 해시는 지금처럼 삭제 기록에 남는다.
- 확정: 검색 권한(기존 source grant), 원본 읽기 권한, 쓰기 권한은 서로 독립이다. 원본 읽기 권한은 새로 만들며, 기존 source grant는 검색만 허용하고 원본 되찾기를 허용하지 않는다. 호출자 구분은 기존 Bearer 토큰이다.
- 확정: source 생성과 source별 권한 부여·회수는 이 명세 범위다. 관리자가 쓰는 구체 경로는 계획 단계에서 정하며 공개 관리 화면은 포함하지 않는다.
- 확정: 제조 자료용 source `factory`는 관리자가 만들고 등록 시 자동 생성하지 않는다. 이 명세의 등록, 원본 되찾기, 권한 부여 대상은 `factory`이며, `omf`에는 REST API 등록을 받지 않고 기존 Git 경로를 유지한다. 기존 검색 요청의 `omf` 고정은 FR-035에 따라 그대로 둔다.
- 의존: `omf`의 REST API 등록 거부(FR-040, User Story 2 시나리오 16)는 이 명세의 규칙이다. `006`(RAG 적재 일반화·OMF 이관)은 이관 방식에 따라 이 규칙을 다시 정할 수 있다.
- 등록 처리 시간과 동시 등록 수의 수치 목표는 승인되지 않아 정하지 않는다.
- 확정(`AGENTS.md` 방향 개정 2026-11-06, 헌법 원칙 VI): 관리자가 호출자마다 외부 LLM 사용 여부를 표시하고, 표시가 없는 호출자는 외부로 간주한다. 원본 파일 전체는 외부로 내보내지 않으며, 외부 사용으로 표시되었거나 표시가 없는 호출자에게는 원본 읽기 권한을 줄 수 없다. FR-047의 "효력을 잃는다"는 이 규칙을 이미 부여된 권한에도 적용한 것이다.
- 기존 호출자(예: 공유 배포의 `local-agent`)는 표시가 없으므로 `외부`로 간주된다. 원본 읽기 권한이 필요하면 관리자가 먼저 `내부`로 표시해야 한다.
- 미결(계획 단계에서 사용자 승인으로 정한다): 외부 LLM 사용 표시가 바뀐 직후 이미 진행 중이던 원본 되찾기를 끝까지 처리할지 중단할지. 표시가 `외부`에서 `내부`로 돌아온 호출자의 기존 원본 읽기 권한 기록이 다시 효력을 얻는지, 아니면 관리자가 다시 부여해야 하는지. 효력을 잃은 권한 기록을 남길지 지울지. 표시 변경 기록을 남길지와 표시를 정하는 관리자 경로의 형태.
- 미결(이전 검토 이월, 계획 단계에서 정한다): M1 완전 삭제 때 등록 기록의 파일별 내용 해시를 지우는지는 FR-026과 위 2026-11-04 확정 항목에서 암시될 뿐 명시되지 않았다. M2 완전 삭제 뒤 등록 기록에 남는 항목(source, 자료 ID, revision, 등록자, 등록 일시, 스키마 ID)은 FR-043에 따라 호출자에게 보이지 않으므로 이를 확인할 관리자 경로가 필요하다. M3 시나리오 6의 문구 정리(User Story 2 시나리오 6의 "거부된다"를 FR-043의 없는 revision과 같은 응답과 맞출지 포함).
- 기존 설계서와 구현 계획이 시스템 정본이며, 이 명세는 기능 완료 시 정본에 반영한다.

## Out of Scope

- `002`: 평가 하네스(평가셋·지표·실험 기록·적용 관문).
- `003`: 파서(파일에서 글자·표·위치를 꺼내는 프로그램), 전처리(등록 전에 내용을 정리하는 단계), 문서 분석 Agent의 문서별 분할 규칙 생성과 그 규칙과 스키마 분할 규칙의 관계, 키워드 사전(용어·동의어·약어 모음). 이 명세는 문서 분석 Agent나 LLM을 쓰지 않는다.
