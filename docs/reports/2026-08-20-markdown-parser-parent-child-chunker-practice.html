요약

두 단계는 같은 “문서 자르기”가 아니다. Markdown parser는 원문을 제목 계층과 물리 행 좌표가 붙은 구조로 바꾸고, Parent–Child chunker는 그 구조를 작은 검색 단위(child)로 결정론적으로 분할한다. 검색에 적중한 child는 ParentContext를 통해 원문에 연속된 더 넓은 문맥으로 확장된다.

Part 1 · Markdown 계층·메타데이터 parser

한 문장으로 이해하기: 제목을 기준으로 원문을 구조화한다

Part 1은 Markdown을 제목 기반 section과 Markdown block으로 구조화하고, 명시된 DTO로 다음 단계에 전달한다. 제목만 뽑고 본문을 버리는 단계가 아니다.

ParsedSection은 제목 하나를 경계로 묶은 section 전체이고, ParsedBlock은 그 본문을 이루는 Markdown 문법 단위다. ParsedBlock은 한 줄 단위가 아니다. 문단·표·목록·인용문·코드·HTML·공백 같은 구조 하나가 여러 물리 행을 가질 수 있다. section의 행 범위는 heading을 포함하지만 body는 heading 다음부터 시작한다.

구현 역할: 문법 해석과 출처 좌표를 한 계약으로 묶는다

MarkdownItParser는 CommonMark와 표(table)를 읽어 제목 단위 section과 block tree를 만든다. 단순히 렌더링용 HTML을 만드는 parser가 아니다. 각 결과에 부모 section ordinal, 전체 heading path, heading을 포함한 1-based section 행 범위, heading 다음부터 다음 section 직전까지의 원문 body, block별 정확한 raw slice를 함께 넣는다. 따라서 후속 chunker는 Markdown을 추측해 다시 자르지 않고 구조와 원문 좌표를 그대로 소비할 수 있다.

문서 occurrence metadata는 별도 함수 extract_metadata()가 담당한다. “같은 내용”이라도 docs와 uiux, 현재 경로와 versions 경로는 소유·버전 범위가 다르므로 metadata는 내용 해시가 아니라 source path occurrence에 붙는다.

발췌 원칙. 보이는 행은 원문 그대로이고, 가운데 생략만 …로 표시했다. 실제 실행과 수치는 위 SHA의 원본 blob 전체에서 생성했다.

parser가 실제로 하는 일

  1. split_physical_lines()가 CR, LF, CRLF만 경계로 삼고 줄 끝을 보존한다. 다시 이어 붙이면 입력과 정확히 같다.
  2. markdown-it-py를 commonmark + table로 실행해 token stream을 만든다.
  3. 최상위 heading_open token만 section 경계로 사용한다. 인용문·목록·코드 안의 #는 제목 section을 만들지 않는다.
  4. heading level stack에서 현재보다 높거나 같은 level을 제거한 뒤 남은 마지막 항목을 parent로 삼는다. heading text가 반복돼도 ordinal로 부모를 식별한다.
  5. 각 section body는 “현재 heading 직후부터 다음 heading 직전”까지의 원문 slice다. 제목 전 비공백 preamble이 있으면 level 0 synthetic root를 만든다.
  6. paragraph, blockquote, list, list item, fenced code, table, table row 등의 token map을 중첩 block tree로 바꾼다.
  7. token이 덮지 않은 행도 버리지 않고 blank 또는 raw block으로 채운다. 그래서 section의 block raw text를 순서대로 합치면 body와 정확히 같다.

metadata는 “그럴듯한 문자열”을 넓게 훑지 않는다. code fence, HTML comment, blockquote, list, inline code 안의 작성일:·버전:·상태:는 문서 본문 예시일 수 있으므로 신호에서 제외한다. top-level paragraph와 실제 delimiter가 있는 top-level table의 첫 두 cell만 구조화 값으로 읽는다. 유효한 확정 신호와 초안 신호가 동시에 있거나 둘 다 없으면 임의 선택하지 않고 unknown이다.

예를 들어 코드 예시의 상태: 확정이나 HTML 주석의 <!-- 버전: v9 -->를 문서 전체 상태로 인정하면 예시 문장 하나가 검색 우선순위를 잘못 바꿀 수 있다. 그래서 상단의 명시적 2열 표·top-level 문단을 먼저 사용하고, 값이 없을 때만 승인된 파일명 패턴으로 fallback한다. 보수적 추출은 정보가 모호하면 추측하는 대신 null 또는 unknown을 선택한다는 뜻이다.

위 JSON의 block_kinds는 정식 DTO 필드가 아니다. 실습 스크립트가 ParsedSection.blocks[*].kind를 읽기 쉽게 요약해 만든 파생 필드다. 실제 block의 원문과 행 좌표는 각 ParsedBlock에 보존된다.

section_2.lines=[19, 59]는 heading을 포함한 section 전체 범위다. 이 section의 heading은 19행, body는 heading 다음인 20행부터 다음 section 직전인 59행까지이며, 그 안의 table block은 21~58행이다. section 행과 body 행은 같은 좌표가 아니다.

왜 version이 null인가? 원문 3행의 v1.1은 blockquote 안에 있어 metadata 신호에서 의도적으로 제외되고, 파일명에도 승인된 독립 version token이 없다. 반면 날짜와 확정 상태는 파일명 2026-07-04-…-확정기록.md에서 명시적으로 얻는다. 이는 누락이 아니라 보수적 설계의 실제 결과다.

DTO의 목적: 임시 상자가 아니라 단계 사이의 데이터 계약

DTO(Data Transfer Object)는 Part 1이 분석한 값을 Part 2가 이해하도록 전달하는 객체다. 그러나 모든 DTO가 같은 수준의 생성자 검증을 하는 것은 아니다. parser의 ParsedBlock, ParsedSection, ParsedMarkdown은 exact type, 1-based 행 좌표, 부모·자식 순서와 tuple 계약을 런타임에 검증한다. 이 검증과 frozen 객체의 생성 후 불변성은 서로 다른 보장이다.

  • ParsedMarkdown: parser behavior를 parser_version으로 식별하고 순서가 고정된 section tuple을 제공한다.
  • ParsedSection: 제목 계층과 상위 관계, heading을 포함한 section 행 범위, heading 다음부터 시작하는 body, block tree를 한 단위로 묶는다.
  • ParsedBlock: table row·list item 같은 atomic 경계를 raw source slice와 함께 전달한다.
  • DocumentMetadata: extract_metadata()가 보수적으로 선별·정규화한 문서 단위 결과를 담는 frozen 값 객체다. 자체 __post_init__ 생성자 검증은 없으며, 직접 생성자가 임의 런타임 타입을 거부한다고 가정하지 않는다.
  • frozen·tuple 기반 불변 컨테이너는 생성 후 재할당을 막아 파싱 결과의 순서와 좌표가 처리 중 바뀌지 않게 한다.

Part 2 · 결정론적 Parent–Child chunker와 ParentContext

입력 계약: 색인 파이프라인이 chunker에 무엇을 주는가

이 계약의 호출자(caller)는 색인 파이프라인이고, 호출 대상(callee)은 ParentChildChunker다. Part 1 parser가 모든 입력을 직접 넘기는 것은 아니다. parser는 ParsedSection과 그 안의 ParsedBlock을 만들고, 색인 파이프라인은 tokenizer 동작·설정·parser version을 준비해 한 호출로 조립한다. chunker는 raw Markdown 전체가 아니라 section 하나를 받는다. 

# Part 1이 생성
parsed = parser.parse(markdown)
section = parsed.sections[2]  # ParsedBlock은 section.blocks 안에 포함

# 색인 파이프라인이 준비하고 호출
chunker = ParentChildChunker(token_counter, tokenizer_descriptor, chunk_config)
chunks = chunker.split(section, parser_version=parsed.parser_version)
# 반환값: tuple[ChunkDraft, ...]

결과는 ChunkDraft tuple이다. 검색은 이 child 중 하나를 선택한다. 그 뒤 ParentContextBuilder라는 별도 객체가 선택된 child의 원문·행·ordinal과 같은 parser·token 설정을 받아 ParentContext를 재구성한다. 즉 ParentContext는 chunker가 split()과 동시에 덤으로 만드는 값이 아니다.

중요. 실습 counter는 알고리즘을 로컬에서 투명하게 관찰하기 위한 fake다. 400자가 Qwen tokenizer의 400 token이라는 뜻은 아니다. 운영 tokenizer adapter는 다음 구현 단계의 대상이다.

normal text 분할

  1. heading path를 줄바꿈으로 연결하고 끝에 줄바꿈을 붙여 heading_prefix를 만든다. 이 prefix는 search_text에만 들어가며 raw_text에는 섞이지 않는다.
  2. 전체 heading_prefix + body가 600 token 이하면 child 하나다.
  3. 길면 paragraph, fenced code, HTML 등 normal block을 400 target에 맞춰 묶는다. heading이 길어 target budget이 부족한 경우 600 soft window를 사용한다.
  4. 한 normal block이 너무 길면 tokenizer offset에서 자른다. 다음 child는 이전 child의 최대 64 token suffix를 이어받는다.
  5. 경계 재토큰화 때문에 예상보다 token이 늘 수 있으므로 실제 heading_prefix + slice를 다시 세고, bounded probe 안에서 안전한 경계를 찾는다.

table·list·quote atomic 분할

표·목록·인용문은 문장 수보다 구조적 단위가 중요하다. 전체 block이 heading_prefix를 포함해 800 token 이하면 그대로 한 child로 보존한다. 넘으면 표는 table_row, 목록은 top-level list_item, 인용문은 child block 경계를 atomic unit으로 삼아 가능한 만큼 묶는다. atomic block의 바깥쪽 whitespace-only 행만 제거하고 내부 공백은 보존한다.

단일 row/item이 그 자체로 800 token을 넘을 때만 tokenizer offset으로 강제 분할하고 oversized_atomic_unit_token_split warning을 붙인다. warning에는 안전한 block_kind와 물리 행 범위만 들어가고 원문은 들어가지 않는다.

ParentContext: 적중 child를 원문 문맥으로 되돌린다

  1. 저장된 section body를 같은 parser로 다시 파싱하고 parser_version, synthetic root, block coverage가 정확한지 확인한다.
  2. matched_ordinal이 있으면 같은 config로 child를 다시 만들고 ordinal의 raw text·행·source offset이 저장된 child와 모두 같은지 검증한다.
  3. section body 전체가 1,200 token 이하면 그대로 반환한다.
  4. 더 크면 적중 행과 교차하는 top-level block을 seed로 잡고, 가까운 block을 앞쪽 우선 동률 규칙으로 추가한다. 왼쪽이 안 맞으면 오른쪽도 시도한다.
  5. seed block 자체가 1,200 token보다 크면 tokenizer offset을 이용해 정확한 match 주변의 가장 넓은 연속 window를 선택한다.
  6. 결과는 heading prefix가 없는 원문 연속 slice와 절대 행 범위다.

실제 OMF 관찰값. table child ordinal 5는 원문 38~40행이다. 같은 ordinal로 만든 context는 원문 36~42행, 정확히 1,200 token이고 child 원문을 포함한다.

matched_ordinal이 필요한 이유. 긴 한 행에 같은 문자열이 여러 번 나오거나 서로 다른 위치의 child가 raw text·행·해시까지 같을 수 있다. ordinal이 실제 분할 순서의 위치를 지정하므로 첫 번째 문자열을 임의로 고르는 오류를 막는다. ordinal이 없고 위치가 모호하면 builder는 안전하게 실패한다.

읽고 나서 설명할 수 있어야 하는 것

Part 1은 Markdown을 제목 기반 section과 Markdown block으로 구조화하고, DTO를 통해 Part 2에 전달한다. Part 2는 section과 tokenizer 설정을 받아 검색용 child를 만들고, 선택된 child로부터 ParentContext를 재구성한다.

Part 1 체크리스트

  • section 전체 행은 heading을 포함하고 body는 heading 다음부터라고 설명할 수 있다.
  • block은 한 줄이 아니라 Markdown 구조 단위라고 설명할 수 있다.
  • parser DTO의 런타임 좌표 검증과 frozen 객체의 불변성이 서로 다른 보장임을 안다.
  • section ordinal과 parent_ordinal을 DB ID·행·제목 level과 구분한다.
  • metadata가 문서 전체에 한 번 추출되는 색인 정보임을 안다.

Part 2 체크리스트

  • parser가 만든 입력과 색인 파이프라인이 준비한 입력을 구분한다.
  • ParsedBlock은 별도 인자가 아니라 ParsedSection 내부 값임을 안다.
  • ChunkDraft ordinal은 section ordinal과 대상이 다름을 안다.
  • 검색이 child를 선택한 뒤 별도 builder가 ParentContext를 만든다고 설명할 수 있다.
  • raw text와 원문 행 좌표가 인용 재현에 필요함을 안다.

한계와 다음 단계

이 보고서가 검증하지 않는 것. Qwen tokenizer의 실제 token 수, GPU embedding 품질, DB 저장, 하이브리드 검색 순위, 운영 성능은 범위 밖이다. character counter의 수치는 알고리즘 학습용이며 모델 성능 수치가 아니다.

  • 실제 OMF 근거는 작성 당시 commit 하나에 고정됐다. 이후 문서가 바뀌어도 이 보고서의 출력은 SHA로 재현된다.
  • 현재 OMF 작업 트리에 untracked 파일이 있어도 git show <SHA>:<path> 결과에는 영향을 주지 않는다.
  • metadata는 명시 신호만 인정하므로 blockquote에만 version이 있으면 null이 정상이다. 필요하다면 원문 metadata 표준을 별도 설계 결정으로 다뤄야 한다.
  • 다음 개발 단계는 운영 tokenizer와 embedding provider다. 그 단계에서 Qwen token 기준으로 chunk 크기 적합성을 별도 검증한다.
