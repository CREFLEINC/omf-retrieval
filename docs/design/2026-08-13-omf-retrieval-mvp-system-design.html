요약

이번 MVP는 자연어 답변을 생성하는 서비스가 아니라 검증 가능한 근거 검색 서비스다. OMF의 고정 commit에서 현재 wiki Markdown만 색인하고, 인증된 질의에 인용·경로·제목 계층·행 범위·검색 순위·commit SHA·내용 해시를 반환한다.

v2.0 MVP 완료. 로컬 PostgreSQL과 실제 Qwen 임베딩 모델로 고정 OMF 현재본을 색인하고 인증된 API 검색과 6개 smoke를 검증했다. 네 실행 단위의 독립 검증은 모두 PASS했으며, 당시 공유 Ubuntu·Docker Compose 배포는 후속으로 분리했다.

승인된 v2.1 corrective plan. 공유 CUDA 배포에서 문서에 없는 질의가 vector-only 근거를 반환해 공개 API를 중단했다. 기존 색인과 5,584개 embedding은 보존하고, 색인 identity와 search policy identity를 분리한 뒤 CUDA 실측으로 검색 하한선을 다시 보정한다.

데이터와 색인 수명주기

작업 1~7 완료 구현과 작업 8~10 WIP를 보존한다. 기존 0002_index_run_activation_lifecycle.py를 MVP migration으로 채택한다.

MVP migration 연쇄
Revision책임
0001기반 schema, 검색·권한 데이터 구조
0002Parse artifact manifest의 section_count, chunk_count, artifact_hash backfill과 activation lifecycle의 activated_at, ARCHIVED, 활성 버전 제약
0003 계획Immutable search policy manifest와 SHA-256 config hash를 additive로 추가하고, 기존 index run이 보존한 query·retrieval snapshot을 정책 manifest로 backfill

Migration 번호 구분. v1.3의 별도 lifecycle 0003 계획은 v2.0이 폐기했고 통합 0002는 그대로 유지한다. v2.1의 0003은 lifecycle 분리가 아니라 검색 정책 manifest만 추가하는 새로운 additive migration이다.

0003은 기존 index run·index_configs snapshot·5,584개 embedding을 삭제하거나 다시 쓰지 않는다. Legacy query·RRF snapshot은 provenance로 남긴다. Upgrade → downgrade → re-upgrade를 검증하되 운영 rollback은 DB downgrade보다 이전 image와 policy 환경설정으로 되돌린 뒤 API를 재시작하는 방식을 우선한다.

  1. index 명령은 고정 commit을 snapshot으로 읽고 include/exclude 규칙을 적용한다.
  2. 문서를 parse·chunk·embed하고 artifact identity가 같은 산출물은 재사용한다.
  3. 모든 저장과 무결성 검사가 성공해 run이 READY가 되면 즉시 active pointer를 전환한다.
  4. 색인 실패 시 새 run만 실패로 기록하고 기존 active pointer를 유지한다.
  5. Rollback 인터페이스는 MVP에 노출하지 않는다.

Index identity와 search policy identity

재현 identity 경계
Identity포함변경 효과
Index identitySource profile·commit, parser, chunker, tokenizer, document embedding provider·model·revision·dimension·normalization·library behavior문서·chunk·vector가 달라지므로 새 index run 또는 embedding 생성이 필요할 수 있음
Search policy identityQuery embedding model·revision·dimension·normalization과 instruction, keyword/vector candidate limits, RRF k·weights, keyword/vector similarity floors, calibration status질의 시점 후보·순위·no_evidence만 달라지며 기존 index·embedding을 재사용

현재 index_configs.config_hash와 그 안의 query·RRF snapshot은 v2.0의 legacy combined identity다. v2.1 이후에는 이 snapshot을 provenance로 보존하되 runtime 검색 정책과의 byte-exact 동등성을 active index 조건으로 사용하지 않는다. Query instruction, RRF 또는 하한선 변경은 index identity 불일치가 아니며 index·embedding pipeline을 호출해서는 안 된다.

Search policy는 exact-key canonical JSON의 SHA-256 config_hash로 식별하는 append-only DB manifest다. 운영 runtime settings가 사용할 정책을 구성하고, serve가 readiness 전에 같은 snapshot을 idempotent register·resolve한다. 공개 관리 CLI와 active-policy pointer는 추가하지 않는다. MVP 운영은 단일 Compose API replica를 전제로 하며 다중 replica의 config consistency는 후속이다.

검색 전 active index의 document embedding descriptor와 선택된 policy의 query model·revision·dimension·normalization 호환성을 강제한다. 불완전한 snapshot, canonical hash 불일치 또는 descriptor 비호환은 안전한 503으로 실패한다. 반면 query instruction·RRF·하한선 차이는 허용하며, 정책 변경은 새 immutable manifest와 API restart만 만든다.

검색·권한 흐름

  • API 인증과 검색 SQL 후보 CTE 양쪽에서 token·source grant·active run을 제한한다.
  • 점수가 lane별 하한선 이상(>=)인 후보만 해당 lane의 RRF 후보가 된다.
  • 작은 child로 검색하고 같은 parent section의 child를 하나의 evidence item으로 묶는다.
  • 그룹은 가장 높은 child RRF 점수로 정렬한다.
  • ANN index와 리랭커는 사용하지 않는다.

각 하한선은 문서에 없는 smoke 질의에서 관찰한 해당 lane 최고점에 nextafter(+inf)를 적용한 다음 표현 가능 부동소수점 값이다. 비교는 >=이므로 관찰된 unknown 최고점은 배제하고 하한선 자체와 같은 점수는 포함한다. 두 lane 모두 하한선을 통과한 후보가 없으면 HTTP 200, status: no_evidence, 빈 evidence_items를 반환한다.

v2.0 구현은 후보 수, RRF 값, 두 하한선과 상태를 index config에 저장하고 runtime과 byte-exact 비교했다. v2.1은 이 값의 소유권을 search policy manifest로 이동한다. 로컬 baseline 값과 분리 margin은 기존 검증의 provenance로 보존하지만 CUDA 하한선의 확정값은 unit 4 실측 전에는 정하지 않는다.

search_policy는 기존 응답에 추가되는 재현 좌표이며 policy_id와 canonical JSON의 SHA-256 config_hash를 담는다. 기존 index.run_id·commit_sha와 evidence provenance는 유지한다. 근거가 없으면 HTTP 200, status: no_evidence와 빈 목록을 반환한다. 오류는 request ID, 안정적 code와 안전한 message만 포함한다.

공유 배포 corrective 상태

API와 192.168.1.185:9090 listener는 안전하게 중단했다. PostgreSQL은 healthy이며 active run 427f2c4a-ab06-486a-9801-4bde3ef17d63과 고정 commit은 유지된다. 저장 데이터는 158개 문서, 4,202개 section, 5,584개 chunk·embedding이다. 정상 5개 질의의 acceptable evidence는 3·4·1·1·2위였지만 문서에 없는 질의가 vector-only 근거를 반환해 gate는 FAIL했다.

사용자가 생성한 local-agent client는 보존했고 deployment token도 서버 내부 mode 0600 파일에 보존했다. Token 값, DB URL, host path 같은 민감값은 문서화하지 않는다. Identity 분리와 CUDA 재보정이 끝날 때까지 공개 API를 재가동하지 않는다.
